# T6.5: the parameter table grown to 0x180 rows (GT00, GT01), proven in the emulator

Date: 2026-10-12 (background agent). Firmware: Digitone II OS 1.12, main OS at `0x40000400`.
Marks: **[verified]** = checked against the bytes or run in the emulator here; **[inferred]** = reasoned
from structure, not run. Emulator and tools only: nothing flashed, nothing committed, nothing pushed.
The elekloader changes are uncommitted on its local branch `dn2-1.12`.

## Summary

The owner's decision: grow the table safely, for the 3-band compressor first. Done in two stages, both
on top of FTN1 (FTD1's DSP + core-dn2 0.1 + fx-rename-dn2 0.1), each proven before the next:

| build | what | syx sha256 | brick checker |
|---|---|---|---|
| **GT00** | FTN1 + **param-grow-dn2 0.1**: the table copied to RAM with room for **0x180 rows** (stock 0x141), every site that holds its address or its row count changed, the MIDI input cache and the display table made to fit 0x180 rows. **No new row**: rows 0x141..0x17f are copies of row 0, which is what stock reads for any row id it clamps | `4cfe8056...b78d13d` | **ACCEPT, 12 PASS** |
| **GT01** | GT00 + **param-rows-dn2 0.1**: 17 inert rows for the compressor (0x141..0x151; FX slots k 70..86; on no page, no CC/NRPN, never p-lockable, no randomiser, default 0, Overbridge ids 0x400+). Data only: below the stock image's end GT01 is GT00 byte for byte | `4c64c5dc...e7f9e41e` | **ACCEPT, 12 PASS** |
| GT1T | GT01 + param-test-dn2 0.1: TEST (row 0x17f, k 48, CC 3, NRPN 307) and TST2 (row 0x17e, k 87) on the flanger page's empty knobs E and F. **For the emulator only, never flash** (TEST shares k 48 with a hidden stock row so that the stock storage keeps it) | `b1f5956f...5f3f3b1` | not run (not for a unit) |

What the emulator shows (FTN1 as the baseline, the same keys on each build):

- **Cold boot** [verified]: GT00, GT01 and GT1T boot from reset to the same main screen as FTN1; the same
  eight tasks are created in the same order with the same entries, priorities, TCBs and stacks, each
  17,930-24,800 instructions later than FTN1 (the table copy and the larger loops).
- **Boot order** [verified, read and write watches from reset]: from reset to 800M, the only instructions that read the stock

  reader of the table (the map builder) comes at 109.4M, the display accessor and the cache only after

- **The maps built at boot** [verified]: every slot table, CC map, NRPN map, filter/machine tree and page
  record is FTN1's, and rows 0..0x140 are FTN1's field for field (names by value) with FTN1's display
  entries byte for byte. GT00: the 63 rows after them are copies of row 0, in no map. GT01: the 17 new
  rows are in the FX slot map at k 70..86 (free in stock) and nowhere else; their display entries are
  Makeup Gain's with flags 9 and no randomiser.
- **Every screen** [verified]: the 218-screen tour of every main page, the send FX pages and the
  mixer pages matches FTN1's except where FTN1 also differs from itself between two runs (2-5 screens,
  a knob's value shown instead of its label at the moment of capture, the header mid-scroll, or a
  detent the emulator dropped); GT1T differs on top of that only by its TEST and TST2 knobs.
- **No reader is left on the stock table** [verified]: during every run of every script on the GT builds,
  not one instruction read the stock table at `0x401f83a4` (FTN1's tour: 500,103 reads by 31 PCs).
- **P-locks, LFO destinations, the randomisers, copy/paste, MIDI out, a MIDI CC/NRPN flood** [verified,
  sections 4.5-4.7]: as FTN1. The same lock records (no lock on any send FX knob, TEST included); the
  same 67 LFO-list screens; the same randomised values; MIDI out message for message (GT00 identical;
  GT01 one fine-step value that FTN1's own two runs also disagree on; GT1T adds TEST's CC 3); from 7,100
  MIDI messages the same 991 cache writes, none outside the resized cache, no flushed value that was not
  sent (T6.1's overflow showed exactly as such values); and after each of these scripts **the 12.9 MB
  working project image is FTN1's byte for byte**, apart from single bytes left by a turn the emulator
  dropped in the tours and MIDI-out runs (each traced, 4.4, 4.7).
- **Storage for the compressor** [verified on the stock code, section 5]: a kit save and reload keeps
  exactly k 25..69 (stored ids 1..45, all taken by stock rows; k 40 and 48 are hidden routing words the
  stock DSP never reads). k 70..100 (31 words) are not saved, and a reload does not reset them. The FX
  record has 28 words (+0x60..+0x97) the serializer never writes and the loader never reads: with T6.0's
  hooks they hold k 70..97, enough for the compressor's 17-20 values. The frame to the DSP carries
  k 25..69 only; k 70+ reach the raw mirror and its smoother, not the DSP (T6.0's 30 tail words are the

- **Not possible here**: a +Drive save/load. The emulator's eMMC is empty; SAVE PROJECT AS fails with
  SAVE ERROR before any eMMC command, and FORMAT +DRIVE reports SUCCESS without writing (section 4.9).
  Kit save/reload was tested on the stock serializer and loader instead, and the working project image
  (what a save writes and a power-off keeps) was compared byte for byte.

## 1. Design

### 1.1 One mod on top of FTN1, not a core change

The relocation is `vendor/elekloader/examples/param-grow-dn2` (id `param-grow`, `requires: core`), not
a change to core-dn2:

- **FTN1 stays reproducible.** FTN1 (the owner's next flash) is built from core-dn2 0.1 out of the
  working tree. Changing core-dn2 would silently change every core build, FTN1's included. With a mod,
  `core-0.1.elemod` and `fx-rename-0.1.elemod` in GT00/GT01 are FTN1's, same sha256 [verified,
  `out/T6.5/build-GT00.json`].
- **GT00 differs from FTN1 by exactly one mod.** Below the appended blob every byte that differs from
  FTN1's main OS is inside one of param-grow's 149 sites [verified, build check].
- **An early enough hook exists without the core.** The OS entry calls the C start at `0x40000568`
  (`jsr 0x40186fa2`) after core's boot copy (`0x40000538`), the SRAM copies and the DDR clear, and before
  any of the OS's own C code. param-grow takes that call (section 1.4).
- **The table is a shared resource.** Other mods add rows through param-grow's table `param_rows`
  (elekloader collection), as core-dn1 2.1 does for the Digitone mk1 with `core_params`; the resource
  name `param-table` keeps a second relocator out, and each row id is claimed as `param-row:<id>`.

### 1.2 The new count: 0x180

- 63 new rows: the compressor's 17-20, second pages for the three send effects (8 each: 24), and about
  20 for synth/filter parameters later.
- The limit with same-length edits is **0x1e0**: the cache's `lea dirty(a0),a0` holds `0x18 + 68 x rows`
  in a 16-bit displacement (`0x6618` at 0x180; `0x7f98` at 0x1e0). Every other constant has room (the
  set function's `move.w #4 x rows,d5w` relies on `34 x rows` < 0x10000) [verified, `scripts/t65_sites.py`
  refuses a count past 0x1e0].
- Cost: the table 0x5a00 bytes and the new rows' display entries 0x10bc in param-grow's region; the cache
  grows on the heap from 0xfff4 to 0x13228 bytes (+12,852), allocated at the same address as on FTN1
  (`0x447ebbf0`) [verified]; loops over all rows run 63 more passes (the boot-time builder, the sound
  randomiser, the machine-row collector) [verified, static].
- Growing again later is the same build with another number (the generator takes `--rows`), re-proven.

### 1.3 Where the grown table lives

A region of the DDR the device profile leaves to mods, claimed in mod.json: **`0x47D00000-0x47D10000`**
(`pg_desc` at `0x47D00000`, 0x180 x 0x3c; the new rows' display entries `pg_xdisp` at `0x47D05A00`;
`pg_xdisp_on`, one byte per new row, at `0x47D06AC0`). Fixed addresses, so adding row mods moves nothing
(GT01 = GT00 below the blob) [verified]. Stock never touches `0x46800000-0x47F00000` (T1.3's write
watches, T1.9's code scan); DDR holds noise at power-on, so pg_boot writes all of the table and clears
`pg_xdisp_on` itself [verified: the code; the region's first read is after those writes, 4.2].

**Static or copied?** The task preferred a static grown table in the image. There is none to be had: the
image has no free room of 0x5a00 bytes, the bytes past the image's end are cleared at boot
(`0x400004b2` clears `0x402fd000..0x466b84d0`), and a table built into a mod's RAM image would put
Elektron's 19 KB table into the mod's source and would not carry other mods' data sites (fx-rename's
names point into the stock table). So param-grow **copies the table at boot, from the image as loaded**,
before any OS code runs: other mods' `ptr` sites in the stock rows come with it, and the copy is read-only
by use, as stock's is (nothing writes the region after boot: 4.2).

### 1.4 Boot order

| when (cold boot, GT1T) | what | n (instructions from reset) |
|---|---|---|
| `0x40000538` | core's boot: run image to 0x47E00000, .bss cleared | |
| `0x40000568` -> `pg_boot` | the stock rows copied from 0x401f83a4, rows 0x141..0x17f set to row 0, the new rows' records written, `pg_xdisp_on` cleared; then `jmp 0x40186fa2` | 26,245,075 |
| `0x40186fa2` | the OS's C start (kernel, tasks) | 26,263,781 |
| `0x401ae0cc` -> `pg_sinit` | calls the static initializer `0x400c2c4e` (display table, page records), then gives each new row its display entry and page slot | 26,345,479 |

### 1.5 The display table

Built in RAM (`0x4243425c`, 0x44 bytes per row) by the static initializer with 1,633 absolute writes, and
read only through `0x400c257c` [verified: T6.1's scan, repeated here]. It is not moved: the accessor's
first two instructions (`move.l 4(sp),d0; cmpi.l #0x141,d0`, the latter one of the 58 bounds) become a
`jmp pg_disp_get`: a stock row reads its stock entry; a new row reads its own entry if a mod gave it one
(`pg_xdisp_on`); anything else reads row 0's, exactly as stock's clamp. A new row's entry is copied at
`pg_sinit` from the stock row it names (`look`), its flags ORed with the row's `flags_set` (8: never
p-lockable), its randomiser std::function cleared (functor, manager, invoker 0). A lock is possible only
when flags bits 0 and 3 are both clear (`0x40064ccc`); the knob drawing reads bits 1, 2, 4, 5 and 6, not
0 or 3 [verified: ParameterPageView::vslot45], so bit 3 changes nothing on screen.

### 1.6 The ParameterUpdateCache (MIDI CC/NRPN in)

Layout with N rows [verified: its five functions read instruction by instruction]: `+0x18` u16 values
[2 banks][17 lanes][N], `+0x18+68N` u32 dirty bitmaps [2][17][N words] (only N bits used; the flush scans
all N words of each lane), `+0x18+204N` the bank word, then a std::vector, size `0x28+204N`. With N =
0x141 the constants are 0x282, 0x2aa2, 0x504, 0x5544, 0x555c, 0xffe4, 0xffe8, 0xffec, 0xfff4; param-grow
puts N = 0x180 into the same formulas (0x300, 0x3300, 0x600, 0x6600, 0x6618, 0x13218, 0x1321c, 0x13220,
0x13228) in **33 operands** of the constructor, the destructor, get, set and flush. One of them is not an
immediate of its own: the flush's `move.b #-0x14,d0b` turns `d0 = vector` into `d0 = vector + 4` by
patching the low byte; it becomes `move.b #0x20,d0b` (the generator checks that `vector` and
`vector + 4` share every byte above the lowest). The script also checks that no other operand of those
five functions holds a cache constant [verified].

## 3. The rows

### 3.1 How a mod adds one

`param_rows.h` (`vendor/elekloader/examples/param-grow-dn2/`): `struct param_row` = id, the 0x3c-byte
descriptor in the stock layout, `look` (the stock row whose display entry it borrows), `flags_set`,
`opts` (keep the randomiser), `page`/`slot` (put it on an empty page slot at boot). A mod contributes one
pointer to an array ended by id 0 to `param_rows`, and claims `param-row:<id>`.

### 3.2 GT01's rows (param-rows-dn2): the compressor's knobs, inert

| rows | names (long / short) | group | k | range | display |
|---|---|---|---|---|---|
| 0x141-0x146 | Low Threshold THR, Low Ratio RAT, Low Attack ATK, Low Release REL, Low Makeup MUP, Low X-Over XOVR | 0x14 (compressor) | 70-75 | 0..127, default 0, plain number | Makeup Gain's (0x99), flags 1 -> 9 |
| 0x147-0x14c | Mid ... (the same six) | 0x14 | 76-81 | | |
| 0x14d-0x151 | High Threshold, Ratio, Attack, Release, Makeup | 0x14 | 82-86 | | |

All: no CC, CC2 or NRPN (-1), no modulation flags, Overbridge ids 0x400-0x410, no randomiser, on no page.
The build checks each against notes/T6.1 section 3.4 (a k free in the FX set, default 0 for a k no stock
row has, no CC, bit 3 set, Overbridge id outside stock's, no randomiser, a stock FX display template)
and so does elekloader's `test_param_rows_are_data_only` [verified]. Names, ranges and formatters are
placeholders until the compressor is designed; rows are never stored (only k is), so changing them later
leaves no trace in projects.

### 3.3 GT1T's test rows (param-test-dn2, emulator only)

- **TEST**, row 0x17f (the last row, so anything sized for fewer rows would be overrun), group 0x10, **k 48**
  (shared with the hidden "Reverb FX Routing", row 0x83, so that the stock storage keeps it; default 1 as
  0x83's, so a new kit is unchanged), 0..127, **CC 3 and NRPN 307** on the FX channel (free in stock), DPTH's
  display entry with bit 3 set, on the flanger page knob **E**.
- **TST2**, row 0x17e, **k 87** (not stored by stock), default 0, no CC, on knob **F**.
- Sharing k 48 breaks rule 3 of the study (the FX map names TEST for k 48 instead of row 0x83), which is
  why GT1T is not for a unit.

### 4.6 MIDI in: the CC and NRPN flood [verified]

`scripts/t65-midi-flood.script` (`scripts/t65_mkflood.py`): every CC 0..127 on all 16 channels (2,048
messages, values a fixed function of channel and number), then NRPN 0..420 (four CCs each: 99, 98, 6, 38)
on channels 1, 9 and 16: 7,100 messages, with `--cache-watch` (a code hook on every store the cache's
own functions make into the object, the address computed from the registers and checked against
`[ptr, ptr + size)`; every set/get checked for lane < 17 and row < the row count) and `--flush-trace`
(every set, and every batch the flush hands its listener).

| | FTN1 | GT00 | GT01 | GT1T |
|---|---|---|---|---|
| cache size | 0xfff4 | 0x13228 | 0x13228 | 0x13228 |
| stores into the cache / outside it | 4,699 / 0 | 4,765 / 0 | 4,694 / 0 | 4,725 / 0 |
| sets (lane, row, value) | 991 | 991, the same multiset | 991, the same multiset | 994: FTN1's 991 (the same multiset) + 3 for TEST |
| flushed values nobody set | 0 | 0 | 0 | 0 |
| last flushed value per (lane, row) = last set | yes | yes, and = FTN1's | yes, and = FTN1's | yes, and = FTN1's (TEST aside) |
| live FX setup, raw parameter mirror (17 rows), all 129 kit FX records | | identical | identical | identical but k 48 (TEST = 7) |
| working project image (12.9 MB) | | identical | identical | identical but kit 0 FX id 24 (k 48) |

The number of flush batches differs (206 / 221 / 204): the same values arrive at slightly different
instruction counts, so the flush groups them differently and coalesces different intermediate values
(a value set twice before a flush is flushed once). The criterion is therefore the one in the table: no
flushed value that was not set, and the same final value for every parameter. T6.1's overflow showed
up exactly as flushed rows nobody set; none here. In GT1T, CC 3 on the FX channel (channel 9) set TEST to 46 and NRPN 307
on channel 9 set it to 7 (twice: data entry MSB and LSB), through the FX CC and NRPN maps, the resized
cache (lane 16, row 0x17f: the very last value word of a bank, `+0x18 + bank x 0x3300 + 16 x 0x300 +
0x17f x 2`) and the stock setter; the last value, 7, is in the live kit, the raw mirror and the stored kit
record (id 24) [verified]. This is the case that corrupted the cache in T6.1.

### 4.9 The +Drive: a project save is not possible in this emulator [verified]

- SAVE PROJECT AS on the warm snapshot: the slot list (001..008 empty), the name screen, then **SAVE
  ERROR**, with **no eMMC command at all** during the attempt (the eSDHC model's command log, read with
  `t65_live.py --emmc`).
- SETTINGS > SYSTEM > FORMAT +DRIVE (tick PROJ+PST+KIT, ERASE SELECTED DATA, YES: "DATA WILL BE ERASED!
  ARE YOU SURE?", then **SUCCESS!**) leaves the card's written blocks as they were (the model's overlay
  is the same 1,024 bytes before and after); SAVE PROJECT AS afterwards still fails.
- The only eMMC data in the snapshot are the two blocks the OS wrote at boot (0 and 2048). So the OS
  treats the empty card as unusable from boot on, and the FUNC+YES / FUNC+NO kit save and reload say
  "Prj must be re-saved!". Making it work needs an eMMC image with a real +Drive filesystem (a dump
  from the unit, or the bootstrap's own FORMAT +DRIVE run in the emulator): not done.
- What a project save would write is the working project image (`0x405ce96c`, 0xc4b010 bytes, which the
  OS also keeps across a power-off): it was compared byte for byte after every script (4.4-4.8), and kit
  save/reload was run on the stock serializer and loader (4.8).

## 5. Storage for the compressor: which kit-level k survive

The FX setup of a kit is 101 live words by k (live kit `+0x48e4`), plus the routing long. What a kit
save and reload do with them, run on the stock code (`scripts/t65_roundtrip.py`: the FX serializer
`0x400dcf34` into a record pre-filled with `0xa5`, every live word changed, the loader `0x400dcef0`
back; on the end snapshots of FTN1, GT00 and GT01, identical results) [verified]:

| k | rows (stock) | stored id | saved and reloaded? | reaches the DSP? |
|---|---|---|---|---|
| 0..24 | 0: row 0x13 (None); 1..24: the LFO rows 0x4b..0x67, which every set files | 0 (the fold sink: all 25 write id 0, the last one wins) | **no** (k 1..24 keep the edit; k 0 gets id 0) | no |
| 25..69 | every one has a stock row (chorus 25..31, delay 32..40, reverb 41..48, ext. inputs 49..59, compressor 60..67, overdrive 68, pattern volume 69) | 1..45 (`0x401fd160`; k 68 -> 36, 60..67 -> 37..44) | **yes**: 45 words | yes: frame word `0x9fa + 2 x (k - 25)` (T3.3/T6.0) |
| 40, 48 (of the above) | Delay FX Routing, Reverb FX Routing: on no page, no CC, value 1 in every kit | 16, 24 | yes | 0xa18 never read by the stock DSP; 0xa28 stored as a byte nobody reads (T3.4) |
| 70..100 | none (GT01: the compressor rows take 70..86) | none (the map ends at 69) | **no**, and the stock loader leaves them as they are: a reload does not reset them | no: the frame copies k 25..69 only; k 70+ live in the raw mirror row 16 and its smoother |

- **The record's free words**: the serializer never writes `+0x60..+0x97` (28 words) and the loader never
  reads them [verified: the 0xa5 marks survive the serializer; T6.0 found them zero in every kit]. With
  T6.0's design (hook the map `0x400dce5e` so k 70..97 -> ids 46..73, and extend the serializer and
  loader to write and read them) they hold **28 values per kit: enough for the compressor's 17-20**.
  One of the 28 should be a check word (stock exports through fresh buffers drop or garble them, T6.0).
- **Free and kept without new code: 2** (k 40 and k 48), both meaning "routing" with value 1 in every
  existing kit, so 1 must stay the classic value; not enough for the compressor.
- More room if needed: the kit record's padding `+0x28af..+0x29ff` (337 bytes; T6.0, [inferred]).
- **What reaches the DSP**: only k 25..69. For k 70+ the planned carrier is T6.0's 30 tail words of the
  SPI frame (a hook at `0x40025e9e` copying the smoothed row-16 words k 70..99; proved end to end in T6.0).
  Measured on GT1T (4.8): TEST's k 48 changes frame word `0xa28`; TST2's k 87 changes only the raw and
  smoothed mirrors [verified].

So the compressor's path is: rows in FX slots k 70..89 (GT01 takes 70..86), T6.0's three storage hooks
for persistence, T6.0's frame hook for the DSP, and the DSP code reading the frame tail.

## 6. Limits, risks left, and what only the unit can show

- **Emulator only.** No DSP, no USB, no Overbridge, an empty eMMC, a ColdFire under Unicorn, key taps in
  wall-clock time.
- **Overbridge**: rows carry an Overbridge id at `+0x20`; `0x400d5a54` sends it to the Overbridge
  stream whenever a parameter changes (its 8 callers are the parameter-change listeners). Traced in the
  emulator (`t65_live.py --ob-trace`, the storage script: knob turns on the flanger page, a pattern
  copied, pasted and switched, which changes the kit) [verified, `out/T6.5/emu/*/t65-ob/t65.json`]:
  FTN1, GT00 and GT01 make the same 11 sends (id 110, DPTH, three times; id 0 eight times); **GT01's 17
  rows are never sent**, not even on the kit change, because nothing changes them. GT1T sends TEST's id
  0x43e ten times and TST2's 0x43d seven times, one per detent: a row past the stock ones is sent like
  any other as soon as it changes. **What the plugin does with an id it does not know (0x400 and up)
  is unit-only**; it matters once the compressor's rows are on pages. Whether Overbridge also reads ids
  the other way (automation in) was not found (T6.1 2.9).
- **The +Drive** [unit only]: project save/load, kit save/reload through the UI, Transfer of kits and
  sounds. Here: the working project image (what a save writes) byte for byte, and the stock kit
  serializer/loader host-called.
- **A real boot from flash** [unit only]: timing and caches. The copy adds about 18,700 instructions to
  the boot [verified count]; the code runs with the caches on, from DDR, as core's handlers do.
- **The heap**: the cache takes 12,852 bytes more from the heap; it is allocated at the same address as
  on FTN1, and every later heap object moves up by that much [verified]. A heap that is nearly full in
  some use (a huge project) would feel it first [inferred: low risk, the heap's free space was not
  measured].
- **Arrays sized by a rounded row count** would not show in the immediate scan [inferred]. Mitigation:
  the top row 0x17f was exercised by the UI, MIDI CC/NRPN, the cache (its value at the very last word of
  the value arrays), the lock check and the randomisers; nothing wrote outside what it should (4.6).
- **MIDI CC out of a new FX row** goes out on the set's channel, not the FX channel: `ParameterSet::
  vslot25` sends rows `0x69..0x83` (and only those) through the FX channel lookup [verified, static];
  in this snapshot's MIDI setup (OUTPUT CH = AUTO CH) TEST's CC 3 went out on the same channel as the stock FX knobs [verified, 4.7], so the difference did not show; with a fixed output channel per track it may [inferred]. When the compressor rows get CCs, extend that range check (one site, `0x400379ec`
  region) or give them the stock compressor rows' behaviour (rows 0x96..0x9f are outside the range too).
- **Wall-clock key timing**: on a loaded machine the emulator drops an occasional encoder detent (4.4,
  4.7). Every difference between FTN1 and the GT builds in this task traced back to that, run by run.
- **The brick checker** counts as a full gate for name and repack changes only until T1.7b's gaps are
  closed (HANDOFF); for code changes its PASS is necessary, not sufficient, which is why the evidence
  above was gathered.
- **Order on the unit**: FTN1 first, then GT00, then GT01. GT1T never.

## 7. What is next

1. **Flash GT00 after FTN1** (`out/T6.5/FLASH-GT00.md`), then GT01 with Overbridge connected once.
2. **The compressor's storage**: T6.0's hooks on `0x400dce5e` (map k 70..97 -> ids 46..73),
   `0x400dcf34` and `0x400dcef0` (write and read `+0x60..+0x97`), with a check word; prove a kit round
   trip keeps k 70..86 and a stock OS ignores them. Then the +Drive question (an eMMC image) matters more.
3. **The frame path to the DSP**: T6.0's hook at `0x40025e9e` copying k 70..99 (smoothed) into the 30
   tail words; the DSP side reads them from the receive buffer.
4. **Real knobs**: three compressor pages. The page records are fixed (37); a SEND FX-style multi-page
   view needs either borrowed page records or the page-accessor hook T5.0's experiment tried; rows go on
   pages through `param_row.page/slot` only for empty slots of existing pages today.
5. **Synth/filter parameters** (p-lockable): rows in free machine-window k (FM Tone 34, 49; WaveTone
   50..64; FM Drum 55..64; Swarmer 33..64; machine 4 25..64) with flags 0: p-locks, LFO destinations,
   MIDI and storage then come from stock code (T6.1 3.2). The shared filter/amp block has no free
   persistent slot.
