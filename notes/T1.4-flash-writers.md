# T1.4 — Flash-writer audit, Digitone II OS 1.12 (main OS, section 3)

Safety-critical. Goal: find every piece of main-OS code that can **erase or write the
unit's SPI NOR flash**, trace each caller chain to its entry point, give the flash
address range each can reach, and decide whether any of it can write the region that
holds the bootstrap.

Method: static only. Source is the decompile/disassembly dump in `out/decomp/` plus
`m68k-elf-objdump -m m68k:cfv4e` and raw-byte scans over `ele3_out/02_type3.unpacked.bin`
(main OS, file offset 0 = `0x40000400`) and `ele3_out/01_type2.unpacked.bin` (bootstrap).
No emulator run and no hardware. Marks: **[verified]** = checked against the bytes or a
run; **[inferred]** = reasoned from structure. The reusable scanner is
`scripts/t1.4_flash_refs.py`; bulky output is under `out/T1.4/`.

---

## 1. Bottom line

- The main OS reaches the NOR through **one SPI driver on DSPI0 (`0xFC05C000`)**. There is
  **no chip-erase command** (`0xC7`/`0x60`) anywhere in the driver, and **no code path writes
  below `0x40000`**. [verified]
- Every normal, musician-facing path (the in-OS OS upgrade over USB/MIDI, the settings store,
  the boot-time persistence migration) writes only at or above `0x80000`, except the
  factory/settings store at `0x380000`. **None of them can touch the bootstrap region
  `0x40000`–`0x80000`.** The in-OS upgrade erases *upward* from `0x80000` only. [verified]
- **Exactly one main-OS path can write the bootstrap region: the factory debug console's
  `#FULL_UPGRADE` command (`FUN_400cd5f2`).** It is gated behind boot-flag bit 5 of
  `0x40287a60`, which the bootstrap sets (`0x80000c42`) only after a UART service/test
  handshake with the panel board at power-on; on a normal boot the console task is never
  created and the path is dead. Even in that mode it must first issue a DYB-unprotect
  (`0xE1`, data `0xff`) to sector `0x40000` before it can erase it. [verified]
- Therefore a **modified MAIN OS delivered through the normal upgrade channel cannot erase or
  write the bootstrap.** The OS carries no embedded bootstrap copy it re-flashes (unlike the
  Analog Rytm). The bootstrap's only re-flashers are its own version-gated self-upgrade
  (`FUN_80001c48`, which no 1.12-derived image can trigger) and that one dormant factory path.
  [verified]
- **One correction to the Digitakt II writeup** (`vendor/elekloader/docs/DEVICES.md`, "What
  writes the flash", which says *"None writes from the main OS image … no range of it is a
  bootstrap the OS could re-flash"*): on the DN2 the bootstrap lives at flash **`0x40000`**,
  not inside the container, and the factory console **does** have a main-OS code path
  (`#FULL_UPGRADE`) that re-flashes it there. It receives the new bootstrap over the wire
  rather than carrying a copy, and it is test-mode-gated, so the brick conclusion still holds —
  but the "nothing in the OS can write the bootstrap" phrasing is not literally true for the
  DN2. [verified]

## 2. The flash driver (DSPI0, `0xFC05C000`)

All flash I/O is on **DSPI0**: MCR `+0x00`, SR `+0x2C`, PUSHR `+0x34`, POPR `+0x38`. Each
primitive raises MCR (`ori.l #0xC00`, HALT/clear-FIFO), sets CTAR0 bit 28, pushes an
8-bit-frame command word to PUSHR (`0x8402_00XX` = PCS, continue; `0x0802_00XX` = last frame),
pushes address/data bytes, polls SR, and reads POPR. The command byte is the low 8 bits of the
PUSHR word. [verified]

DSPI1 (`0xFC03C000`, `FUN_400cec50`/`FUN_400cedfc`/`FUN_400cf7f8`) and DSPI2 (`0xEC038000`,
`FUN_400cf5ea…`) are the inter-processor command/response and SHARC-frame links; they send no
flash opcodes and are **not** flash writers. [verified]

Command primitives (all in `0x40134a28`–`0x40136100`):

| entry | opcode | purpose | addr bytes |
|---|---|---|---|
| `0x40134a28` | `0x06` | write-enable (WREN) | — |
| `0x40134b04` | `0x05` | read status register (RDSR) | — |
| `0x40134b58` | `0x30` | read flag/clear status, 1 byte | — |
| `0x40134bce` | `0x90` | read electronic manufacturer/device ID (REMS) | 3 |
| `0x40134c96`/`0x40134ee4` | `0x4B` | read OTP / unique-ID region | 4 + dummy |
| `0x40134dde` | `0x5A` | read SFDP | 3 + dummy |
| `0x40135994` | `0x9F` | read JEDEC ID (RDID) | — |
| `0x401353ae` | `0x03` | **READ** (`flash_read`, matches T1.1) | 3 |
| `0x401354d6` | `0x02` | **PAGE PROGRAM** (write) | 3 |
| `0x40135618` | `0x12` | **PAGE PROGRAM, 4-byte addr** (no resolved caller) | 4 |
| `0x40134a6a` | `0x20`/`0xD8` | **ERASE** (arg0=0 → `0x20` 4 KB subsector; arg0≠0 → `0xD8` block) | 3 |
| `0x401357ce` | `0xD8` | **block erase** (WREN + `0x40134a6a(1,addr)` + poll) | 3 |
| `0x40135850` | `0xD8` | **block erase, services watchdog `0x4013492c` during the wait** | 3 |
| `0x40135e7c` | `0xE0` | DYB read (dynamic protection bit) | 4 |
| `0x40135f80` | `0xE1` | **DYB write** (unprotect/protect one sector) | 4 + 1 |
| `0x40135ba2` | `0xE2` | PPB read (persistent protection bit) | 4 |
| `0x40135ca6` | `0xE3` | **PPB program** (protect a sector) | 4 |
| `0x40135dc8` | `0xE4` | **PPB erase** (clear protection bits) | — |

The opcodes `0x03/0x02/0x12/0x20/0xD8/0x06/0x05/0x9F/0x90/0x5A/0x4B` are read straight from the
PUSHR immediates (`out/T1.4/opcodes.txt`). [verified] The mapping of `0xE0`–`0xE4` to
Cypress/Spansion **advanced sector protection** (DYB/PPB) is [inferred] from the opcode values
plus the usage pattern (read protection → clear → erase → program → re-protect). digikit
(`docs/findings/08-hardware-and-ghidra.md`) identifies the part as an S25FL127S-class
(Cypress/Spansion) 128 Mbit device, which defines exactly these opcodes. [inferred]

**No `0xC7` or `0x60` (chip erase) exists** in the driver region or anywhere in either image's
DSPI immediates. [verified]

Geometry is discovered at runtime by the JEDEC/SFDP probe `FUN_40135a7c`, which stores the page
size in `0x402a12f8` (256 or 512) and the erase-block size in `0x402a12f4` (`0x40000` on the
recognised part). Getters: `FUN_401361f6` (page), `FUN_4013620a` (erase block). [verified]

### Wrappers (what callers actually use)

| wrapper | wraps | job |
|---|---|---|
| `0x401360a2` → `0x401353ae` | READ | `flash_read(off,len,dst)` |
| `0x401360a6` | `0x401354d6` | program a buffer across page boundaries |
| `0x40136122` | `0x401357ce` | erase a region, normalised to the `0x40000` block (one native erase if block==`0x40000`, else a loop) |
| `0x4013618c` | `0x40135850` | same, watchdog-serviced variant |

## 3. Caller chains and the flash range each can reach

Caller edges are from `out/decomp/main_os/calls.tsv` (Ghidra-resolved, incl. the register
calls the in-OS writer uses) cross-checked with a raw reference scan
(`scripts/t1.4_flash_refs.py`). The writers/erasers fall into four clusters.

| # | entry point(s) | reaches flash via | flash range erased/written | how the address is computed | gate |
|---|---|---|---|---|---|
| A | **In-OS OS upgrade.** UI `OsUpgradeMenuView` confirm ("UPGRADE OS NOW?", `0x401096be`/`0x401098d8` → job `0x401094e8`) and the SysEx / `MidiRpcOsUpgrade*` channel (`FUN_40125f9e`, `FUN_40129f36`) → deferred job `0x40109144` ("ERASING FLASH…") → **`FUN_40139104`** | erase `0x401357ce`, program `0x401360a6` | **`0x80000` upward only**: erase `ceil(len/blk)` blocks from `0x80000`; program `ceil(len/page)` pages from `0x80000` | `len = *param_1` = the container header length, taken **after** the validator `FUN_400dbdb0` (content checksum `FUN_401226f8` + HMAC trailer `FUN_400d2bc4`) returns 1. `a_base = 0x80000` is hard-coded (`moveq`/`addi`); the loop only increments | validator must pass; user confirms in the UI / RPC. Normal path. |
| B | **Factory debug console** `FUN_400cd5f2` (task `FUN_400cebd2`), command `#UPGRADE` | program `0x401360a6`, erase `0x40136122` | container at **`0x80000` upward** (erase `((len+0x3ffff)>>18)` 256 KB blocks from `0x80000`, program `0x200`-byte pages from `0x80000`) | `0x80000` constant; `len = *(buf+0x20004)` from the received ELE3 header | boot-flag bit 5 of `0x40287a60` (see §5). Dormant on a normal boot. |
| B′ | **Same console**, command `#FULL_UPGRADE` | DYB-unprotect `0x40135f80(0x40000,0xff)`, erase `0x40136122(0x40000)`, program `0x401360a6` from `0x40000`; then the `#UPGRADE` container write at `0x80000` | **`0x40000`–`0x80000`** (one 256 KB block — the **bootstrap**), plus `0x80000` upward | writes the first received chunk (`*(buf+4)-8` bytes) to `0x40000`; chunk ≤ 60 KB fits one block | same bit-5 gate. **This is the only main-OS writer of the bootstrap region.** |
| C | **Factory/settings store** `FUN_400cccc6`, `FUN_400ccda2`, `FUN_400cce7e`, `FUN_400ccf5a`, `FUN_400cd036`, `FUN_400cd10a` (serial "SERI", UI/audio-tested flags, factory-reset flag) | PPB read/erase/program `0x40135ba2`/`0x40135dc8`/`0x40135ca6`, program `0x401360a6`, erase `0x40136122`/`0x4013618c` | **`0x380000` and `0x3c0000`** (two 256 KB sectors) | `0x380000`/`0x3c0000` are `move.l #imm` constants in each writer | every one is reached only from `FUN_400cd5f2` / its `#WRITE <name>` table (`#WRITE_SERIAL`, `#*_TESTED`) — i.e. the same bit-5 console. I found **no normal-session caller**. [verified] |
| D | **Boot-time persistence migration** `FUN_400f2022` (← `FUN_400f2168` ← init `FUN_400cedfc`) | erase `0x40136122`, read `0x401360a2` | erases the 256 KB NOR block at whichever of **`0x400000`, `0x800000`, `0xc00000`** currently holds a `"COKi"` magic (`0x434f4b69`), after copying it to the eMMC (`FUN_4012ca60`, eSDHC `0xFC0CC000`) | addresses from the table at `0x401ffafc` = `{0x400000,0x800000,0xc00000}` | runs at boot; only erases a block that holds a live `COKi` copy. Never ≤ `0x400000`. |

Notes:
- Cluster A's writer `FUN_40139104` re-runs the full validator (`FUN_400dbdb0` at `0x40139114`)
  **before** erasing, so a container whose length/content does not checksum-and-HMAC never
  reaches the erase loop. [verified] The erase extent is `ceil(len/blk)` blocks from `0x80000`
  with **no explicit upper clamp at `0x380000`** — but `len` is authenticated by the HMAC, and
  the loop only ever increases the address, so it cannot reach the bootstrap below `0x80000`,
  and reaching the settings store would need a legitimately sealed >3 MB container. [verified]
- The console's byte stream (cluster B) is received through `FUN_4011f644` and answered through
  `FUN_400053d4`, which drives the USB-OTG FIFO (`0xFC0B01C8`, buffer `0x80000C00`); the device
  descriptor string is "Unnamed device" (`0x40287ab4`). So the factory console is a **USB CDC**
  surface, not a MIDI one. [verified]
- `0x40135618` (4-byte page program) and the subsector-erase arm (`0x20`) of `0x40134a6a` have
  no resolved live caller; on this ≤16 MB part the 3-byte path covers the address space. [verified]

## 4. Flash layout (16 MiB NOR on DSPI0)

| range | contents | written by | notes |
|---|---|---|---|
| `0x000000`–`0x040000` | NXP serial-boot / reset image | **no firmware path found** | the first image the ColdFire boot ROM loads; written only at factory (JTAG/bdm). [inferred] |
| `0x040000`–`0x080000` | **bootable bootstrap** (section 2, runs at `0x80000400`, version word `0x0201`) | bootstrap self-upgrade `FUN_80001c48`; main-OS `#FULL_UPGRADE` (B′) | one 256 KB block, DYB-protected. Both writers DYB-unprotect `0x40000` (`0xE1`,`0xff`) first. [verified] |
| `0x080000`–`0x380000` | **OS container** (ELE3: sections 5,2,3,4,7,8; the updater is section 4, inside the container at its section-table offset) | in-OS upgrade (A), console `#UPGRADE` (B), bootstrap STARTUP-menu upgrade | 3 MB window; stock OS ≈ 1.1 MB packed. Bootstrap reads sections from `0x80000`+offset (T1.2). [verified] |
| `0x380000`–`0x400000` | **settings / factory store** (serial, UI-/audio-test flags, factory-reset) | cluster C (console only) | sectors `0x380000` and `0x3c0000`; same addresses as DT2. [verified] |
| `0x400000`, `0x800000`, `0xc00000` | legacy `"COKi"` persistence copies | cluster D (boot migration) | read to RAM and copied to eMMC, then the NOR block erased. [verified] |

The updater (section 4) is **not** at a separate fixed flash offset; it is stored inside the
container at `0x80000` and the bootstrap loads it from there (T1.2, `0x8000357c`/`0x80007a00`).
[verified] One open point: `FUN_400f2022` reads `0xC4B114` (≈12.9 MB) from a NOR base of
`0x400000`, which overruns a 16 MiB part — either the NOR is larger than digikit's DT2 figure
or the read is bounded elsewhere; it does not change the brick picture (all cluster-D erases are
≥ `0x400000`). [inferred, unresolved]

## 5. Can any of it write the bootstrap? (the safety question)

**The bootstrap store is `0x40000`–`0x80000`.** Proof: the bootstrap's own self-upgrade
`FUN_80001c48` reads the new bootstrap from the container (`local_10 + 0x80000`), checks its
CRC-32 residue and its version word (`DAT_4041000c` vs running `0x0201`), then
`FUN_80002742(0x40000,0xff)` (DYB-write `0xE1`, unprotect), `FUN_80002896(0x40000)` (256 KB
erase), and programs it with `FUN_8000282a(i+0x40000, …)` in 512-byte pages, ending
"PLEASE RESTART ME". Size guard `uVar2 < 0xF001` (≤ 60 KB → one block). [verified] The main-OS
`#FULL_UPGRADE` (B′) writes the **same** `0x40000` block with the **same** DYB-unprotect-then-
erase-then-program sequence. [verified]

Who can reach `0x40000` from the main OS:

- **Nobody on a normal boot.** The factory console task `FUN_400cebd2` is created by init
  `FUN_400cedfc` **only when boot-flag bit 5 (`0x20`) of `0x40287a60` is set**
  (`moveq #32,d0; and 0x40287a60,d0; beq …` at `0x400cf1ea`, falling through to the
  `jsr 0x400cebd2`). [verified] `0x40287a60` is loaded at main-OS entry from the flags word the
  bootstrap passes (`0x400004ec`). The bootstrap sets bit 5 at `0x80000c42` only after a UART
  handshake with the panel/UI board succeeds during STARTUP (`pea 0x11; jsr 0x80001302`, then
  `or #0x20`). So bit 5 = a factory/service request from the panel, not something a musician
  session reaches. [verified]
- Even with bit 5 set, the console must send `#FULL_UPGRADE` (not `#UPGRADE`) and the firmware
  still DYB-unprotects `0x40000` explicitly before erasing it. The `0x40000` erase is a single
  256 KB block and does **not** extend down into `0x0`. [verified]

The ordinary upgrade channels cannot reach `0x40000`:

- The UI `OsUpgradeMenuView` confirm and the MIDI/USB `MidiRpcOsUpgrade*` / SysEx channel both
  end at the single writer `FUN_40139104`, whose base is a hard-coded `0x80000` and whose erase
  loop only increments. There is no address from the wire that steers it below `0x80000`.
  [verified]
- The settings store (cluster C) is `0x380000`/`0x3c0000` only, and is itself console-gated.
  [verified]
- The boot migration (cluster D) is `0x400000`+ only. [verified]

**Conclusion:** a modified **section 3 (main OS)** flashed through the normal in-OS upgrade (the
route Elektron Transfer takes) can never erase or write the bootstrap at `0x40000`–`0x80000`,
nor anything below `0x80000`. The bootstrap is re-flashable only by (a) its own self-upgrade,
which fires solely when an incoming bootstrap's version word exceeds the running `0x0201` — and
no 1.12-derived build carries a higher one (the STARTUP-menu gate `0x80001c72`, T1.2) — and
(b) the factory console `#FULL_UPGRADE`, dormant unless the panel board puts the unit in service
mode at power-on. Neither is reachable by flashing a custom OS image the normal way. [verified]

## 6. For the brick checker (T1.7)

- Invariant to enforce in the emulated upgrade session: **every flash erase/program stays at or
  above `0x80000`.** If a candidate's emulated in-OS upgrade (`FUN_40139104`) ever issues an
  erase below `0x80000`, or a `0xE1`/`0xE4` protection write to `0x40000`, refuse. In a correct
  session it will not: the base is `0x80000` and the loop only increments.
- `#FULL_UPGRADE` / the factory console are not part of any candidate `.syx` upgrade; they are a
  separate USB-CDC service surface gated by panel test mode. A brick checker over a candidate
  image does not need to exercise them, but should assert the candidate does not *enter* that
  mode (boot-flag bit 5 stays clear on a normal emulated boot).
- There is no chip-erase opcode to worry about, and the OS holds no embedded bootstrap copy that
  a bug could splice into the `0x80000` write.

## 7. What this does not cover / gaps

- **Static only.** The ranges in §3 are from the decompile/disassembly, not a dynamic run. The
  emulator work (T1.2) deliberately stopped before the writer executed. A write-watch run of
  `FUN_40139104` in digikit's emulator would confirm the erase/program addresses dynamically;
  not done here. [inferred where it says "upward only" beyond the loop structure]
- Virtual-dispatch edges that Ghidra did not resolve are not in `calls.tsv`; I covered the
  in-OS writer's function-pointer invocation (`local_38 = FUN_40109144`) by hand but did not
  prove there is no *other* indirect caller of the primitives. The raw reference scan
  (`scripts/t1.4_flash_refs.py`) found no additional direct `jsr`/`bsr`/`pea` to any primitive
  beyond those listed. [verified for direct refs; indirect is [inferred]]
- The `0xE0`–`0xE4` → DYB/PPB mapping is inferred from opcode values and usage, not from a part
  datasheet in hand. The addresses those functions are called with (≥ `0x380000`) are verified
  regardless. 
- `FUN_400f2022`'s 12.9 MB read size vs a 16 MiB part is unresolved (§4); it does not affect the
  bootstrap conclusion.
- The role of `0x0`–`0x40000` (serial-boot image) is inferred from the boot architecture; I
  verified only that no firmware path writes it.
