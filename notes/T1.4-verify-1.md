# T1.4 verification 1: flash writers, Digitone II OS 1.12

Independent check of `notes/T1.4-flash-writers.md`. I started from the bytes instead of from
that report's list: every DSPI register reference in all three ColdFire images, every PUSHR
command frame, every reference to every flash write/erase/protect primitive, and a dynamic run
of the in-OS writer under Unicorn.

Marks: **[verified]** = I checked it against the bytes, the disassembly, or a run;
**[inferred]** = reasoned from structure or from the S25FL-S datasheet family (no datasheet
was at hand). Addresses: main OS file offset 0 = `0x40000400`, bootstrap file offset 0 =
`0x800003FC`, section 4 file offset 0 = `0x80000400`.

---

## Verdict: holds with corrections

The bottom line survives: if a build changes **only section 3** and is flashed through the
normal in-OS upgrade, the stock code does not erase or write flash below `0x80000`, **as long as
the container stays under 3 MB**. But several supporting claims are wrong or depend on
conditions the report does not state:

1. The writer has no length clamp, and the flash address is only 24 bits wide. A container
   longer than `0x300000` erases the settings store at `0x380000`. A container longer than
   `0xF80000` wraps around to `0x000000` and then `0x040000`, the bootstrap. I confirmed both
   in an emulator run (§2, R1/R2). The "legitimately sealed" argument does not hold, because
   the HMAC key is public and we sign our own builds.
2. The bootstrap rewrites itself from the stored container on **every boot** whenever the
   section-2 table entry carries a version above `0x0201`. So the normal channel *can* lead to
   a bootstrap rewrite one boot later, if section 2 or its table entry is changed (R6).
3. The report missed the real backstop against stray writes. Every boot, the bootstrap locks
   sectors `0x0` and `0x40000` (DYB). That lock works only on the Spansion S25FL127S
   (256 KB-sector) branch of the flash probe (M1).
4. The report's account of how boot-flag bit 5 gets set ("maintenance mode", the factory
   console) is wrong. There are three setters, and the main one is a five-key combination held
   at power-on (R3).
5. Three flash writers were missed: the panel MCU firmware updater, which runs on every normal
   boot (M2); the USB accessory uploader for section 8 (M3); and dead security-register
   program/erase code (M4). None of them writes the DN2 NOR, but M2 matters for recovery.
6. The "correction" to elekloader's DT2 write-up comes from a misreading (R5).

---

## 1. Method

- `scripts/t1.4v_pushr_scan.py` makes linear `m68k-elf-objdump -m m68k:cfv4e` disassemblies of
  the main OS, the bootstrap and section 4 (`out/T1.4/verify-1/*.dis`). Over those it does three
  things:
  - scans **every 32-bit immediate in every instruction and register** for DSPI PUSHR-shaped
    values;
  - lists the command frame of **every DSPI0 transaction** (SR write followed by the first
    PUSHR write);
  - does a raw byte scan at every even offset for words inside the four DSPI blocks.

  Output: `out/T1.4/verify-1/pushr_scan.txt`, `dspi_raw.txt`.
- I collected caller sets from raw references (`scripts/t1.4_flash_refs.py refs`: `jsr`/`jmp`
  abs, pc-relative `jsr`/`bsr`/`bra`/`lea`/`pea`, and word32 at any even offset), and
  cross-checked them with `out/decomp/main_os/calls.tsv`.
- `scripts/t1.4v_writer_emu.py` runs the real `FUN_40139104` and the real erase and program
  driver under Unicorn (ColdFire V4e, from digikit's `.venv`). It uses a DSPI0 model and stubs
  the validator, UI and locks, then logs every flash command. Outputs:
  `out/T1.4/verify-1/emu_*.json`.

## 2. Confirmed

- **C1. All NOR I/O is on DSPI0, chip select PCS1.** [verified]
  - Raw scan: 314 words in `0xFC05C000-0xFC05C0FF` in the main OS. All of them sit in three
    places:
    - the driver at `0x40134a28-0x40136100`, including an undiscovered run at
      `0x40135074-0x4013537a`, see M4;
    - `FUN_400f19b4`, which only polls RDSR `0x05` (`0x80020005` at `0x400f1c3c`; a fatal
      handler that dumps RAM to eMMC);
    - the DSPI0 init at `0x400ced72` (CTAR0/MCR).
  - Every flash frame uses PCS byte `0x02`.
  - DSPI1 (`0xFC03C000`) carries no flash commands:
    - `FUN_400cec50` sends 16-bit register writes (`0x2002A000 | reg<<8 | val`);
    - `FUN_400cf7f8` sets up an eDMA stream to PUSHR with frames `0x8001xxxx`.
  - DSPI2 (`0xEC038000`, `FUN_400cf4b0`) streams section 7 to the SHARC (`0x9001xxxx`).
  - DSPI3 has no references.
- **C2. No chip erase.** [verified] No `0xC7`/`0x60` command frame appears as any 32-bit
  immediate in the main OS, the bootstrap or section 4. The same holds for WRR `0x01`/`0x31`,
  `0x11`, ASPP `0x2F`, PLBWR `0xA6`, PASSP `0xE8`, BRWR `0x17` and RESET `0xF0`. The raw-word
  hits for these (for example `0x08020001` at `0x40040baa`) are `btst #n,%d2` instructions and
  jump tables, not frames.
- **C3. The in-OS writer `FUN_40139104`** (the base address is right; for the loop, see R1).
  [verified]
  - It runs the validator at `0x40139114` (`bne` unless it returns 1).
  - The base is `movea.l #0x80000,A3` at `0x4013912e`.
  - It erases `(len-1+blk)/blk` blocks and adds `blk` each time.
  - The program base is `moveq #8; swap` = `0x80000`, writing pages of `0x200`.
  - **Emulated with the stock length 1,886,016:** 8 block erases `0xD8` at
    `0x080000..0x240000`, 3,684 page programs of 512 B from `0x080000` to `0x24c600`, and only
    opcodes `0x05/0x06/0xD8/0x02` (no DYB or PPB).
- **C4. Reachability of the in-OS writer.** [verified] The only caller is `0x4010921c` in
  `FUN_40109144`. Its only reference is a word32 at `0x401095c0` inside `FUN_401094e8`, which
  is reached from `FUN_401098d8` ("UPGRADE OS NOW?") and `FUN_401096be`. The RPC handler
  `FUN_40129f36` only stages and validates.
- **C5. The bootstrap lives at `0x40000`.** [verified]
  - `FUN_80001c48` calls DYB(`0x40000`,`0xFF`), erases `0x40000`, then programs
    `0x40000+i`.
  - The console's `#FULL_UPGRADE` does the same at `0x400cd838` (`pea 0xff`), `0x400cd846`
    (`jsr 0x40135f80`), `0x400cd852` (erase) and `0x400cd890` (program).
- **C6. The console is created only when boot-flag bit 5 is set.** [verified]
  - The test is `moveq #32; and.l 0x40287a60` at `0x400cf1ea`.
  - `FUN_400cebd2` has one call site (`0x400cf206`), and `FUN_400cd5f2` has one reference
    (`pea` at `0x400cebf8`).
  - The flags are stored at `0x400004ec` from the word the bootstrap pushes
    (`move.l 0x80008404,-(sp)` at `0x80000f02`/`0x80000f34`).
  - No main-OS code ORs bit 5 at run time: the only ORs are `0x92`/`0x02` at `0x400f21d4` and
    `0x04` at `0x400f2212`.
- **C7. The settings-store writers write only `0x380000`/`0x3c0000`.** [verified] Every
  `#0x380000` and `#0x3c0000` immediate lies in `0x400ccb90-0x400cd230`. They are all
  console-rooted (details in R9).
- **C8. The COKi migration `FUN_400f2022`.** [verified]
  - Its table at `0x401ffafc` is `{0x400000,0x800000,0xc00000}`, followed by the eMMC slots
    `{0x40000,0x48000}`.
  - It erases only a block whose first word is `"COKi"`.
  - `FUN_400f2168` calls it only when both eMMC copies fail. `FUN_400f2168` itself runs at
    `0x400cf102` only when bit 6 is clear.
- **C9.** `0x40135618` (`0x12`, 4-byte page program) has no reference. [verified]
- **C10. Geometry.** The probe `FUN_40135a7c` sets page `0x200` and block `0x40000` for mfg
  `0x01` / `0x2018` / ext `0x00`. [verified] It also accepts other vendors; see M1.
- **C11. Sections are read from the container.** The bootstrap reads section entries from flash
  `0x80020` (`FUN_80005462`) and section data from `0x80000 + offset` (`FUN_80001c48`).
  [verified] For section 4 I rely on T1.2.

## 3. Refuted or corrected

- **R1. "No code path writes flash below `0x40000`" and "the loop only increments, so it cannot
  reach the bootstrap".** Refuted as stated. [verified]
  - The erase command sends three address bytes (`FUN_40134a6a`, `0x40134aa8-0x40134ad8`), and
    so does the page program (`FUN_401354d6`, `0x40135540-0x4013556a`). Bits 24-31 are dropped.
  - Nothing clamps `len`.
  - Emulated:
    - `len = 0xF80001`: the 63rd erase goes to `0x000000`;
    - `len = 0xFC0001`: the erases end with `0x000000` and `0x040000` (the bootstrap block).
  - The console's `#UPGRADE` loop (`0x400cd8ba`) and the bootstrap's own STARTUP-menu writer
    (`FUN_80003c9c`, erase `FUN_8000237c` with three address bytes) have the same shape.
  - So the claim holds only for `len <= 0xF80000`. What actually saves the bootstrap is M1, and
    only on one flash part. Reaching this needs a sealed container over 15.5 MB, so it is
    unlikely by accident, but nothing in the writer prevents it.
- **R2. "Reaching the settings store would need a legitimately sealed >3 MB container".**
  Corrected. [verified]
  - The seal is no barrier for self-built images: the key is derivable from `"Multiplier"`.
  - Emulated:
    - `len = 0x300000`: the last erase is at `0x340000`;
    - `len = 0x300001`: it erases `0x380000`;
    - `len = 4,300,000`: it erases `0x380000`, `0x3c0000`, `0x400000`, `0x440000` and
      `0x480000`.
  - For scale, the unpacked sections add up to 4,256,285 B, so a store-only container would hit
    this.
  - The writer ignores errors: there is no test of `d0` after `jsr (a4)` at `0x40139158` or
    `jsr (a6)` at `0x401391ba`, and it still shows "Success! Rebooting".
  - So the `0x380000` limit exists only if the build tool enforces it, as elekloader's
    `flash_limit` does for the DT2.
- **R3. "The bootstrap sets bit 5 at `0x80000c42` only after a UART handshake
  (`pea 0x11; jsr 0x80001302`)".** Wrong in detail. [verified]
  - **`0x80000c42`** runs after `FUN_8000136c(table 0x80005ed6, 5)` returns true. That means
    exactly five keys are down at power-on, with ids `{18,19,20,21,35}`, and no bootstrap
    self-upgrade happened this boot.
  - `pea 0x11; jsr 0x80001302` (`0x80000c4a`) is a different branch: the STARTUP-menu key
    check, leading to `FUN_80002dc4`.
  - **`0x80000b3c`** sets bit 5 after a software reset (RSR `0xEC090001 & 0x20`) when the RAM
    word `0x48000000 == 0xB0B0DADA`.
    - The main OS writes that magic only in the console's `#REBOOT` and
      `#REBOOT_INTO_MAINTENANCE` (`0x400ce336`, `0x400ce39a`; strings `0x4021b169`,
      `0x4021b171`). These are the only two copies of the constant in the image.
    - Every other store to `0x48000000` writes 0: `0x40001a7a`, `0x40005614`, `0x400f1786`,
      `0x400f1e4c`, `0x401391f8`.
  - **`0x80000b9a`** sets bits 5 and 6 when the panel key read `FUN_80001276` times out.
  - In the main OS, bit 5 is shown as "MAINTENANCE MODE" (`0x4002f01c` → getter `0x400cedc6`,
    string `0x402141a0`).
  - The conclusion still holds: a flashed image cannot enter this mode in a normal session. But
    maintenance mode is a power-on key combination a person can hold, and it is also what a unit
    with a silent panel boots into.
- **R4. "#FULL_UPGRADE chunk ≤ 60 KB fits one block".** Unsupported. [verified]
  - The console's bootstrap length is `*(buf+4)-8`, with a loop `while > 0`
    (`0x400cd81c-0x400cd8b8`). It erases one 256 KB block and has no size guard.
  - The `< 0xF001` guard belongs to the bootstrap self-upgrade `FUN_80001c48`.
  - The console also does not checksum, HMAC or version-check that image. It checks only the OS
    part's `"ELE3"` magic and the header word `0x34` (`0x400cd78c-0x400cd7a6`).
- **R5. "Correction to elekloader DT2 DEVICES.md".** A misreading. [verified]
  - `vendor/elekloader/docs/DEVICES.md:96-98` already says the factory console upload "writes a
    container to 0x80000 or another image to 0x40000-0x80000".
  - The sentence at `:99`, "None of them writes anything from the main OS image", is about data
    taken from the OS image ("it holds no copy of the bootstrap to re-flash").
  - So this is not a DN2/DT2 difference.
  - The transport may differ: the DT2 doc says debug UART, while on the DN2 the console's output
    goes through `FUN_400053d4`, which reads USB OTG `0xFC0B01C8`. [verified for output only]
- **R6. "The self-upgrade cannot be triggered by any 1.12-derived build".** Conditional.
  [verified]
  - `FUN_80001c48` runs on every boot (`0x80000aea`), not only from the STARTUP menu. It reads
    the section-2 entry from the **stored container**.
  - The version is the high half of that entry's load field: `0x02010000` at container offset
    `0x3c` in stock, compared against `0x80000408` = `0x0201`.
  - The in-OS upgrade writes that table. If a container's section-2 entry says more than
    `0x0201`, the bootstrap rewrites `0x40000` on the next boot, provided:
    - the depacked image's word at +`0xc` matches;
    - the CRC-32 residue is `0xDEBB20E3`;
    - the packed size is ≤ `0x10000` and the unpacked size is < `0xF001`.
  - Safe only while section 2 **and its table entry** stay stock.
- **R7. The opcode scan was incomplete.** [verified]
  - `t1.4_flash_refs.py opcodes` matches only `move.l #imm,%d0`, and only inside
    `0x40134a00-0x40136100` / `0x80002000-0x800029f0`.
  - It misses frames loaded into other registers:
    - main OS: `0x42` (`0x401351e4`, `d3`), `0x44` (`0x40135308`, `d1`), `0x48` (`0x4013509c`,
      `d3`);
    - bootstrap: `0x48` (`0x80002622`, `d2`) and `0x03` (`0x80007942`, the SRAM-copied read).
  - The "no chip erase" result still stands with the full scan (C2).
- **R8. "The 0x20 subsector arm is unused".** The outcome is right but a function was missed.
  The arm has its own wrapper, `FUN_4013576c` (WREN + `FUN_40134a6a(0,addr)` + poll), and that
  wrapper has no reference. The report's primitive table also leaves out `FUN_401358f2`
  (`0x2B`, ASP register read). [verified]
- **R9. "Every settings writer is reached only from FUN_400cd5f2 or its #WRITE table".**
  Imprecise, though still console-rooted. [verified]
  - `FUN_400ccda2` is not called by the console directly. It is reached through `FUN_400d032c`
    (console only) and through the callback `FUN_400cfef2`. That callback's only reference is in
    `FUN_400d06b6` (`0x400d0712`), which is referenced only from `FUN_400d032c` (`0x400d0364`).
  - `FUN_400cd036` has no reference at all.
- **R10. "The protection command call sites are ≥ `0x380000`"** does not hold for PPB erase.
  - `FUN_40135dc8` sends a single frame `0x080200E4` with no address (`0x40135e20`).
    [verified]
  - On S25FL-S parts, PPBE clears the PPB of **every** sector. [inferred, datasheet family]
  - So the console-only settings writers also remove any persistent protection on sectors 0 and
    1, and put it back only on `0x380000`/`0x3c0000` (`FUN_400cd10a` re-protects exactly those
    two).
- **R11. The 12.9 MB read in `FUN_400f2022`** is a READ (`0x03`) whose 3-byte address
  auto-increments, so it is harmless. `0xC4B114` is the size of the RAM persistence image that
  `FUN_400f2168` and the crash dump `FUN_400f19b4` also move to and from eMMC. It is not a NOR
  partition size. [inferred]

## 4. Missed

- **M1. The bootstrap locks sectors 0 and 1 on every boot.** [verified code; lock semantics
  inferred]
  - `FUN_800009c6` calls `FUN_80002742(0,0)` and `FUN_80002742(0x40000,0)` at
    `0x80000a70-0x80000a7e`, before it hands over to the main OS. That is DYB write `0xE1` with
    data `0x00`, which means "protected": the same code writes `0xFF` right before it erases
    `0x40000`.
  - The main OS's only DYB write is `#FULL_UPGRADE`'s (`0x40000`,`0xFF`).
  - The main OS erase and program routines catch a protection failure: if `SR & 0x60` is set,
    they send CLSR (`FUN_40134b58`) and return -1 (`FUN_401357ce`, `FUN_401354d6`).
  - So in a session, a stray erase or program at `0x0`/`0x40000` (R1) fails.
  - **It depends on the flash part.**
    - The bootstrap's `FUN_80002742` and the main OS's DYB/PPB functions run only when the probe
      found mfg `0x01` / `0x2018` / ext `0x00` (flags `0x80007d04`, `0x4463fc64`).
    - Both probes also accept ISSI `0x9D` (`0x6017/0x6018`), Macronix `0xC2`
      (`0x2017/0x2018`), Winbond `0xEF` (`0x4014`, `0x7015`, `0x4017/0x4018`), EON `0x1C`
      `0x7015`, and Spansion with ext `0x01`. Those get 64 KB erase blocks and **no protection
      at all**.
  - The DN2's actual part is not known. The S25FL127S figure is digikit's for the DT2.
- **M2. Panel MCU firmware updater, on every normal boot.** [verified structure; command
  meanings inferred]
  - `FUN_400dbbd8` is called from `FUN_400cedfc` at `0x400cee7a` (when bit 6 is clear) and works
    over UART8 (`0xEC070000`).
  - It asks the panel for its version (`0x60 0x02`, `0x70 0x00`). It updates if the reply is
    `'p'`, `0x0C`, type `2`, and the panel version is below `0x15` (word `0x402f7d44`).
  - The update sends `0x80 0x42`. Then, for each 1 KB page, it sends cmd `3` (erase, inferred)
    and cmd `1` (address), then cmd `2` with words from run address `0xC004` up, and finally the
    header word at `0xC000`. It retries 3 times.
  - The image is the embedded blob from `0x402F7D40` to the end (linked at `0xC000`, header
    `0x0000E778`, `0x15`).
  - This does not write the DN2 NOR, but it matters for recovery: the bootstrap's key read and
    STARTUP menu depend on that panel answering (`FUN_80001276`, `FUN_80001302`).
- **M3. Section 8 is uploaded to a USB accessory.** [verified path; device identity inferred]
  - `FUN_400f2a82` reads section 8 from NOR (`FUN_4013487a(8)`). It sends it as Elektron SysEx
    (`F0 00 20 3C 17 00 7E`…, 101-byte packets, 7-bit, with checksum) through `FUN_40004734`
    (USB OTG `0xFC0B01C4`).
  - It is triggered from `FUN_400f2c76` ← `FUN_4012072c` when a device reports a release below
    `0x12` that differs from the cached one, and whose version string does not start with
    `"dev-"`.
  - The strings "BOBSETTINGS" and "OUTBOX 8 UPDATE REQUIRED" point to an external breakout box.
    So section 8 (the i.MX RT image) is that box's firmware.
- **M4. Undiscovered security-region code in the driver.** [verified]
  - Three functions sit outside every Ghidra function:
    - `0x4013503e`: `0x48` read;
    - `0x4013517e`: WREN + `0x42` program;
    - `0x401352b8`: WREN + `0x44` erase.
  - Their address is `(arg0<<12)|arg1`, Winbond-style security registers.
  - They have no direct or word32 reference, so they are dead.
  - No status-register write exists that could lock those registers.
  - The bootstrap has a matching unreferenced `0x48` read at `0x80002612`.
- **M5. Section 4 has the same NOR library, but no writer can be reached.** [verified for
  direct and word32 references]
  - None of these is referenced: the write wrappers `0x800055a2`, `0x8000561e`, `0x80005688`;
    the protection functions `0x800051a2`, `0x800052c4`, `0x8000547c`; the pointer table
    `0x800077cc` for "CLEARING %x"/"WRITE"/"DONE".
- **M6. The bootstrap's recovery writer `FUN_80003c9c` has no upper clamp either.** Its erase
  wait (`FUN_80002714`) polls WIP only, with no error handling. Recovery with a stock image is
  unaffected. [verified decomp]

## 5. For the brick checker (T1.7)

1. Reject any build where container `len > 0x300000`, so the container ends at or below
   `0x380000`. Stock is 1,886,016. The writer itself enforces nothing (R1, R2).
2. Keep section 2's bytes **and** its table entry (load field `0x02010000`) identical to stock
   (R6).
3. Keep the panel firmware blob (`0x402F7D40`-end, version word `0x402f7d44`) and
   `FUN_400dbbd8` identical to stock. Keep section 8 unchanged (M2, M3).
4. In the emulated upgrade: allow no `0xE1/0xE3/0xE4` frames, and keep every erase/program
   address in `[0x80000, 0x380000)`. On an emulated boot, bits 5 and 6 must stay clear.
   `scripts/t1.4v_writer_emu.py` already does the first part for the writer alone.
5. Do not count on M1: it protects only on the S25FL127S branch.

## 6. Not done / open

- The DN2's flash JEDEC ID is unconfirmed, so it is unknown whether M1 protects this unit.
- The S25FL-S meanings (DYB `00h` = protected, PPBE is chip-wide, E_ERR handling) come from the
  datasheet family and from the firmware's own usage, not from a datasheet in hand.
- The emulator run is of the writer alone, with stubs (validator forced to 1, a DSPI0 model that
  always reports idle). It is not a full boot.
- Calls through computed addresses are not excluded. Every reference scan here is for direct
  references and word32 references.
