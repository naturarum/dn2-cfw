## Dangerous files that PASS the checker

### A. Neutered in-OS upgrade validator (`danger-validator`) [verified]

- **The change.** Depack stock section 3, overwrite the four bytes at `0x400dbdb0` with
  `70 01 4e 75` (`moveq #1,d0; rts`), repack at level 0, seal. The function at `0x400dbdb0`
  is the main OS's upgrade validator (acceptoracle's `M['validator']`; HANDOFF/T1.2). It now
  returns 1 (pass) for any input.
- **Why it is dangerous.** Once this OS is installed, every later *in-OS* OS UPGRADE is
  checked by this validator before the in-OS writer `FUN_40139104` flashes it. Neutered, it
  accepts an unsigned, corrupt or downgraded image, which `FUN_40139104` then writes with no
  length clamp (T1.4). The STARTUP-menu recovery path still uses the stock bootstrap's own
  validator (section 2 is pinned), so recovery is intact; the brick vector is the normal in-OS
  upgrade, from a file the checker *accepted*. [inferred from T1.2/T1.4; not run on hardware]
- **Why it passes.** `0x400dbdb0` is **2 bytes past** the protected updater range end
  `0x400dbdae`, and is in none of the seven protected ranges, so check 6 PASS [verified:
  `protected_report` reports all seven unchanged]. The patch bytes `0x70014e75` are not a flash
  reference, PUSHR word, DSPI0 address or `0xB0B0DADA`, so check 7 PASS [verified:
  `scan_new` returns nothing]. Check 4's device half runs the *stock* validator (resolved in
  the stock image), so it still returns 1 and passes. Check 5 enters the main OS at the entry
  with output = the intended (patched) image. The validator is never called during the cold
  boot, so check 8 passes. This is open problem #1 of the checker report, concretely realised.

### B. Unchecked SHARC/DSP program (`danger-dsp`) [verified]

- **The change.** Replace section 7 (the DSP program) with a copy whose byte at offset
  `0x1000` is flipped; main OS (section 3) left stock, so `--intended-main` is stock.
- **Why it matters.** ROADMAP lets sections 3 and 7 differ, and check 2 only requires section
  7 to depack. No check runs the SHARC, so a corrupt or hostile DSP program (crashing audio,
  wrong routing, a DSP that hangs) is invisible to every check. This is not a CPU brick, but it
  is a functional break the checker calls safe. The checker report lists it as a known limit.

### C. Flash gadget via a computed address (`danger-computed`): passes all ten [verified]

The full run accepted this file (exit 0, 850 s): check 7 did not flag the gadget, and the
check-8 watch was clean (cold boot and emucheck both saw only PUSHR `0x9f`, no write/erase/
protect), because the gadget at `0x40100100` is off the cold-boot path. So the whole file is
accepted although it contains a reference into the NOR driver.

Check 7 scans only the literal bytes of changed regions for an address *inside* the NOR driver
`0x40134a28-0x4013621c` or a writer entry. It is defeated by computing the address:

| gadget at `0x40100100` | reaches | `scan_new` verdict |
|---|---|---|
| `4eb9 401354d6` (`jsr 0x401354d6`) | PAGE PROGRAM `0x02` | **flagged** `flash_refs` (control) |
| `207c 40134000` `d1fc 00000a28` `4e90` (`movea.l #0x40134000,a0; adda.l #0xa28,a0; jsr (a0)`) | WREN `0x40134a28` | **not flagged** |
| `207c 40139000` `d1fc 00000104` `4e90` | in-OS writer `0x40139104` | **not flagged** |
| `4e71` `0802 00c7` (EOQ PUSHR chip-erase word stored as data after a nop) | DSPI0 frame | **not flagged** |

[all verified with `bc_static.scan_new`.] The base `0x40134000` is below the driver range, so
`_flashy()` is false; the `+0xa28` is a small immediate; `jsr (a0)` carries no target word.
A modder can call any erase/program primitive or the writer without tripping check 7. The
only remaining static backstop is check 6, which keeps the driver and `FUN_40139104`
byte-identical -- this evasion does not touch them -- and check 8's watch, which covers only
the cold boot and the 600M instructions at the main screen, not a path behind a key, a USB
message, or an in-OS upgrade. A gadget in such a path would never be seen. The EOQ-only word
`0x0802_00c7` as a data constant is also missed, confirming the report's stated blind spot (b):
`0x0802_00XX` is `btst #n,d2`, so `pushr_raw()` excludes it unless it is a long-immediate
operand.

## Gaps found, with suggested fixes

1. **The in-OS upgrade validator `0x400dbdb0` is not protected.** `danger-validator` was
   **accepted** (all ten PASS, 854 s). [verified]
   *Fix:* add the validator to check 6's `PROTECTED` in `bc_static.py`, e.g.
   `(0x400DBDB0, 0x400DBDE4, 'in-OS upgrade validator FUN_400dbdb0')`. The checker report
   already proposes this range; this run shows it is reachable and dangerous, not theoretical.
   A brick-safe mod never needs to weaken the validator, so pinning it costs nothing.

2. **Section 7 (SHARC/DSP) is unchecked beyond depacking.** `danger-dsp` passes. [verified]
   *Fix:* if DSP integrity matters, either pin section 7 to stock unless the caller passes an
   explicit `--intended-dsp <image>` (mirroring `--intended-main`), or boot the SHARC in the
   emulator to a checkpoint. At a minimum, check 2's line "section 7 differs and depacks"
   should be an explicit WARNING that DSP content is otherwise unvalidated, not a PASS, so a
   changed DSP alone makes the verdict "incomplete" rather than "accept" until an intended DSP
   is supplied.

3. **Check 7 only sees literal flash addresses; a computed or indirect reference evades it.**
   `danger-computed` reaches WREN `0x40134a28` and the writer `0x40139104` with no flagged
   bytes, and the whole file was **accepted** (850 s) because the gadget is off the cold-boot
   path that check 8 watches. [verified]
   *Fix:* treat check 7 as a tripwire, not a gate. The real gate for flash safety is check 6
   (driver + `FUN_40139104` byte-identical, which the evasion cannot touch) plus a **dynamic**
   watch of the actual erase/program wire addresses during an emulated **in-OS upgrade**
   (T1.4-verify-2's rule: every `0x20/0xD8/0x02/0x12` address in `[0x80000, 0x380000)`, no
   `0xE1/0xE3/0xE4`). That catches any write however the address was formed. It needs digikit
   to drive an upgrade session, which it cannot yet (check 8's limit) -- so prioritise that,
   and until then state in the verdict that check 7 is best-effort against computed references.

4. **Check 8's watch covers only the cold-boot and main-screen window.** A flash gadget behind
   a key, a USB message or an in-OS upgrade is never executed by the emulated boot, so neither
   check 7 (if computed) nor check 8 sees it. [verified by construction in gap 3]
   *Fix:* same as 3 -- drive key/USB/upgrade sessions in the emulator; the watch is already
   written and would cover them.

## Things that are NOT gaps (checker behaved correctly)

- **A resealed, modded section 2/4/8 is refused by check 2, not by the seal.** `s2/s4/s8-bodyflip`
  reseal cleanly: check 4 (checksum + HMAC, independent and on the device) PASSES, and check 2
  FAILS on the byte difference. [verified] The byte-identity rule is load-bearing: if check 2
  were loosened, a resealed modified bootstrap would pass check 4. Worth keeping check 2 strict.
- **A reset-entry crash is caught only by the emulated boot.** `reset-illegal` passes checks
  1-7, 9, 10 and fails only check 8. [verified] So `--no-emu-boot` must never be read as an
  accept; the checker already enforces this (SKIP -> "incomplete", exit 3, never 0).
- **The two independent halves of check 4 each catch their own break.** `cksum-broken` (valid
  seal, wrong preamble checksum) and `seal-broken` (valid checksum, flipped HMAC) are each
  refused by check 4. [verified]
