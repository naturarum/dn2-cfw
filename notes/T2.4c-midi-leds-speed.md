  `emu/midi.py` models it; with CLOCK/TRANSPORT SEND on and a MIDI-machine track, PLAY sends start,
  24 ppq clock at 80.9 BPM (project 81.0) and the trig notes exactly 4 sixteenths apart. [verified]

- LEDs: `B9 index palette-entry`, `B5 entry r g b`; index -> key from the factory UI test tables.
  Drawn on the keys in the window. [verified]
- Speed: C block counter + batched SSI minors. With the clock: 0.82x real time, from 0.10x. [verified]
- Bug found: with the clock on, timer ticks were dropped (phase coincidence), the UI loop barely ran. Fixed. [verified]

## (c) Speed with the audio clock on

### Where the time went (cProfile of the worker thread) [verified]

`scripts/t24c_profile.py` wraps `LiveEmulator.run` in cProfile; `out/T2.4c/play3.script` presses PLAY,
waits 3 s of emulated time (new script command `wait-emu`), STOP. Before any change: 40.1 s wall for
3.85 s emulated (0.10x), profile `out/T2.4c/prof/base.txt`:

| where | wall s | share |
|---|---|---|
| `Ssi0Dma.service` -> `_run_minor`: 96,000 eDMA minors a second, each a dozen 2-4 byte `mem_read`/`mem_write` calls through ctypes | 17.0 | 44% |
| the fast stepper's Python block hook (`_on_block` + the binding's `wrapper`/`__hook_code_cb`): 29.1M calls, about 0.4 us each | ~12 | 30% |
| guest code itself (`emu_start` own time) | ~6.6 | 17% |
| everything else (timers, forced interrupts, idle hooks, raise_vector) | ~2 | 5% |

The guest load is real work, not a missed idle loop: a block histogram while playing
(`scripts/t24c_hotblocks.py`, `out/T2.4c/prof/hotblocks.txt`) puts 30% in `FUN_400db28e`
(EMAC loop of 867 iterations per audio block, writing the SHARC frame area at `0x800068e0`), 17% in
`FUN_40137a06`, 15% in `FUN_400db340`, 10% in the memcpy `FUN_40134770`: all called from the frame
handler `FUN_40025e36`, 1,500 times a second. That is about 30M guest instructions per emulated
second (CPU load 20% of 150M).

### Fixes (behaviour kept)

1. **`emu/ssi.py`: `_run_minors(channel, n)`** runs a batch of minors with one 32-byte TCD read per run
   of minors (up to the next major-loop end), one contiguous read of the TX data, and three writes.
   Major-loop completion, scatter/gather and the INT_MAJOR flag are handled as in `_run_minor`, which
   stays as the reference. RX and TX are batched one after the other instead of interleaved per
   request (separate descriptors; RX writes no data). Test: `test_batched_minors_match_one_by_one`
   compares memory and counters after `n` x `_run_minor` and `_run_minors(n)` across major loops,
   scatter/gather and a shortened loop (62 minors, as the vector-170 handler programs to realign).
2. **`emu/nativehook.py`: the block budget in C.** The same three lines as `_FastStepper._on_block`
   (stop if no budget left, else count), compiled once with the system `cc` into
   `~/.cache/digikit-native/` and installed with Unicorn's own `uc_hook_add` (the binding's prototype,
   our function pointer and a ctypes struct as user data). `_FastStepper.blocks/left` read and write
   that struct, so idle skipping and the DTIM0 interpolation are unchanged. No compiler, or
   `DIGIKIT_NATIVE_HOOKS=0`: the Python hook as before. `_FastStepper.NATIVE = False` forces Python
   (needed to wrap `_on_block`, as `t24c_hotblocks.py` does).
3. **Timer ticks were being dropped with the audio clock on** (found while checking the LEDs, below).
   With `--ssi0-hz --ips 150e6`, PIT0, PIT2 and DTIM3 were refused about 100% of the time
   (2 emulated s: PIT2 120 missed / 1 fired, PIT0 100/1, DTIM3 61/0) [verified]. Cause: a snapshot
   is saved on a timer deadline, the SSI clock was aligned on `timers.now`, and at 150M every timer
   period is a whole number of 100,000-instruction SSI periods (PIT2 25, PIT0 30, DTIM3 50). Each
   SSI event therefore fell a few instructions before a timer deadline, the timer found the CPU in
   the channel-50 ISR (`0x40025394`, IPL 7) or the frame handler (IPL 5), and `Pits.service` drops a
   refused tick [verified: SR/PC logged at each miss]. So the RTOS tick task and the UI main loop
   (`0x4002f178`) hardly ran: 3 main-loop messages in 2 s instead of 60, the LED refresh never ran.
   Fix in `emu/live.py`: start the SSI clock half a period after `timers.now` (the real phase is
   unknown). After: 0 missed of 299/250/150 PIT2/PIT0/DTIM3 ticks in 5 s of playing, main loop at
   its normal rate [verified]. Also `spin(..., timers_first=True)` (new, default off; emu.live uses it):
   at an exact tie the timer is taken first and the audio interrupt preempts it.
   This also explains part of T2.4b's "UI never redraws" at low `--ips`.

### Speed now [verified]

Apple M2 Pro, warm snapshot, `--speed 0`, PLAY pressed, emulated seconds per wall second:

| | before | after fixes 1-2 | after fix 3 (UI running again) |
|---|---|---|---|
| playing, `--ssi0-hz --ips 150e6` | 0.10 | 0.92 | 0.82 |
| stopped, `--ssi0-hz --ips 150e6` (`--bench 12`) | | | 0.81 (0.24 with `DIGIKIT_NATIVE_HOOKS=0`) |
| main screen, no audio clock (`--bench 12`) | 1.95 (T2.4a) | | **8.0** (1.99 with `DIGIKIT_NATIVE_HOOKS=0`) |

JSON: `out/T2.4c/prof/bench-*.json`, `out/T2.4c/proof/report.json`.

**Same behaviour, checked** [verified]: the batched SSI path against the per-minor one in a unit test;
the C block counter against the Python one on a real Unicorn loop (identical blocks, budget, PC and
registers per step) and on the firmware: tempo from the sequencer position over 10 s of playing,
`scripts/t24c_tempo.py`: 80.807 BPM with the C counter, 80.789 BPM with `DIGIKIT_NATIVE_HOOKS=0`.
The MIDI proof gives 80.89 BPM from the clock and exactly 4.000 sixteenths at 81 BPM between notes.
So the emulated tempo is 81.0 within 0.3%; T2.4b's "5.4 steps per second" was rounded (5.386-5.394
measured here, before and after these changes).

The remaining cost is mostly Unicorn running the guest's own work (about 0.8 wall s per emulated s:
`emu_start` own time 3.4 s of 5.5 s in `out/T2.4c/prof/opt1.txt`), plus about 3,700 timer/SSI step
boundaries per emulated second handled in Python. Real time with the clock on is not reached on this Mac:
the window runs slightly slow (the emulated clock lags, then `MAX_LAG_S` lets it go).

## (a) DIN MIDI: UART9

### Where it is on 1.12 [verified: image bytes, then the emulator]

- `FUN_400cedfc` (OS init) calls `FUN_4000243e(0x2625a, FUN_4011ffbc)` (UART8, 156,250 baud, the panel
  MCU) and `FUN_40002844(0x7a12, FUN_4011f3ac)`: **UART9 at 31,250 baud** (UBG2 = 132 MHz / (32 x baud)),
  receive callback `0x4011f3ac`. No other UART is set up for MIDI.
- **Out, bulk: eDMA channel 37.** TCD37 (0xFC0454A0): SADDR walks a 4 KB ring (ATTR 0x6000: source
  modulo 4096, base `[0x4058e580]` = 0x4e6c9000), DADDR = UART9 data 0xEC07400C, 1 byte per minor.
  `FUN_40002612(len, buf)` copies into the ring and starts the channel (SERQ 0x25); while a transfer
  runs it only queues (`[0x4058e594]`). Completion = **vector 157** (`FUN_40002102`), which chains
  the queued bytes. The MIDI task's flush `FUN_4012a36c` uses it when bit 0 of `[0x446181f0]` is set
  (bit 1 = USB, `FUN_40004734`); both bits are set in the warm project.
- **Out, single bytes: programmed I/O.** `FUN_40002746(byte)` writes the data register when no DMA
  transfer is running and USR has TXRDY, else queues into a 1 KB ring (`[0x4058e584]`), pauses
  channel 37 (CERQ 0x25) and unmasks INTC1 source 53. **Vector 181** (`0x40001f86`) sends one byte
  per TXRDY and masks source 53 (SIMR 0x35) when empty, then resumes the DMA. Realtime bytes take
  this path: the step handler `0x400d99de` calls `FUN_4012343e` -> `FUN_401233de` (gate `[0x446488d0]`,
  port bits from settings: bit 0 DIN, bit 1 USB).
- **In: eDMA channel 36.** TCD36 (0xFC045480) moves each received byte into a 32 KB ring (ATTR 0x0078:
  destination modulo 32768, base `[0x4058e588]` = 0x4e6c0000); DADDR is the producer pointer.
  **Vector 156** (`0x400021a0`) drains it from `[0x4058e5a8]` and calls `[0x4058e5b8]` = `0x4011f3ac`
  per byte, which feeds the parser `FUN_4011ee4a` (state at 0x445290c4). Parsed messages go to queue
  0x445f0400 and post semaphore 0x445f03b8, which the MIDI-in task `FUN_40120a02` pends on (it also
  polls the USB queue 0x445f03e0); DIN messages are dropped unless bit 0 of `[0x42432b11]` is set.
- INTC1 levels for sources 28 (RX), 29 (TX DMA) and 53 (UART9) are all 4.

### The model: `emu/midi.py` (new)

Like `emu/edma.py`'s UART8 transmit: a write of 37 to SERQ runs channel 37's whole major loop at once
(SADDR advanced with the 4 KB modulo, CITER reloaded, CSR DONE set, the completion queued); a byte
written to UART9's data register is sent at once; USR always reads TXRDY|TXEMP; INTC1 SIMR/CIMR writes
for source 53 switch the UART interrupt. Owed interrupts (157, 181, 156) are raised when the IPL allows,
at spin() step boundaries and after every `rte`. `feed(bytes)` writes the receive ring at DADDR (32 KB
modulo), advances DADDR and owes vector 156. Each byte sent is logged as (time handed to the UART,
time on the wire at 31,250 baud back to back, byte, path), in emulated seconds.

One fix was needed for MIDI in [verified]: `build(unblock=True)` force-satisfies pends whose semaphore
has no known poster. Once real input had woken the MIDI-in task, every later pend was faked and the
task spun on its empty queues at 86% of the CPU (the UI starved). `midi.install` now adds that
semaphore (read from the parser struct named by the receive callback's `pea.l`) to `unblock_skip`.

### Proof: notes and clock at the project tempo [verified]

`out/T2.4c/proof/midi-proof.script` (keys only, from `warm800M.snap`, `--ssi0-hz --ips 150e6`):
SETTINGS > MIDI CONFIG > SYNC, CLOCK SEND and TRANSPORT SEND on (both were off); FUNC + SYN (MACHINE
SEL) on track 1 -> MIDI; FUNC + encoder A push enables CHAN (it reads "Func+Press to enable", then 1);
RECORD, TRIG 1 5 9 13, RECORD; PLAY 4 s; STOP. Output `out/T2.4c/proof/midi.txt`, `proof.mid`, PNGs;
checked with `scripts/t24c_midi_check.py`:

- `FA` (start) at 12.3925 s, `FC` (stop) at 16.5365 s, clock `F8` before, during and after play.
- Clock while playing: 135 ticks at 32.357/s = **80.89 BPM** (24 ppq) against 81.0 on screen; each
  interval is 46, 47 or 48 audio blocks (the step handler runs once per 1/1500 s block).
- Notes: 4 x `90 3C 64` (note-on ch 1, C4, velocity 100), the first 1.4 ms after `FA`, spaced
  **4.001, 4.000, 4.000 sixteenths at 81 BPM** (0.7407 s); each ended by `90 3C 00` after 0.997-1.011
  sixteenths (default length 1/16). Bulk bytes go by DMA (vector 157 x8), realtime bytes by PIO.
- The warm project's pattern is **128 steps** (8 page LEDs lit, see LEDs), so the 4 trigs on page 1
  repeat only every 23.7 s; an earlier 13 s run showed exactly 4 notes for that reason.
- `proof.mid` reads back in mido as format 0, 960 ppq, tempo 81: start marker, 4 note-on/off pairs
  at 12.393 + 0.741 n s, stop marker. Time 0 of the file is the start of the run.

### MIDI in [verified]

`out/T2.4c/midiin/clockin.script` sends `FA`, then 120 x `F8` about 20.8 ms apart (script command
`midi-in HEX`), then `FC`, into the DIN in (clock receive and transport receive are on in the

### Live CoreMIDI port [verified]

`--midi-port [NAME]` opens a **virtual** output (default name "Digitone II (emulator)") with
python-rtmidi and sends each message as it completes; `--midi-in [NAME]` opens a virtual input whose
messages go to the DIN in. Only virtual ports are opened. Needs `uv run --with python-rtmidi`
(pyproject unchanged). `scripts/t24c_coremidi_check.py` ran the proof script with the port open and
read it back from a second rtmidi client on the same virtual port: 478 messages arrived (start,
stop, 4 note pairs, 468 clocks). In wall time the notes were 0.92 s apart and the clock 26.0/s,
because the emulator ran at about 0.8x real time with the clock on (below): a synth plugged in
plays the pattern about 20% slow.

## (b) Panel LEDs: UART8 to the panel MCU

### The messages [verified: decompile, wire capture, firmware tables]

All go through the UART8 transmit ring `FUN_4000220c` (eDMA 35, already modelled by `emu/edma.py`):

| bytes | sender | meaning |
|---|---|---|
| `B9 i v` | `FUN_40132428`, `FUN_401320e8` | LED at wire index `i` (0-53) shows palette entry `v` |
| `B5 i r g b` | `FUN_401322fc` | palette entry `i` (0-135) = r, g, b, 6 bits each |
| `B7 x`, `BC x` | `FUN_4011fb28`, `FUN_4011fb94` | from the render loop; not LEDs (`BC 01` about once per redraw) |
| `BB a b c` | `FUN_4011fb58` | not LEDs |
| `B8` | `FUN_40131eec` | not LEDs |
| `0x40\|x 00` | `FUN_4011faf6` | not LEDs |
| `0x10\|x n` + 8 bytes | `FUN_40131f04` | 10-byte blocks, heads 0x10-0x16 with n = 0x10..0x78 step 8: a bitmap upload (911 bytes when the FLTR page opened); not decoded |

- **Values are palette indices.** `FUN_40132388` sends the palette: 0 = off, 1 = dim white (the
  unlit-key glow), then 16 levels each of red 2-17, green 18-33, blue 34-49, yellow 50-65, cyan 66-81,
  magenta 82-97, white 98-113, orange 114-129, and 6 specials 130-135; one of three tables
  (0x4020905c + 0x192 n) by the LED brightness setting. Cached in RAM at 0x402a10d0 (0x00RRGGBB).
  Used: 0x11 red 16/16, 0x21 green 16/16, 0x41 yellow 16/16, 0x71 white 16/16, 0x83 special, 6 and
  10 dim reds, 26 green 9/16.
- **Index -> key.** Views call `FUN_4002c318(manager, led_code, mode, colour)`, which calls
  `FUN_40132428(led_code, value)`: wire index = table 0x401f3a14[led_code] = led_code - 1. LED codes
  are their own numbering, not the panel's button codes: the main screen maps page ids 1-6 to LED codes
  0x14-0x19 (`MainScreenView::vslot18`). The key for each LED code comes from the factory UI test
  (constructor `FUN_400d2626`): 45 LED codes at 0x401f37b0 paired with 45 button codes at 0x401f3628
  (pressing button i lights LED i), plus 8 "round" LEDs at 0x401f36dc. On 1.12:

  | LED code (wire = code - 1) | key |
  |---|---|
  | 1 2 3 | TRK, KEYBOARD, FUNC |
  | 4 5 6 7 8 9 | PTN, SONG, PRESET, SETTINGS, VOICE, TEMPO |
  | 10 11 12 | RECORD, PLAY, STOP |
  | 13 14 15 16 17 18 19 | YES, NO, UP, DOWN, LEFT, RIGHT, PAGE |
  | 20-25 | page keys TRIG, SYN, FLTR, AMP, FX, MOD |
  | 26-33, 34-41 | TRIG 1-8, TRIG 9-16 |
  | 42-49 | the 8 round LEDs (pattern pages 1-8 on the main screen) |
  | 50 51 52 53 | ARP, PLUS, STACK, MINUS |

- The firmware keeps the state at 0x466b8420[54] (an alternate layer at 0x466b8456 where
  0x466b848c[i] is set); the main screen refreshes its LEDs 30 times a second and only changes go on
  the wire.

### In the emulator

`emu/leds.py` (new): `PanelLeds` decodes the stream incrementally, seeds palette and values from the
RAM copies when the image matches (anchor literals checked in `FUN_40132428`, `FUN_401322fc`,
`FUN_400d2626`), maps wire index -> button code from the factory test tables. `emu.live` feeds it the
UART8 bytes after every step. Window: each key with an LED gets a lit strip along its top in the
LED's colour (dim levels lifted with a 0.5 gamma so the glow shows), and a row of 8 round "PAGE LEDS"
under the panel; checked with the window withdrawn (`scripts/t24c_tk_smoke.py`: FUNC held -> every
trig key's strip (0, 182, 0), STOP and SYN white, round LEDs red). Headless: `png NAME` writes the LED
state next to the screen.

## How to use

```sh
# window, audio clock, LEDs on the keys, DIN MIDI out to a virtual CoreMIDI port (and MIDI in from one)
DN2_RTMIDI=1 scripts/dn2-live.sh --ssi0-hz --ips 150e6 --midi-port --midi-in
# start from the MIDI-ready snapshot: clock + transport send on, track 1 = MIDI ch 1, trigs 1 5 9 13
DN2_SNAP=out/T2.4c/saved/midi-ready.snap scripts/dn2-live.sh --ssi0-hz --ips 150e6
# headless: log and .mid of what the unit sends, LEDs saved with every png
scripts/dn2-live.sh --ssi0-hz --ips 150e6 --script S --out DIR --midi-log DIR/midi.txt --midi-file DIR/out.mid --midi-bpm 81
python3 scripts/t24c_midi_check.py DIR/midi.txt 81      # tempo/notes check of a log
```

In a script: `wait-emu S` (emulated seconds), `midi-in 90 3c 64` (bytes to DIN in). In the window
the status line shows the MIDI byte counts. To send notes, a track must be a MIDI machine with
CHAN enabled (FUNC + encoder A push; the CHAN box shows "Func+Press to enable" while it is off).
Synth tracks send nothing on DIN in the warm project. `out/T2.4c/saved/midi-ready.snap` was saved
with the audio clock running and reloads with it (checked: same notes and clock after reload).

## Limits and open

- **Speed with the clock on is about 0.8x real time** on the M2 Pro, so the virtual port plays about
  20% slow. The rest is the guest's own frame work under Unicorn (about 30M instructions per emulated
  second). Next steps if needed: turn the narrow MMIO memory hooks into Unicorn `mmio_map` regions
  (not measured to matter: 40 extra narrow hooks cost nothing measurable), or an opt-in skip of the
  SHARC frame builder (`0x400db28e` and helpers, about two thirds of the guest work; it would change
  what the DSP would receive, which nothing reads in the emulator, but it is entangled with the
  sequencer's per-track values, so it needs care).
- MIDI is DIN only; USB MIDI (bit 1 of the port mask) is not modelled. The UART is ideal: no
  31,250-baud back-pressure on what the firmware queues (the log computes wire times instead).
- The arp-on-MIDI-track and >4-voice tests (T2.0, T2.6) can now be prepared in the emulator: NOTE EDIT
  on a MIDI trig, then read the chord off `--midi-log`. Not done here.
- LEDs: the 10-byte bitmap blocks to the panel MCU (heads 0x10-0x16) are not decoded; FUNC's own LED
  never lit in these runs; after a MIDI stop on DIN in, PLAY stayed green next to STOP.
- Nobody has watched the window with LEDs or played a synth from the virtual port yet; the window was
  checked withdrawn, the ports by a second rtmidi client in the same process.
