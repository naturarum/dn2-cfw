## Answer

- **Digitone II OS 1.12 is a device in elekloader** (`vendor/elekloader`, local branch
  `dn2-1.12`, uncommitted): profile `elekloader/devices/digitone_mk2.py` (key `digitone-mk2`,
  name `Digitone II`), registered in `devices/__init__.py`. From the stock file's own main OS
  stream the writer gives the stock file byte for byte, seal included, and the stock file
  verifies. [verified]
- **Both stages are checked.** `syx.verify` now runs the in-place depack at every stage a
  profile names (`stage`, then `more_stages`) and refuses a gap <= 0 at any of them. For the
  Digitone II: `0x40400000` (bootstrap) and `0x40200000` (section 4, the stricter one). Stock:
  2,128,334 and 31,182. [verified]
- **The 2 MiB receive buffer is enforced.** Neither `flash_limit` (the container's end in flash,
  `0x380000` here) nor `blob_max` (a cap on a format-1 blob, checked in `elemod`) covers it, so
  there is a new `receive_max`: the decoded stream, in whole 101-byte chunks as the OS writes
  them from `0x4038bee0`, must fit `0x200000`. That is a little stricter than "container <=
  0x200000" (it counts the 8-byte preamble and the last chunk's padding). [verified]
- **Step 4, elekloader's own packer:** a no-mod build packed with `codec/aplib.py` keeps a
  positive gap at `0x40200000` (+292,128), so the in-place margin is not its problem. Its size
  is: 1,392,294 bytes against Elektron's 1,131,348, so the container (2,146,960 bytes) overruns
  the receive buffer, and `syx.verify` now refuses it. So elekloader needs a denser packer that
  keeps the margin, and `codec/dense.py` (left by the interrupted run) is that: 1,155,260 bytes,
  gap +55,094, 187,141 bytes spare in the buffer. It is kept, reviewed against the unit's
  depacker, and chosen per device (`packer='dense'`); every other device still packs with
  aplib, byte for byte as before. [verified]
- **The unit's own code accepts elekloader's builds** (digikit's `tools/acceptoracle.py` under
  Unicorn): the no-mod build boots through both loaders to the stock image and passes the
  bootstrap's verify-and-commit; a build sitting exactly on the floor (gap 1 at `0x40200000`)
  depacks right through section 4's loader too. [verified]
- **New limit to know (T1.9 and every mod):** with both limits, a Digitone II build's image can
  grow by only about 164 KB of data that does not pack (168,000 random bytes fit, 168,320 do
  not), or about 236 KB of zeros. [verified] So a core's `.bss` has to be zeroed at run
  time, not stored in the image. [inferred]

## Step 4: elekloader's packer on 1.12

Stored section 3 (8-byte header included), each the stock image unless said, measured by
`scripts/t1.6_builds.py` (`out/T1.6/builds.json`) and `syx.inplace_depack`. [verified]

| stream | stored bytes | container | gap at `0x40400000` | gap at `0x40200000` | buffer (`0x200000`) | `verify` |
|---|---|---|---|---|---|---|
| Elektron's (stock) | 1,131,348 | 1,886,016 | 2,128,334 | 31,182 | 211,078 spare | passes |
| elekloader `codec/aplib.py` | 1,392,294 | 2,146,960 | 2,389,280 | 292,128 | 49,906 over | refused: receive buffer |
| elekloader `codec/dense.py` (`packer='dense'`), `nomod-DN01` | 1,155,260 | 1,909,920 | 2,152,246 | 55,094 | 187,141 spare | passes |
| dense, stock + 120 KB zeros, with the floor, `zeros120k-DN02` | 1,223,048 | 1,977,712 | 2,097,153 | **1** | 119,370 spare | passes |
| dense, the same image without the floor, `zeros120k-nofloor` | 1,155,362 | 1,910,032 | 2,029,467 | **-67,685** | 187,040 spare | refused: `0x40200000` |
| elektron-firmware-tool `-l 3` (T1.2, for scale) | 1,060,848 | 1,815,504 | 2,057,834 | -39,318 | | refused: `0x40200000` |

- So yes: elekloader's own packer keeps a positive margin at `0x40200000` (+292,128), but its
  file is too big for the unit's in-OS upgrade. The Digitakt II's builds have the same
  looseness (+206 KB at `0x40200000`, T1.11) and fit there only because that device's limit
  checked by elekloader is the flash (3 MB). Whether the Digitakt II's OS has the same 2 MiB
  receive buffer was not checked.
- What elekloader needed is a packer that is dense and keeps the margin, chosen per device.
  `codec/dense.py` does both: it codes matches from two bytes up to 1 MiB back, with the
  decoder's last-offset code, chosen by bit cost with one step of lazy evaluation; and with a
  floor (`base` = lowest stage - load address) it writes literals where a match would bring the
  writer to the next unread stream byte. It predicts each match's gap and checks it against the
  stream as written, raising rather than returning a stream that would fail. About 4 s for the
  3.2 MB image here.
- **The floor is exact on the unit's code.** `zeros120k-DN02` sits on it (gap 1 at
  `0x40200000`), and section 4's loader, run under Unicorn, gives the intended image with 0 bytes
  wrong and enters the main OS. The unfloored control is below. [verified]
- The growth cap above (164 KB of data that does not pack, 236 KB of zeros) comes from these
  two limits together: section 4's stage needs the stream to stay longer than the image minus
  `0x1ffc00`, and the buffer caps the stream. [verified] by bisection over appended random bytes
  and zeros.

## Open problems and recommendations

- **Digitakt II profile (not changed here):** add `more_stages=((0x40200000, "section 4's loader
  (0x8000357c)"),)` so `verify` checks the stage T1.11 found. elekloader's DT2 builds pass it
  today (+206 KB), so nothing existing would be refused. Also check whether the DT2 OS receives
  upgrades into the same 2 MiB buffer (its `flash_limit` allows 3 MB); its builds are about
  1.72 MB, under it either way. [inferred]
- **T1.9 (the core):** the image can grow only ~164-236 KB on this device (above). A DN2 core
  needs its `.boot` before the clear at `0x40000542` (the Digitakt II's boot site `0x40000538`
  holds the same `jsr 0x400019b0` here), its run image copied to `areas['ddr']`, and `.bss`
  zeroed at run time. Then set `ddr`, `sram_code` and `fast_table` in the profile. The SRAM tail
  is only 1,664 bytes.
- **The version a unit reports** was not looked for on 1.12 (T1.8 will show it on the unit).
- **The web page** (`web/app.js` `DOWNLOADS`) has no Digitone II entry; the page copes with a
  missing one (`dl` is undefined), but it shows no download link. Not changed: the web build was
  out of scope.
- **Not run:** `test_link`, `test_patcher`, `test_digitone`, `test_octatrack`, `test_sdk` and most
  of `test_octabam` skipped (no Digitakt mk1, Digitone mk1 or Octatrack stock files here);
  `test_gui` and `node tests/test_web.mjs` were not run. The Digitone II changes do not touch
  those devices' code paths (new fields default to the old behaviour), but they were not run.
- **T1.7 (brick checker)** still has to add what a profile cannot: no new references to the NOR
  primitives, no new DSPI PUSHR command immediates, no `0xB0B0DADA` store, and an emulated boot.
  `protected` only keeps the existing bytes.
