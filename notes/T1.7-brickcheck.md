## The tool

`tools/brickcheck/` (new; README there):

```sh
tools/brickcheck/brickcheck <candidate.syx> [--stock Digitone_II_OS1_12.syx] \
                            [--intended-main <main_os.bin>] [--out DIR] [--no-emu-boot] [--no-device]
```

It prints each check as PASS, FAIL or SKIP with its evidence, then the verdict, and writes
`out/brickcheck/<candidate name>/report.md` and `report.json` (screen PNG and emulator logs in
`emu/` beside them). Verdict and exit status: **accept** (0) only when all ten checks PASS;
**refuse** (1) when any FAILs; **incomplete** (3) when none FAILs but any is SKIP; 2 for a usage
error. A check that crashes counts as FAIL. A check is PASS only if it has at least one PASS
line and no FAIL or SKIP line, so a check that ran nothing is SKIP, never PASS. [verified: the
code, and the stock run with `--no-emu-boot` came out "incomplete", exit 3]

It runs under digikit's environment (`vendor/digikit/.venv/bin/python`, patched Unicorn) and
imports digikit's `tools/acceptoracle.py` (T1.2) and `tools/recovery_harness.py` (T1.5); no
digikit file was changed. The emulated boot wraps `emu.harness.Machine.__init__` inside its own
child processes to add observe-only hooks.

| file | what |
|---|---|
| `brickcheck` | bash wrapper: digikit's venv Python, `brickcheck.py` |
| `brickcheck.py` | the ten checks, the verdict, the two reports |
| `bc_syx.py` | own .syx reader: messages, 8-in-7, per-message checksum, counters, framing count, ELE3 table, content checksum, seal key and HMAC. Imports nothing from digikit or elekloader |
| `bc_device.py` | the unit's code under Unicorn via acceptoracle (verify-and-commit, OS validator, both loaders, in-place gap) and the T1.5 harness |
| `bc_static.py` | protected ranges, changed ranges, reference scans, function names |
| `bc_emuboot.py` | T1.1's emulated boot (`emu.extract`, cold boot to 400M, `emucheck` to 1000M) plus a flash-command watch |
| `selftest.py` | builds the test files and checks every verdict |

## Decisions, and where each rule comes from

- **Stock pin.** The stock file must hash to `7e5b8a73...ceb35`; otherwise check 1 FAILs and
  checks 2-10 are SKIP ("cannot be trusted"), so the verdict is refuse. Its bootstrap and main
  OS are also checked against `038aa5d1...` and `a098f620...` before they are used.
- **Section 5 must be stock too.** The task names sections 2, 4 and 8; ROADMAP's T1.7 list says
  only sections 3 and 7 may differ. Section 5 is the 15-byte build stamp ("260930 10:59:50")
  that TEST MODE reads (T1.5). Nobody has looked at what a different stamp does, so it is held
  to stock. A changed section 7 is allowed but must still depack.
- **ELE3 header.** Must equal stock's apart from the version field at 0x14..0x18 (T1.8 wants a
  rebuild "with its own version name"; elekloader's verify uses the same rule).
- **Container size.** Both the container and the stream as the OS receives it (data messages x
  101 bytes, T1.6's `receive_max`) must fit `0x200000`; the second is a few dozen bytes stricter.
- **Margins.** At least **1** byte at both `0x40400000` and `0x40200000`, measured by
  acceptoracle's `inplace_gap` (the measure elekloader uses). HANDOFF says "non-negative";
  elekloader refuses `gap <= 0`, and T1.6 ran gap 1 on the unit's section-4 loader, so 1 is the
  lowest value shown to work. The margin rule and the device run must both pass.
- **Panel blob range.** The task says "from 0x402F7D40 to the end", T1.6 measured the blob the
  updater sends as `0x402f7d40-0x402fb494`. Both are checked; the wider one (to the stock end
  `0x4030C980`) decides. Bytes appended past the stock end are not in it (they show in the diff).
- **What counts as "new" in check 7.** Every 32-bit word at any byte offset, and every
  pc-relative `jsr/jmp/pea/lea/bra/bsr/bcc` form at even offsets, whose bytes overlap a range
  that differs from stock. So anything stock already has is never reported, and anything a mod
  writes is. Targets: any address inside the NOR driver `0x40134A28-0x4013621C` (all 28 entries
  from T1.4 and T1.4-verify-2 named, reads included, as the task asks for "the DSPI0 NOR driver
  functions"), and the flash writers of T1.4's clusters A-D (`FUN_40139104` and its range,
  `FUN_40109144`, `FUN_401094e8`, `FUN_400cd5f2`, `FUN_400cebd2`, `FUN_400cccc6`, `FUN_400ccda2`,
  `FUN_400cce7e`, `FUN_400ccf5a`, `FUN_400cd036`, `FUN_400cd10a`, `FUN_400f2022`; each checked as a
  function entry in `functions.tsv`). PUSHR words (PCS field `0x02`, CTAS 0, data byte in bits
  7..0; the driver's `0x8402_00XX`, `0x0802_00XX`, `0x8002_00XX` and their CONT/EOQ/CTCNT
  siblings) count in two ways. (a) As the operand of a long-immediate instruction (`move.l
  #imm,<ea>`, or `ori/andi/subi/addi/eori/cmpi.l #imm,Dn`), any form: on stock this finds
  exactly the 100 words of T1.4-verify-2's `cmds.txt`, no more and no fewer [verified]. (b) As a
  raw word anywhere (data tables too), only the forms whose top byte cannot start a ColdFire
  instruction (`0x80/0x84/0x88/0x8C` would be `or.b`, `0x04` `subi.b`; ColdFire has neither) and
  only with a non-zero command byte. The first version took every form as a raw word; on stock
  that matched 716 words, because `0x0802_00XX` and `0x0C02_00XX` are also `btst #n,d2` and
  `cmpi.b #n,d2`, and stock's data holds 414 `0x80020000` words. A mod's compiled code would have
  tripped it. Rule (b) matches 10 words in the whole stock image [verified].
  `0x0002_00XX` is never counted: it is the constant `0x20000` plus a byte. Also any word in the DSPI0 register block `0xFC05C000-0xFC05C0FF` (T1.4-verify-2: "no
  0xFC05C0xx words outside the sites in dspi0.txt"), and any `0xB0B0DADA`. New `0x48000000` words
  are listed but not refused (it is also the stack top).
- **Check 8's extra watch.** ROADMAP's list has "nothing writes to the bootstrap's flash during
  emulated sessions (T1.4)". So both emulator phases carry hooks on every NOR write/erase/protect
  entry and on the in-OS writer, and a write hook on DSPI0 PUSHR (`0xFC05C034`) that splits frames
  into transactions on the CONT bit and records each command byte. Any write, erase, protect or
  configuration command (`0x01 0x02 0x06 0x12 0x17 0x20 0x21 0x2F 0x42 0x44 0x52 0x60 0xA6 0xB7
  0xC7 0xD8 0xDC 0xE1 0xE3 0xE4`) or any call to those entries is a FAIL.
- **Check 9's pass rule.** From T1.5's own statement for the brick checker: a FUNC run must stop
  in the menu key loop with the menu drawn, and no run may reach the flash erase/program
  landmarks. Added: the menu screen must be byte-identical to the stock container's run (the
  reduced recovery menu of a bumped section 2 has 1,129 lit pixels, not 1,486); a no-key run must
  reach the loader without opening the menu (that is how a section-2 version bump shows up even
  with no key); the silent-panel run must end where stock's does; OS UPGRADE must reach the MIDI
  wait with no flash read.

## What a PASS does not show, and open problems

- **The validating code is stock 1.12's.** That is what the user's unit runs today. Once a mod
  is installed, a later in-OS upgrade is validated by the mod's own validator `0x400dbdb0`
  (check 6 does not protect it), while the STARTUP-menu path always uses the stock bootstrap.
  [inferred] Worth adding the validator `0x400dbdb0-0x400dbde4` to the protected list once a mod
  exists that does not need to touch it.
- **Check 7 is a byte scan, not a disassembly.** It does not see an address built at run time
  (from pieces, from a pointer the stock OS already stores, or from a RAM table), an EOQ-only
  PUSHR word stored as data (`0x0802_00XX` is also `btst #n,d2`), or a reference through an
  indexed or 8-bit-displacement form other than `bra/bsr/bcc.b`. The backstops: check 6 keeps
  the driver and the writer byte-identical, any new DSPI0 register word is refused, and check 8's
  watch sees any flash command on the code the emulated boot actually runs. [inferred]
- **Check 7 can refuse a harmless mod.** A word in new bytes that happens to fall inside the
  driver (a 6.1 KB window) or equal a writer entry is refused. 300,000 random bytes (case
  n7-big) produced one such word, at `0x40317acc` = `0x40135ed1`; the expected count is about 0.4
  [verified]. Packed or random data in a mod has this chance, about 1.4 in a million per byte.
  There is no override: such a refusal needs a manual look, and then either moving the data or a
  reviewed exception mechanism (not built).
- **A mod that moves code** shifts every byte after the move, so check 7 treats all of it as new
  and refuses anything there that looks like a flash reference. That is intended.
- **Check 8 boots digikit's Python depack** of the candidate (`emu.extract` uses `dt2/elz`), not
  the unit's. Check 5 is what ties the two together. The emulator replaces the flash read with
  HLE, models no DSP audio, USB or panel MCU, and runs no key presses. The flash watch therefore
  covers the cold boot and 600M instructions at the main screen, not an in-OS upgrade, the
  factory console, or any path behind a key or a USB message. T1.4-verify-2's dynamic rule for an
  emulated in-OS upgrade (every erase/program wire address in `[0x80000, 0x380000)`, no
  `0xE1/0xE3/0xE4`) is not run: digikit cannot drive an upgrade session yet. [inferred]
- **Check 9 runs T1.5's harness**, with its stubs (clock, DDR, interrupt controller, panel wire
  protocol). T1.5's verifier found one way flash content could stop the menu: a crafted section
  2 with a bumped version that never ends the depacker. Check 2 (section 2 byte-identical, its
  entry unchanged) excludes it; case n2-sec2ver shows checks 2 and 9 both catch the version bump.
- **Section 7 (DSP)** may differ; the checker only requires that it depacks (Python codec). It
  does not check the DSP program. The emulated boot loads it but does not run the SHARC.
- **Margin rule.** `>= 1` byte, not `>= 0`: gap 0 has never been run on the unit's code. The
  model is acceptoracle's `inplace_gap` (elekloader's measure); the device run at `0x40200000`
  is the real test and must also pass.
- **Not included:** elekloader's own `syx.verify`. It checks layout rules that are elekloader's
  writer's (16-aligned sections, container length) and would refuse files from
  elektron-firmware-tool that the unit accepts. Every one of its safety checks has an equivalent
  here.
- **Time:** a full run is about 14 minutes. Runs can go in parallel (six at once here); each uses
  its own `out/brickcheck/<name>/` and its own emulator sections and snapshots, never digikit's
  `out/sections` or `sections/`.
