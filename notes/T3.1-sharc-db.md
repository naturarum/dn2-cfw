# T3.1b: digikit's SHARC database for Digitone II 1.12

Date: 2026-10-05. Input: section 7 of OS 1.12 (`vendor/digikit/out/sections/dn2-1.12/section_7_BLOB.bin`,
identical to `ele3_out/04_type7.unpacked.bin`, 836,956 bytes, sha256
`336e340aa0cdcd34e314cfa44849f709a3134f6bd4cd57dfc7e15702c83115e2`). digikit at commit `21b38b9`
(branch `dn2-1.12`, nothing of mine in its tree), sharcdb `DB_VERSION` 11.

Marks: **[verified]** = checked here against the bytes, the database or by running the tool;
**[inferred]** = reasoned from structure. In section 4, `(dk V)`, `(dk D)`, `(dk O)` and `(dk C)` are digikit's
own marks (verified by two of its reviewers, documented once, open, corrects an earlier claim). They are
digikit's claims, not re-checked here unless a line says "checked on 1.12".

Addresses: SW = short-word (VISA) program address. DM addresses are digikit's "bare" convention: loader
byte address = bare + `0x28000000` (L1). L2 code: byte `0x20000000 + 2*(SW - 0xb80000)`.

## Summary

- **The 1.12 DSP program is the 1.11 one.** Its sha256 is the one digikit records as DN2 1.11 in
  `tools/sharcdb.py` (`KNOWN_CODE_BLOCKS`), `tests/test_sharcdb.py`, `tools/sharc-discovery/dn2-1.11.json`
  and `docs/findings/11`. So the build needed no registration and no code change, and every DN2 1.11 SHARC
  fact in digikit applies to 1.12 unchanged. **[verified]** (hash equality; there is no 1.11 image here to
  compare byte by byte.)
- `uv run python tools/sharcdb.py build out/sections/dn2-1.12/section_7_BLOB.bin` builds
  `out/sharcdb/dn2-1.12.sqlite` in 17 s: 1,157 functions, 8,611 edges, 1,901 roots, 59,454 reach rows,
  362 loops. digikit's own DN2 1.11 acceptance facts hold on it (`cond_jump 0x1c99a8 -> 0x1c9b73`,
  cond 8; stage 6 at `0xb806f5` in `func_hash`). **[verified]**
- **Roots.** Loader entry `0x1c12e2` -> C runtime `FUN_1c1390` -> `jump 0x1ca76b` (main, **[inferred]**).
  Three FreeRTOS tasks: **"Audio Task" at `0x1c9fe7`** (created at `0x1ca013`, stack 1000), "IDLE" at
  `0xb88aa6`, "Tmr Svc" at `0xb89885`. digikit's `rtos_task` detector finds only the Audio Task. 25
  populated interrupt-vector slots go to 6 distinct targets. **[verified]**
- **The Audio Task** loops: call `0xb891fa`; if it returns 1, call the block handler `0x1c9d6b`, which
  dispatches on a command word through the 4-entry table at DM `0x268a68` = {`0x1c9dc2`, `0x1c9e76`,
  `0x1c9eda`, `0x1c9f0f`}. This is the same shape as DT2 1.16's task (`0x1c7749`, table `0x25f7b0`), and
  command 3 (`0x1c9f0f`) is the one that calls the 16-track render function `0x1c2712`. **[verified]** for
  the bytes and table; the command meanings are **[inferred]** from DT2.
- **Call graph and reach.** 1,167 distinct caller-callee pairs, maximum call depth 7, no recursion. The
  structural roots (loader entry, interrupt vectors, the three tasks) reach 480 functions, 60.6% of the
  main program's instructions. The Audio Task alone reaches 154 functions (32.9%). Adding every pointer-like
  root reaches 91.4%. **[verified]**
- **Decoder cross-check against selache (seldump):** across 52,300 shared instruction starts in the L1/L2
  main program and the init program, widths agree at 99.1%. Direct branch targets agree at 5,011 of 5,013
  once selache's printing conventions are allowed for, and immediates at 4,146 of 4,147 (the one miss is a
  register name). Where they differ, dataflow sides with digikit in every checkable case except one: a
  **digikit bug in Type 9a PC-relative jumps** (the 6-bit offset is not sign-extended; 2 wrong edges in the
  init program). **[verified]**
- **Database gaps found** (all **[verified]**, details in 2.6): COMP/COMPU/FCOMP recorded as register
  writes at 948 sites (digikit's own tracer says they write status only); IVT dispatch-table addresses
  hardcoded to DT2's; two of three task entries merged into the previous function; block 57 (data)
  decoded as code; the 20-byte entry stub at `0x1c12e2` and the first instructions of block 81 not
  decoded.
- **Effects.** digikit has **not** located chorus, delay, reverb or the master compressor by name on
  either device. On DT2 1.16 it has a verified master stage (`0x1c207b`) with a "dynamics" call
  (`0xb82d41 -> 0xb82cba`, name only documented), a verified per-slot stage table with a saturator,
  sample-and-hold, low-pass and an 8192-word feedback comb or delay (`0x1cbf07`, name documented). On DN2
  it has the relocated copies of those stages and the render-dispatch skeleton, no FM voice map, and no
  master stage. Section 4 lists it all.
- **Frame.** On DT2 1.16 the ColdFire-to-DSP frame is mapped on both ends (SHARC DM `0x2558dc`, per-track
  page `0x2559b6 + t*0x60`). On DN2 only the ColdFire side is known. On 1.12 the frame-send call is still at
  `0x40025e9e` with the 1.11 buffers and lengths (`0xa80`/`0xabc`), but the DSPI2 driver moved from
  `0x400cf7be` to `0x400cf922`. **[verified]**

### 2.2 Roots

| kind | count | note |
|---|---:|---|
| `loader_entry` | 1 | `0x1c12e2`, last of 2 BFLAG_FIRST entries (the first, `0x120230`, is the init program) |
| `interrupt_vector` | 25 | 6 distinct targets, below |
| `rtos_task` | 1 | `0x1c9fe7`, helper `0xb88839`, call site `0x1ca013` |
| `code_pointer_array` | 25 | 3 overlapping tables at `0x8052db90` (14 entries), `0x8052dba4` (9), `0x8052dbc0` (2), all into `0x1c90b2`-`0x1c98b9`, inside `FUN_1c8ef1` |
| `dataref_code_pointer` | 1,752 | any literal or table value that lands inside a function |
| `no_static_entry` | 97 | functions with no incoming edge, 38 clusters |

**Boot entry.** `0x1c12e2` (BTB disable, `r0=dm(0x31400)`, `bset`, store, then NOPs, per selache) is in
block 79, which sharcdb classes as data, so it has no function. Reach falls back to the next function,
`FUN_1c1390` (C runtime startup), which jumps to `0x1ca76b` at `0x1c1428`. `0x1ca76b` calls `0x1ca000`,
which creates the Audio Task, and it has the most transitive callees in the image (129), so it is main
**[inferred]**. Loader-entry reach contains `0x1c1390` and `0x1ca76b` (depth 0), `0x1ca000` (1) and the
create helper `0xb88839` (2). It does not contain the scheduler-start path that creates IDLE (`0xb88778`)
or any task body.

**RTOS tasks** (found with a wider idiom than digikit's: R8 a literal pointer to a NUL-terminated ASCII
string, R4 a literal inside a function, any R12):

| name | entry | name pointer (bare / loader) | helper | call site | notes |
|---|---|---|---|---|---|
| Audio Task | `0x1c9fe7` (inside `FUN_1c9e76`) | `0x268a78` / `0x28268a78` | `0xb88839` | `0x1ca013` in `FUN_1ca000` | R12 = `0x3e8` (1000); stack pushes `0x268a84`, 5, 0 |
| IDLE | `0xb88aa6` (own function) | `0x2d0760` / `0x282d0760` | `0xb886f0` | `0xb887e1` in `FUN_b88778` | R12 from `DM(I6-2)`; immediate push 0 (priority, **[inferred]**) |
| Tmr Svc | `0xb89885` (inside `FUN_b89780`) | `0x2d08a8` / `0x282d08a8` | `0xb886f0` | `0xb89956` in `FUN_b89916` | R12 from `DM(I6-2)`; immediate push 5 (priority, **[inferred]**) |

- The bytes at loader `0x28268a78` are `"Audio Task\0"`. This is the string `docs/SHARC-ADDRESS-MAP.md` lists
  at exec address `0x13453c` (`2 * 0x13453c = 0x268a78`). **[verified]**
- Reading the arguments against FreeRTOS: `0xb88839` is `xTaskCreate(fn, "Audio Task", 1000, NULL, 5,
  &handle)` with the handle at `0x268a84`, and `0xb886f0` is `xTaskCreateStatic` (four stack arguments:
  task buffer, stack buffer, priority, parameter) used by the scheduler for IDLE (priority 0) and by the
  timer service (priority 5). **[inferred]** from the argument shapes and the FreeRTOS source.
- `0xb88839` has a second caller, `0xb8a6d9` in `FUN_b8a6ad`. That function has no static caller and
  takes the task function, name and stack size from a record passed in R8 (`R4 = DM(I4,M5)`, `R8 =
  DM(I4+5)`, R12 = `(DM(I4+3) >> 2) & 0xffff`). It is a generic create wrapper, so more tasks may exist
  that cannot be resolved statically. **[verified]** for the code; "more tasks" is **[inferred]**.

**Audio Task body** (both decoders agree on every instruction here):

```
0x1c9fe7  cjump 0xb891fa (db)          ; wait (DT2 calls 0xb8615d here; notify-take per digikit, dk D)
0x1c9fee  r2 = btgl r0 by 0            ; SZ set when the result is 1
0x1c9ff1  if not sz jump 0x1c9ffb
0x1c9ff4  cjump 0x1c9d6b (db)          ; block handler
0x1c9ffb  jump 0x1c9fe7
```

Block handler `0x1c9d6b`: saves registers, reads `EMUCLK`/`EMUCLK2` (the cycle counter, a lead for T4.1)
in the delay slots at `0x1c9d87`/`0x1c9d89`, calls `0x1ca020`, then loads the command into M4, loads
`I12 = DM(M4, I4=0x268a68)` at `0x1c9db2` and jumps `(M13, I12)` at `0x1c9dbf`. The table at
`0x268a68` (loader block 29) holds `0x1c9dc2`, `0x1c9e76`, `0x1c9eda`, `0x1c9f0f`. The flag word is
`DM(0x268a38)`, read by every case. **[verified]** Compare DT2 1.16: handler `0x1c74cd`, table `0x25f7b0` =
{`0x1c7524`, `0x1c75d8`, `0x1c763c`, `0x1c7671`}, command 3 renders (dk V). On DN2, `0x1c9e76` is the
case digikit matched to DT2's `FUN_1c75d8` (command 1) by relocation-tolerant hash (dk O for the
semantics). `0x1c9fbc`, the call into the 16-track render `0x1c2712`, lies in the command-3 range
`0x1c9f0f`-`0x1c9fde`. **[verified]** for the addresses; "command 3 renders" is **[inferred]** from DT2.

### 2.5 Leads for T3.3 and T3.4 found on the way

- `0x1ca812` in main loads `R4 = 0xabc` (2748, the frame length) and calls `0x1ca46a`. DT2 1.16 does the
  same at `0x1c80a0` before its SPI2 setup (dk V). `0x1c1442` in `FUN_1c1390` loads `R0 = 0xabc`, like DT2's
  `0x1c1496` (dk V). **[verified]** for the instructions.
- In `FUN_1c2712` (DN2's 16-track render), the loop `0x1c2d10`-`0x1c2df3` advances six pointers by `0x92`
  bytes per pass (I0, I4, I8, I11, I14, I15) and I10 by 2. The prologue sets `I14 = 0x25c5e0`,
  `I8 = 0x25c5e2`, `M8 = 0x25c5e4` (`0x1c2cf5`-`0x1c2cfb`). `0x92` is the size of the DN2 frame's per-track
  slot on the ColdFire side (dk D), so this loop probably walks the received frame. Absolute loads in
  `0x25c4ae`-`0x25cee4` would then be other frame fields. **[verified]** for the instructions, the frame
  reading is **[inferred]**.
- DT2's master stage multiplies by 3.1623 (+10 dB). No literal in the DN2 database decodes to a float in
  3.160-3.163, so the master stage has to be found another way. **[verified]** negative.

### 2.6 Gaps in digikit's database (upstream material, nothing changed)

1. **COMP writes no register, but `regdef` says it does.** 948 of 950 aligned `comp`, `compu` and
   `fcomp` instructions get a `regdef` row for their nominal destination (`R0 = comp(R0, R2)`,
   `F0 = fcomp(F7, F15)` at `0xb8074b`). digikit's tracer (`tools/sharc_trace.py`, citing PRM Table 18-5)
   says comp/compu "update status only". `img.last_def()` can therefore name a compare as the last writer
   of R0/F0. **[verified]** that the rows exist and that the tracer disagrees.
2. **Type 9a PC-relative offset not sign-extended.** The 6-bit `reladdr` (bit 32 plus bits 31..27) goes
   to `sharcflow.pcrel_target`, which sign-extends at bit 23, so -7 becomes +57. There are 5 sites with a
   negative offset in this image: 2 in the init program, where digikit's targets (`0x1214f2`,
   `0x121615`) are not instruction starts and selache's (`0x1214b2`, `0x1215d5`) are, and 3 in block 57
   (data). The main program has none. **[verified]**
3. **IVT dispatch tables hardcoded to DT2.** `IVT_DISPATCH_TABLES` holds `0x240ad8`/`0x240948`; DN2's
   dispatcher uses `0x240aa0`/`0x240910`. Both pairs are zero at boot here, so no root is lost today.
   **[verified]**
4. **`rtos_task` requires a literal R12.** It misses IDLE and Tmr Svc, whose stack size is loaded from
   the frame (`R12 = DM(I6-2)`). **[verified]**
5. **Task entries merged into the previous function.** `0x1c9fe7` (Audio Task) sits inside `FUN_1c9e76`
   (`0x1c9e76`-`0x1ca000`), and `0xb89885` (Tmr Svc) inside `FUN_b89780`. selache shows the code before
   `0x1c9fe7` ending with a delayed tail jump at `0x1c9fde`. The wait call target `0xb891fa` is also inside
   `FUN_b891eb`. Entries that are reached only through a pointer do not start a function. **[verified]**
6. **Block 57 is data** (T3.1a showed it; digikit's own address map calls the region data), yet
   `KNOWN_CODE_BLOCKS` includes it: 11,199 decoded "instructions", no functions, a few spurious edges.
   **[verified]**
7. **Startup code not decoded.** Block 79 (the 20-byte entry stub at `0x1c12e2`) is classed as data, and
   the first rows of block 81 (`0x1c130f r0=0`, `0x1c1311 jump 0x1c0000`, `0x1c1314 bit set mode1`) are
   decoded but marked unaligned by the sweep-depth filter. The startup jump to `0x1c0000` has no edge.
   **[verified]**
8. Rendering only: the `raw` column drops leading zeros (`83f282001fb`); 17b immediates print unsigned
   (`R2 = 0xfffe` while `literals.value` is -2); the 9a indirect jump prints `PM(I4, M5)` where digikit's
   own correction (finding 05) says DAG2, `(M13, I12)`; `leftz` prints a second operand, and `reguse`
   records it (spurious R0 use at `0x1cdb85`). **[verified]**

## 3. Decoder cross-check: digikit against selache

Method: `scripts/sharc_decoder_crosscheck.py` compares sharcdb's aligned `insn` rows with selache
`seldump` listings of the same final memory image (made in T3.1a by `scripts/sharc_visa_disasm.py`,
`out/T3.1/disasm/`). It checks instruction starts, widths and raw bytes over whole regions, then direct
branch targets and immediate loads at shared starts automatically. It also writes side-by-side windows
for reading by hand. Output: `out/T3.1b/crosscheck.json`, `out/T3.1b/side_by_side.txt`. T3.1a compared
selache with a width-only decoder built from digikit's table; this compares digikit's actual decoder
output, including operands. **[verified]**

| region | digikit starts | selache starts | shared | widths equal | branches equal / compared | immediates equal / compared |
|---|---:|---:|---:|---:|---:|---:|
| init `0x1201f8`- | 2,272 | 2,279 | 2,272 (100%) | 2,272 | 229 / 231 | 152 / 152 |
| L1b3 low `0x1c0000`- | 1,911 | 2,026 | 1,827 (95.6%) | 1,812 | 140 / 140 | 161 / 162 |
| main `0x1c12e2`- | 22,411 | 22,446 | 21,350 (95.3%) | 21,114 (98.9%) | 1,671 / 1,671 | 2,008 / 2,008 |
| L2 `0xb80000`- | 27,579 | 27,549 | 26,851 (97.4%) | 26,657 (99.3%) | 2,971 / 2,971 | 1,825 / 1,825 |
| block 57 (data) | 11,199 | 14,847 | 6,179 (55.2%) | 5,285 | 6 / 8 | 11 / 11 |

- Where widths agree, the raw bytes agree too (same image, same parcel order). **[verified]**
- "Branches equal" counts three selache printing conventions as equal: 40 cross-region calls printed as
  the unwrapped sum (`call (pc,0x63ff7f)` at `0xb8073b` = `0x1c06ba` after the 24-bit wrap), one
  PC-relative `cjump` printed as an absolute (`0x1c0eef cjump 0x9caa07` = `0x1c0eef + 0x9caa07` =
  `0xb8b8f6`), and DO-loop ends printed with bit 23 set (`do (pc,0x800003)`). The 2 real misses are the
  digikit Type 9a sign bug (2.6 #2). **[verified]**
- Width disagreements in the main program are mostly selache reading 48-bit Type 4a (62), 3a (57),
  16a (42) and 7a (37) as 32-bit, and 32-bit Type 3b as 48-bit (20). T3.1a's branch-target vote and digikit's
  finding 05 already put these on selache's side. **[verified]** (counts)
- The one immediate mismatch: `0x1c0ecf` `0f7300e0b003`, ureg `0x73`. digikit names it MMASK, selache
  ASTATX. Both tools number the Type 18 system registers MODE1 = 2, MMASK = 3, ASTATx = 6 (selache
  `disasm.rs`, digikit `UREG_CODES` `0x72`/`0x73`/`0x76`), so `0x73` is MMASK. A startup store of
  `0xe0b003` right after three MODE1 bit operations also fits MMASK better than ASTATX. **[verified]** for
  the tables, **[inferred]** for the verdict.
- **48-bit Type 9a (indirect jump/call) field layout.** The two decoders differ. digikit: pmi = bit 32 and
  bits 31..30, pmm = bits 29..27, delay bit 26. selache's 48-bit decoder: delay = bit 32, pmm = bits 29..27,
  pmi = bits 26..24. selache's own 32-bit Type 9 decoder uses digikit's layout (pmi low bits in p2[15:14],
  pmm in p2[13:11], DB in p2[10]), and its encoder comment disagrees with its encoder code. Of 56 absolute
  Type 9a sites inside functions, 49 name the same I register. At the 7 that differ, digikit's register is
  written earlier in the same function at 4 sites, both are at 1, neither at 2, and selache's alone at none.
  Example: `0x1c9dbf 083f282001fb`. digikit reads a non-delayed `JUMP (M13, I12)`, and `I12` was just
  loaded from the command table at `0x1c9db2`. selache reads `jump (m13,i8) (db)`, and I8 is not written in
  the function. **[verified]** digikit is right on these sites.
- Read by hand: about 170 rows in six windows (C runtime start `0x1c131a`, block handler `0x1c9d6b`,
  Audio Task and its creation `0x1c9fe7`, stage 6 prologue and float code `0xb806f5`, stage 3 `0x1cdb56`,
  the generic create wrapper `0xb8a6c4`). All agree in meaning except: the 9a jump above; Type 3a M register
  at `0x1c132e`/`0x1c1337`/`0x1c1340` (digikit `DM(I0, M0)`, selache `m4`; M0 = 1 was loaded at `0x1c1327`,
  and digikit's finding 05 documents this selache bug, `bits(39,38)+4`); and the rendering points in
  2.6 #8. Multifunction float rows (`f8=float r10 , r13=dm (0xe,i4)`, `fmin`/`fmax` with parallel moves),
  delayed calls with their two pushes, `(sw)` short-word loads (`0x1c9da8`, also `short-word` in
  `mem_access`) and system-register moves (`EMUCLK`, `MODE1` bit operations) all match. **[verified]**

Verdict: digikit's decoder is the more reliable of the two on this image. Use it (through sharcdb) to read
code, use selache as the assembler and as a second opinion, and treat the database's `regdef` near
compares, and Type 9a relative targets, with care until those bugs are fixed.

`04-coldfire-dsp-link.md` (skimmed: sections on the audio path, voice record, per-frame chain, stages,

### 4.0 Address map (`docs/SHARC-ADDRESS-MAP.md`, measured on DN2 1.11 = 1.12)

- Code addresses are short words: loader byte = `2 * SW + 0x28000000` for L1 (591 of 591 L1 call targets
  land in loaded code) (dk V, rests on two measurements). The `0xb8` space is L2:
  `0x20000000 + 2*(SW - 0xb80000)` (later finding 06, dk D, used by sharcdb).
- Code is about 240 KB of the 837 KB section: L2 `0x20000000-0x2001e880` and L1 `0x283825c4-0x2839bffc`,
  plus small regions. `0x2001e888-0x2008823c` is data. DDR `0x80000000-0x8052fbe0` is almost all fill
  (dk D; L1/L2 labels corrected, dk C).
- Landmark strings: "Audio Task" and the FreeRTOS `__FILE__` paths (event_groups, queue, stream_buffer,
  port, tasks, timers, heap_4). A plain word scan never finds their addresses, because code builds them
  as instruction literals. Checked on 1.12: the Audio Task string pointer is a `17a` literal
  (`R8 = 0x268a78`). **[verified]**

### 4.1 Effects and the master section

Product names (chorus, delay, reverb, master compressor) appear nowhere in digikit's docs or tools. Its
results are about function roles. **[verified]** (grep of `docs/`, handovers, `tools/`.)

Digitakt II 1.16, verified dataflow (dk V; names are dk D unless said):
- **Master stage `0x1c207b`** (303 instructions). It sums 16 tracks at `0x252df8 + t*0x100` (32 L + 32 R
  floats) into bus A `0x254878` (bit t of `0x252538` set) or bus B `0x254a78`, and calls
  `0xb82d41 -> 0xb82cba` (**"dynamics", dk D**, output `0x254978`: the best candidate for the master
  compressor). It then computes `clip((0x254978 + 0x254a78) * 3.1623, 1.0)`, runs stage 3 `0x1cb3d8` per
  channel into `0x25f180`/`0x25f200`, and applies `DM(0x2526ec)` squared as gain, ramped in 1/32 steps. The
  render then converts `0x25f180`/`0x25f200` to Q31 into ring A (DAC side, dk D).
- **Per-slot stage table `0x8055c874`** (inside `FUN_1c642a`'s out-of-line blocks): slot type 1
  `0x1cdbb2`, 2 `0x1cd286`, 3 `0x1cc79e`, 4 and 6 `0x1cbf07`, 5 `0x1ccd96`. Gated passes then run
  `0x1cb3d8` (saturator, `x <- x*(2-|x|)`, dk D), `0x1cdecb` (sample-and-hold rate reduction, dk D) and
  `0x1ccbd8` (low-pass plus DC blocker, dk D). The first block lerps 128-entry cosine and sine tables
  `0x8055c440`/`0x8055c640` (equal-power curves, dk D).
- **`0x1cbf07`** reads four taps off an 8192-word ring and writes `fclip(x + g*taps, 1.0)` back into it;
  its index steps `(idx+1) & 0x1fff`. digikit calls it "an 8192-word feedback comb or delay" (dk D). At
  an assumed 48 kHz that is about 171 ms per ring. Comb, delay or a modulated-tap chorus are all possible
  **[inferred]**.
- "There is no FFT" (dk V). Stage 4 `0x1cd286` is a 9-field-pair MAC gather (compute opcodes partly
  undecoded, dk O). Stage 5 `0x1cc79e` is a table-interpolated resampler, table `0x26bb68`.
- Per-track filter/amp/FX parameters reach `FUN_1c24e9` from the frame (4.3) and are stored as floats
  into 32 slots of `0xdc` bytes at `0x2506ec` (dk D/O for the destinations).

Digitone II 1.11 (= 1.12):
- The six stages exist in DN2, byte-identical or relocated (dk V): stage 1 `0xb81368` (L2 byte
  `0x200026d0`), 2 `0xb8265b` (`0x20004cb6`), 3 `0x1cdb56` (L1), 4 `0xb81a16` (`0x2000342c`), 5 `0xb80f2e`
  (`0x20001e5c`, its table pointer is `0x26b3a8`), 6 `0xb806f5` (`0x20000dea`). The shared reciprocal
  helper is at `0x1c06ba` in both. Checked on 1.12: `0xb806f5` is a function in the database, and its
  prologue and first float block decode identically in both decoders. **[verified]**
- `0x1c9b73` (126 instructions, reached only by `cond_jump 0x1c99a8` from inside `0x1c8ef1`) calls stages
  1, 2, 4, 5 and 6 (twice): the counterpart of DT2's `FUN_1c71ec` stage block (dk V; edge checked on 1.12
  **[verified]**). `0x1c8ef1` (1,352 instructions) calls stages 1, 2, 3 and is called from `0x1c3044`
  inside `0x1c2712`.
- **Not known on DN2:** the master stage, the dynamics block, which slot type is which effect, where
  the send effects sit. **(dk O)**

Open on both devices (dk O): which stage or slot type is chorus, delay or reverb; whether `0xb82cba` is the
compressor; the effect parameters' scaling; the real cadence and DMA path to the codec.

### 4.2 Voice engine

Digitakt II 1.16 (dk V unless marked):
- `FUN_1c2b24` (per-frame render, 16-track loop) -> `FUN_1c24e9` (per-track unpack) -> `FUN_1c642a`
  (1,458 instructions: per-slot dispatch, voices, effect stages) -> master `0x1c207b`.
- 32 voice records at `0x2412cc`, stride `0x1d8` bytes. `0x1c4ecf` (or `0x1c5576 -> 0x1c5615`) renders.
  `0x1c4f81` makes 64 samples by 6-tap polyphase interpolation (table `0x25d940`) into record
  `+4..+0x103`, and `0xb80000` decimates 2:1 to 32 outputs. Record contract: loop/start/end Q31 at words
  `0x64-0x69`, step at `0x6a-6b`, phase `0x6c-6d`, rate word `0x61`, flags at bytes `+0x17c..+0x1bc`.
- Pitch: step = `powf(2, clip((note-60)+(tune-64), +-64)/12) * rate / 96000 * 2^31` (`0x1c0d68` is the
  power function; note/tune names dk D).
- Machine selection: selector = `0x2567c0[0x255970[track]]`, stored at slot word 19 (`+0x4c`); remap
  `[0,1,2,3,4,0,5]` for types 0-6. `0x1c6ae8`/`0x1c6aeb` pick `0x1c5576` for selector 2, else `0x1c4ecf`.
  Trigger table `0x8055c840` (15 entries).
- Amplitude envelope `0x1cbb57` on 11-word records; its base is open (dk O).

Digitone II 1.11 (= 1.12):
- Same dispatch shape: `0x1c8ef1` jumps into `0x1c9b73` (`JUMP IF SZ` at `0x1c99a8`). The stage A bound is
  5, not 6 (handover, dk D). `0x1c2712` has a 16-iteration `DO ... UNTIL LCE` at `0x1c2937`, like
  `FUN_1c2b24` (dk V). `0x1c9e76` matches DT2's `FUN_1c75d8` by hash (dk O).
- The FM voice engine (operators, algorithms, the voice record) is **not mapped**: digikit's handover
  lists it as the next step ("Next 2: the DN2 voice engine"). Five ColdFire machine descriptors: 0 FM TONE,
  1 WAVETONE, 2 FM DRUM, 3 SWARMER, 4 MIDI (dk D).
- New on 1.12 from this task: the Audio Task root and its reach set (2.2, 2.4), which was digikit's own
  first step for the DN2 voice work. **[verified]**

### 4.3 The ColdFire-to-DSP parameter frame

Digitakt II 1.16:
- Transport: DSPI2 (`0xEC038000`), eDMA 28/29, 16-bit SPI frames (CTAR0 `0xFA010000`). Each exchange is
  one fixed 2,748-byte (`0xabc`) full-duplex frame; the first argument (`0x802` on DT2) is how many
  payload words the driver copies (dk V/C). The send runs in the vector-191 handler, software-forced
  after SSI0 eDMA-50 completion (vector 170); the cadence and counter reload are open (dk V/C/O).
- Layout: per-track words at `offset + 2t`; `0x94 + 2t` is the machine type, `0x73c` is a type/flag word
  (dk V); `0x02`, `0x34`, `0x54`, `0x74`, `0xb4`, `0x77c`, `0x79c`, `0x7bc` sources are known (dk D). A
  17-word header, then per track a `0x60`-byte parameter block at `0xda + t*0x60`: mirror indices 25-34
  (SRC page, the machine's own parameters) at `+0xda`, 35-48 (filter) at `+0xfa`, 49-61 (amp and FX
  sends) at `+0x116`, 64-68 (FX) at `+0x130` (dk C/V). Portamento (62-63) is skipped. Where indices
  >= 54 really live is open (dk O). LFOs and the modulation matrix run on the ColdFire in the frame ISR
  (dk D/O).
- SHARC side: the frame lands in DM at `0x2558dc`, at byte-identical offsets (11 of 11 scalar fields
  match); the parameter page is `0x2559b6 + t*0x60` (dk V). `FUN_1c24e9` reads five SRC-page words
  unconditionally, and the machine type serves only as a change detector in `FUN_1c2b24` (dk V/C).
  Destinations: 32 slots of `0xdc` at `0x2506ec` (dk D/O). The 2,748-byte return block's meaning is open.

Digitone II 1.11 (dk) and 1.12 (checked here):
- Same link: DSPI2 driver `0x400cf7be` called at `0x40025e9e` with `(0xa80, 0x80005e60, 0xabc,
  0x800053a4)`: 2,688 payload bytes in the same 2,748-byte frame (dk V). Test-mode handler `0x400d0fec`
  with `(0xa80, 0x4244098c, 0, 0)`. The boot upload `0x400cf34c` reads section 7, mallocs 1 MB and pushes
  it byte by byte over DSPI2 (dk D, from the cross-check note).
- **On 1.12** the same instruction sequence is at the same address: `pea 0x800053a4; pea 0xabc; pea
  0x80005e60; pea 0xa80; jsr` from `0x40025e8a`, with the jsr at `0x40025e9e`. Only the driver moved, to
  `0x400cf922`. **[verified]** (byte pattern in `ele3_out/02_type3.unpacked.bin`; the pattern occurs once.)
- Layout: 16 per-track slots of `0x92` bytes copied from `0x800068e4 + i*0xca`, four copies per slot;
  `FUN_400db12a` rebuilds the table from `0x80003af0` (dk D). Which bytes are which knobs, and where the
  machine type is, are not known (dk O).
- SHARC side on DN2: **not mapped by digikit.** The leads in 2.5 (`0xabc` at `0x1ca812`, the `0x92`-stride
  loop from `0x25c5e0` in `0x1c2712`) are where T3.3 can start.

### 4.4 Free memory (for T3.2/T3.8, dk V)

DN2 1.11's L2 is written up to `0x2008823c`, leaving 490,948 bytes of L2 past the loader (DT2: 939,140).
The DT2-only DDR command block at `0x82a00000` does not exist on DN2. Whether the free L2 is really unused
at run time (heap, stacks; the context-switch pointer `DM(0x2ca3e0)` is built at run time) is open.
