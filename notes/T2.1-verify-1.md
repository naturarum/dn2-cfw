# T2.1 verification 1: MIDI voices (Digitone II OS 1.12)

Independent check of `notes/T2.1-midi-voices.md` and the T2.1 report. Static only: `ele3_out/02_type3.unpacked.bin`
(file offset 0 = `0x40000400`) read with `m68k-elf-objdump -m m68k:cfv4e` (helper `out/T2.1-verify-1/dis.sh`), the
dump in `out/decomp/`, and raw-byte reads in Python. No device, no emulator.

Tags: **[verified]** = checked in the disassembly or the raw bytes. **[verified (C)]** = read in the decompiled C
only. **[inferred]** = reasoned from structure.

## Verdict

**The report holds, with small corrections.** Every main claim I re-derived matches the bytes. That includes the
storage-format conclusion, which I tried hardest to break. The 4-note limit is a UI and editing limit. The MIDI
engine and the pattern format have no 4-note cap. I found no extra cap in the sequencer, the MIDI task or the save
path. I did find four things the report missed or got slightly wrong:

1. The proposed one-byte patch has a side effect on lock clears (section 3.1).
2. Note-off bursts can wrap the same 8-bit output counter, which can leave notes stuck (section 3.2).
3. Chains written at runtime are not sorted by micro-timing, and an unsorted chain can drop notes (section 3.3).
4. The grid-record branch labels are swapped in the notes file (section 4).

## 1. Claims confirmed

### MIDI engine: no count limit
* **The note loop has no counter** [verified]. The MIDI task `FUN_4012ac88` walks the chain from `0x4012b442`:
  * note = `mvs.b (2,a3)` plus the per-track value at `0x4461823c + 4·track` (`0x4012b454`–`0x4012b45e`);
  * velocity and length fall back to track `+0x480`/`+0x481` when negative (`0x4012b46c`–`0x4012b48c`);
  * next = `pool + 2·(0x6800 + idx)` (`0x4012b5f2`–`0x4012b600`); each entry is 6 bytes (`idx·8 − idx·2`,
    `0x4012b60c`–`0x4012b618`).
  * The only exits: next < 0 (`0x4012b608`), or an entry whose micro-timing differs from the first one's
    (`0x4012b442`–`0x4012b44a`). That case reschedules the event (`0x4012b63a` → `0x4012b70a`).
* **Where the entry pointer comes from** [verified]. `a3` is `pool + 6·head` or, when head < 0, the inline note at
  event `+0x24` (`0x4012af9e`–`0x4012afb4`).
* **Event builder** `FUN_400d8cbe` [verified (C)]:
  * event `+0x14` = pattern + 0x6a50;
  * `+0x18` = head from `pattern + 2·(step + track·0x80 + 0x9528)`;
  * inline note from track `+0x485/+0x480/+0x481` only when head < 0.
* **MIDI or synth** [verified (C)]. The schedulers `FUN_400d907a`/`FUN_400d99de` pick the builder by the kit
  + 0x5cda bit.
* **Type-3 events skip the voice allocator** [verified]. In `FUN_40025e36`, type 3 links the wrapped MIDI event into
  the list and jumps to the loop end `0x40026e50` (`0x40026294`–`0x400262ee`). `FUN_4002a6a2` is called only at
  `0x400269e6` and `0x40026d86`.
* **Live path** [verified (C)]. `FUN_4012bb90` is called only from `FUN_40121b0a` and `FUN_40121db2`. It builds
  head = −1 with one inline note.
* **Note-off records cannot run out** [verified]:
  * A (channel, note) pair holds at most one record. If the slot at `0x446014a8` is set, `FUN_4012a3ec` unlinks and
    frees the old record first (`0x4012b4a4`–`0x4012b4ac`; free at `0x4012a460`).
  * The free list holds exactly 2048 = 16 × 128 records of 24 bytes, `0x446034b8`–`0x4460f4b8` (`FUN_4012ba7a`).
* **Event pool** [verified (C)]: 64 MIDI events of 0x60 bytes (head `0x4460f4bc`, last at `0x44610cbc`).
* **8-bit output length** [verified]:
  * `mvz.b 0x44600ca0` at `0x4012aaa6` and `move.b` at `0x4012aac2`;
  * cleared once per queue message (`0x4012acb2`);
  * flushed once at the end (`0x4012ba32`–`0x4012ba44`).
* **Output does not drop data** [verified (C)]:
  * DIN `FUN_40002612` busy-waits on its 4 KB eDMA ring.
  * USB `FUN_40004734` also busy-waits (loop on `0x4058f224`) and returns early only when USB is not configured.
  * So the only place output can lose data is the 8-bit counter.

### Pattern storage (checked hardest)
* **Loader `FUN_400de4b0`** [verified, disassembly `0x400de4b0`–`0x400de5ee`]:
  * copies 0xc000 bytes of storage;
  * sets head (0x1000), next (0x4000) and the bitmap (0x400) to 0xff;
  * for each of 0x2000 entries, skips only track byte = −1 (`0x400de534`–`0x400de538`);
  * inserts the entry into the (track, step) chain sorted by micro-timing, stable for equal values
    (`0x400de580`–`0x400de586`, `ble`);
  * has no per-step count and no range check on track or step.
* **`FUN_400de77a` offsets** [verified (C)]: version word = 4; tracks at +4, stride 0x4a3; pool at
  `+0x128d·4 = +0x4a34`; p-locks at `+0x428d·4 = +0x10a34`; settings at `+0x56b5·4 = +0x15ad4`.
  * The pool is exactly 0xc000 bytes (0x10a34 − 0x4a34).
* **Save path: no cap, no stale entries** [verified]:
  * `FUN_400de5f0` copies 0xc000 bytes.
  * Per-step mirror `FUN_400de61a` copies every entry of the step's chain.
  * The chain free `FUN_40034f9c` sets the first 4 bytes of each freed entry to 0xff. It then tail-calls
    vtable + 0x10 with a NULL change-info (`clr.l (48,sp)` at `0x4003509e`, `jmp (a1)` at `0x400350aa`).
    `NotePool::vslot17` turns a NULL change-info into a full 0xc000 copy [verified (C)], so freed entries are
    cleared in storage too.
* **Step helpers have no cap** [verified (C)]:
  * `FUN_400357f0` (read a step's notes) walks the whole chain into a vector.
  * `FUN_400350b6` (write) writes the whole vector and stops only when `FUN_40034f26` returns −1. That allocator
    covers 256 words × 32 bits = 8192.
* **Copy and paste have no fixed array** [verified (C)]. `NotePoolEntryCopy` holds a std::vector (`FUN_40193406`).
  I scanned every caller of the two helpers for small constants. The only hits besides the documented 16-caps and
  `FUN_40055606` are:
  * the unrolled std::find in grid record (`0x4002cb4a`–`0x4002cbd4`);
  * a 16-byte chord-slot reserve (`0x4002445c`);
  * per-step defaults (0x40).
* **Stock itself writes more than 4 notes per step** [verified (C)]. The mk1 import `FUN_4001464c` writes the base
  note plus up to 7 non-zero offsets per trig directly into storage +0x4a34, for all 8 mk1 tracks.
* **No spare bytes in trackStorage** [verified (C)]. `FUN_400de0ee` reads every storage byte 0x000–0x4a2.
  * Bits 2–6 of storage byte 0x498 are ignored: runtime 0x498 = bit 7, runtime 0x4a3 = bits 0–1.
  * That is too little for chord notes. A stock save would probably write those bits as 0 [inferred].

### Where the 4 comes from
* **Descriptor rows** [verified, raw bytes]. Rows `0x1c`–`0x1f` at `0x401f8a34`–`0x401f8ae8` are group 0x16, ids
  8–0xb, range 0..0x7f00, defaults 0x3c00/0x4000/0x4000/0x4000, formatters `0x400e3030`/`0x400e3254`. They are the
  only group-0x16 rows in the 0x141-row table.
* **Gate** `TrigParameterSet::vslot27` allows group 0x16 only when `FUN_400313f4` (is synth) is false
  [verified (C)]. `FUN_400313f4` is `FUN_40031274 ^ 1` (`0x40031404`), and `FUN_40031274` reads kit + 0x5cda
  (`0x4003129c`) [verified].
* **`FUN_40055606` forces exactly 4 notes** [verified]:
  * count = (end − begin) >> 2 (`0x40055656`);
  * `cmp`/`bcs` at `0x40055664`: count ≤ 3 pads with `{−1, −1, −1, 0}` up to 4 (`FUN_4019c390`);
  * `moveq 4`/`beq` at `0x40055680`/`0x40055684`, then end = begin + 16 (`0x40055686`–`0x4005568c`): count > 4
    truncates to 4;
  * notes[k].note = value (`0x40055698`).
  * Bytes at `0x40055684` are `67 0a`, so the patch `60 0a` is a valid `bra.b` to `0x40055690`.
  * It is called only from `FUN_400556d2`/`4005574a`/`400557c2`. These are reached from `vslot17` rows
    `0x1d`/`0x1e`/`0x1f` and from the lock clear `FUN_4005583a` (value −1) [verified (C)].
* **Preview chord** `FUN_40054000` [verified]:
  * base = track `+0x485` (`0x40054122`);
  * MIDI only (`FUN_40027c36`, `0x40054134`);
  * i = 1..3 reads `+0x485+i`, skips 64 (`0x40054158`–`0x40054164`), adds base + v − 64 with a 0..127 check;
  * loop bound `moveq 4` at `0x400541fc`.
* **New trig** `FUN_400544d8` writes one entry `{track+0x485, 0xff, 0xff, 0}` [verified (C)]. Its `moveq 0x40`
  (`0x40054642`) is the per-step array default at `+0x200`, not a chord.
* **Track-level fields** [verified (C)]:
  * getters and setters: `+0x485`/`+0x486`/`+0x487`/`+0x488` in `FUN_4004ebbc`…`FUN_4004edc4`;
  * defaults 60/64/64/64 in `FUN_400e752c`;
  * storage mapping 0x480 → 0x485 and 0x486–0x488 → 0x486–0x488 in `FUN_400de0ee`.
  * The only other code touching 0x486–0x488 is load and save (`FUN_400de0ee`/`FUN_400de388`), track copy
    (`FUN_400dfca4`/`FUN_400dfda4`), and the mk1 track import `FUN_40013cda`. The open question about new trigs
    stands.
* **SHAPE chords** [verified]:
  * `FUN_40150204` writes exactly four ints in the shape path (`0x40150238`–`0x40150256`, −1 = unused).
  * Its second path (scale triads, table `0x4020e140`, `0x4015025c`–`0x40150300`) writes 3 notes plus −1. So the
    maximum is 4 on both paths.
  * The table bytes for shapes 0–11 match the report.
  * The BASS branch at `0x40034624` (`moveq 3; cmp; bge`) matches.
* **16-note caps** [verified]. Each compares the vector byte span with 63:
  * NOTE EDIT at `0x4001fc1a`, then "MAX NOTES REACHED" (`0x40212ffd`);
  * live record at `0x40045328`;
  * grid record at `0x4002c9a6` and `0x4002cb3a`.
  * Chord-memory learn: after the push it erases the oldest when size > 15 (`0x40020ec4`–`0x40020ef6`).
  * Slot store `FUN_4003ad50` copies min(size, 16) bytes [verified (C)].
* **NOTE EDIT on MIDI tracks** (the report had this as [inferred]):
  * The open path in `MainScreenView::vslot02` (`0x4005fab8`–`0x4005fada`, then `jsr 0x4001ce42` at `0x4005fe74`)
    tests only a key state (`FUN_4011639c`), a global flag (`FUN_400bbc04`, `0x405ce8ac`) and a view flag
    (`FUN_40055cca`, `+0x269`/`+0x270`). None of these is a track-type test [verified].
  * In all NOTE EDIT code, the only track-type call is `NoteEditorMenuView::vslot04` → `FUN_400313f4` (the
    MID/SYN label) [verified, call graph and grep]. No NOTE EDIT function reads kit + 0x5cda directly [verified].
  * Live and grid recording (`FUN_4002d2b0` → `FUN_40045188`/`FUN_4002c902`) have no MIDI gate either
    [verified (C)].
  * Reachability on the unit is still [inferred]. No static gate exists.

## 3. Things the report missed

### 3.1 Side effect of the proposed patch on lock clears [inferred, code verified]
The MIDI loop skips any note outside 0..127 (`0x4012b490`–`0x4012b498`). No path turns a −1 note into the track
NOTE:
* neither the MIDI task nor `FUN_400d8cbe` does it;
* only the inline-note builders read `+0x485` [verified, grep of every `(0x485,An)` access].

So the padding entries `{−1, −1, −1, 0}` from `FUN_40055606` are silent placeholders on MIDI.

The lock clear `FUN_4005583a` calls `FUN_40051c34(−1)`, which stores −1 raw as notes[0].note [verified (C)]. It
then calls the three NOT2–4 setters with −1.
* **Stock:** a cleared trig ends up as 4 entries, all with note −1.
* **After the patch** (`0x40055684` → `60 0a`): notes 1–4 become −1, but notes 5..N stay and keep sounding.

The patch outline presents "lock clears stop truncating" as a benefit. A mod should handle `FUN_4005583a` on its
own, for example by keeping the truncation (or a full clear) in that path.

The −1 result also deserves a unit test on stock: clear the locks of a MIDI trig and watch MIDI out (test 6). It
may expose a resolution path that static reading missed.

### 3.2 Note-off bursts wrap the same 8-bit counter [verified path, consequence inferred]
Message type 3 (`0x4012b7f6`–`0x4012b894`) sends a 3-byte note-off for every expired record in one pass, then flushes
once. It uses the same counter at `0x44600ca0`. Chords with equal lengths end together, so more than 85
simultaneous note-offs wrap the counter. Example: 11 tracks × 8 notes = 264 bytes. Wrapped note-offs are lost or
garbled, so notes can be left **stuck**. That is worse than the lost note-ons the report describes. Fix it together
with the note-on side (section 4.5 of the T2.1 notes).

### 3.3 Chains must stay sorted by micro-timing [inferred, code verified]
* `FUN_400350b6` writes a step's notes in vector order and does not sort. Only the loader sorts
  (`0x400de580`–`0x400de586`).
* When a utm group ends, the MIDI task computes the next group's time. If that time is before the current one
  (`sub.l`/`bmi` at `0x4012b750`–`0x4012b754`), it frees the event (`0x4012ba6e`), and the rest of the chord is
  lost.
* A mod that writes notes 5–8 at runtime should keep each step's chain sorted by entry[5], as the loader does.

### 3.4 `Project::checkNotepoolIntegrity` exists but is never called [verified]
* `FUN_40044e04` stores the std::function manager `FUN_4003e034`, whose typeinfo `0x401dd098` names
  `Project::checkNotepoolIntegrity` lambda #3.
* For each of 128 patterns (stride 0x954) it copies the 0xc000 pool, flags duplicate (track, step, note, utm)
  entries and ordering faults, and counts them.
* It has no per-step cap and writes nothing back to the project [verified (C)].
* It has no caller, no pointer, no pc-relative reference and no vtable slot in the image [verified, raw scan of the
  image for the 32-bit address and every `jsr`/`bsr`/`lea`/`pea` (d16,pc) encoding].
* For safety, a mod should not create duplicate (note, utm) entries on a step, in case a later OS enables this check.

### 3.5 Other points [inferred unless marked]
* **Per-track value at `0x4461823c`.** It is copied from the type-2 config event (`FUN_4012ac88`, about
  `0x4012ad2e`). The audio task writes the same source values to the synth side at `0x80005381 + track`
  (`0x40026216`–`0x40026226`) [verified]. That fits a per-track transpose and supports absolute pool notes.
* **No exhaustion checks.** `FUN_4012a6e8` pops the 64-event free list without an empty check (`0x4012a6ee`)
  [verified]. Queue sends `FUN_40001896` (64-slot ring, `& 0x3f` in `FUN_4012bb90`) have no full check
  [verified (C)].
  * A sequenced trig uses one event whatever its chord size, so N = 8 changes nothing there.
  * A live chord uses one event and one queue slot per note. Stock 16-note chord memory already does that.
* **`dn2_param_table.py` docstring.** It labels row offset +0x20 as "row index". Row 0x1c holds 0x1e there, and 302
  of the 0x141 rows do not equal their own index [verified]. That is a documentation slip only.

## 4. Corrections to the T2.1 notes
* **Grid record branch labels are swapped** (section 2.3 table). At `0x4002c94e`–`0x4002c962`, `FUN_400313f4`
  (is synth) returning 0 branches to `0x4002cafa`. So **`0x4002cb3a` is the MIDI-track cap** and `0x4002c9a6` is
  the synth one [verified]. Both are 16, so the conclusion stands.
* **The patch outline's lock-clear benefit is not clean** (section 3.1).
* **NOTE EDIT reachability** can move from "gate not decoded" to "no track-type gate on the open path"
  (section 1).

## 5. Not checked
* The pattern-settings block (`+0x15ad4`, `FUN_400ddae0`) for spare bytes that could hold a longer default chord.
* Where the TRIG-page view converts per-trig NOT2–4 between the raw pool byte and the value − 64 display.
  * `vslot17` passes the raw parameter value straight to `FUN_400556d2` (`0x40038402`) [verified (C)].
  * `FUN_400518f8` returns the raw notes[1] byte [verified (C)]. The open question stands.
* Chord-memory slot count (16) and the `FUN_400576a4`/`FUN_40123510` direct sender.

## 6. Extra test for the unit (stock 1.12, MIDI monitor)
6. On a MIDI track, place a trig, add NOT2 = +4 on it (the chain becomes 4 entries), then clear its locks. Expected
   from static reading: notes 1–4 become −1 and nothing is sent. If the trig still plays NOTE, there is a
   resolution path this check missed.
