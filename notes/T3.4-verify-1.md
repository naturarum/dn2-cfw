# T3.4 verify 1: chorus, delay, reverb and master compressor on the Digitone II DSP

Date: 2026-10-05. Independent check of `notes/T3.4-fx-locate.md`. Image: section 7 of OS 1.12 (= 1.11),
digikit's database `vendor/digikit/out/sharcdb/dn2-1.12.sqlite`, image words read with
`sharc.load("dn2-1.12")`, selache listings from T3.1 (`out/T3.1/disasm/`). Addresses as in T3.4:
SW = short-word program address, DM = digikit's bare byte address.

Marks: **[verified]** = re-derived here from the database, the image words or a run of my own script;
**[inferred]** = reasoned from structure.

## Verdict

**The identification holds, with small corrections.** All four entry points, call sites, parameter
structs, state addresses and buffer sizes re-derive from the database and the image words. No other
code reads the global FX block or the four parameter structs, so there is no better candidate.

Corrections, none of which changes an identification:
1. **Chorus order.** The 6 biquads run *before* the modulated delay, not after it. The report's
   steps 3 and 4 in section 3.1 are swapped. **[verified]**
2. **F15 and R14 hold at the unpack.** The report marks `F15 = 1/32512` and `R14 = -15` as
   [inferred] because "the voice loop's side blocks also write R15 and R14". They do not. Every
   path from the set points to `0x1c2dfc`, side blocks and switch cases included, is free of writes,
   and the one callee that touches them (`0x1c9c9d`) saves and restores them. selache also decodes
   `0x1c2b0e` as `r14=-0xf`. Both can be upgraded to **[verified]**.
3. **The cross-check is weaker than stated.** "1,133 identical bytes" only shows that both decoders
   start an instruction at the same address. Within the report's own ranges, selache also prints 7
   of those same-bytes instructions (`0x68fe...`, reverb diffuser `0xb82b15`-`0xb82b2a`) as loads
   where digikit prints stores. digikit is right: seven identical loads into `R2` would be dead. This
   selache direction bug is not in T3.1's list. None of the cited load-bearing instructions is
   affected. **[verified]**
4. **Reach in the database.** digikit's `reach` table reaches the chorus and compressor from the
   Audio Task, but not the delay or reverb, because their entries sit inside the DB functions
   `FUN_b8478d` and `FUN_b836ac`. Both of those are out-of-line blocks of the parameter updates,
   entered by conditional jumps (`0xb8470f`, `0xb83586`). Reachability holds through the call
   edges. The report says the boundaries are wrong but never says that `reach` misses the two
   effects. **[verified]**

Missed by the report (new facts):
- **Compressor gain-reduction readout.** At the end of the render, `0x1c3105` calls `0xb8552b` with
  `R4 = 0x257ab0` (compressor state). That routine returns `1 - clamp(10^(0.05 * state[0x5b]), 0, 1)`,
  which is gain reduction from 0 to 1. The render converts it to Q15 (`fix_by(F0, 15)`, `0x1c3115`)
  and stores it at word 11 of the buffer passed as its first stack argument (`DM(I6-33)`, saved at
  `0x1c2776`). **[verified]** for the code. It is most likely the GR meter value sent back to the
  ColdFire **[inferred]**. Where that buffer points is **[open]** (the caller pushes `R1` at
  `0x1c9fb3`). This is the only other user of the compressor state, and it confirms the role.
- **The delay reads the tempo.** The descriptor `0x257e6c` that every effect receives in `R12` holds
  at `+0x14` the word `0x257e80`, which the unpack fills from frame word `0xd8` times `1/120`
  (`R4 = 0x3c088889`, `0x1c3009`-`0x1c302a`). The delay's entry loads `R12 = DM(I5+5)` from the
  descriptor (`0xb84849`). So frame `0xd8` is the tempo, and the delay is its consumer
  **[verified for the loads; tempo meaning inferred]**. The report lists `0xd8` only as
  "tempo-like" and does not link it to the delay.
- **The render has a 4-way switch.** `0x1c29aa` is an indirect jump (`jump (m13,i12)` in selache;
  digikit prints the registers differently) through the table at DM `0x25d968` =
  {`0x1c29ac`, `0x1c3219`, `0x1c3381`, `0x1c34f0`}. None of the cases skips the unpack, the end copy
  or the three calls (below). The report's "no branch around them" is right, but its walker does not
  follow this jump.

## 1. Reachability and "unconditional"

- **Edges** (digikit `edges`, each the only static caller) **[verified]**: `0x1c9ff4 -> 0x1c9d6b`
  (in the Audio Task loop `0x1c9fe7`-`0x1c9ffb`), table `0x268a68` = {`0x1c9dc2`, `0x1c9e76`,
  `0x1c9eda`, `0x1c9f0f`} read from the image, `0x1c9fbc -> 0x1c2712` (with `R12 = I3` at
  `0x1c9fb5`), `0x1c3044 -> 0x1c8ef1`, `0x1c3054 -> 0x1c1738`, `0x1c305d -> 0x1c1f1e`,
  `0x1c1be1 -> 0xb84d5c`, `0x1c1c58 -> 0xb8482c`, `0x1c1d11 -> 0xb836bc`, `0x1c215c -> 0xb8541d`.
  All eight calls have no condition field. There are no literals or data pointers to any of the four
  entries (`literals`, `dataref`), so there is no indirect caller.
- **No path around the calls** **[verified]**, using my own CFG walker (`scripts/t34v_avoid.py`). It
  follows aligned instructions and DB edges, with delayed branches taking effect after two slots,
  and steps over calls. From each entry it asks whether a return is still reachable with one
  instruction removed:
  - `0x1c1738` (757 instructions, one return `0x1c1e1e`): removing `0x1c1be1`, `0x1c1c58` or
    `0x1c1d11` leaves no return reachable.
  - `0x1c1f1e` (499 instructions, return `0x1c22dd`): removing `0x1c215c` leaves none.
  - `0x1c2712`, with the 4 switch targets of `0x1c29aa` added (1,467 instructions, return
    `0x1c315a`): removing `0x1c2dfc` (unpack), `0x1c302d` (end copy), `0x1c3044`, `0x1c3054` or
    `0x1c305d` leaves none.
- Whether command 3 runs on *every* block depends on the ColdFire's command word, which is outside
  this check. Within a command-3 block all four effects run whatever their settings.

## 2. Frame image and unpack

- `I5 = 0x25c48c` (`0x1c2877`) and `I4 = 0x25c48c` (`0x1c301a`) are the only literals for the base.
  Its two stores are the 672-trip copies (`lcntr=0x2a0` in both decoders) at `0x1c287a`, skipped by
  `JUMP IF SV` at `0x1c2872`, which then clears the flag word `0x25d6c4`, and at `0x1c302d`. Both
  copy from `DM(I6-32)`, the render's `R12` (saved at `0x1c2767`). **[verified]**
- **Readers of the global block** (`mem_access` and `ptr`, whole image): 33 absolute loads, all in
  `0x1c2712`, covering `0x9fa`-`0xa52` except `0xa18` (k40). No register-based access lands in
  `0x25ce80`-`0x25cee8`. **[verified]** So k40 is unread both by absolute address and through the
  pointer table. The voice loop's `0x92`-stride pointers end below `0xa18` (slot 15 send words are
  at frame `0x9e2`-`0x9e6`).
- **Half-word order.** A 32-bit load at an even offset `o` puts word `o` in the low half. The
  report states this without evidence, and if it were the other way round, neighbouring parameters
  would swap. Semantics settle it **[verified]**:
  - the low half of `0x25ced4` (`0xa48`) goes through `ashift` and `* 0x3e124925` (1/7) into
    `comp+8`, the ratio index, and RAT is the 8-value (0..7) parameter. The high half (`0xa4a`) stays
    an integer at `comp+0x1c`, the side-chain source selector.
  - the low half of `0x25ceca` (`0xa3e`, DUAL, a toggle) becomes the byte flag `0x257aa4`. The high
    half (`0xa40`) is scaled into `comp+4`, which the detector uses as `60*THR - 60`.
  - short-word loads at an address (for example `0x25ce8e`) read the same bytes as the low half of a
    32-bit load there.
- **Destinations.** I re-traced every row of the report's table from the listing
  (`out/T3.4-verify-1/unpack.lst`), following each register from its load through
  `fext-se`/`ashift`, `float`, `* F15` or `float_by R14`, to its store. All 44 global rows, plus
  `0xd4`/`0xd6`/`0xd8`, match the report, including the gates (`R10` bits 16, 17, 21, 23) and the
  delay-slot stores (`0x257950` at `0x1c2ef6`, `0x257964` at `0x1c2fc5`). **[verified]**
- **Scale constants.** `R15 = 0x38010204` at `0x1c2b23` (= 3.0758e-5 = 1/32512) and
  `R14 = 0xfff1` at `0x1c2b0e` (selache: `r14=-0xf`). On every path from those instructions to
  `0x1c2dfc` (351 instructions, including the out-of-line blocks `0x1c317f`-`0x1c3217` and
  `0x1c31e9`) neither register is written. The three callees on those paths are `0x1c8ac4` and
  `0x1c8ae0`, which do not touch them, and `0x1c9c9d`, which saves and restores both
  (`0x1c9cac`/`0x1c9cb1`, `0x1c9cf9`/`0x1c9cfd`). **[verified]**
- **Who reads the structs.** Absolute loads of `0x257918`-`0x257988` exist only for the
  compressor's `+0x1c`/`+0x20`/`+0x24` (the master, `0x1c1fef`/`0x1c2009`/`0x1c2084`). Everything
  else in the four structs is read only through `R8` inside the effects. Each struct's literal
  appears exactly three times: init `0x1c16xx`, the call setup and the unpack. **[verified]**
- k48's flag `0x2579d4`: one store (`0x1c2e63`), no load by absolute address or in `ptr`.
  **[verified]** The report's negative holds.

## 3. The four effects

**Call setup** (`0x1c1bc6`-`0x1c1bde`, `0x1c1c31`-`0x1c1c55`, `0x1c1ce9`-`0x1c1d0e`,
`0x1c2140`-`0x1c2158`): `R4` = state (`0x80459388`, `0x8005912c`, `0x80000018`, `0x257ab0`),
`R8` = struct (`0x257950`, `0x257934`, `0x257918`, `0x257964`), `R12 = 0x257e6c`. Before each call,
`M3 = 1.0` is stored into `0x257960`, `0x25794c` and `0x257930`. **[verified]**

**Chorus `0xb84d5c`** **[verified]**
- Parameter update `0xb84c1f`: `I4 = R8`. It reads `+8` (HPF, `* 127.0`, clamp, `trunc`, index
  into `I3 = 0x2cfbc0`), `+4` (`* 2.82 + 0.28`, constants `0x40347ae1`/`0x3e8f5c29`), `+0xc`, `+0`
  and `+0x10`. 7 `fmul F2,F2` plus `F6 = F2*F2` at `0xb84c99`-`0xb84ca3` raise a value to the 256th
  power.
- Real order in the entry: update (`0xb84d7c`) -> one-pole `0xb80c39` L/R (`0xb84d92`,
  `0xb84da9`) -> **6 biquads `0xb84ccb` (`0xb84db6`)** -> **modulated delay `0xb84b39`
  (`0xb84dc0`)** -> output `0xb8499c` (`0xb84dd0`).
- `0xb84ccb` calls `0x1cdfa1` six times with states `+0x1210`, `+0x1234`, `+0x1258`, `+0x127c`,
  `+0x12a0`, `+0x12c4` (stride `0x24` = 9 words). `0x1cdfa1` runs a DO loop over the block calling
  `0x1cdf46`, a direct-form-I biquad (5 coefficients, 4 state words).
- `0xb84b39` is a per-sample loop (`R14 = dec(R14)`, back jump `0xb84bf5`). Each sample it calls
  `0xb84a3b`, reads per-channel offsets at `I1 = +0x1104`, and computes `write - offset` and
  `write - offset + 1`, each `fext(...,0,9)`, for rings `I2 = +0x4` and `I3 = +0x804`. It
  interpolates the pairs linearly and writes the new input sample (taken from the work buffers
  before the output overwrites them) at the write index, which is then `inc`'d and wrapped by
  `fext 9`. The rings are 512 samples, and the output does not feed back into them.
- The table `0x2cfb40` starts at 259.3, 263.5 (delay in samples) **[read]**.

**Delay `0xb8482c`** **[verified]**
- Entry: `I5 = R12` (descriptor), `R14 = DM(I5)` (block length), `R12 = DM(I5+5)` = `0x257e80`
  (tempo), then the update `0xb84604` with `I5 = R8`, which reads `+0`, `+4`, `+8` and `+0x14`.
  Constants 30.0, 300.0, 120.0, 32512.0, `0xbb80`, `0x384`, `0x5dc00`; calls `0x1c06ba` (divide).
- Rings: `fext(...,0,19)` at `0xb83e9d`, `0xb84071`, `0xb8431b`, `0xb846ce`, `0xb846d6`;
  `R8 = 0x7ffff` at `0xb83fcc`; bases `+0x4` and `+0x200004` (`0xb83fb9`, `0xb842e5`). 2 x 2^19
  floats = 4 MiB. Chorus state minus delay state = `0x40025c`, which fits.
- The entry follows an unconditional `JUMP 0xb846f5` and its two delay slots (`0xb84824`-`0xb8482a`).
  The DB's `FUN_b8478d` is an out-of-line block of `0xb84604`.

**Reverb `0xb836bc`** **[verified]**
- Init `0xb83cbd`, with each call to `0xb80079` taking `R4` = descriptor, `R8` = buffer and
  `R12` = length:
  - pre-delay: `R4 = state+4`, `R8 = state+0x38`, `R12 = 0x4000`.
  - long lines: a 4-pass loop (`R10 = 4`), two calls per pass with `R12 = 0x2000`. Descriptors are
    at `+0x18218 + 0x34*i` and that plus `0x202a0`; buffers at `+0x182e8 + 0x8000*i` and that plus
    `0x202a0`. That makes 8 x 8,192.
  - short lines: an 8-pass loop with `R12 = 0x400`. Descriptors at `+0x10058 + 0x34*i`, buffers at
    `+0x10218 + 0x1000*i`. That makes 8 x 1,024.
  - Each descriptor block ends exactly where its buffers start (`0x10058 + 8*0x34 = 0x10218`,
    `0x18218 + 4*0x34 = 0x182e8`), so the layout is consistent.
- The entry follows `JUMP 0xb83592` and its delay slots. The DB's `FUN_b836ac` is an out-of-line
  block of the update `0xb8351c`.
- Not re-derived: the tank `0xb82d1a` internals and the 8 damping calls. They are structural
  [inferred] in the report too.

**Compressor `0xb8541d`** **[verified]**
- Ratio table `0x2cfde0` (image words) = 0.666667, 0.5, 0.333333, 0.25, 0.166667, 0.125, 0.0625,
  0.05. Its only reference is `I3 = 0x2cfde0` at `0xb850bd` (in both decoders).
- The detector `0xb85070` has constants 7.0 (`0xb85089`), 60.0 (`0xb8509a`) and 20.0 (`0xb850b5`).
  Its per-sample loop (`0xb850ca`-`0xb850f4`) does `fabs`, `fabs`, `fmax`, then calls `0x1c0c76` and
  `0x1c0b60`.
- Tables: `0x2cfe00` starts 0.811936, 0.821863; `0x2d0000` starts 0.997919, 0.997921; `0x2d0200`
  starts 0, 2.44e-05. **[read]**
- The extra user `0xb8552b` (gain reduction) is described in the Verdict.

## 4. Better candidate?

None found. **[verified]** for the searches below.
- The global FX block `0x25ce86`-`0x25cee0` has no reader outside the unpack (section 2).
- The four parameter structs have no reader other than the effect called with them, plus the master
  for the compressor routing fields.
- The ratio table has one reader. The state addresses `0x80459388`, `0x8005912c` and `0x80000018` are
  used only by init and the call setups. `0x257ab0` is used by init, the call setup and the GR
  readout `0x1c3105`.
- Per-voice stages (digikit's DT2 "8192-word comb or delay" family) are per-voice, take no global FX
  words, and so are not send effects.

  (Checked: each DDR state literal appears twice, in init and in its call setup: `0x1c163d`/`0x1c1d03`,
  `0x1c1666`/`0x1c1c4a`, `0x1c168f`/`0x1c1bd5`. The `literals` table stores values of `0x80000000`
  and above as negative integers, so mask with `& 0xffffffff` when querying.)

## 5. Decoder cross-check and cost

- In the sites I sampled, selache and digikit agree on every load-bearing instruction: the frame
  loads `0x1c2eba`, `0x1c2e01`, `0x1c2f0d` and `0x1c2efe`, the stores `0x1c2e0e` and `0x1c2f46`, the
  copy `0x1c287a`/`0x1c3030`/`0x1c3033`, the calls (selache prints `cjump ... (db)`, the C-call
  form), `r15=0x38010204`, `r14=-0xf`, `fext ... 0x0:0x9` at `0xb84ba1`, `i3=0x2cfde0` and
  `r9=0x3e124925`. selache prints `???` at `0x1c2dfc`, as the report says. **[verified]**
- New selache bug class: the `0x68fe....`/`0x68be....` long load/store form is printed as a load
  where digikit has a store. This happens at `0xb82b15`-`0xb82b2a` (7 starts in the report's ranges),
  at `0x1c3117`, and in the render prologue (`0x1c2969`, `0x1c2992`). Dataflow sides with digikit
  each time: the values are just computed, or the same register would be loaded 7 times. **[verified]**
- Cost (section 4 of the report): not re-derived. It is a static count and stays **[inferred]**. The
  per-sample `powf`/`log` in the detector loop and the per-sample biquad and one-pole calls the
  estimate rests on are confirmed above.

## 6. Open after this check

- Destination of the GR word (`DM(I6-33)`, word 11): probably the DSP-to-ColdFire reply. Tracing
  `R1` at the caller (`0x1c9fb3`) would settle it, and T4.1 could then read the compressor GR from
  the reply.
- Per-voice send gains (k86-k88): the pointer table shows a store through `I3 = 0x2579d8` at
  `0x1c2c5f` in the render's voice section, and the FX bus reads `0x2579d8` (`0x1c178b`) and indexes
  from `I5 = 0x257990` (`0x1c181b`). This supports the report's inferred stride-`0x1c` row table as
  the destination, but I did not trace it.
- Whether the ColdFire sends command 3 every block.
