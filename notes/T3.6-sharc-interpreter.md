## 1. Design

- **Core in C** (`tools/sharcvm/sharcvm.c`, `sharcvm.h`), built into `out/T3.6/build/libsharcvm.dylib` by
  `vm.py` on first use (`cc -O2 -ffp-contract=off -mno-outline`). It holds the register files of both processing
  elements (40-bit data registers, MRF/MRB as 80-bit accumulators), the DAG registers with their secondary
  sets, the PC, loop and status stacks, delayed-branch state, and the memory (L1 0x240000-0x39ffff, L2 1 MiB,
  32 MiB of DDR, the 0x28xxxxxx system alias of L1; core MMRs (word-addressed 0x30000-0x3ffff) and system
  MMRs are plain stores: reads return what was written, nothing is modelled behind them).
- **Decoding stays in digikit**: `tools/sharcvm/decode.py` calls `vendor/digikit/tools/sharc_disasm.py` at
  the exact PC and gets (form, length, fields). Two corrections are applied on top, counted in
  `decode.OVERRIDES` so they stay visible (section 2.2, items 5 and 6).
- **Translation** (`tools/sharcvm/translate.py`): form + fields -> one fixed-size `insn_t` record: an
  operation kind, condition, flags, up to three compute slots (ALU, multiplier, shifter; multifunction and
  dual add/subtract are slot combinations), and up to two memory transfers. The 23-bit compute field is
  decoded from digikit's transcription of the PRM opcode tables (`tools/sharcspec/compute_table.json`).
  Anything without semantics becomes `K_UNIMPL`, which **traps when executed** (never a silent no-op).
- **Lazy predecode**: code pages (4096 instructions) are created on demand; the core returns `ST_DECODE` at
  an undecoded PC, Python decodes and translates that one instruction, and the core continues. Each
  instruction is decoded once; data that is never executed is never decoded.
- **Driver** (`tools/sharcvm/vm.py`): loads the DN2 image (`out/T3.2/mem/*.bin`, T3.2) or a selache ELF
  (`elf.py`), sets the C-runtime state the reset code leaves (MODE1 = 0x1011800, M5/M6/M7/M13/M14/M15,
  L = 0, stack B7/I7/L7 as in T3.2 section 2.1), and calls functions: `vm.call(entry, R4=.., R8=..)` for
  the C convention (CJUMP + the two delay-slot pushes, return through `JUMP (M14,I12)`), `call_rts()` for
  assembly helpers returning with RTS. A call returns when the PC reaches a sentinel return address.

Semantics sources, in order of use: the classic **SHARC Processor Programming Reference rev 2.4** (PGR,
ADSP-214xx, which already has VISA), full text from the Internet Archive item `manualzilla-id-5944459`
(saved as `out/T3.6/refs/pgr_archive_djvu.txt`; analog.com's PDFs of the PGR and of the SHARC+ PRM did not
download from here, every attempt stalled); digikit's transcription of the SHARC+ PRM opcode tables and its
tracer's reading of the PRM (`tools/sharc_trace.py`); selache's VISA width rules (`selinstr/src/visa.rs`) and
runtime comments; and evidence in the DN2 code itself where those disagree (section 2.2).

### 2.2 Rules that needed evidence (the documents did not settle them)

1. **Address spaces and modifier scaling.** An I register holding a byte-space address (L1 0x240000-0x3fffff,
   L2, DDR) has its M register or immediate offset scaled by the access width (x4 normal and long word, x2
   short word, x1 byte). NW-space (0x90000-0xe7fff, byte = 4 x a), SW-space and LW-space addresses are
   converted to byte addresses, unscaled. Other values (0, core MMRs) are not scaled: DN2 0xb83f47
   `I0 = modify(I3, M4)` adds a byte address held in M4 to I3 = 0. **[verified]** by the DN2 code paths that
   depend on it (the delay output routine, the stack frames).
2. **Type 7 MODIFY options.** digikit's table leaves frame bits 39 and 23 unlabelled. Bit 39 is the (NW)
   option (selache prints `i7=modify (i7,m7)(nw)`; every stack-pointer modify has it). Bit 23 behaves as a
   short-word option: the reverb tank (0xb82e43) reaches its second descriptor set only if
   `I5 = modify(I2, M6)` adds 2 bytes, and the render's 16-bit frame walks (0x1c2cc2, 0x1c3a9f) use it.
   Without bit 23 the reverb read garbage and diverged to 1e38 within 7 blocks. **[inferred]** from these
   uses (no document). Bits 39 and 23 together (4 instances): meaning unknown; accepted only when the M
   register is 0 (the DSP boot's cache routine 0x1c0807 has M9 = 0), trap otherwise.
3. **Access widths of Types 3b/3d and 4b/4d.** digikit's ACCESS_WIDTHS table, keyed (l, x, w), fits Type 3b
   (DN2 0xb82976: `(1,1,1)` is a long-word load: R1 is used afterwards without being loaded). It does not fit
   Type 4b: there `111` is the plain normal word (0xb81a54: a 7-word struct stride, the values used as 32-bit
   words), `000` byte, `001` byte sign-extended (0xb8babf: a bool returned from FP-5 bytes), `100`/`101`
   short-word unsigned/signed. Unlisted combinations trap. **[verified]** against the DN2 code that uses them.
4. **Misaligned accesses** are byte-exact (item 11). selache's hardware-validated cases make misaligned Type 3
   word accesses in L1 and need byte-exact results. An earlier "drop the low address bits" hypothesis came from
   the Type 7 bug above and was withdrawn.
5. **Type 2c vs 2b.** A first parcel with bits 15:13 = 110 is always a 16-bit short compute (selache's VISA
   rule). digikit's exact-PC decoder reads `0xC000-0xC07F` followed by more parcels as a 32-bit "2b" (sharcdb's
   sweep decodes the DN2 instances as 2c). Overridden in decode.py, counted in `decode.OVERRIDES`.
6. **IDLE.** The 16-bit parcel 0x0081 is IDLE (selache); digikit reads it as the 48-bit provisional form
   22p_undoc48. Overridden in decode.py.
7. **Type 9a PC-relative offsets** are sign-extended at bit 5 here (T3.1b found digikit's flow code does not).
8. **Compute field 0** is no operation (DN2 uses `modify(I7,M7)` with compute = 0 in live code).
9. **SIMD transfers of registers without a complement.** The PGR names the complementary register as the
   PEy side of a SIMD transfer but says nothing about I, M, L, B. The DN2 master stage clears its
   2-samples-per-pass SIMD buses with `DM(I4, M4) = M12` (0x1c2026): only if the same value is also written
   to the implicit word do the odd samples get cleared (without it the full render came out with every odd
   sample wrong). Loads into such registers in SIMD take the explicit word only (0x1c2784 loads a zero into
   I13 that way). Immediate stores (Type 16) in SIMD write both words. **[inferred]** from these uses.
10. **SIMD sub-word accesses** use the next element as the implicit address (+2 bytes for short words): the
    render (0x1c2a17) converts consecutive 16-bit frame words two at a time with a post-modify of two short
    words, which reads every word once only this way. The classic PGR's k = 2 (for SW-space addresses)
    would read overlapping pairs. **[inferred]**
11. **Misaligned word accesses are byte-exact**, also in DN2 code: the frame unpacker (0x1c28e3) reads two
    16-bit words with one 32-bit load at an address 2 mod 4 (T3.4 already described the halves). DN2 runs
    still trap on word accesses at odd addresses, except in the full-block runner: the voice code (0x1c57a1)
    makes short-word stores at odd addresses on its (uninitialised) state, unexplained (section 6).

## 3. Test results

### 3.1 Oracle 1: selache's C test cases

`tools/sharcvm/build_cases.py` compiles all 2,039 cases of `vendor/selache/xtest/cases/` with selcc, selas,
seld and libsel (built from source into `out/T3.6/libsel/`), with a minimal harness
(`tools/sharcvm/harness/hmain.c`) instead of the UART one. `tools/sharcvm/run_cases.py` loads each ELF, runs
from selache's own `start` (reset code, C runtime set-up, main) to IDLE and compares `test_main()` with the
case's `@expect` (from gcc/clang; selache promotes a case only after it passed on an ADSP-21569 board with
both CCES and selcc, `xtest/grow_drafts.py`).

**2,036 of 2,039 pass. [verified]** The 3 failures are csmith programs where selcc's own assembly stores a
non-pointer into a pointer's stack slot (cctest_csmith_bda514fc: in the second loop `DM(-0x61,I6)=R6` stores
the loop counter over the pointer stored there by `DM(-0x61,I6)=R3`, then the pointer is dereferenced; the
other two, 2263b3eb and 5daf02be, show the same pattern of two stores of different registers to the slot).
That is visible in the `.s` text, independent of the interpreter, so these look like selcc miscompiles
**[inferred]** (selcc may have changed since the cases were validated on hardware). The run takes 9 s on all
cores (112M instructions).

What this covers: what selcc emits, i.e. the C-level semantics of 2a/2c/15a/15b/3a/3b/3c/14a/16a/17a/17b/5a/5b
moves, calls and returns, loops (12a), shifts, integer and float arithmetic, libsel's math. It does not cover
SIMD, multifunction, sub-word widths, long words or most of the DN2's DAG tricks: selcc does not emit them.

### 3.3 Oracle 3: behaviour of the effects

- **Compressor:** a -6 dBFS sine with THR = 0.5 (-30 dB), RAT = 3/7 (4:1), side-chain filter neutral
  (SCF = 0.5) settles at 0.0631 = **-24.0 dBFS**, exactly the static curve (-30 + 24/4). **[verified]**
- **Delay:** TIME = 64/127 at 120 BPM gives echoes every 48,749 samples = 65 x 750, i.e. the time is counted
  in 1/128 bar; with FDBK = 0.5 (about knob 64, "99 %") the echoes decay slowly through the soft clip
  `x*(2-|x|)` that T3.4 found in the feedback path; left-only input gives a silent right output (X = 0).
  **[verified]** for the numbers; the 1/128-bar reading is **[inferred]**.
- **Chorus:** on a noise burst the output correlates with the input at a delay of 314 samples (L) and 292
  (R), inside the 259-368-sample range of its delay table 0x2cfb40 (T3.4). **[verified]**
- **Reverb:** an impulse gives a smooth decaying tail (block peaks 0.02 at 50 ms, 0.001 at 1 s with DEC 0.6).
  Plausible; nothing independent to compare with until T3.5. **[inferred]**
- **Robustness:** `tests/fuzz_params.py`: each effect with 12 random settings (extremes included) x 150 blocks of
  noise, and the whole block with random FX/mixer/routing words: no trap, no NaN or infinity. **[verified]**

### 3.4 Oracle 4: the T3.11 effects built with selcc vs built natively (the task's goal 2)

`tools/sharcvm/tests/fxcheck.py` builds one driver (`tools/sharcvm/harness/fxdrv.c`) with T3.11's
`tapedelay.c` and `mbcomp.c` twice: with selcc `-O1` for the ADSP-21569 (run here, state in DDR) and with
clang `-O2 -ffp-contract=off` as a native library. Both get the same calls (init, tempo, knobs, snap, the test
signal in 32-sample blocks) and the outputs are compared sample by sample (2 s, stereo):

| sources | tape delay | 3-band compressor |
|---|---|---|
| `fx/` as is | 39 % bit-identical, max difference 0.071 (-15 dB re peak) from sample 7,050 | 6 % identical, max difference 0.80 (above the peak) from sample 1 |
| `out/T3.6/fxcheck/src/` (bit casts instead of the union in `fx_exp2`/`fx_log2`) | **97 % bit-identical, max difference 1.9e-9 (-166 dB)** | **33 % identical, max difference 3.6e-7 (-123 dB)** |

**[verified]** for both rows. The cause of the first row is a **selcc bug**, not the interpreter: in
`fx_exp2` (fxmath.h) selcc drops the store `u.f = p` and adds the exponent to the stack slot that still holds
the clamped input (`R3 = R1 + R5` with `R1 = DM(-0x6,I6)`), then returns `p` unadjusted (`R0 = PASS R6`); the
same at -O0, -O1 and -O2 and with `volatile`; `fx_exp2(7.6f)` gives 1.516 instead of 194.0, `fx_log2(196.0f)`
gives 1.25e10 instead of 7.615. Small union snippets compile correctly, so it needs the shape of these
functions. A bit cast through pointers (`*(uint32_t *)&f`) compiles correctly and gives bit-exact results.
**T3.11 must change fxmath.h (or avoid the union) before any SHARC build.** The remaining differences after
the workaround are at float rounding level (selcc's libsel division and conversions are not always correctly
rounded; native division is): the selcc builds behave like the native ones. selcc's code costs 44,500
instructions per block for the tape delay and 102,000 for the compressor in the interpreter (T3.11's static
counts: 59k and 137k, "probably high").

**2026-10-06 (T3.11 section 11):** `fx/fxmath.h` now uses the pointer casts (commit `b40a4c6`), so
`fxcheck.py` builds from `fx/` directly. `fxcheck.py` gained `--set`, `--at` (knob moves), `--profile`
and `--annotate` (selcc's assembly with executions per line per block), and builds the native library
with `-fno-strict-aliasing`. The T3.11 effects were restructured for selcc: **tape delay 18,566 and
compressor 47,718 instructions per block** in the default runs (from 44,473 and 102,301), with the same
SHARC-vs-native figures as above (-166.5 dB and -122.7 dB, the same bit-identical sample counts)
[verified]. A second selcc bug turned up: **a local initialised with a comparison is re-evaluated at
every use with the operands' current values** (`const int on = a != 0.0f;` then `a` changes: `on`
follows it); `int`/`float` initialisers are fine. Repro and workaround in notes/T3.11 section 11.3.

## 4. What renders

### 4.1 The four stock effects, one call per 32-sample block

`tools/sharcvm/fx.py` calls each effect the way the FX bus does (T3.4 section 2): R4 = state, R8 = parameter
struct, R12 = the I/O descriptor at 0x257e6c (block length 32, a pointer to the input pointer array, the
output pair, the tempo at +0x14 which the delay reads). The state comes from running the effect init
0x1c1445 once (326M instructions, 14 s, cached as `out/T3.6/state/dn2-fxinit.*`).
`tools/sharcvm/render_fx.py` renders a test signal or a WAV file:

```
python3 tools/sharcvm/render_fx.py delay  --set TIME=0.252 FDBK=0.4        # also chorus, reverb
python3 tools/sharcvm/render_fx.py comp   --set SCF=0.5 THR=0.5 RAT=0.4286 # 4:1 at -30 dB
python3 tools/sharcvm/render_fx.py reverb --in my.wav --seconds 10         # 48 kHz WAV in
```

Parameters are the floats the DSP sees (knob/127 for most; delay WID and FDBK are value x 2^-15, so FDBK 0.5
is about knob 64; the compressor's RAT is index/7 and SCF 0.5 is the neutral side-chain filter).

**2026-10-06 (T3.11 section 10):** `--knob NAME=V` takes raw knob values and converts them as the DSP
does (`tools/sharcvm/stockmap.py`), `--preroll S` settles the effect on silence first (the stock delay
glides to a new TIME over about a second, so a render that sets TIME at block 0 has misplaced echoes
for that long), `--mix send --vol V` writes dry + V/127 x wet, `--key FILE` feeds the compressor's side
chain (`FxRunner` now has separate side-chain buffers; without a key it copies the input, as before).
`render_file()` does the same from Python. The defaults were WID 0.0 (screen -64, which with X off
halves the left echo and with X on bounces) and SCF 0.0 (a side-chain low-pass below 20 Hz, so the
compressor hardly reacts to mids and highs); they are now WID 0.5 (screen 0) and SCF 64/127 (neutral).
The renders in the table below were made with the old defaults. Measured behaviour of all four knob
sets (time law, feedback gain FDBK/64, filter corners, WID, ATK/REL tables, MUP, SCF corners): T3.11
section 10.1. Outputs in
`out/T3.6/wav/` (24-bit, 48 kHz, not normalised), each with the `_input.wav` it was fed:

| file | effect, settings | instructions/block | speed **[verified]** |
|---|---|---:|---|
| `delay_default.wav` | delay, TIME 32/127, FDBK 0.4, LPF open | 5,424 | 8.1x real time |
| `chorus_default.wav` | chorus, DPTH 0.5, SPD 0.3, WDTH 0.7 | 14,457 | 3.5x |
| `reverb_default.wav` | reverb, PRE 0.1, DEC 0.6, FREQ/GAIN 0.5, LPF open | 14,563 | 3.3x |
| `comp_thr-30_4to1.wav` | compressor, THR -30 dB, 4:1, SCF neutral | 16,560 | 2.9x |

The test signal (`render_fx.test_signal`): plucked tones on L and R at 0, 0.25 and 0.5 s, a noise burst at

### 4.2 The whole DSP block handler

`tools/sharcvm/fullblock.py` does T3.2 section 3.5 (b): per block it writes a ColdFire frame (command 3, the
global FX/mixer words of T3.3/T3.4 by name, `knob << 8`) into the SPI receive buffer, writes the codec input
as interleaved Q31 into the SPORT4B buffer of the current DMA half, calls the block handler 0x1c9d6b and reads
the 32 + 32 floats at 0x268438. `tools/sharcvm/render_full.py` renders the test signal through IN L/R with
sends to the delay and reverb:

```
python3 tools/sharcvm/render_full.py --seconds 4 --set IN_L=40 IN_R=40 IN_REV_L=80 REV_DEC=90 ...
```

- **It runs [verified]:** 320,300 instructions per block with no voices playing (the handler's own EMUCLK
  measurement, which it writes into word 0 of the frame sent back to the ColdFire, says 320,236: the
  interpreter's EMUCLK counts instructions). `out/T3.6/wav/fullchain_in_rev_del.wav` has the dry signal,
  delay echoes and the reverb tail; an input impulse comes out 7 samples later with an alternating-sign
  ringing tail and a hard ceiling of 0.693, which fits the oversampled soft clipper T3.4 saw in the master
  overdrive. **[inferred]** for that reading.
- Pans are bipolar with 64 = centre (0 sends IN L hard left). The frame image is used one block late (T3.4).
- Speed: 0.19x real time (4 s of audio in 21 s), 92.6M instructions/s. Tempo word 0xd8 = 120 x BPM (T3.3).
- Not done: voices. Notes would need the per-track part of the frame (T3.3). `main` has no other
  DSP-algorithm init than 0x1c1445 (section 6, item 7), so the voice set-up comes from the frame.

### 4.3 Where one block's instructions go (for G6 and G10)

`tools/sharcvm/tests/block_profile.py` stops the block handler at the render's stage call sites (T3.4
section 2; return addresses from the pushed constants) and counts instructions between them, 30 blocks,
input through the delay/reverb/chorus sends, **no voices triggered** **[verified]** for the counts:

| stage | instructions/block | share |
|---|---:|---:|
| voices 0x1c8ef1 (16 slots, none triggered) | 222,005 | 69.3% |
| compressor 0xb8541d | 16,591 | 5.2% |
| render tail (frame image copy, 672 words) | 14,595 | 4.6% |
| reverb 0xb836bc | 14,566 | 4.5% |
| chorus 0xb84d5c | 14,396 | 4.5% |
| FX bus (16 rows x 3 sends, cross-sends, returns) | 10,194 | 3.2% |
| render: frame copy and unpack | 8,897 | 2.8% |
| master without the compressor (routing sums, overdrive chain, volume) | 12,568 | 3.9% |
| delay 0xb8482c | 5,427 | 1.7% |
| handler before/after the render | 1,108 | 0.3% |
| **total** | **320,352** | |

- **Idle voices dominate:** about 13,900 instructions per slot per block even with no note playing. By
  function (exclusive counts, profile mode): 0x1c3911 53.5k, 0x1c37b4 38.3k, 0x1c54c7 23.1k, 0x1c36ed 22.3k,
  0x1c8ef1 15.5k, 0xb826c8 15.8k per block. So for G10 (32 voices) the per-slot cost, not the effects, sets
  the limit, and the first saving may be skipping silent slots. Caveat: here the voice state is only what the
  image and 0x1c1445 set up and the per-voice frame slots are zero; the unit's idle path may differ
  **[inferred]**.
- The effects total about 51,000 instructions per block, consistent with T3.4's static ~61,000 ("probably high").
- At an assumed 1 GHz core (666,667 cycles per block, T3.4), the 320k instructions would be about 48% before
  stalls and DDR latency, which this interpreter does not model. The handler's own EMUCLK measurement on the
  unit (word 0 of every DSP-to-ColdFire frame, T3.2) is the real number to compare with (T4.1).

## 5. Speed

Apple M2 Pro, one core, `cc -O2 -mno-outline`. **[verified]**

| workload | instructions/block | M instructions/s | real-time factor |
|---|---:|---:|---:|
| stock delay | 5,424 | 77 | 8.1x |
| stock chorus | 14,457 | 82 | 3.5x |
| stock reverb | 14,563 | 78 | 3.3x |
| stock compressor | 16,560 | 77 | 2.9x |
| whole block handler (no voices) | 320,300 | 93 | 0.19x (1 s of audio in 5.2 s) |
| effect init 0x1c1445 (once) | 326.8M in total | 23 | 14 s, cached afterwards |
| selache C suite (8 workers) | 112M in total | | 8 s wall |

Compared with T3.2's estimate for digikit's sharcemu (~2.7k instructions/s today, ~49k after its fix), this is
about 30,000x faster. Where the time goes: two fast paths (single-slot computes, and an unconditional SISD
normal-word access to byte-space memory) cover most of the dynamic mix (single loads/stores are 45% of the
full block, float multiply/add most of the rest); both are checked to give bit-identical results to the
generic path (`selftest.py` check 8, and the four renders compared byte for byte). What remains is dispatch
and the generic SIMD memory path. Real time for the whole program would need about 480M instructions/s (5x
more): a direct-threaded dispatch with handlers specialised at translation time is the next step if that
is ever needed; offline renders do not need it.

Dynamic mix of the whole block (profile mode, `vm.profile_report`): forms 3a 19%, 2a 15%, 4a 10%,
2a_short 9.5%, 5a 7.6%, 15b 6.8%, 6b 6.7%; operations: NW loads 13% and stores 10% without compute, FMUL 8%,
FADD 7%, FMUL with a parallel load 5%, FEXT 4.6%.

## 6. Decode cross-check, coverage and what is blocking

- **Decode vs sharcdb:** translating every aligned instruction of the main program (`coverage.py`): 51,886 of
  51,901 (99.97%) translate; the exact-PC decoder picks a different form from sharcdb at 5 PCs (the 2b/2c
  case, section 2.2). Of the 17,015 instructions the Audio Task reaches (sharcdb reach), 5 would trap, all in
  two spots digikit itself marks as decode gaps (0x1c0e1b, 0x1c4f4c: probably data). None was hit in any run.
  Over the whole program the rest are three bit-FIFO shift-immediates, two 20a cache-lock options and other
  decode gaps. Output: `out/T3.6/coverage/static*.tsv`. **[verified]**
- **Compute semantics vs digikit's tracer** (`tests/xcheck_compute.py`): all 3,857 distinct compute fields of the
  DN2 code, 20 random register states each: 70,112 results agree bit for bit; the only differences are inputs
  that are denormal/NaN/inf bit patterns and denormal products (the PGR has the SHARC flush them, digikit uses
  IEEE behaviour) and FLOAT, which the PGR rounds to 40 bits (1 ulp). digikit does not model 134 cases (MR
  moves, bit FIFO, a few float ops). **[verified]**

**Open / blocking:**
1. **Voices.** The block handler runs, but no notes play: they need the per-track part of the frame (T3.3:
   0x92-byte slots at 0xda). Real frames could come from the
   ColdFire emulator (T3.3's `scripts/t33_frame.py` saves the TX buffer), but its EMAC fractional mode is not
   emulated, so smoothed frame values come out at about 1/34 (T3.3 "Emulator caveat"). Fixing that in digikit
   would make offline renders of the whole unit possible (stage 3 without real time).
2. **Not documented, inferred from the code** (section 2.2): Type 7 bit 23 = short-word scaling, the SIMD rules
   for registers without a complement and for sub-word accesses, byte-exact misaligned accesses. All fit
   every use found, but a unit measurement (T3.5/T3.7) is the only real check.
3. **RECIPS/RSQRTS seed tables** are not documented: 8 of 2,000 quotients of the DN2 divide differ by 1 ulp,
   probably from this. Effect on audio: nil at the 1-ulp level.
4. **Odd-address short stores** in the voice code (0x1c57a1, on uninitialised voice state): unexplained;
   allowed (byte-exact) in the full-block runner and counted.
5. **Not modelled:** interrupts, RTI, the bit FIFO, PX long-word transfers, bit-reverse, 64-bit float ops,
   circular-buffer wraps (trap: the L unit in byte space is unverified), cycle timing (EMUCLK counts
   instructions; stalls and DDR latency are not modelled, so it is not the unit's cycle count).
6. **selcc bugs for T3.11:** union punning in `fx_exp2`/`fx_log2` (section 3.4, worked around in
   `b40a4c6`), and comparison initialisers re-evaluated at every use (2026-10-06, T3.11 section 11.3).
   Later on 2026-10-06 (T3.11 section 12.7) two more: a static const table indexed by a fresh integer
   can read a wild address (the index register is reused for a float constant), and in
   `float a = X, b = a;` the store of `a` is dropped. Both worked around; `fxcheck.py` now also runs the
   flanger (`--fx flanger`). selcc emits no immediate-count shifts (the selas encoding hazard).
7. **Booting from reset** (entry 0x1c12e2, `vm.pc = 0x1c12e2; vm.run(...)`): runs the reset code, the C
   runtime (48-bit PX read of the init table `PM(0xe00e0)`, ACONV B2W/W2B around the second constructor list,
   which sits at 0x10000000, outside the known memory map; a zero page is mapped there for this) and `main`'s
   board, PCG and GPIO set-up: 561.7M instructions in 15 s, most of it a 16.7M-pass delay loop in the PCG
   driver. The GPIO/PINT init stores through a NULL pointer (0x1ca70c passes `R12 = M5 = 0` as an out pointer
   to 0xb8cabb, which writes it): absorbed by a zero page at 0 for the experiment. It stops in the SPORT driver
   set-up (null-pointer chase at 0x1cce1e after reading SPORT4 registers 0x310024xx), which needs a peripheral
   model. Not needed for rendering: T3.2's start-up table shows 0x1c1445 is the only DSP-algorithm init in
   `main`, and the renders run it. **[verified]** up to that point.
