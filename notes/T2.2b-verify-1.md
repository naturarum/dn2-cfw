## Verdict: holds, with corrections

- **The analysis holds.** These parts are right in the bytes:
  - the arp's place in the voice interrupt and its 1/60-step self clock;
  - the three UI gates;
  - the classification of the seven named mask readers;
  - the engine barrier (sequencer split, live-key routing);
  - the MIDI-out path through the interrupt's per-pass list and the MIDI task;
  - the tables and the cave sizes.
- **The design has one real defect in the shared sink**, so options 1–3 are not correct as
  sketched:
  - The sink always takes the note-off base `[0xc]` from the time bucket.
  - The first note of a live arp started while the sequencer is stopped is in a "now" bucket. Its
    time word is never written, so it holds a stale time.
  - That note's MIDI off is then booked at a stale base. It is sent at once (a blip), or, after a
    wrap, up to about 2^31 clock units late (a hanging note).
  - Fix: the clock `0x80005398` when bucket `[0]` ≠ 0, as the interrupt itself does at `0x400268e2`
    and `0x400268b0`.
- **Option 3 is not workable as written:**
  - its restore-skip hook targets `0x4012b06a`, which is the "send every base value" path, not
    "nothing to restore";
  - its double build runs the trig-condition evaluator `FUN_401369cc` twice per step.
- **Several smaller statements are wrong or overstated:**
  - `0x400265d2` is track-relations cloning, not voice-mask bookkeeping;
  - arp notes do add message posts;
  - one-period INF notes overlap the next note for 11 of the 23 speeds;
  - `FUN_4012a6e8` on an empty pool also writes to addresses 0, 4 and `0x5c`.
- Open problem 3 (which events post the flush on stop) is resolved below (5).

## 2. Claims refuted or corrected

### 2.1 Option 3's restore hook targets the wrong path [verified bytes]
- **Claim** (4.8, open problem 4): a hook at `0x4012b016` returns to `0x4012b06a` ("nothing to
  restore") for marked events.
- **Wrong.** `0x4012b06a` is reached when the per-track word `0x446173c8+4t` is **0**. The word is
  a pointer to the track's MIDI config, not a flag:
  - `FUN_4012a2ec` writes it (`0x4012a314`);
  - `FUN_4012a516`, `FUN_4012a5b8` and a kit change (`0x4012ad0c`) clear it;
  - the restore loop reads through it (`0x4012b14c`).
- The path at `0x4012b06a`–`0x4012b13c` does three things:
  - it reloads the config (`FUN_4012a2ec`);
  - it clears the lock count (`0x4012b090`);
  - it loops `d3 = 26..48` and **sends the base value of every unlocked parameter**
    (`FUN_4012ab2a`/`FUN_4012ab7a` for 26–28, `FUN_4012a814` for the rest).
- Jumping there for every arp note would send up to 23 parameter messages per note. That floods
  MIDI out and the 8-bit output count.
- **Correct target:** `0x4012b1f0`. It is the common continuation after the restore loop
  (`0x4012b198` → `0x4012b1ec` → `0x4012b1f0`) and after the full dump (`0x4012b13c`). Jumping there
  skips the restore and keeps the lock count `0x466768b8+208t` for the next real trig.
- **The other half of the claim holds** [verified]: the restore loop is entered at
  `0x4012b016`/`0x4012b01a` when the word is non-zero. It sends the base values of the parameters
  the previous event locked, `0x466768bc+208t`, count `0x466768b8+208t`. It then clears the count
  at `0x4012b1ec`.

### 2.2 "Arp notes add no queue messages" (3.5, "by design")
- **Overstated.** A pass posts message 1 only when its list is non-empty (`0x40026f26`).
- A pass posts message 3 whenever the earliest booked off is due (`0x400260ac`–`0x400260e4`). It
  posts again every pass until the MIDI task has sent that off.
- So arp notes add message-1 posts in passes that would otherwise post none, and their offs add
  message-3 posts. [verified bytes]
- The worst case stays at about two posts per pass, as in stock. The 32-slot ring is still
  unchecked [inferred].

### 2.3 "Each INF note ends as the next tick fires, before the next note-on" (4.4, 4.3)
- **True only for the 12 exact speeds.**
- For the other 11, `speed_len` is longer than one period, by up to 450,000 half units (1/6 step,
  speed 4) [verified, recomputed]. The note-off then comes after the next note-on:
  - a different pitch overlaps;
  - the same pitch is handled cleanly by the MIDI task's retrigger: old off cancelled, `9n kk 00`,
    new note-on [verified (C)].
- No note hangs, but the claim as written is false.

### 2.4 `0x400265d2` is track relations, not "allowed-voice mask … can release internal voices" (4.6, open 5)
- `kit+0x5ce0+2t` is the "WILL TRIGGER" mask of `TrackRelationsMenuView`, strings `"%s WILL
  TRIGGER..."` and `"%s CHOKES..."`. Its accessors are `FUN_400315dc`/`FUN_4003153c`/
  `FUN_40031620`/`FUN_4003167e` at index `0x2e70` [verified (C)].
- For each bit, the code calls `0x400255b4(ev, track)` [verified bytes `0x400255b4`–`0x40025610`].
  That function:
  - **copies the note event**;
  - sets `[4]` to the other track and `[0x17]` to the source track;
  - sets flag `0x20000`;
  - links the copy after the current event.
- It releases no voices. The risk is real but different:
  - a note on an arp-on MIDI track (live, or sequenced in option 2) now triggers that track's
    related tracks;
  - each arp copy re-enters the note-on branch from the top and also goes through this code
    [verified flow].

### 2.5 `FUN_4012a6e8` on an empty pool "reads address 0x5c" (3.5, key finding)
- **Understated.** With head = 0 it loads the new head from `[0x5c]`, then **writes 0 to
  addresses `0x4`, `0x0` and `0x5c`** (`0x4012a700`–`0x4012a706`) [verified bytes].
- The sink's guard is right, and the harness confirms it leaves low memory untouched (S4).

### 2.6 Open problem 3 is resolvable statically
- Message 4 (flush both off lists) is posted only by `FUN_4012a716`. That function sets
  `0x446014a4 = 1`, which makes the MIDI task drop `[0xd] = 1` events until message 4 clears it.
- Its callers are `FUN_400d854e`, `FUN_400d929c` (transport stop) and `FUN_400d97ca`.
- The same three functions call `FUN_40025594`, which calls `FUN_40029c72` (`0x4002559e`).
  `FUN_40029c72` **clears every track's held set and expiry list**.
- So on stop an arp on a MIDI track stops, and its sounding MIDI notes are flushed.
- [verified bytes `0x40025594`–`0x400255ae`; callers verified (C)]

### 2.7 Small corrections
- The live note-on's length is not "infinite" by default. `FUN_40121db2` passes the caller's
  length, or the track default `+0x481` when the caller's length is negative (`0x40122022`–
  `0x40122038`). `FUN_4013801c` uses `0x7f` only when that is still negative [verified].
  - The arp is unaffected: source 2 has no expiry.
  - But a plain live note that reaches the sink (race: arp switched off before the interrupt runs)
    gets a finite length. That length is booked on the stale base of 3.1.

## 3. Missed by the report

### 3.1 The sink books the first live-arp note's off on a stale time (options 1–3) — defect
- **Mechanism** [verified bytes, and run: harness S7]:
  - Live keys are posted by `FUN_4013801c` → `FUN_40138f16`. That function puts them in a "now"
    bucket: `[0] = 1`, `[2]`/`[3]` = the event (`0x40138f44`–`0x40138f6a`). It **never writes the
    bucket's time word `+4`**.
  - `FUN_40138b50`, which hands out buckets from a LIFO free list (`FUN_40138d64`), clears `+0`,
    `+8`, `+0xc` and `+0x10`, but **not `+4`** (`0x40138b6e`–`0x40138b78`).
  - So a "now" bucket's time is whatever the last timed bucket held.
  - The interrupt knows this. For a "now" bucket it uses the clock `0x80005398` instead of the
    bucket time (`0x400268e2`, `0x400268b0`).
  - Stock never puts a type-3 event in a "now" bucket. Stock live MIDI notes (`FUN_4012bb90`) set
    `[0xc]` = the clock.
- **Where it bites:**
  - A live key on an arp-on MIDI track while the sequencer is stopped starts a new generation.
  - Its own event is played at once as the first arp note (`0x40026868`–`0x400268da`), inside the
    "now" bucket.
  - `cave_sink` copies `bucket+4` into `[0xc]` (`arp_midi_v2.s`, `move.l %a0@(4),%a3@(48)`).
  - The MIDI task then books the off at stale + `2·len` (`0x4012b546`).
- **Effect** [inferred]:
  - Usually the stale time is older than `2·len`. The off is due at once and is sent at the next
    pass's poll, so the first note lasts about one pass plus task latency: a blip.
  - If the unit has been idle for more than 2^31 clock units, the stale time wraps and looks like
    the future, so the note can sound until that pitch is played again or the time comes round.
    2^31 units is about 2^31/(360,000·BPM) s, so ≈ 50 s at 120 BPM, assuming the interrupt runs
    about 1,500 passes per second; that figure is inferred from 187.5 passes per step at 120 BPM.
  - Later arp notes come from type-9 ticks in timed buckets and are correct.
- **Fix:** in `cave_sink`, `[0xc]` = bucket `[0]` ≠ 0 ? `[0x80005398]` : bucket `[1]` (+4 bytes,
  same pattern as `0x400268e2`–`0x400268f2`).
- The same base is used for a plain live note that reaches the sink because of a race (2.7).

### 3.2 Option 3's double build evaluates trig conditions twice [verified (C); effect inferred]
- `FUN_400d8cbe` and `FUN_400d87b8` both run the probability draw `FUN_40136984` (shared PRNG
  `0x402a12fc`/`0x402a1300`) and the condition evaluator `FUN_401369cc`. Call sites:
  `0x400d8dbc`/`0x400d8dd2` and `0x400d88b6`/`0x400d88cc`.
- In `FUN_400d99de` both are called with no static event, so `FUN_401369cc` writes the per-track
  condition state `0x4463fc89[t]`/`0x4463fc79[t]`.
- Building both events for one step therefore causes three problems:
  - two independent probability draws, so the lock-only MIDI event and the arp trigger can
    disagree;
  - PRE/NEI-style conditions, which read `0x4463fc89[t]` or `[t−1]`, see the first evaluation's
    result for the same step;
  - the PRNG sequence shifts for every track.
- Option 3 needs one decision per step, reused for both events.

### 3.3 The sink's MIDI-event use raises the empty-pool risk for stock code [verified callers; risk inferred]
- The sink checks the pool, but the four stock users of `FUN_4012a6e8` do not:
  - interrupt types 2 and 5;
  - the sequencer's `FUN_400d8cbe` (writes `puVar6[1]` at once);
  - `FUN_4012bb90`.
- On an empty pool they write to addresses 0, 4 and `0x5c` (2.5).
- With 16 arp-on MIDI tracks, the sink can take up to 16 of the 64 events in one pass.
- The sink should keep a reserve, for example by refusing when fewer than about 16 events would be
  left. Testing `head`, `[head+0x5c]`, … a few links deep is cheap.

### 3.4 The sink converts every note the interrupt plays on a MIDI track [inferred; test]
- `cave_sink` fires on any note-on that reaches `0x400269e6` for a track in `0x8000537c`. That
  includes plain notes, not only arp copies.
- Track-relation clones ("WILL TRIGGER", 2.4) from a synth track to a MIDI track would also become
  MIDI notes. In stock they would go to the voice allocator for the MIDI track.
- Whether the relations UI allows a MIDI target was not checked. `TrackRelationsMenuView` has no
  `isMidiTrack` reference in `calls.tsv`.
- Add to U2/U3.

### 3.5 Option 1: live arp notes revert a sequenced trig's MIDI p-locks [verified flow; inferred effect]
- In option 1 the same MIDI track keeps stock MIDI trigs with locks. Its lock count
  `0x466768b8+208t` is then non-zero.
- The next sink event (no lock list) enters the restore loop (`0x4012b016` → `0x4012b140`) and
  sends the base values.
- This is the same rule stock applies to a live MIDI note, but an arp makes it happen every few
  milliseconds. Each restore also costs output bytes in that message.
- Worth stating in U2.

### 3.6 Minor
- The interrupt's range check uses the synth-side transpose before the sink is reached
  (`0x80005381[t]`, global `0x80005380`, `0x40026980`–`0x400269aa`). The MIDI task applies its own
  transpose (`0x4461823c+4t`, `0x44618238`). A note in range for one but not the other is dropped
  or clipped [verified flow; whether the two transposes differ on a MIDI track: inferred].
- `FUN_4013801c` applies the mono-priority logic when `sound+0x146 ≥ 2` [verified (C)]. With
  `cave_liveon`/`cave_liveoff` it now reads that field from a MIDI track's record, which normally
  holds no synth voice mode. This is untested.
