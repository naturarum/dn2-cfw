# T1.4 verification 2: flash writers, Digitone II OS 1.12

Independent check of `notes/T1.4-flash-writers.md`. I tried to refute it: for each writer,
re-derive the flash range it can reach from the code and look for a way into the bootstrap
(0x40000-0x80000) or the updater, and check the claimed layout against the bootstrap's own
flash reads.

Method: static only, no emulator, no hardware. I used the decompile dump (`out/decomp/`),
`m68k-elf-objdump -m m68k:cfv4e` on the raw sections, and raw-byte scans. The new scanner is
`scripts/t1.4_verify_scan.py`; its output is in `out/T1.4-verify-2/` (`cmds.txt`,
`dspi0.txt`, `updater_refs.txt`, `wrap.txt`). The updater (section 4) has no dump, so I
disassembled `ele3_out/03_type4.bin` at base 0x80000400.
Marks: **[verified]** = checked against the bytes or a run; **[inferred]** = reasoned.

---

## 1. Verdict: holds, with corrections

The headline survives. A modified **main OS** sent through the normal in-OS upgrade
(Transfer over USB, or SysEx) does not erase or write 0x0-0x80000 in practice.
**But the main reason the report gives is wrong.** It says "the loop only ever increments
from a hard-coded 0x80000, so it cannot reach below 0x80000". The SPI address is 24-bit,
though, so an address that keeps increasing wraps from 0xFFFFFF back to 0x000000. Nothing in
the code limits the length. What actually keeps the writes away from 0x0-0x80000 is:

1. the length is covered by the checksum and HMAC (but a modder signs their own builds, so
   this check does not protect against the modder's own mistakes),
2. the in-OS receive buffer holds only **2 MiB**, so a wrapping length (over 15.5 MB) can
   never be received intact, and
3. on the Spansion 256 KB-sector part only, the bootstrap DYB-protects sectors 0x0 and
   0x40000 at every boot.

Other corrections:

- The factory-console gate works differently from what the report describes.
- The list of driver primitives is incomplete.
- The "correction to elekloader DEVICES.md" is a misreading.
- The report missed some hazards that matter for modding: the 2 MiB container ceiling, no
  read-back check, and the extra bootstrap-side triggers.

## 2. Confirmed

- **One flash bus, DSPI0.** I scanned every 32-bit word 0xFC05C0xx in the main OS. All of
  them are inside these places:
  - the driver, 0x40134a28-0x40136000;
  - DSPI0 init at 0x400ced92/0x400ced9e (CTAR0 and MCR only);
  - the crash handler FUN_400f19b4, which only polls RDSR 0x05 (0x80020005).

  No other address form (0xFC05xxxx) points at DSPI0. [verified, `dspi0.txt`]
- **No chip erase.** I looked for every PUSHR command word (0x8402_00XX, 0x0802_00XX,
  0x8002_00XX) loaded as an immediate into *any* data register, in the main OS, the
  bootstrap and the updater. None of them is 0xC7 or 0x60, in any frame form. [verified,
  `cmds.txt`] (The report's own scan matched only `move.l #imm,d0`, which is why it missed
  three opcodes; see §3.4.)
- **Exactly one in-OS writer.** FUN_40139104's only reference is `jsr` at 0x4010921c in
  FUN_40109144, and FUN_40109144's only reference is from FUN_401094e8. [verified, raw scan]
  At 0x40139114 it calls the validator 0x400dbdb0 and branches away at 0x40139120 unless the
  result is 1. The erase base is `movea.l #0x80000,a3` (0x4013912e) and the program base is
  `moveq #8,d6; swap d6` (0x40139172). [verified]
- **Every primitive caller is accounted for.** Raw direct and word32 references, which cover
  vtables and pointer tables:

  | primitive | referenced only from |
  |---|---|
  | erase 0x401357ce | 0x40136122, 0x40139104 |
  | erase 0x40135850 | 0x4013618c |
  | program 0x401354d6 | 0x401360a6 |
  | DYB write 0x40135f80 | console FUN_400cd5f2 |
  | PPB 0x40135ca6/0x40135dc8 | the six cluster-C functions |
  | WREN 0x40134a28 | other primitives only |

  So clusters A-D are the complete set of NOR modifiers in the main OS. [verified]
- **The bootstrap lives at 0x40000.** The self-upgrade FUN_80001c48 does three things:
  1. DYB 0xFF at 0x40000 (0x8000206a),
  2. erases the 0x40000 region (0x80002076),
  3. programs from 0x40000 (0x800020ce).

  Before writing it checks: packed ≤ 0x10000, CRC-32 residue 0xDEBB20E3, version word
  matches, unpacked < 0xF001. [verified] Flash 0x40000 holds unpacked section 2 from byte 0,
  so flash 0x40000 corresponds to SRAM 0x800003FC. [verified from the programming source
  0x40410000+i]
- **Console task creation.** The console task FUN_400cebd2 is created in exactly one place,
  0x400cf206, behind `moveq #32; and.l 0x40287a60; beq` at 0x400cf1ea. FUN_400cd5f2 is
  referenced only by FUN_400cebd2 (0x400cebf8). 0x40287a60 is the boot-flags argument,
  stored at 0x400004ec. [verified] (§3.3 covers who sets bit 5.)
- **Cluster C addresses** are 0x380000 and 0x3c0000, as `move.l #imm` constants. Example:
  FUN_400cccc6 at 0x400cccdc, 0x400ccd1e and 0x400ccd58, with the final PPB program of
  0x380000 via `moveq #56; swap` at 0x400ccd82. All of these writers are reached only through
  the console. [verified]
- **Cluster D addresses** come from the table at 0x401ffafc, which holds 0x400000, 0x800000
  and 0xc00000. Each one is erased with a single FUN_40136122 call (256 KB in total), and only
  when the 4 bytes read there are "COKi". [verified]
- **The updater (section 4) sits inside the container.** Bootstrap FUN_80007a00 (run from
  SRAM at 0x8000F100) looks up section type 4 in the table at 0x80020. It reads the section
  from `0x80000 + offset` to its load address and calls the entry vector. [verified] For
  stock 1.12 that is flash 0x198330-0x1A0338.
- **No embedded bootstrap copy.** None of the packed section 2 occurs in the main OS. Only
  3 of the unpacked 48-byte sample chunks occur there, and those are shared library code or
  tables (0x401368ea, 0x40290fd4, 0x4021bb23), not an image. [verified]

## 3. Refuted or corrected

### 3.1 "No code path writes below 0x40000" and "the loop only increments" (A, B, B′)

Every erase and program primitive sends address bits 23..0 only:

- FUN_40134a6a, 0x40134aa8-0x40134ace: `clr.w/swap/mvz.b`, then `lsr #8`, then the low byte;
- FUN_401354d6, 0x4013553c-0x4013556a;
- bootstrap FUN_8000237c and FUN_8000227e: the same pattern.

[verified]

On a 16 MiB part, address A+0x1000000 is therefore address A. None of the length-driven loops
limits the length:

- **A** (FUN_40139104). Count = ceil(len/blk), with len = the first word of the received blob.
  Erases start at 0x80000. This is the arithmetic, from `scripts/t1.4_verify_scan.py wrap`
  (`wrap.txt`), and it is the same for 256 KB and 64 KB blocks:

  | len | erase reaches |
  |---|---|
  | > 0x300000 | 0x380000 |
  | > 0xF80000 | wraps to 0x000000 |
  | > 0xFC0000 | 0x040000 |

  [verified]

  The validator FUN_400dbdb0 checks only the checksum (FUN_401226f8) and the HMAC
  (FUN_400d2bc4), and returns 1, 3 or 4. It checks neither length nor version. [verified]
  The HMAC check does not hold back a modder, who signs their own builds.
- **B, the console `#UPGRADE`** (0x400cd7e6-0x400cd92e):
  - erase count = (len+0x3ffff)>>18 calls to FUN_40136122 from 0x80000;
  - program count = (len+0x1ff)>>9 pages;
  - len = *(buf+0x20004), straight from the received header.

  The only checks are "ELE3" at buf+0x20008 and the word 0x34 at +0x2000c (or a numeric
  argument instead). There is **no checksum and no HMAC** on this path. [verified]
- **B′, `#FULL_UPGRADE`** (0x400cd81c-0x400cd8b8). It programs `*(buf+4) - 8` bytes from
  0x40000 in 0x200 steps. The only test is `> 0`; **nothing enforces the report's "≤ 60 KB"**.
  [verified]

  With a header word over 0x40008, it programs past 0x80000. With a word over 0xFC0008, it
  wraps onto 0x0. The received bootstrap part can be at most 0x20000 bytes, because the OS
  part lands at buf+0x20000, but the header word is never compared with it. [verified]

So the correct statements are:

- For A, the reachable range is [0x80000, 0x80000 + ceil(len/blk)·blk) mod 2^24.
- For B and B′, it is unbounded, constrained only by the header word.

A is held well away from 0x0-0x80000 by the 2 MiB buffer (§4.1). It is also held by the
boot-time DYB protection, on the Spansion 256 KB part only (§4.3).

### 3.2 Geometry: "erase block 0x40000 on the recognised part"

The probe FUN_40135a7c (and the bootstrap's copy, FUN_800024ec) recognises several parts:

| JEDEC | page | block | DYB/PPB code active |
|---|---|---|---|
| 0x01 0x2018 (Spansion 128 Mbit), byte 5 = 0 | 0x200 | 0x40000 | yes (`_DAT_4463fc64`/`_DAT_80007d04` = 1) |
| 0x01 0x2018, byte 5 = 1 | 0x100 | 0x10000 | no |
| 0x9d 0x6017/0x6018, 0xc2 0x2017/0x2018, 0xef 0x4014/0x4017/0x4018/0x7015, 0x1c 0x7015 | 0x100 | 0x10000 | no |

[verified]

FUN_40135f80 (DYB) and the bootstrap's FUN_80002742 do nothing unless the flag is set.
[verified] So the "must DYB-unprotect 0x40000 first" layer exists **only on the Spansion
256 KB-sector variant**. On every other part nothing in hardware protects 0x0 or 0x40000.
[verified] Which part this unit has is unknown. digikit's S25FL127S-class identification is
for the DT2. [inferred]

The accepted 8 MiB parts (0x2017/0x6017/0x4017) would make the slot 0x800000 alias 0x0
and 0xc00000 alias 0x400000. Cluster D only reads 4 bytes there looking for "COKi", so this
is harmless. [inferred]

### 3.3 The console gate

The report says the bootstrap sets bit 5 at 0x80000c42 "only after a UART handshake with the
panel succeeds (`pea 0x11; jsr 0x80001302`, then `or #0x20`)". That is wrong. Bit 5 has three
sources in FUN_800009c6. [verified, disassembly 0x80000b20-0x80000da8]

| site | condition |
|---|---|
| 0x80000b20-0x80000b3c | RCM RSR (0xEC090001) bit 5 set **and** RAM 0x48000000 == 0xB0B0DADA |
| 0x80000b8e-0x80000b9a | panel key-state read FUN_80001276 returns -1 (a UART receive in FUN_80000f50 fails) → `or #0x60` (bits 5 **and** 6) |
| 0x80000c26-0x80000c42 | no bootstrap self-upgrade this boot, and exactly the 5 keys in the table at 0x80005ed6 = {0x12,0x13,0x14,0x15,0x23} are held at power-on (FUN_8000136c) |

The `pea 0x11; jsr 0x80001302` at 0x80000c4a is on the other branch: it is the STARTUP-menu
key test that leads to FUN_80002dc4. A 3-key combo {0xb,0xe,0x26} sets bit 8 instead
(0x80000da8). [verified]

Meaning of each source:

- RSR bit 5 being the soft-reset flag is from the MCF5441x map. [inferred]
- The 0xB0B0DADA magic is written only by the console itself: `#REBOOT` at 0x400ce336 and
  `#REBOOT_INTO_MAINTENANCE_MODE` at 0x400ce39a. Each is followed by `move.b #0x80,0xEC090000`,
  a soft reset. [verified] Every other store to 0x48000000 writes 0: 0x40001a7a, 0x40005614,
  0x400f1786, 0x400f1e4c, 0x401391f8. [verified] Stock code therefore cannot enter console
  mode except from the console.
- The 0x60 path fires whenever the panel does not answer at power-on (a failed or unplugged
  UI board, or the factory testing a bare main board). [inferred] Bit 6 then has these
  effects:
  - the bootstrap runs the section-4 updater before the main OS (0x80000ee4-0x80000eee);
  - the main OS skips the COKi migration (0x400cf0f8);
  - the main OS parks its init task (0x400cf23c-0x400cf246).

  [verified]

So "no normal boot reaches it" is wrong: a boot where the panel does not answer reaches it,
and so does a held 5-key combination. The conclusion still stands, because no upgrade channel
sets bit 5. But the console is not a "panel handshake succeeded" mode.

### 3.4 Incomplete primitive list

The report lists 18 primitives. It missed these:

- **0x4013576c**: WREN plus 0x20, a 4 KB subsector erase. This is the only user of the 0x20
  branch. No references. [verified]
- **0x401358f2**: opcode 0x2B, a 2-byte read (ASPRD on Spansion). No references. [verified]
- **0x4013503e** (0x48 read), **0x4013517e** (WREN plus 0x42, program) and **0x401352b8**
  (WREN plus 0x44, erase). These are security-register/OTP operations with the address
  formed as (reg<<12)|offset. [verified] Ghidra never made them functions; they hold the 47
  DSPI0 words found outside any function. No direct or word32 references. [verified] They
  write OTP/security registers, not the main array. [inferred from the opcode values]
- 0x40134b58 (0x30) is a single-frame `0x08020030`, i.e. CLSR (clear status). It is not a
  "read flag" command. [verified frame; name inferred]

None of these changes the conclusion. But the report's "[verified]" opcode list was not
complete: its scanner only matched immediates loaded into d0.

### 3.5 Cluster C: "every one reached only from FUN_400cd5f2 / its #WRITE table"

- FUN_400ccda2 (UI-tested flag) has two direct callers, FUN_400cfef2 and FUN_400d032c.
  FUN_400cfef2 is a UITestView callback stored by FUN_400d06b6 (0x400d0712), which FUN_400d032c
  installs, and FUN_400d032c is called from the console. [verified]
- FUN_400cd036 has **no** reference at all. [verified]

Both still start at the console, so the conclusion holds. The wording is loose.

There is also a side effect the report does not state. When 0x380000 or 0x3c0000 is
PPB-protected, these writers call PPB erase 0x40135dc8 (0x0802_00E4). On S25FL-S that clears
the persistent protection of **every** sector, and the writer then re-protects only
0x380000/0x3c0000. [verified call; chip-wide effect inferred from S25FL-S semantics]

### 3.6 "Correction to elekloader DEVICES.md": refuted

DEVICES.md ("What writes the flash", lines 85-105) already says the DT2 factory console
"writes a container to 0x80000 or another image to 0x40000-0x80000". Its sentence "None of
them writes anything from the main OS image" means that no writer copies data out of the OS
image, i.e. there is no embedded bootstrap. It does not mean nothing can write the bootstrap.
DN2 matches that description, so no correction is needed. [verified, read the file]

### 3.7 Smaller points

- **Cluster D's "12.9 MB read overruns 16 MiB" (open problem).** This is resolvable. FUN_401353ae
  sends one READ (0x03) with a 24-bit start address and streams `len` bytes, so the part's
  address counter simply wraps. It is a read, and it runs only when "COKi" is present.
  [verified one command; wrap is part behaviour, inferred]
- **"len = the container header length."** It is the first word of a length/checksum prefix in
  front of the ELE3 container (blob at 0x4038bee0: [len][checksum][ELE3…]). The ELE3 header
  starts at +8. [verified FUN_40139104 programs from param_1+8]

## 4. Missed

### 4.1 The 2 MiB in-OS receive buffer (matters for every mod)

- FUN_40122574 returns the static buffer at 0x4038bec0. The container starts at 0x4038bee0.
- The next object referenced by code is at 0x4058bee0, a SysEx TX buffer used at 0x40000574.
  That gives exactly 0x200000 bytes for the container. No code references anything in
  between: 0x40400000 and 0x40490fdb are float constants. [verified] That this is the
  object's declared size is [inferred], since there is no symbol table.
- The SysEx decoder FUN_4012257c writes packet n to `0x4038bee0 + n*0x65` and never checks n
  against the buffer. The packet count comes from the sender as a 21-bit number. [verified]
- The stock 1.12 container is 0x1CC740 bytes (1,886,016; `ele3_out/image.bin`, ELE3 magic and
  HMAC trailer checked). [verified] That leaves **211,136 bytes of headroom**.

**Any build whose container exceeds 0x200000 bytes overruns RAM during an in-OS upgrade.**
This is a tighter limit than elekloader's DT2 `flash_limit` of 0x380000. The console path
receives at most 0x1E0000 bytes for the OS (`move.l #0x1e0000` at 0x400cd746, then FUN_4011f62e
into buf+0x20000), which leaves 80,064 bytes. [verified]

With a ≤ 2 MiB container, A erases at most 0x80000-0x280000 (`wrap.txt`). That is far from
0x380000 and from the wrap.

### 4.2 No error handling in the in-OS writer

FUN_40139104 ignores the return values of the erase (0x40139158) and the program (0x401391ba)
calls. It does no read-back and always prints "Success! Rebooting". [verified]

The erase calls FUN_401357ce directly, which does not need the geometry probe. FUN_401360a6,
by contrast, returns -1 without programming when the probe fails. So an unrecognised part
gets its container erased but not written. [verified] This is recoverable through the
STARTUP menu, which the user tested on 2026-10-05.

### 4.3 The boot-time DYB protection is the real hardware backstop

FUN_800009c6 calls FUN_80002742(0,0) at 0x80000a74 and FUN_80002742(0x40000,0) at 0x80000a7e:
a DYB write of 0x00, which means protect, for sectors 0x0 and 0x40000, on every boot.
[verified] This applies on the Spansion 256 KB part only (§3.2). Erase/program failures set
SR bits 5/6, which 0x401357ce reports as -1. [verified] The report says "DYB-protected" but
never shows where the protection comes from.

### 4.4 Indirect bootstrap rewrite through a written container

Each in-OS upgrade rewrites the section table at 0x80020. On the next boot, FUN_80001c48
compares section 2's table version (ushort at entry+0xc; 0x0201 at container offset 0x3c) with
the running 0x0201. If it is greater, the bootstrap re-flashes 0x40000 itself. [verified]

So a main-OS-only upgrade can trigger a bootstrap rewrite on the next boot, if the builder
changes section 2 or its table entry. The report's T1.7 list does not include this check.

### 4.5 The updater writes no flash

Section 4 contains a full copy of the NOR driver: erase 0x20/0xD8, program 0x02/0x12,
DYB/PPB, and security-register ops (`cmds.txt`). But none of its write, erase or protect
functions or wrappers has a direct or word32 reference: 0x8000467a, 0x800047b4, 0x800049d2,
0x80004b14, 0x80004c68, 0x80004cca, 0x80004d4c, 0x800051a2, 0x800052c4, 0x8000547c,
0x800055a2, 0x8000561e, 0x80005688 (`updater_refs.txt`). [verified for direct and word32
refs; computed calls inferred absent]

It reads only the container header (0x80003d18) and sections (0x800035a6). [verified] It runs
only on bit-6 (panel-failure) boots (§3.3).

### 4.6 What the bootstrap reads and writes (layout check)

| region | bootstrap reads | bootstrap writes |
|---|---|---|
| 0x000000 | never | DYB-protect at boot (0x80000a74) |
| 0x040000 | never | DYB-protect at boot; self-upgrade erase/program (FUN_80001c48) |
| 0x080000 | header 0x20 B (FUN_800053ec), table 0x80020+16n (FUN_80005462), sections 2/3/4/5 at 0x80000+offset | STARTUP-menu upgrade: ceil(len/256 KB) erases and pages from 0x80000 (FUN_80003c9c; checksum + HMAC; length unchecked like A) |
| 0x380000 | never | never |
| 0x3c0000 | 0x16 B serial record, CRC-32 (FUN_8000470c, shown as "SN: %.12s-%.2s" by FUN_80004942) | never |
| ≥ 0x400000 | never | never |

[verified]

This matches the report's layout, with one refinement:

- 0x380000 = 0x200-byte test/flag record (main OS only);
- 0x3c0000 = serial-number record (also read by the bootstrap).

The main OS also reads 0x80000/0x80020 itself (FUN_40134804, FUN_4013487a). [verified] The
bootstrap never reads 0x0-0x80000, so whatever loads it from 0x40000 into SRAM is outside the
bootstrap: the boot ROM or the stage at 0x0. [inferred] That stage is protected along with it.

## 5. Re-derived reachable ranges

| writer | address on the wire | bounded by code? | auth | gate |
|---|---|---|---|---|
| A in-OS FUN_40139104 | (0x80000 + k·blk) mod 2^24, k < ceil(len/blk); pages likewise | **no** | checksum + HMAC | user confirm (UI) or RPC |
| B console #UPGRADE | (0x80000 + k·0x40000) mod 2^24, k < (len+0x3ffff)>>18 | **no** (len = header word) | **none** (magic + 0x34) | bit 5 |
| B′ #FULL_UPGRADE | DYB 0xFF and erase 0x40000; program (0x40000 + k·0x200) mod 2^24 for header−8 bytes | **no** | **none** | bit 5 |
| C settings | 0x380000, 0x3c0000 (+ chip-wide PPB erase) | fixed | — | console |
| D COKi | 0x400000 / 0x800000 / 0xc00000, 256 KB each | fixed | magic | every boot without bit 6 |
| bootstrap self-upgrade | 0x40000, ≤ 0xF000 B | yes | CRC + version | section-2 table version > 0x0201 |
| bootstrap STARTUP upgrade | as A | **no** | checksum + HMAC | STARTUP menu |
| security-register ops 0x4013517e/0x401352b8 | OTP space | — | — | unreferenced |
| updater section 4 | — | — | — | write paths unreferenced |

Only B′ and the bootstrap self-upgrade target 0x40000 by design. A and B can get there only
by 24-bit wrap: a length > 0xF80000, which A's 2 MiB buffer prevents. On the Spansion 256 KB
part, the DYB protection stops any such wrap.

## 6. For the brick checker (T1.7)

Add these to the report's §6:

1. **Container length ≤ 0x200000 bytes** (in-OS buffer; ≤ 0x1E0000 if the console path
   matters). Never > 0x300000 (would erase the 0x380000/0x3c0000 records).
2. **Section 2 bytes and its table entry unchanged** (version 0x0201 at container 0x3c). This
   stops the next-boot bootstrap self-upgrade.
3. **Section 4 unchanged**. It runs on panel-failure boots.
4. **Static diff against stock**, all of which must hold:
   - no new direct or word32 reference to 0x40135f80, 0x40135ca6, 0x40135dc8, 0x401357ce,
     0x40135850, 0x4013576c, 0x40134a6a, 0x401354d6, 0x40135618, 0x401360a6, 0x40136122,
     0x4013618c, 0x4013517e or 0x401352b8;
   - no new 0x8402_00XX/0x0802_00XX immediates (`t1.4_verify_scan.py cmds`);
   - no 0xFC05C0xx words outside the sites in `dspi0.txt`;
   - no new 0xB0B0DADA store.
5. **Dynamic invariant on the wire address (mod 2^24), not on the C variable.** Every 0x20,
   0xD8, 0x02 or 0x12 address must fall in [0x80000, 0x380000), and nothing may issue 0xE1,
   0xE3 or 0xE4 during an emulated in-OS upgrade.
