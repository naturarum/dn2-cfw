## Design

The Digitone II core is `vendor/elekloader/mods/core-dn2` (new, uncommitted, branch `dn2-1.12`). It
is core-dt2 with the Digitone II's addresses, plus one file of its own:

| file | what |
|---|---|
| `mod.json` | id `core`, version 0.1, device `digitone-mk2`, OS 1.12; the defsyms and the 10 sites below |
| `../core/core.s`, `../core/settings.s`, `../core/fast.s` | shared with the Digitakt mk1, Digitone mk1 and Digitakt II cores, unchanged |
| `../core-dt2/personalize.s` | the Digitakt II's PERSONALIZE hook, unchanged: the Digitone II's builder ends with the same instructions |
| `midi.s` (new) | `ev_midi_step` and `ev_midi_note`, the Digitone II's own events |

It mirrors core-dt2 [verified: build, link map, disassembly of the linked blob]:

- **Install path.** The `.boot` code is appended to the main OS at its stock end `0x4030C980`. The
  OS entry's call at `0x40000538` (`jsr 0x400019b0`, the same instruction as on the Digitakt II)
  goes to `boot` instead. `boot` copies the run image to DDR, zeroes `.bss` and jumps to
  `0x400019b0`, whose `rts` returns to `0x4000053e`. This runs before the SRAM copies
  (`0x4000053e`), the DDR clear (`0x40000542`, which then wipes the appended blob) and before the
  caches go on (`0x40000554`), so the copied code can't be stale in a cache. `NO_DTIM0` is set as
  on the Digitakt II: DTIM0 stays stopped, as stock leaves it.
- **Where the code and data live.** The linker's DDR (`ddr` in the profile) is
  `0x47E00000-0x47F00000`, the top megabyte of T1.3's free DDR `0x46800000-0x47F00000`. It holds
  every format-2 mod's `.run`, the event tables and `.bss`. The rest (`0x46800000-0x47E00000`)
  stays in `areas['ddr']` for regions that mods claim, so no region can overlap the linker's
  memory (the linker does not check a region against `ddr`). `.fast` code goes to the SRAM tail
  `0x8000F980-0x80010000` (1,664 bytes), copied by `core_fastcopy` on the first `ev_tick`
  because the reset zeroes that tail after `boot` runs. The DDR clear ends at `0x466B84D0` and
  the boot stack never goes below `0x47FFFFCC` (T1.3), so neither touches `0x47E00000-0x47F00000`.
  [verified: T1.3's measurements; the link map: core alone uses `0x47E00000-0x47E002F8`, core +
  test mod `0x47E00000-0x47E00448`]
- **The hook bus.** The same tables as every core: each event is a zero-terminated list of handler
  pointers the linker builds from the mods' `subscribe` entries, called in `order`, with the C
  convention (d0-d1/a0-a1 scratch).

## Addresses (Digitone II OS 1.12)

### The Digitakt II core's sites, found again

`scripts/t19_sites.py` takes a window around each Digitakt II 1.17 address, masks every absolute
address and pc-relative displacement, and searches the Digitone II 1.12 main OS. Every one of the
17 addresses matched exactly once [verified]. `--verify` then compares each routine core calls as
a whole function (size from the DN2 Ghidra function table), addresses masked: all nine are
identical to the Digitakt II's [verified]. The code around every site is the same instruction
for instruction (objdump side by side).

| site / routine | DT2 1.17 | DN2 1.12 | stock bytes (DN2) | event |
|---|---|---|---|---|
| OS entry's call | `0x40000538` | `0x40000538` | `4eb9 400019b0` | `boot` (VBR_FN `0x400019b0`) |
| UI loop dirty check | `0x40032ad4` | `0x4002e464` | `4eb9 4011d5d4` | `ev_tick` |
| frame composition | `0x40032b3a` | `0x4002e4ca` | `4eb9 4011d60a` | `ev_draw` (DRAWALL `0x4011d60a`) |
| key dispatch | `0x40033d94` | `0x4002f20c` | `4eb9 4002c5c8` | `ev_key` (KEYDISP `0x4002c5c8`) |
| encoder dispatch | `0x40033dde` | `0x4002f256` | `4eb9 4002c55c` | `ev_enc` (ENCDISP `0x4002c55c`) |
| SETTINGS builder's end | `0x400a5eac` | `0x4009ff88` (in `FUN_4009fbe0`) | `2052 48780002` | `ev_settings` (SETTINGS_RET `0x4009ff8e`) |
| PERSONALIZE builder's end | `0x4009e2a2` | `0x400987a2` (in `FUN_40097eac`, `PersonalizeMenuView`) | `4cef 7c7c 0018` | `ev_personalize` |
| `operator new` | `0x4011ebd0` | `0x40120544` | | OP_NEW |
| `MenuItem` constructor | `0x40115a44` | `0x401173b8` | | ITEM_CTOR |
| `Menu::addItem` | `0x4011527a` | `0x40116bee` | | MENU_ADD |

| `Bitmap::fillRect` (examples) | `0x401131ae` | `0x40114b22` | | hello-marker-dn2 |

The tick callee `0x4011d5d4` is `movea.l 4(sp),a0; move.b 0x20(a0),d0; rts`, which `core_tick`
reproduces. In the PERSONALIZE builder `a5` = `Menu::addItem` and `fp` = the `MenuItem`
constructor, and `a4` holds the view (its vtable `0x401ea890` is `PersonalizeMenuView`'s), as on
the Digitakt II [verified]. The SETTINGS builder `FUN_4009fbe0` references MIDI CONFIG, SYSEX DUMP,
AUDIO ROUTING and PERSONALIZE [verified, string refs].

### The two MIDI events (new, Digitone II only)

| event | site | stock instructions | where | runs in |
|---|---|---|---|---|
| `ev_midi_step` | `0x400da0b2` | `2f02 4eba ec08` = `move.l d2,-(sp); jsr 0x400d8cbe(pc)` | the step handler `FUN_400d99de` (vector 121), MIDI-track branch | interrupt |
| `ev_midi_step` | `0x400d9230` | `2f02 4eba fa8a` = the same | the pending-step pass `FUN_400d907a`, MIDI-track branch | interrupt |
| `ev_midi_note` | `0x4012b490` | `727f c280 2841` = `moveq #127,d1; and.l d0,d1; movea.l d1,a4` | the MIDI task `FUN_4012ac88`, note loop | MIDI task (priority 8) |

- **`ev_midi_step`: `void f(void *vev, int track, int step, void *pattern, void *kit)`.** Called
  after the sequencer's MIDI event builder `FUN_400d8cbe` (T2.1 1.2, T2.2 3.1) returns a voice
  event for a MIDI-machine track's step. `vev` is the type-3 voice event; the MIDI event is the
  long at `vev + 0x18`, with the fields of T2.2 3.1 (track `+0x08`, note-on `+0x0c`, trig flags
  `+0x10` with bit 7 = play the notes, pool `+0x14`, chain head `+0x18`, inline note `+0x24..+0x29`,
  track data `+0x2c`, source `+0x34` = 1). Both call sites push the track last; the caller has
  pushed the builder's other six arguments. `core_midistep` calls the builder itself with all
  seven, runs the handlers when it returns a non-zero event, and returns with the replaced push
  left on the caller's stack (seven longs, as stock), d0 = the event, d2 unchanged. The
  instruction after the site sets the condition codes itself (`move.l d0,d5` at `0x400da0b8`;
  `lea 28(sp),sp` then `tst.l d0` at `0x400d9236`). [verified: the listing; run, below]
- **`ev_midi_note`: `void f(struct core_midi_note *n)`, `{int track, chan, note, vel, len; void
  *event;}`.** Called for each note of a MIDI event, after the task has added the transposes and
  filled in the default velocity and length, just before the range check. Here d0 = the note,
  `d5.b` = the length index, the velocity byte is at the task's `56(sp)`, d2 = the track, d7 = the
  channel, a2 = the MIDI event (T2.1 1.2, T2.2 3.3). `core_midinote` copies these into the struct,
  runs the handlers, writes back the note (d0), the velocity byte and `d5.b`, restores a0/a1/a2,
  and does the replaced instructions. Everything after uses the handler's values: the same-note
  retrigger off, the note-on, and the booked note-off (which stores `a4` = the note). A note set
  outside 0..127 is skipped by stock's own check (no note-on, no off booked). Live notes take the
  same loop (source `+0x34` = 2); their offs come from the key release through the off loop at
  `0x4012b624`, which this event does not see, so a mod that changes a live note's number must
  handle its off too.

Arguments for the first tier-1 mods [inferred]: the MIDI arp (T2.6) and more MIDI notes (T2.5)
both need "a MIDI-machine trig was built" (to tag, retime or replace it) and "a MIDI note is going
out" (to change, drop or follow it). The arp's own sites from T2.2-v2 4.1 (`0x400269e6`,
`0x40026d86`, `0x40121f2a`, `0x40121bcc`, `0x400da036-0x400da045`, `0x400d91bc-0x400d91c7`, UI
`0x4005f9c2`, `0x400187f6`, `0x40060dea`) stay that mod's: none overlaps a core site (the nearest,
`0x400da036-0x400da045` and `0x400d91bc-0x400d91c7`, end before `0x400da0b2` and `0x400d9230`).
[verified: address ranges]

## Why each change is safe

The question for each item is the one T1.4-T1.7 ask: can it touch the bootstrap's flash, the
STARTUP menu, or the boot path, and if it misbehaves, is the unit still recoverable.

- **Only the main OS changes.** The core is 10 code sites inside section 3 plus a blob appended at
  its end; sections 2, 4, 5, 7 and 8 are byte-identical (elekloader's verify and brick checks 2
  and 6) [verified, below]. The STARTUP menu and its OS UPGRADE receiver live in the bootstrap
  and read nothing from the stored OS (T1.5), so a core that hung at boot would still be
  recoverable over DIN MIDI as on 5 Oct [inferred from T1.5; check 9 re-runs it on each
  candidate].
- **No site is in a protected range.** The nearest are `0x400da0b2`/`0x400d9230` (below the panel
  updater `0x400DBA28`) and `0x4012b490` (below the NOR driver `0x40134A28`) [verified: brick check
  6, elekloader's `protected` check]. No site is in the in-OS upgrade writer or the panel blob.
- **The core calls only what the sites called, plus the menu routines.** Its code jumps to
  `0x400019b0` (the call it replaced at boot), DRAWALL, KEYDISP, ENCDISP and MIDI_BUILD (the calls
  it replaced), and, only when a mod calls `core_additem`, `operator new`, the `MenuItem`
  constructor, `Menu::addItem` and the `std::function` manager, each the Digitakt II's routine
  whole [verified: linked blob disassembly; `t19_sites.py --verify`]. It names no NOR driver
  entry, no PUSHR word, no DSPI0 register, no `0xB0B0DADA` (brick check 7) [verified].
- **Every site is whole instructions, and nothing jumps into the middle of one.** elekloader
  refuses a code site that is not whole instructions; `t19_sites.py --verify` found no explicit
  branch target inside any of the 10 sites (objdump sweep of the image), and Ghidra's call and
  data-reference tables have none either [verified]. One word in the image equals `0x4000053c`
  (inside the boot site), at `0x402536ce` and `0x402729be`: both in the data area past the code
  (code ends at `0x401d07fb`, T1.3), so not a jump [verified address; meaning inferred]. The
  switch tables (gcc's `jmp (T,pc,dn.l)` with 16-bit offsets after it: 94 of the image's 95
  computed `jmp (pc,dn)`, 1,014 case targets) start no case inside a site [verified,
  `t19_sites.py --verify`]; the one other form (`0x4020c3ce`, in data) is far from every site. The first scan had found that the step sites' original choice (`jsr; move.l
  d0,d5` and `jsr; lea`) took in the synth branch's join point (`bra.s 0x400da0b8` from
  `0x400da09c`, `bra.s 0x400d9236` from `0x400d91ee`), so the sites were moved to `move.l
  d2,-(sp); jsr`, which only the MIDI branch runs.
- **Registers and stack.** `core_midistep` leaves the caller's stack exactly as the replaced push
  would (seven longs), returns the builder's d0, keeps d2-d7/a2-a6 (handlers are C), and the
  next instruction sets the condition codes itself. `core_midinote` keeps every register the task
  uses after the site (a0, a1, a2 restored; d1 and a4 set by the replaced instructions; d5's upper
  bytes untouched) [verified: the listing; the emulator runs below].
- **Memory.** Code and tables run from `0x47E00000`, which nothing in stock names, maps or writes
  in T1.3's runs, above the DDR clear and below the boot stack [verified in emulation, T1.3]. The
  build's size: core alone grows the image by 804 bytes, core + test mod by 996; the in-place
  margin at `0x40200000` is 54,790 / 54,751 bytes (stock 31,182) and the receive buffer has
  186,636 / 186,535 bytes spare [verified: elekloader verify, brick check 3 and 5].
- **Contexts.** `ev_midi_step` handlers run in the sequencer's interrupt (vector 121), so they
  must be short and must not block; `ev_midi_note` handlers run in the MIDI task. Neither event
  can come before `boot` has copied the code (the sequencer and the MIDI task start long after
  0x40000538), but both can come before the first `ev_tick`, so only `.run` code may subscribe to
  them (`.fast` code is copied on that tick) [inferred from the boot order].
- **What a bad mod could still do.** A handler can corrupt RAM or hang the MIDI task or the
  sequencer interrupt like any code; the core does not sandbox it. The recovery path is the same
  as for any OS: STARTUP menu, OS UPGRADE, stock over DIN [verified on the unit 5 Oct, T0.3].

## The test mod and the candidates

`vendor/elekloader/examples/midi-hooktest-dn2` (C, 184 bytes of `.run`, 144 of `.bss`, no sites of
its own). On `ev_midi_step` it remembers (MIDI event, step) in a 16-entry ring. On `ev_midi_note`,
for a sequencer note (the MIDI event's source word `+0x34` = 1) it adds 12 to the note and, when the
ring has the note's MIDI event, sets the velocity to step + 1. Live notes (source 2) are left alone,
since their note-off comes from the key release. So stock's `90 3C 64` on a trig at step 1 should
become `90 48 01`, on step 5 `90 48 05`, and each booked off `90 48 00`. One effect proves each
event: the transpose shows `ev_midi_note` ran and its write-back reaches both the note-on and the
booked off; the velocity shows `ev_midi_step` ran with the right step and the right event, before
the task sent it. It also counts calls (`hooktest_steps`, `hooktest_notes`, `hooktest_tagged`),
read from RAM at the end of a run.

Also `examples/hello-marker-dn2` (the Digitakt II's hello-marker with `Bitmap::fillRect` at
`0x40114b22`, which is the Digitakt II's `0x401131ae` whole) for `ev_draw`; built and linked, not
run in the emulator.

Candidates, built with elekloader's packer and verify (`out/T1.9/build/`, git-ignored; never
flash them without the steps at the end of this note):

## Test in the emulator: method

**Why not the MIDI-ready snapshot.** A snapshot is the whole RAM, including the main OS code the
stock boot loaded and everything the OS built since. The modded code only gets in through a boot
(the depack of the candidate's section 3, then `boot` at `0x40000538`). So the proof boots each
candidate cold and repeats the MIDI set-up with keys, exactly as T2.4c did for stock:

1. `scripts/t19-emu.sh ladder NAME CAND.syx`: `emu.extract`, `emu.checkpoint make` to 400M
   instructions from reset, then `tools/guirun.py` to 800M with timers saved: the same recipe as
   stock's `out/T2.4a/warm/warm800M.snap`.
2. `scripts/t19-emu.sh proof NAME`: T2.4c's `midi-proof.script` (SETTINGS > MIDI CONFIG > SYNC:
   CLOCK SEND and TRANSPORT SEND on; track 1 = MIDI machine, CHAN 1; RECORD, trigs 1 5 9 13;
   PLAY 4 s; STOP), headless, `--ssi0-hz --ips 150e6`, DIN out logged (`--midi-log`,
   `--midi-file`). The same command with NAME=stock runs it on stock's warm800M.snap.
3. `scripts/t19-emu.sh ui NAME`: `scripts/t19-ui.script` (main screen, SETTINGS scrolled row by
   row and a row opened, SYN and FLTR pages, an encoder turn, TRIG 2), screens compared with stock's.

`scripts/t19_live.py` wraps `emu.live` (unchanged) to read mod symbols from RAM at the end
(`--read-syms`), to trace addresses (`--trace`), and, for development only, to hot-patch a build
into a stock snapshot (`--hotpatch`: the site bytes, the run image copied to `0x47E00000`, `.bss`
zeroed, i.e. what `boot` does). The hot-patch is not a proof of boot; it was used once to check the
handlers before the slow cold boots.

**Development check (hot-patch on `out/T2.4c/saved/midi-ready.snap`, PLAY 3 s)** [verified,
`out/T1.9/hot/`, `out/T1.9/hot2/`]: the four notes went out as `90 48 64`, `90 48 05`, `90 48 09`,
`90 48 0D`, each ended by `90 48 00`, at the same spacing as stock. The first note kept velocity
100: its event had been built by the pending-step pass when the snapshot was made, before the
patch, so `ev_midi_step` never saw it. A trace showed the pending-step site (`0x400d9230`)
fire after STOP for step 0 with the static event `0x4464b5a4`, and the step handler site
(`0x400da0b2`) once per step for track 0 (a MIDI event only on steps 4, 8, 12 there). That is
why the cold boot is the real test.

## Test in the emulator: results (cold boots)

All on this Mac, 6 Oct 2026, digikit `dn2-1.12` (`88cc210`, unchanged). Outputs in
`out/T1.9/emu/<name>/` (`proof/`, `ui/`, logs), comparisons in `out/T1.9/emu/compare-*.txt`.

**Boot** [verified, `out/T1.9/emu/*/checkpoint.log`, `guirun-warm.log`]. Both candidates boot from
reset like stock: the same eight task creations, each a fixed number of instructions later than
stock's, the cost of the boot copier's loops (DH01: 829 later, 233 words copied and 41 zeroed;
DC01: 577 later, 185 and 5), e.g. the UI task at 315,718,995 and 315,718,743 (stock
315,718,166). From 400M to 800M the UI main loop ran 854 times in both (stock 854), the CPU parked
in the same idle loop `0x400cf246`.

**A digikit limit found on the way** [verified]: `emu.live` identifies the panel by the `.syx`
file's sha256, so for any modded file it sets `device_error` and silently drops every key (the
first run on DH01 sent no MIDI and the screen never left the main page). `t19_live.py
--identify-as STOCK.syx` identifies a modded file as the release it was built from (same
hardware, same panel); nothing in digikit was changed. Worth a small fix in digikit later (accept
a declared base release for modded files).

snapshot, START to STOP [verified, `compare-hooktest-DH01-midi.txt`]:

- Every note an octave up (C4 to C5), every velocity = step + 1 (steps 0, 4, 8, 12), every booked
  note-off on the transposed note: exactly what the mod intends. Nothing else changed: the same
  messages in the same order, clock 80.87 BPM against stock's 80.88 (project 81.0), every
  message within one audio block (0.67 ms) of stock's. Stock against itself (this run vs T2.4c's
  proof) differs the same way, by 0 or 1 block, because script key taps are timed in wall time.
  The candidate has 134 clocks to stock's 135 because its STOP came 8.5 ms earlier.
- RAM at the end: `hooktest_notes` = 4, `hooktest_tagged` = 4, `hooktest_steps` = 24, `fast_done`
  = 1 (core's `ev_tick` handler ran).
- `ev_midi_step` call by call (`T19_TRACE_STEP=1 ... --trace 0x47e002b0`, `steptrace.txt`): while
  stopped, the pending-step pass (`0x400d9230`) rebuilds step 0 of track 1 five times after each
  trig entry (20 calls) and once more after STOP; while playing, the step handler (`0x400da0b2`)
  builds steps 4, 8 and 12, each a beat ahead of its note. The trig flags word is `0x00010781`
  (bit 7, play the notes, set), chain heads 0, 1, 2, 3. So the first note of a PLAY always comes
  from the event the pending pass built, which is why a hot-patched stock snapshot missed it.

## What's open

- **Nothing has run on a unit.** All of the above is digikit's emulator: no DSP, no USB MIDI, an
  empty +Drive, a ColdFire under Unicorn.
- **`ev_settings` and `ev_personalize` with a handler** are not tested: the menus build exactly as
  stock with core in place, but no mod added a row (the row callbacks' conventions are not
  documented for this firmware; core-dt2 has a PERSONALIZE checkbox example in perform-direct's
  history). `ev_key` and `ev_enc` are tested only as pass-through (every key and encoder acted as
  on stock), not with a handler that takes an event. `ev_draw` with a handler: hot-patch only.
- **The live-note side of `ev_midi_note`**: not run (no live MIDI-track notes in the scripts). The
  hook sees them, but a mod that changes a live note must also change its note-off, which this
  event does not see (the off loop at `0x4012b624`). A third event there would be needed for a
  live transposer; the arp design (T2.2-v2) does not need it.
- **USB MIDI**: the same MIDI task sends to USB when its port bit is set; the emulator models DIN
  only, so USB output was not observed [inferred: the bytes go through the same buffer, so the
  hook covers both].
- **The arp's own sites** (T2.6) sit next to `ev_midi_step`'s and do not overlap; whether the arp
  mod should use `ev_midi_step` instead of its `cave_seq`/`cave_pre` routing is for T2.6.
- **digikit's panel identification by sha256** makes `emu.live` drop keys for modded files
  (worked around in `scripts/t19_live.py`); worth a fix in digikit.
- **elekloader's linker** does not check a mod's region against the linker's own `ddr`. On the
  Digitone II the areas are split so it cannot happen; on the Digitakt II `areas['ddr'] == ddr`, so
  a region there could overlap core's RAM. Worth reporting upstream with C8.

## Memory check before the first flash (2026-10-12)

Prompted by dn2_firmware_explore's LFO4 bug on 1.11: its state sat in the eMMC driver's 64 KiB bounce
buffer (around `0x466f1300`), so saved projects carried LFO data. The core's DDR is the top megabyte
`0x47E00000-0x47F00000`, well above that. digikit's code-aware `tools/refscan.py` on the 1.12 main OS finds no
reference into `0x4FE00000-0x4FF00000` (the uncached alias) and three into `0x47E00000-0x47F00000`, none of
them an address [verified]:
- `0x40172a7a` and `0x40173014` load `0x47efffff` together with `0xe0000000` into one 64-bit slot.
  `0x47EFFFFFE0000000` is FLT_MAX as an IEEE double.
- `0x402871fc` is in data decoded as code.

This agrees with T1.3's write watches (nothing writes `0x46800000-0x47F00000` during the emulated sessions)
and with dnfw's measurement that stock 1.11 never touches `0x46701340-0x48000000`, saves included.
