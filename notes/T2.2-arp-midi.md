## Answer

**Hypothesis (c): both.** [verified]

- **UI.** Two explicit checks keep the ARP page and the ARP on/off toggle away from MIDI tracks,
  and a third keeps the ARP LED off on them. All three call the same predicate, `FUN_40031274`
  (is the track a MIDI track).
- **Engine.** No code tests "MIDI track" inside the arp. The exclusion comes from the structure:
  the arp lives in the voice/frame interrupt `FUN_40025e36`. It is fed only by internal-voice note
  events, and its output goes only to the internal voice allocator `FUN_4002a6a2`. MIDI-track trigs
  never become voice events. At `0x400da046` the sequencer sends them down a separate MIDI-event
  path, and on that branch it also skips the per-step arp clock event (type 9). Live keys on a MIDI
  track skip the interrupt entirely (`FUN_40121db2` -> `FUN_4012bb90`, which posts straight to the
  MIDI task).
- **Patching the UI alone would not help.** You could then set arp parameters on a MIDI track, but
  the engine would never read them for that track. [inferred from the two paths below]
- **Smallest working patch (section 3).** Three UI branch flips (8 bytes). One 18-byte rewrite in
  the sequencer, so that a MIDI track with its arp on is scheduled like an audio track (voice event
  plus arp clock). One 6-byte call redirect in the interrupt, so that a note the voice allocator
  would play on a MIDI track becomes a MIDI note event in the list the interrupt already forwards
  to the MIDI task. An optional 6-byte jump handles live keys. New code: 326 bytes in three caves.
  The arp settings are already stored for MIDI tracks (they live in the track's sound record), so
  the project format does not change. [inferred]
