## Summary

- **Loader:** `scripts/t32_load.py` turns section 7 into six flat images (four L1 blocks, L2, DDR) plus a JSON map.
  All 36 self-checks pass, including a byte-for-byte match of all 65,372 instructions in digikit's database and of
  the four effect entries and call sites. **[verified]**
- **Stream:** an init program (app 0) that sets up the clocks and the DDR controller (**[inferred]** from its DMC and
  CDU register writes), then the main program:
  14 code blocks, 40 data blocks, 37 zero-fill blocks (5.6 MB, the BSS), 4 markers. Section 1 lists every block.
- **Memory map (section 2):** L1 block 0 holds the IVT, 191 KB of C data/BSS, the system stack
  (`0x26f000-0x26f7f0`) and a 2 KB C heap; L1 block 1 holds driver memory, every DMA buffer, constant tables and
  the 50 KB FreeRTOS heap (`0x2d08b8-0x2dd0b8`, which holds the Audio Task's stack); L1 block 3 and L2
  `0x20000000-0x2001e880` hold the code; DDR holds the reverb, delay and chorus state back to back, then 330 KB of
  sample data.
- **Free (static):** L1 block 2 entirely (128 KB), L1 block 1 tail (76.5 KB), L1 block 3 tail (16 KB), L2
  `0x2008823c-0x200f9fff` (466 KB). Run-time confirmation is open.
- **Audio (section 3):** SPORT4 A/B is the codec (32 frames x 2 slots per DMA buffer); its DMA-done callback
  `0x1ca136` notifies the Audio Task, so **one SPORT4 DMA completion = one block, 1,500 per second**. SPORT0 A/B is
  a 16-slot TDM link. **SPI2** (slave, two ping-pong DMA lists of `0xabc` bytes) carries the ColdFire's frame; the
  block handler picks the last completed half. The output is negated Q31.
- **Bonus for G6:** the block handler already measures each block with EMUCLK and writes the cycle count into the
  first word of the frame it sends back to the ColdFire.
- **Offline rendering needs no peripherals:** write the frame and inputs, call the block handler `0x1c9d6b`, read
  the floats at `0x268438` (section 3.5).
- **sharcemu.py (section 4):** its p-code back end has no semantics for 48.7% of the instructions (moves, basic
  loads, stack frames, DO loops, pushes), so every routine faults at its first instruction; it runs at ~2.7k
  instructions per second today (~49k after fixing an eager big-integer shift). A dedicated interpreter is the
  better base for T3.6.

## 0. Address conventions [verified unless marked]

The ADSP-2156x has one SHARC+ core. The code uses several views of the same memory, and every address in
the other notes is in one of them:

| view | used by | L1 | L2 | DDR |
|---|---|---|---|---|
| **core byte** ("DM bare", what C pointers and `DM(abs)` operands hold) | all data accesses in this program (byte-addressed C) | block 0 `0x240000-0x26ffff`, 1 `0x2c0000-0x2effff`, 2 `0x300000-0x31ffff`, 3 `0x380000-0x39ffff` | `0x20000000-0x200fffff` | `0x80000000-` |
| **loader / system** (boot-stream targets, DMA) | the boot ROM | core byte + `0x28000000` | same as core byte | same |
| **short word (SW)**, the VISA PC | code addresses, call targets | byte = 2 x SW (block 3 code = SW `0x1c0000-0x1cffff`) | byte = `0x20000000 + 2*(SW - 0xb80000)` | not used for code here |
| **normal word (NW, 32-bit)** | a few PM/DM accesses | byte = 4 x NW (block 0 = NW `0x90000`) | - | - |
| **48-bit NW** | `PX = PM(...)` instruction-width data, the IVT | byte = block base + 6 x (NW - block NW base) | - | - |

- The block sizes (192, 192, 128, 128 KiB = 640 KiB) are the ones `scripts/sharc_ldr_parse.py` uses; every
  loaded byte falls inside them, and block 0 is written up to `0x26f000` and used up to `0x26f7f0` (the stack,
  section 2). **[inferred]** from the ADSP-21569's documented 640 KiB L1; not checked against the HRM here.
- L2 is taken as 1 MiB (`0x20000000-0x200fffff`). The code compares pointers against `0x200fa000` and
  `0x200fdfff` (T3.1a), which fits. **[inferred]**
- 48-bit NW: the C runtime reads `PX = PM(0xe00e0)` at `0x1c0efe`. With 6 bytes per 48-bit word that is byte
  `0x380000 + 6*0xe0 = 0x380540`, which is exactly block 77, an 8-byte block of its own (all zero). **[verified]**
  for the bytes; the conversion rule is **[inferred]** from that fit.
- Code SW addresses and the L2 rule were measured by digikit (591 of 591 L1 call targets) and checked here: all
  65,372 aligned instructions in sharcdb match the loaded image byte for byte under these rules (section 1.3).

## 1. Every boot-stream block

### 1.1 Shape

- Two applications. **App 0** (blocks 0-6) loads a 10,312-byte init program into L1 block 0 and the boot ROM
  runs it through the INIT block 6 (entry SW `0x120230`). **App 1** (blocks 7-94) is the main program; its
  FINAL block 94 jumps to the entry `0x1c12e2`. **[verified]**
- 95 blocks: 4 markers (FIRST x2, INIT, FINAL), 54 payload blocks (835,436 bytes) and 37 FILL blocks (fill value
  0, 5,601,712 bytes). 6,437,148 bytes are written in all; 14,040 of them are written twice (app 1 over app 0),
  so the final image holds 6,423,108 bytes. Only 8 bytes of app 0 survive (two 4-byte holes in block 1's range,
  `0x240458` and `0x24128c`). **[verified]** (`scripts/t32_load.py`)
- Kinds below: **code** = VISA or 48-bit instructions; **initialized data** = a payload that is not code;
  **zero-fill** = a FILL block (the loader's BSS); **code fill** = a 68-byte FILL inside code, which is zero and
  decodes as NOPs (selload's code-fill rule, T3.1a); **init program** = app 0. Code vs data for each payload
  was decided in T3.1a/T3.1b (disassembly coherence, call targets) and is re-confirmed in section 1.3.
  "survives" = bytes of the block still present in the final image.

## 2. Memory map of the loaded image

How a range was classified: the block kinds of section 1; then references from code (digikit's `literals`,
absolute `mem_access` and resolved `ptr` rows, any form and register) and 32-bit words in loaded data whose
value falls in the range (`scripts/t32_refs.py ranges|range LO HI`; the per-range counts are in
`out/T3.2/ranges.txt`). **"Free" means: never written by the loader, and no static reference of either kind.**
It does not exclude a pointer computed at run time from an unrelated base, a DMA set up from a computed
address, or the boot ROM's own use, so every "free" below is **[verified]** for the static part and
**[inferred]** for run time. A watch run on the unit or in a full simulator is the only way to close that.

Totals per memory (bytes): L1 b0 768 code, 61,372 initialized data, 130,124 zero-fill, 4,336 unwritten; L1 b1

### 3.3 The audio path and what paces the blocks

`0x1ca167` and `0x1ca2d1` open the two SPORT pairs and give each half a cyclic two-descriptor DMA list
(descriptor fields `DSCPTR_NXT, ADDRSTART, CFG = 0x100000, XCNT, XMOD = 4`) **[verified]**:

| SPORT | half | DMA | descriptors | buffers (ping, pong) | per buffer | role (from the command-3 case) |
|---|---|---|---|---|---|---|
| 4 | A | `0x31023000` | `0x2c0878` <-> `0x2c0894` | `0x2c0478`, `0x2c0578` | 64 words = 32 frames x 2 slots | **codec output**: `0x1c9d3f` interleaves the rendered L/R into it at `0x1c9fd2` |
| 4 | B | `0x31023080` | `0x2c08b0` <-> `0x2c08cc` | `0x2c0678`, `0x2c0778` | 64 words | **codec input** (IN L/R): `0x1c9d00` de-interleaves it into `0x268538` at `0x1c9f20` |
| 0 | A | `0x31022000` | `0x2c28e8` <-> `0x2c2904` | `0x2c08e8`, `0x2c10e8` | 512 words = 32 frames x 16 slots | 16-channel TDM out: the render's 4th argument; command 0 writes the `0x7fffffff` marker into its first word |
| 0 | B | `0x31022080` | `0x2c2920` <-> `0x2c293c` | `0x2c18e8`, `0x2c20e8` | 512 words | 16-channel TDM in: channels de-interleaved into `0x268638`-`0x268938` |

- **The output path, per block** (`0x1c9d6b` tail, every command) **[verified]**: the render leaves 32 L and 32 R
  floats at `0x268438` (its `R4`); `0x1c9d3f` converts them with `fix` by 31 (to Q31) and interleaves them into
  the SPORT4A buffer; the shared tail `0x1c9e29`-`0x1c9e3d` then **negates all 64 words** (`neg` in SIMD), so the
  codec receives the inverted signal (polarity is corrected in the analogue stage or not at all; not known).
- **The block's cycle count goes back to the ColdFire already** **[verified]**: the handler reads `EMUCLK` at
  entry (`0x1c9d87`/`0x1c9d89`) and again at the end (`0x1c9e47`/`0x1c9e49`), and stores the difference,
  half-word swapped (`(d >> 16) | (d << 16)`), into the first word of the SPI **tx** frame (`DM(I6-2)` from
  `0x1ca020`, store at `0x1c9e62`). So the DSP load per block is in every frame the ColdFire receives. This is
  most of T4.1/T4.2 (G6): find where the ColdFire reads word 0 of its RX frame (`0x800053a4`, T3.3).
- Each buffer is exactly one 32-sample block, so every DMA completion is one block. The half in use is
  `DM(0x268a38)` (0/1), flipped by the Audio Task after each block (`0x1c9e5f`). **[verified]**
- **Pacing.** `0x1ca167` ends with `0x1cd1c3`, which joins the two SPORT4 handles into one object
  (`DM(0x2c2958)`), and `0x1ccba3`, which stores the callback `0x1ca136` in it. `0x1ca136` checks for event
  `0x100` and then runs `vTaskNotifyGiveFromISR(DM(0x268a84) = the Audio Task)` (`0xb88e41`, call at `0x1ca14f`)
  and requests a context switch (`IRPTL` bit 31 set at `0x1ca15f`). The Audio Task's wait `0xb891fa` returns 1
  and the task runs one block. **So one SPORT4 DMA completion (codec, 32 frames at 48 kHz) = one Audio Task
  block, 1,500 per second.** **[verified]** for the registration chain and the calls; the meaning of event
  `0x100` (buffer done) and the 48 kHz frame rate are **[inferred]** (PCG ratios above, 48000.0 in the effect
  config). The SPORT0 pair gets no callback: it runs in lock-step from the same clocks.
- The interrupt itself comes through the SEC: IVT slot 15 (SECI) -> `0x1c0acd` reads `SHDBG_SECI_ID`
  (`0x300eb`) and dispatches through the table at `0x240910`, which the drivers fill at run time (T3.1b). The
  SPORT4A record lists SEC IDs `0x35` and `0x36` (and `0x94`), SPORT4B `0x37`, `0x38` (`0x95`); which of them is
  the DMA-done source is not read here. **[verified]** table values; roles open.
- The core timer tick (1,000,000 cycles) is FreeRTOS's only other time base; the Audio Task does not depend on it.

### 3.4 The SPI link that carries the ColdFire's frame

- `0x1ca46a(0xabc)` opens **SPI2** (`0x1cc753(2, …, mem 0x2c0240)`), configures it (`0x1cb7d2` … `0x1cb60a`;
  `0x1cb7d2` registers the callback `0x1ca04a`) and gives it two cyclic DMA lists with 16-bit transfers
  (`XMOD = 2`, `XCNT = 0xabc/2 = 1,374`) **[verified]**:
  - list `0x2c2960` <-> `0x2c297c`, buffers `0x2c39d0` and `0x2c29d0`: **received frames** (the ColdFire's TX).
  - list `0x2c2998` <-> `0x2c29b4`, buffers `0x2c49d0` and `0x2c59d0`: **frames sent back** to the ColdFire.
  Each buffer slot is 4 KiB; the frame is `0xabc` = 2,748 bytes, of which the ColdFire fills `0xa80` (T3.3).
- `0x1ca04a` flips the SPI half index `DM(0x2c0450)` on event `0x20` (a completed transfer). **[verified]**
- Every block, the block handler `0x1c9d6b` first reads EMUCLK (the cycle counter, for T4.1), then calls
  `0x1ca020`, which returns rx = `0x2c29d0 + DM(0x2c0450)*0x1000` and tx = `0x2c49d0 + DM(0x2c0450)*0x1000`.
  The first 16-bit word of rx is the command (`(sw)` load at `0x1c9da8`; the ColdFire always sends 3, T3.3) and
  indexes the table `0x268a68`. Command 3 (`0x1c9f0f`) calls the render `0x1c2712` with `R12` = rx, which copies
  `0xa80` bytes of it into the frame image `0x25c48c` (T3.4). **[verified]** addresses and calls; "rx/tx"
  naming **[inferred]** from which buffer the render reads.
- So the SPI frames are **not** what paces the audio; the DSP takes whatever frame was last completed when the
  codec block arrives. The ColdFire sends one frame per its own audio period (vector 191, T3.3).

### 3.5 What to emulate, by goal

**(a) One effect on a buffer (T3.6's first target).** No peripherals. Load `out/T3.2/mem/*`, set the C stack
(`I7`/`I6` = `0x26f7f0`, `B7`, `L7` as in 2.1, `M5 = 0`, `M6 = 1`, `M7 = -1`, `M13 = 0`, `M14 = 1`, `M15 = -1`,
all `L` registers 0, MODE1 as the reset code leaves it), run the effect's init once, then per block fill the
input buffers, write the parameter floats and call the effect with `R4` = state, `R8` = params, `R12` =
`0x257e6c`, as T3.4 section 2 describes. Needs `powf`/`log` (`0x1c0c76`, `0x1c0b60`) only for the compressor.

**(b) The whole Audio Task, offline, block by block.** Run the C start-up and `main` up to the scheduler start,
or skip it and run only the inits that matter (`0x1c1445` effect init, and whatever voice init `main` does
before `0x1ca000`). Then per block, with no RTOS:
1. write a ColdFire frame (T3.3's format; first word 3) into `0x2c29d0 + 0x1000*DM(0x2c0450)`;
2. write codec input into `0x2c0678 + 0x100*DM(0x268a38)` (or zeros) and the TDM input buffer;
3. call the block handler `0x1c9d6b` directly (that is what the Audio Task does after its wait returns 1);
4. read the output: 32 L + 32 R floats at `0x268438`/`0x2684b8` (before conversion), or the 64 interleaved,
   negated Q31 words at `0x2c0478 + 0x100*h`, where `h` is `DM(0x268a38)` before step 3 (the handler flips it);
   the 16-slot TDM output is at `0x2c08e8 + 0x800*h`, and the block's cycle count at the start of the tx frame;
5. optionally flip `DM(0x2c0450)` to model the SPI half change.
Nothing else is needed for sound: no SPORT, DMA, SEC or PCG model. EMUCLK/EMUCLK2 reads must return something.

**(c) Linked to the ColdFire emulator in real time (T9.1).** Then the SPORT4 DMA completion must become a SEC
interrupt (SECI, ID from the SPORT4 record) every 32 frames, the SPI2 DMA must deliver the ColdFire's DSPI2
frames (16-bit words, `0xabc` bytes) into the rx ping-pong and raise its event, and the core timer must tick
for FreeRTOS. The SPORT0 TDM link is the path to the ColdFire's SSI (it carries 16 slots each way; DT2
digikit work points the same way) and would be needed for USB audio, not for the main outputs.

## 4. digikit's `tools/sharcemu.py` for T3.6

`sharcemu.py` has two back ends: Ghidra's EmulatorHelper over a live pyghidra project (none exists for DN2
here, and it needs the JVM), and `PypcodeConcreteBackend`, which lifts each instruction with pypcode from
digikit's own generated SLEIGH language and interprets the p-code in Python, with ALU results bridged to
`tools/sharc_trace.py`'s `_compute()`. I tried the second one, unchanged, through
`scripts/t32_emu_probe.py` (run with digikit's `uv` environment). The probe generates the SLEIGH language into
`out/T3.2/sleigh/` by importing `gen_sleigh.py` with its `OUT_DIR` redirected (so nothing is written in
`vendor/`), compiles it with pypcode's bundled `sleigh` (0.3 s, 609 constructors, "56 NOP constructors"
warning), and gives the backend the whole loaded image (code fetched at `2*SW`, L2 code redirected to
`0x20000000 + 2*(SW - 0xb80000)`, data at core byte addresses).

```
cd vendor/digikit
uv run python ../../scripts/t32_emu_probe.py sleigh
uv run python ../../scripts/t32_emu_probe.py coverage --json ../../out/T3.2/emu_coverage.json
uv run python ../../scripts/t32_emu_probe.py run 0xb8482c --set I7=0x26f7f0 --set I6=0x26f7f0 ...
uv run python ../../scripts/t32_emu_probe.py speed
```

### 4.1 How far it gets: nowhere yet [verified]

| start | first instruction | result |
|---|---|---|
| delay `0xb8482c` | `R2 = I5` (Type 5b move) | no-semantics fault at step 0 |
| chorus `0xb84d5c` | `I7 = modify(I7, -10)` (19a) | no-semantics fault at step 0 |
| biquad `0x1cdf46` | `I4 = R4` (5b) | no-semantics fault at step 0 |
| FX bus `0x1c1738` | `I7 = modify(I7, …)` (19a) | no-semantics fault at step 0 |

| Audio Task `0x1c9fe7` | `cjump 0xb891fa (db)` | executes as a plain `call` (no delay slots, no frame push), then faults on `I7 = modify(…)` at `0xb891fa` |

**Semantics coverage**, every aligned instruction of the main program lifted once (`out/T3.2/emu_coverage.txt`):
25,299 of 51,901 (48.7%) lift to **empty p-code**. Per routine tree: delay 49.6%, chorus 46.0%, reverb 57.9%,

the C compiler uses everywhere:

| form | count | empty | example |
|---|---:|---:|---|
| 2a_short (16-bit compute) | 3,308 | 3,308 | `R0 = leftz(R0, R0)` |
| 5b_move (register move) | 3,202 | 3,202 | `R0 = M5` |
| 3c (short DM load/store) | 2,963 | 2,963 | `R0 = DM(I3, M5)` |

The forms that do have semantics (15b, 14a, 3a, 17a/17b, 25a calls, 9a jumps, …) cover addressing and control
flow but not the C calling convention: the indirect return `jump (m14,i12) (db)` lifts to a bare `return`
(the backend stops there), delayed branches ignore their two delay slots, and DO loops are not modelled.

### 4.2 Speed [verified]

On 3,000 straight-line L2 instructions that do have semantics (`speed`): lifting alone runs at about 180,000-
320,000 instructions per second; lift plus execute at about **2,500-2,900** per second. A per-instruction
timing shows the cause: 297 Type 15b loads/stores (`DM(Ix - n)`) take 10-60 ms each; the other 5,370 run at
about **49,000 per second**. The binary-op branch of `PypcodeConcreteBackend.step` builds a dict of *all*
results (`{'INT_ADD': a + b, …, 'INT_LEFT': a << b, …}[name]`), so an `INT_ADD` of a negative offset
(`b = 0xfffffff6`) also computes `a << 0xfffffff6`, a 4-gigabit integer (68 ms on its own here). Computing only
the selected operation is a small fix. Two correctness bugs sit next to it: `INT_SLESS`/`INT_SLESSEQUAL` compare
unsigned, and `INT_SRIGHT` is a logical shift.

### 4.3 What this means for offline rendering

Static instruction counts per 32-sample block (T3.4, ±50%): delay ~6k, chorus ~18k, reverb ~18k, compressor
~19k, FX bus without effects ~12k, master without compressor ~14k, the whole render `0x1c2712` ~258k.

| target | instructions | at ~49k insn/s (after that fix) | at today's ~2.7k/s |
|---|---:|---:|---:|
| delay, one block | ~6k | 0.12 s | 2.2 s |
| delay, 1 s of audio (1,500 blocks) | ~9M | 3 min | 55 min |
| full render, one block | ~258k | 5 s | 95 s |
| full render, 1 s of audio | ~390M | 2.2 h | 40 h |
| real time (full render) | 390M per second | 8,000x too slow | |

Even with complete semantics, a per-instruction p-code interpreter in Python is good for unit tests of one
routine and a few blocks of one effect, not for rendering a sound. **For T3.6 I would not build on the
SLEIGH/p-code path.** Options, roughly in order of effort:
1. Complete the missing semantics in `gen_sleigh.py` (25,299 instructions in 30-odd forms), plus delayed
   branches, the C return, DO loops and SIMD (`MODE1` bit 21 is set around most inner loops of the effects);
   fix the eager-dict and signed-compare bugs; cache lifts per PC. Gets correct but slow (~50k insn/s).
2. A dedicated interpreter: decode each instruction once with digikit's decoder (`sharc_disasm.py` /
   `sharcdb` fields, more reliable than selache's per T3.1b) into a Python closure, reuse `sharc_trace._compute`
   for ALU semantics, and implement the ~20 data-move, branch, loop and stack forms directly. A few hundred
   thousand insn/s in CPython, enough for offline renders of seconds of audio. A port to C or Rust of the same
   tables reaches tens of millions per second, which is what real time (~390M/s at full load, less with few
   voices) would need on top of being a big job.
3. Before either: unit-test the semantics against the unit via T3.5 recordings, and against the static
   per-effect expectations in T3.4 (the delay of an impulse must come back at the set time).

What any of these needs from this task: the memory images and conventions (sections 0-2), the effect calling
convention (T3.4 section 2), the per-block recipe (section 3.5), and the stack set-up (2.1).

## 5. Open

- Run-time confirmation of the free ranges (L1 block 2, L1 block 1 tail, L1 block 3 tail, L2 tail): a write
  watch in a full simulator, or a fill pattern checked on the unit. Static analysis cannot see computed pointers
  or DMA set up from computed addresses.

  of the run-time buffer at `0x8052fbe0`.

  the top of L2.

  `0x20` (SPI). Not needed for offline rendering.

  the tick is 1 kHz).
- The SPI1 path (`0x1ca63e`, no static caller, buffers overlapping the SPI2 ones) and the GPIO callback
  `0x1ca6a7`: a second link mode, or dead code.
- Peripheral names marked (fit) need `defADSP21569.h` or the ADSP-2156x HRM to confirm.

## Correction (2026-10-06, from notes/prior-art-2026-10.md)

The DSP's startup code turns on all three L1 caches, so these ranges are cache and **not free**:
`0x39c000-0x39ffff` (the L1 block 3 tail listed above), `0x2ec000-0x2effff` and `0x31c000-0x31ffff`
[inferred here from the DN2 1.11 modding project dn2_firmware_explore, whose section 7 is byte-identical to
ours; to verify in our own startup code]. That project places new code in L1 block 1 at `0x2dd600-0x2e7000`,
below the DM cache. Also: the ColdFire's DSP loader refuses a section 7 over 1 MiB, and the DSP then never
boots, so section 7 must stay under 1 MiB.
