# T6.3: CMP2F, our code out of 0x315f8c-0x318000, plus a memory scanner

Date: 2026-10-20 (one builder; started 2026-10-18). Follows notes/T6.3-cmp2e.md. CP2E on the unit: with LOW XOVR at max
(the probe) turning LOW MUP gives no stop, so the cause is our use of the value, not the transport. In the stop test the
heartbeat froze and the MID crumb read 12 px = **step 4, cmp_tail_apply**. Marks as before. Nothing flashed,
committed, pushed or posted.

## 1. Why the move

CP2E's LOW MUP block is sw `0x18b353-0x18b397` = bytes **`0x3166a6-0x31672f`**. The part the probe skips (the
knob compare, the call set-up and the call) is `0x3166ec-0x31672f` [verified, listing]. It is encoding for encoding
the same as MID and HIGH MUP (notes/T6.3-cmp2e.md 3). cmp_tail.c sat at `0x315f8c-0x316c62`, a range no build before
CMP2 used for code: CMP1's code2 ended at `0x315f8c`. CMP2D/CMP2E's cmp_load.c ran at `0x316c62-0x317a14` without a
problem. The hypothesis to test: something on the chip writes into L1 around `0x3166xx`, or code there misbehaves.

## 2. What CMP2F is

- **Layout** [verified, `out/T6.3/CMP2F-dsp/build.json`]. Our code and state:
  - `0x2dd600-0x2e1c36`: flanger, its glue and the stubs, byte-identical to CMP2's;
  - `0x2e2900-0x2e49c2`: code4, the glue then **cmp_tail.c**, inside dnfw's silicon-proven `0x2dd600-0x2e7000` and
    where CP2E's glue already ran;
  - `0x308400-0x30ff76`: code3, mbcomp.c, **cmp_load.c**, **cmp_clk.s** and stubs3;
  - `0x310000-0x315f8c`: code2, the tape delay alone, byte-identical to CMP2's and the unit's;
  - `0x2e6000-0x2e604c`: data;
  - FILLs: CmpSlot `0x2e1c40-0x2e2370`, CmpTail `0x2e2400-0x2e24d0`, CmpLoad `0x2e2800-0x2e28b8`, FlgSlot
    `0x300000-0x308400`, save area `0x2e6800-0x2e686c`;
  - the page table `0x2e6880-0x2e6f90`;
  - the six stock CJUMP patches.

  **The only blocks in `0x315f8c-0x318000` are three watermark payloads.**
- **Behaviour**: as CP2E. The heartbeat (LOW) and the breadcrumbs (MID) are the same, and so is the probe switch. The
  LOW MUP block is now at sw `0x1721f5-0x172239` (bytes `0x2e43ea-0x2e4473`, page 34). The audio is CMP2's except in
  the probe mode.
- **Watermarks**: payload blocks, not FILLs. The stock stream uses FILL only with value 0, so a non-zero FILL value is
  unproven on the device [verified: all 37 stock FILLs are 0]. Each word is
  `0xC000C000 | ((a>>2) ^ 0x0A5C) & 0x1FFF | (((a>>2) ^ 0x15A3) & 0x1FFF) << 16`: position-dependent, and every 16-bit
  half is a short-compute parcel. This matters because the brick checker decodes payload blocks for its shift check:
  0 findings. The page table uses the same 13-bit-per-parcel encoding.
- **Scanner** (cmp_load.c `cl_scan`, from `cmp_load_end`). Each block it checks 64 words of the 45-page table:
  watermark pages word by word, code and data pages by Fletcher-32 against build.py's values. Bad pages are latched.
  A full sweep takes about 406 blocks (0.27 s).
  - **HIGH** = 2 px per bad page (at most 24), +1 px once any is a code page (odd = code).
  - **Right bar** = the lowest bad page number, 1 px per page, both direct and through the stock getter
    (q = n·655 + 300, a mid-pixel value).
  - The load meter is still measured but no longer shown.
- **Cost**: +4,400 instructions per block over CMP2 (est. +0.9 %; the unit sits near 50 %); stack 1,752 B.

## 4. Checks [verified, `out/T6.3/CMP2F-dsp/verify.json`, `tools/dspsplice/verify_cmp2f.py`, PASS, 107 s, RSS 340 MB]

- **(a) audio**: CMP2E's 11 settings × 600 blocks against CMP2, including the power-on state with LOW MUP 0 → 127,
  LOW ATK/REL moving, every band knob moving, a key, FX and MIX 0. **38,400 of 38,400 samples bit-identical in each**,
  with the state blocks identical as on CMP2E.
- **(p)**: the probe as CMP2E, 38,400/38,400.
- **(s)**: 3,000 blocks with every knob moving, FX and a key. 0 bad pages over the first 1,700 blocks (4+ sweeps), with
  the crumbs and the heartbeat as on CMP2E. Then three pokes:
  - a byte in watermark page 8: found 335 blocks later; HIGH 2 px, right 8 px (direct = getter);
  - a byte in a code page (mbcomp_gr_db, never called, page 36): HIGH 5 px (odd), right still 8;
  - a byte in page 2: HIGH 7 px, right 2 px.
- **(c)**: 0 stores outside CmpSlot, CmpTail, CmpLoad, stack, save area, outputs, `0x257c1c` and reply +0x10..+0x17;
  the watermarks and the table are never written. **(d)**: as above.
- **Build checks**:
  - encoding audit: 20,255 instructions, 0 unseen, no findings;
  - brick checker's DSP scans on the stream: parse ok, no cache hit, no region miss, **0 bad shifts**;
  - section 7 is 942,972 B (< 1 MiB), stored 627,226 B;
  - CMP2 → `1a888114`, CMP1 → `ee82aa7c`, CMP2F twice the same.

## 5. Static look for writers into `0x3160xx-0x3170xx` (stock image)

- **No decoded reference** [verified, sharcdb]: none of its literal, absolute-access, pointer or data-reference tables
  holds a value in the range in any view: byte, loader alias `0x2831…`, sw `0x18afc6-0x18bfff`, nw32 `0xc57e3-0xc5fff`,
  nw48 `0xc3a97-0xc3fff`. In all of block 2 the only such value is `0x300000`, a mask (T3.2 2.3).
- **Raw parcel scans** [verified]: the few hits are coincidences inside other encodings, e.g. at `0xb8b79b` and
  `0x1ca792`; none is an operand.
- **The loader**: no stock block writes L1 block 2 [verified].
- **DMA rings**: the SPI2 RX/TX rings and the second list use block 1 buffers (`0x2c29d0..0x2c64c0`) [verified, the
  `0x1ca46a` and `0x1ca59f` listings].
- **The C runtime init table** `PM(0xe00e0)` is 0, so no start-up memset or copy [verified, T3.2].
- **Stacks**: the FreeRTOS heap is in block 1 (`0x2d08b8-0x2dd0b8`) [verified, T3.2]; interrupt contexts go on the
  task stack [inferred].
- **Stock delay and reverb buffers** are in DDR [verified, T3.4].
- **The L1 PM cache** takes block 2's top: 16 KB at `0x31c000` (dnfw's reading), 32 KB would start at `0x318000`.
  64 KB would cover the unit-proven tape delay at `0x310000`, so it is not 64 KB [inferred].

**Statically nothing writes there.** A run-time writer, if there is one, should now show up as watermark pages 2-17.
