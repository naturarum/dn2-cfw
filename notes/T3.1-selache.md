# T3.1a: selache and the Digitone II DSP image

Date: 2026-10-05. Input: `ele3_out/04_type7.unpacked.bin` (section 7 of OS 1.12, 836,956 bytes,
sha256 `336e340aa0cdcd34e314cfa44849f709a3134f6bd4cd57dfc7e15702c83115e2`).
Marks: **[verified]** = checked against the bytes or run here; **[inferred]** = reasoned from structure.
Short-word (SW) addresses are VISA program-counter addresses; loader addresses are the byte
addresses in the boot stream (`L1 byte = 0x28000000 + 2 * SW`, `L2 byte = 0x20000000 + 2 * (SW - 0xb80000)`).

## Summary

- **The 1.12 DSP image is byte-identical to 1.11.** Its sha256 equals the DN2 1.11 section-7 hash
  recorded in digikit (`tools/sharcdb.py`, `docs/findings/11-sharc-cross-image-comparison.md`). So
  everything digikit measured on DN2 1.11's SHARC code applies to 1.12 unchanged. **[verified]**
- selache (commit `2b26d3b75c53063575bc5c820fa0d38879335187`, 2026-06-04, the same revision digikit
  pins) builds clean with `cargo build --release` (rustc/cargo 1.96.0, about 16 s, no warnings). **[verified]**
- Section 7 is a standard ADSP-2156x boot stream: 95 blocks, two applications (an init program run
  by an INIT block, then the main program), no CRC. Every byte of the stream is accounted for and
  every header checksum passes. digikit's parser gives the same blocks and the same memory. **[verified]**
- selache's VISA disassembler decodes this code well enough to read: the entry is a clean SHARC+
  C-runtime startup, functions open and close with the standard calling convention, and 596 of 603
  direct branch targets in the main program land on decoded instruction starts. Its widths are
  wrong for a few instruction classes (Type 3a/4a/7a/16a forms read as 32-bit, Type 3b read as 48-bit).
  It resyncs within a few instructions, but about 5% of instruction starts in the main program differ
  from a second, table-driven decoder. **[verified]**
- **selload writes exactly our block format.** Fed the final bytes of the stock L1 block-3 code,
  selload reproduces all 20 stock blocks (64 to 83) byte for byte, including the 68-byte code FILL
  blocks. The only change is the target address, because selload has no mapping for L1 block 3.
  **[verified]**
- Gaps that matter for rebuilding section 7 with new code: selload cannot address L1 block 3
  (`0x1c0000`, where the main program lives); it mangles DDR data unless the output section name
  contains `_bw`; by default it writes no FILL for data; it builds single-application streams (plus
  an optional CRC preamble). A whole-stream rebuild is not possible anyway, because we have no ELF of
  the stock program. The workable route is a block-level splice: keep the 95 stock blocks, insert
  selload's blocks for the new code before the FINAL block, and fix one FIRST-block argument. A
  scratch splice parsed with every check passing. Nothing has been tried on a device. **[verified]** for the parse only.

## 2. The block format selload writes (from `selload/src/ldr.rs`, `crc32.rs`, `cli.rs`)

Every block starts with a 16-byte, little-endian header, followed by its payload:

| offset | field | contents |
|---|---|---|
| +0 | byte 0 | `BFLAG[7:4] \| BCODE[3:0]` (BCODE from `-bcode`, default 0) |
| +1 | byte 1 | `BFLAG[15:8]` |
| +2 | HDRCHK | XOR of the other 15 header bytes (so the XOR of all 16 is 0) |
| +3 | HDRSIGN | `0xAD` (core 0) |
| +4 | u32 | target address (a loader byte address; a SW address for FIRST/FINAL) |
| +8 | u32 | byte count (payload length, or the fill length for FILL) |
| +12 | u32 | argument |

Flags selload uses: `FINAL` bit 15, `FIRST` bit 14, `IGNORE` bit 12, `INIT` bit 11, `CALLBACK`
bit 10, `FILL` bit 8. The parser and digikit also know `SAVE` bit 4, `AUX` bit 5 and `INDIRECT` bit 13.
Bit 9 is reserved.

The stream selload writes:
- **FIRST block:** flags `FIRST|IGNORE`, target = entry point (ELF `e_entry`, a SW address; `0x90004`
  if the entry is 0), count 0. The argument is the number of bytes after this header up to the end
  of the application, FINAL block included.
- **Data and code blocks:** flags 0, one block per ELF section (or one per segment between fills),
  target = the translated loader address, count = payload length, which is always padded to a
  multiple of 4. The argument is 0, or the payload's CRC32 when `-CRC32` is set (then the flag is
  `CALLBACK`).
- **FILL block:** flag `FILL`, no payload, count = fill length, argument 0 (the boot ROM writes
  `count` bytes of the argument, so zeros).
- **FINAL block:** flag `FINAL`, target = entry point, count 0, argument 0.
- **`-CRC32 [poly]`:** puts a preamble first: a `FIRST|IGNORE` block with argument `0x10`, then an
  `INIT` block with target `0x00B4003C` and argument = the polynomial (default `0xD8018001`), then the
  normal FIRST block. Payload blocks get `CALLBACK` and argument = CRC32 of the payload as it sits in
  the stream (reflected table, init 0, no final XOR). FILL and FINAL blocks carry no CRC.

Payload conversion, chosen per ELF section:
- SW (VISA) code: swap the two bytes of every 16-bit parcel. selache's ELF holds parcels big-endian;
  the stream holds them little-endian.
- IVT / 48-bit NW code (`sh_addralign <= 1`, names `ivt`, `iv_*`, or PM NW addresses): reverse each 6-byte word.
- Byte-width data (`_bw` in the section name, or an L1/L2 byte address): copied as is.
- Anything else ("normal word" data): 5-byte ELF words become 4 bytes (`[b0..b4] -> [b3 b2 b1 b0]`).

Address translation (`collect_sections`):

| ELF `sh_addr` | stream target |
|---|---|
| PM NW `0x080000-0x0bffff` | `4 * addr + 0x28000000` |
| PM SW `0x100000-0x18ffff` | `2 * addr + 0x28000000` |
| L2 SW alias `0xb80000-0xbfffff` | `0x20000000 + 2 * (addr - 0xb80000)` |
| L1 byte `0x240000-0x31ffff` | `addr + 0x28000000` |
| anything else (L2 byte `0x2000_0000+`, DDR `0x8000_0000+`, L1 block 3) | unchanged |

Fill policy: SW code gets fixed 68-byte FILL blocks, placed as late as possible in each zero run of
68 bytes or more and 4-byte aligned (2-byte scan step). By default data gets no FILL: the comments
say a data FILL broke booting on the author's UART-host setup. With `-MaxBlockSize`, data fills come
back as FILL blocks unless `-NoFillBlock` is also given. IVT code and L2 sections are never filled.
Order: L1 sections first, sorted by address, then L2 sections. The boot mode `-b` is parsed but
`ldr.rs` never reads it, so it does not change the output. **[verified]** by reading the source, and
by running selload on test programs and parsing the output (section 5).

## 3. Our stream: `scripts/sharc_ldr_parse.py`

```
python3 scripts/sharc_ldr_parse.py --digikit vendor/digikit --dump-payloads
```

Stdlib only. Outputs (git-ignored) in `out/T3.1/`: `blocks.json` (every block, the checks, the
regions), `image/final/<start>-<end>.bin` (memory after the whole stream, last write wins),
`image/app0/` (memory at the moment the INIT block runs), `segments_final.tsv` (which block supplied
each final byte range), and `payloads/`.

**Checks, all PASS on 1.12** **[verified]**:
- The chain parses to the last byte: 95 headers (1,520 bytes) + 835,436 payload bytes = 836,956. No
  byte is unowned or owned twice.
- Every HDRCHK makes its header XOR to 0. Every HDRSIGN is `0xAD` (core 0). There are no undocumented
  flag bits, and BCODE is 1 on every block.
- All byte counts are multiples of 4, and all load targets are 4-byte aligned.
- FIRST arguments: block 0's `0x2964` and block 7's `0xc9bd8` are exactly the byte distance to the
  next FIRST block or to the end of the stream.
- FINAL (block 94) target `0x1c12e2` = the last FIRST target.
- No CALLBACK blocks, so the stream carries no per-block CRC. The integrity checks are the header XORs
  plus the container's own checks (section byte sum and HMAC, already verified in HANDOFF).
- 37 FILL blocks, all with fill value 0, writing 5,601,712 bytes in total.

Observations for T3.2:

## 4. selache's disassembler on our code: `scripts/sharc_visa_disasm.py`

```
python3 scripts/sharc_visa_disasm.py          # init, l1b3_low, main, l2, l2ext
```

Method: take a region from the final image, swap the bytes of every parcel to selache's big-endian
order, and wrap it in a minimal ELF32 (`e_machine 0x85`, one `SHT_PROGBITS` ALLOC|EXEC section
`seg_swco` with `sh_entsize 1`, which selects seldump's VISA decoder, and `sh_addr` = the region's
SW address). Then run selache's unmodified `seldump -ns seg_swco`. Listings go to
`out/T3.1/disasm/<region>.txt`, numbers to `summary_*.json`.

As a second opinion, the script runs a width-only decoder over the masks, values and widths in
digikit's `tools/sharcspec/decode_table.json`. It reads that file as data and does not run digikit's
code. The selection rule is digikit's: the longest leading run of fixed bits wins.

**Does it decode VISA correctly?** Mostly, yes. **[verified]**

| region (SW) | bytes | instructions (16/32/48-bit) | `???` | starts shared with table decoder | width disagreements |
|---|---|---|---|---|---|
| init `0x1201f8-0x12161c` | 10,312 | 2,279 (366/949/964) | 0 | 2,271 | 3 |
| l1b3_low `0x1c0000-0x1c12e0` | 9,664 | 2,026 (207/832/987) | 7 (0.33% of bytes) | 1,930 | 21 |
| main `0x1c12e2-0x1cdffe` | 105,016 | 22,446 (2,654/9,522/10,270) | 161 (0.71%) | 21,338 (95.1%) | 259 |
| l2 `0xb80000-0xb8f440` | 125,056 | 27,549 (3,772/12,575/11,202) | 67 (0.22%) | 26,829 (97.4%) | 208 |
| l2ext (block 57) `0xb8f444-0xb97866` | 67,652 | 14,847 | 569 (3.86%) | 8,908 | 1,052 (data, not code) |

**Is the decoded code coherent?** Yes. **[verified]**
- The entry `0x1c12e2` reads `r0=dm (0x31400)` / `r0=bset r0 by 0x0` / `dm (0x31400)=r0`, then
  twelve 48-bit NOPs. That is the SHARC+ BTB-disable sequence and its errata padding, the same one
  selache's own `libsel/src/support/startup.s` uses. Next it clears the hardware loop, status and PC
  stacks (`pop loop`/`pop sts`/`pop pcstk` loops at `0x1c1391-0x1c13b8`), stores the entry address
  to `0x3108c02c`, and calls `0x1c0e70`. Then come C calls such as
  `cjump 0xb8b5b0 (db); dm (i7,m7)=r2; dm (i7,m7)=0x1c13cd`, where the pushed return address is the
  next instruction minus 1, as the SHARC C convention expects.
- `0x1c1311 jump 0x1c0000` goes to `dm (0x3e000)=r0`, twelve NOPs and `jump 0x1c1314`, which comes
  straight back.
- The init program at `0x120230` is the same kind of C code: `r8=0x1312d00`, then `cjump` calls with
  the same delay-slot pushes.
- Returns follow the C convention: `i12=dm (m7,i6)` ... `jump (m14,i12) (db)` ... `rframe`. The main
  program has 304 `jump (m14,i12)`, 305 `rframe` and 138 complete three-part epilogues. L2 has 716,
  650 and 459.
- Call targets look like function starts. `main` calls 241 distinct `call`/`cjump` targets: 132 in
  `main`, 91 in L2 code, 9 in `l1b3_low`, and 9 elsewhere (probably from misdecoded rows). Of the
  132 inside `main`, 130 are decoded instruction starts. 113 of those follow an `rframe` or a `nop`
  (the end of the previous function). The most common first instruction is `i7=modify (i7,-N)(nw)`
  (59), the stack-frame allocation selcc emits too.
- Branch targets: 596 of the 603 direct `call`/`cjump`/`jump 0x...` targets in `main` that land in
  loaded memory fall on a decoded instruction start. In `l2` it is 1,004 of 1,005, and in `init`
  72 of 72. 604 of the 620 direct branches in `main` are `cjump` (the C call).

**Where selache is wrong.** A width disagreement starts where both decoders begin an instruction but
pick different widths. Branch targets that land on a start only one decoder has count as a vote
for that decoder. **[verified]**

| first parcel (example) | selache | table | main: targets for selache / table | l2 |
|---|---|---|---|---|
| `59be` Type 3a (`0x1c179d 59be0313`) | 32-bit | 48-bit | 4 / 97 | 1 / 22 |
| `6a3e`, `6abe`, `6afe` Type 4a | 32-bit | 48-bit | 10 / 17 | 4 / 11 |
| `9980`, `9b80`, `9780` Type 16a | 32-bit | 48-bit | 0 / 2 | 2 / 19 |
| `043e`, `043f` Type 7a | 32-bit | 48-bit | 8 / 6 | 3 / 15 |
| `593e` Type 3b (`0x1c1f50 593e963f9908`, printed `compute(0x3f9908) , ...`) | 48-bit | 32-bit | 0 / 0 | 0 / 0 |

- DO-loop ends (`do (pc,X) until`, taking the low 23 bits of the printed offset) land on table starts
  85 of 85 times in `main`, and on selache starts 64 of 85 times. selache prints most DO offsets with
  bit 23 set (77 of 93 in `main`, e.g. `lcntr=0x400 , do (pc,0x800003)until lce` at `0x1c132b`).
- PC-relative jumps land on table starts 1,101 of 1,150 times in `main` and on selache starts 1,005
  of 1,150 times.
- digikit already documents the Type 4a width bug and a merged Type 3c pair (`90 34 90 15`) in
  `docs/findings/05-sharc-isa-and-decoding.md`. The `59be`/Type 3a class, which has the most hits
  here, is not in that list.
- The table decoder is not authoritative either. Its `Type21p_undoc16`/`Type22p_undoc48` forms are
  provisional (they decide `0x0000` and `0x0081`), and in `init` and `l1b3_low` a few votes favour
  selache.
- Unknown rows in `main` start mostly with `663e`, `643e`, `643f`, `623e`, `1a58` and `1a52`.

**Text round trip** (`scripts/sharc_visa_roundtrip.py`). Each unique (bytes, text) row of `main`,
`l2` and `init` (21,003 rows) was re-assembled with `selas -proc ADSP-21569` **[verified]**:
- 17,166 (81.7%) give identical bytes.
- 1,343 (6.4%) give a different length. In 1,199 of them selas picks a shorter encoding for the same
  text (for example a 48-bit `nop` becomes `0001`, and `i7=modify (i7,m0)(nw)` becomes 32-bit), so the
  image uses uncompressed forms. In 144, selas only has a longer form (for example `9fc40000`
  `dm (i7,m7)=0x0` is re-assembled as 48-bit).
- 1,885 (9.0%) give the same length but different bits, so a field decodes and encodes differently.
  The most frequent differing bits include bit 40 of the 48-bit word, the Type 3 M-register field
  digikit reports selache misreading.
- 609 (2.9%) give text selas cannot parse (`compute(0x...)`, `ureg(0x..)`, `shift(..)` placeholders).

Verdict: good enough to read and navigate the code, and to find functions, calls and the calling
convention. It is not good enough to trust instruction by instruction without a second decoder. Any
code we write should be assembled from our own source, not re-assembled from a disassembly.

## 5. Can selload produce our format?

Test programs (scratch) built with `selcc`/`selas` + `seld` + `selload -proc ADSP-21569 -bcode 1`,
then parsed by `sharc_ldr_parse.py` **[verified]**:
- Header layout, HDRCHK, HDRSIGN `0xAD`, the FIRST block (`0x5001` low half, argument = bytes to the
  end of the application), FINAL (`0x8001`, target = entry), FILL (no payload, argument 0) and BCODE
  are all identical to ours.
- `-CRC32`: the parser's CRC32 check matches selload's CRCs on all three CALLBACK blocks. Its preamble is the
  same two-application shape as ours (FIRST, INIT, FIRST).
- SW code payload = the ELF bytes with each parcel swapped. BW data = the ELF bytes.

`scripts/sharc_selload_repro.py`, run against the stock bytes **[verified]**:
- **L1 block 3 code (stock blocks 64-83):** the final bytes are fed to selload as four SW code
  sections, split where stock blocks abut, and moved 0x80000 bytes down into L1 block 2. **All 20
  blocks come out identical**: payloads, sizes, the eight 68-byte FILL placements, flags and
  arguments. Only the target address differs, by the shift. So the stock stream was made with the
  same code-fill rule selload implements.
- **L1 block 1 data (stock blocks 38-55):** with the defaults, selload writes one 0x1d52c-byte block
  where stock has 18 blocks, because data FILL is off. With `-MaxBlockSize 0x7FFFFFFC` it writes 18
  blocks, 6 identical. The others differ by one word: stock keeps 4 more zero bytes in each data block
  before its FILL (e.g. stock block 41 is `0x9c2c` bytes, selload's `0x9c28`). That could be different
  section boundaries in the original ELF. **[inferred]**

What matches and what does not:

| point | stock section 7 | selload | effect |
|---|---|---|---|
| header, HDRCHK, HDRSIGN, BCODE | 16 B LE, XOR 0, `0xAD`, BCODE 1 | same (`-bcode 1`) | none |
| FIRST/FINAL semantics | arg = bytes to end of application; FINAL target = entry | same | none |
| code payload byte order, code FILLs | parcels LE, 68-byte fills | identical output (20/20 blocks) | none |
| two applications (init program + INIT, then main) | yes | single application, or the CRC preamble only | keep the stock app 0 as is |
| L1 block 3 (SW `0x1c0000-0x1cffff`, byte `0x380000-0x39ffff`) | main program lives here | not translated: a block-3 SW section is written to target `0x001c0000` instead of `0x28380000` | patch selload's two ranges (`PM_SW_END` to `0x1d0000`, `BW_L1_END` to `0x3a0000`) or rewrite targets after the fact |
| DDR `0x80000000+` data | byte data | treated as 5-byte "normal word" data and mangled (64 test bytes came out as 52), unless the output section name contains `_bw` | name DDR sections `*_bw` (tested: then correct) |
| data FILLs | variable-length data FILLs (5.1 MB of them in DDR) | none by default; on with `-MaxBlockSize`, boundaries off by 4 bytes | a whole-stream rebuild would grow by MBs; irrelevant for a splice |
| block order | L1 b0/b1, L2, L1 b0 patches, L1 b3, DDR | L1 by address, then L2 | none for a splice |
| CRC | none | only with `-CRC32` | don't pass it |

**Rebuilding section 7.** selload cannot regenerate the whole stream, because there is no ELF of the
stock DSP program. The format is not the obstacle. The workable route is a block-level splice: parse
the 95 stock blocks, insert the new data/code blocks taken from selload's output (without its FIRST and
FINAL) just before block 94, add their wire size to block 7's argument (`0xc9bd8`) and recompute block
7's HDRCHK. A scratch test inserted two selload blocks into L1 block 2. The result was 837,360 bytes,
parsed cleanly, and passed every check, including the FIRST argument (`0xc9d6c`). **[verified]** for the
parse only. Nothing was saved in `out/`, and it is not for flashing.

Limits still open:
- The ColdFire uploads section 7 to the DSP over SPI. digikit's DN2 1.11 note
  (`docs/refs/dn2-dspi2-cross-check-2026-09-16.md`) says routine `0x400cf34c` mallocs 1 MB for it. If
  1.12 does the same, a rebuilt stream should stay under 1,048,576 bytes: 211,620 bytes of headroom over
  stock. **[inferred]** Not checked on 1.12.
- Where new code can go without clobbering run-time state (L1 block 2, the L2 tail, DDR) is T3.2's
  job; no claim is made here.
- The selload comment about data FILLs breaking boot does not seem to apply to this boot path: the
  stock stream uses data FILLs everywhere and boots. **[inferred]**
