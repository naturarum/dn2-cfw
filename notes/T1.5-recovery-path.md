**[inferred]** = reasoned from structure; **[open]** = not resolved. All addresses are in the
bootstrap (section 2), which runs at `0x80000400` (file offset 0 = `0x800003FC`), unless noted.

## Answer, in one line

**No content of flash at `0x80000` and above can stop the STARTUP menu from appearing when FUNC is
held.** [verified, static + 15 emulated boots] The menu lives inside the bootstrap (flash
`0x40000`-`0x80000`), draws from code and font tables inside the bootstrap, and reads the panel,
not the container. The one thing in the stored container that changes the boot is section 2's
table entry: a bumped bootstrap version there drives the boot-time self-upgrade, and the only
outcomes of that are (a) it does nothing, or (b) it *force-opens the same recovery menu*, or
(c) with a genuinely modified, resealed, higher-versioned **bootstrap image** it re-flashes
`0x40000` -- which is why section 2 and its table entry must stay stock.

## 1. The complete power-on decision tree

Every address below is in `out/T1.5/boot.dis` (`m68k-elf-objdump -m m68k:cfv4e`). [verified]

### Reset entry `FUN_80000de8` (`0x80000de8`)

1. `0x80000de8`-`0x80000e34` clock/DDR controller bring-up (`0xEC09000E`, `0xFC0C0004`); spins at
   `0x80000e36` on `0xFC0C0008` bit 4 (PLL lock). Hardware, no flash.
2. `0x80000e56` sets `RAMBAR1` (SRAM at `0x80000000`). `0x80000e5a`-`0x80000e6e` copies
   `0x80007900..0x80007a55` to SRAM `0x8000F000`: the SPI-NOR read (`0x80007910`->`0x8000F010`)
   and "run section 4" (`0x80007a00`->`0x8000F100`).
3. `0x80000e76`-`0x80000e96` builds the exception table at `0x80000000` (all vectors -> `0x80000416`
   `rte`) and sets `VBR` = `0x80000000`.
4. `0x80000e9a` `tst.l d2`. **d2 is the reset selector.**
   - **d2 == 0** (normal power-on): fall through to step 5. [verified it is 0 on the cold path]
   - d2 in 1..5: jump table at `0x80000ed4` to debug/alternate entries (several reach
     `halt; tpf.l #0x10adc0de` at `0x80000f16`/`0x80000f22`, i.e. factory/debug stubs). Not a
     cold-boot path. [verified code; **[inferred]** these are JTAG/warm entries]
   - d2 > 5: returns at `0x80000f40` (does nothing).
5. `0x80000ee0` `jsr 0x800009c6` -- **init: clocks, panel, self-upgrade, and the STARTUP-menu
   decision all happen here** (see §1b). This call returns only if the menu was not entered, or
   was entered and EXITed.
6. `0x80000ee4` `moveq #64,d0; and.l 0x80008404,d0` -- test **boot-flag bit 6**.
   - bit 6 set -> `0x80000eee` `jsr 0x8000F100` run **section 4** (the factory board-test program;
     it has its own in-place main-OS loader `0x8000357c`, stage `0x40200000`). [verified]
   - bit 6 clear -> `0x80000ef4` `jsr 0x80000596` the **normal main-OS loader** (reads section 3
     from flash `0x80000`+offset to `0x40400000`, depacks to `0x40000400`).
7. `0x80000efc`-`0x80000f08` enters the main OS at `*(0x40000400)` (= `0x400004e8`), passing the
   boot-flags word.

### Init `FUN_800009c6` (`0x800009c6`) -- where recovery is decided

In call order [verified]:

1. `0x80000a70`-`0x80000a7e` DYB-lock flash sectors `0x0` and `0x40000` (`FUN_80002742`). Only on a
   Spansion S25FL (`0x01 2018`); no effect on other parts (T1.4 M1).
2. `0x80000a80` `jsr 0x800006ac` DDR training; sets the DRAM-trouble flag `0x800083FC`.
3. `0x80000aea` **`jsr 0x80001c48` -- the self-upgrade. It runs on every boot, before the menu.**
   (§2). Returns 0 if it did nothing, or a non-zero error code after showing an error screen.
4. `0x80000af6`-`0x80000b1a` build the boot-flags word `0x80008404`: `d2 = (self-upgrade returned
   non-zero)`; flags seeded from the DRAM flag `0x800083FC << 17` and a strap bit (`0x80005884`,
   `0xEC094019 & 8`).
5. `0x80000b20`-`0x80000b3c` **reset-cause / RAM-magic branch**: if RCM reset-status
   `0xEC090001 & 0x20` (a software reset) **and** `*0x48000000 == 0xB0B0DADA` -> set **bit 5**
   (maintenance). This is the main-OS console `#REBOOT_INTO_MAINTENANCE` handshake.
6. `0x80000b42` drain panel link; `0x80000b4e`-`0x80000b66` read panel firmware version
   (`FUN_80001518`) into `0x80008400`, with a timeout flag.
7. `0x80000b8e` **`jsr 0x80001276` -- the panel key read** over UART8. Returns 0 (all expected key
   bytes arrived) or **-1 on timeout**.
   - **-1 (panel silent)** -> `0x80000b9a` `or #0x60` sets **bits 5 and 6** (maintenance + the
     section-4 path). [verified this is the only setter of bit 6]
8. `0x80000c26`-`0x80000da8` **key-combo branches** (only when the self-upgrade did not fail,
   `d2 == 0`):
   - 5 keys `{0x12,0x13,0x14,0x15,0x23}` held (`FUN_8000136c`, table `0x80005ed6`) ->
     `0x80000c42` set **bit 5** (maintenance). [verified]
   - else 3 keys `{0x0b,0x0e,0x26}` held (table `0x80005eea`) -> `0x80000da8` set **bit 8**.
   - else fall to the FUNC check.
9. `0x80000c4a`-`0x80000c66` **the STARTUP-menu gate**: `pea 0x11` (FUNC keyid) `jsr 0x80001302`
   tests the FUNC bit in the key bitmap. The menu `FUN_80002dc4` is entered when
   **FUNC is held, OR the self-upgrade returned non-zero (`d2 != 0`)**; its argument is `d2`
   (0 = full menu; non-zero = reduced "forced recovery" menu). [verified]
10. `0x80000c68`-`0x80000d6c` post-menu init: panel LEDs, read **section 5** (the build-timestamp
    string, `FUN_80005462(5)`) and draw it *if present*; a failed read just skips the draw.
11. `0x80000d72` `tst.l 0x800083FC; beq +; halt` -- **halts if the DRAM-trouble flag is set**
    (`0x80000d7a`). A hardware gate, not flash-dependent.
12. returns to the reset path (step 6 above), which then tests bit 6.

### Outcomes and the inputs each depends on

| outcome | entry | set by | inputs |
|---|---|---|---|
| **STARTUP menu** | `0x80002dc4` from `0x80000c60` | FUNC held (`0x80001302`, keyid `0x11`) **or** self-upgrade failed (`d2`) | panel keys; section-2 table version (via `d2`) |
| normal main-OS boot | loader `0x80000596` from `0x80000ef4` | boot-flag bit 6 clear and menu not entered/exited | panel answered, no FUNC; container section 3 |
| section-4 path | `0x8000F100` from `0x80000eee` | boot-flag bit 6 set | panel key read timed out (`0x80001276` = -1) |
| maintenance mode (bit 5) | flag, read by main OS `0x40287a60` | `0x80000b3c` (RSR `0x20` + `0x48000000`=`0xB0B0DADA`), `0x80000c42` (5 keys), `0x80000b9a` (panel timeout) | reset cause + RAM magic; or 5 keys; or panel silent |
| self-upgrade (reflash `0x40000`) | `0x80001c48`, writes at `0x80001dxx` | incoming section-2 version > `0x0201` **and** its CRC+version+length checks pass | container section-2 table entry `0x80020+` and section-2 content |
| hang: DRAM | `halt` `0x80000d7a` | DRAM-trouble flag `0x800083FC` set | hardware only |
| hang: self-upgrade done | spin after "COMPLETE" in `0x80001c48` | a successful bootstrap reflash | needs a resealed higher bootstrap |
| abort: OS-UPGRADE commit fail | `0x80003bfc` spin | checksum/HMAC of a *received* file fail | only reachable from inside the menu |

## 2. Does any flash content stop the menu? (the safety question)

**No.** [verified, static + emulated]

### What the menu and its recovery item read from the container

Reachability over the bootstrap call graph (`out/decomp/bootstrap/xrefs.sqlite`), from each entry,
to the flash-touching routines (`FUN_80007910` SPI read, `FUN_800053ec` header, `FUN_80005462`
lookup, `FUN_8000470c` serial, `FUN_80002896` erase, `FUN_8000282a` program) [verified]:

- **Entering and drawing the STARTUP menu `FUN_80002dc4`, and idling in its key loop**: reads **no
  flash at all**. It draws from code and from the font/glyph tables that `FUN_80001a04` builds out
  of bootstrap rodata (`0x800063a0`), and it reads keys from the panel (`FUN_800013ac`). The only
  flash-touching functions reachable from the menu are the *erase/program* inside the OS-UPGRADE
  commit, which run only after a valid file is received and its checksum+HMAC pass.
- **"4 OS UPGRADE" (`FUN_80003e5a`)**: draws "READY TO RECEIVE", then spins on `DAT_80008f40`
  waiting for the UART9 (DIN-MIDI) ISR `FUN_800038fa` to assemble a file. It reads **nothing** from
  the container while waiting (confirmed dynamically, §3). The commit `FUN_80003c9c` it finally
  calls *writes* (erase from `0x80000`, program), gated on the received file's own content checksum
  (inline `0x80003ca6`) and HMAC trailer (`FUN_80005e3a`); on failure it shows "UPGRADE ABORTED"
  and spins (`0x80003bfc`). It never *reads* the stored container.
- **"1 TEST MODE" (`FUN_80002ae6` -> `FUN_80004942`)** is the only menu item that reads the
  container: section 5 (build info, via `FUN_80005440`/`FUN_800053ec`) and the `0x3c0000` serial
  record (`FUN_8000470c`). Both are read defensively -- a failed/garbage read is shown as "WRONG
  CARD"/absent, not acted on -- and neither is on the path to recovery.

So a corrupt, truncated, all-`0xFF`, or hostile-but-sealed container changes nothing about whether
the menu appears or whether OS UPGRADE can receive a stock file.

### The self-upgrade `FUN_80001c48` and garbage in the table

It runs on **every** boot, at `0x80000aea`, **before** the menu. Its logic [verified from the
decompile and the bytes]:

1. `FUN_80005462(2, entry)` looks up section 2's 16-byte table entry (scans `0x80020+16k`, needs
   the ELE3 magic+`'4'` at `0x80000`). **If the lookup fails** -- no container, truncated before
   the entry, or an all-`0xFF` region -- it **returns 0 immediately** (does nothing).
2. `if (incoming_version <= 0x0201) return 0;` -- the running version is `0x0201`
   (`0x80000408`). A stock table entry is `0x02010000`, so **stock does nothing**.
3. Only if the table claims a **higher** version does it proceed: read section-2 content to
   `0x40400000`, depack to `0x40410000`, check CRC-32 residue (`0xDEBB20E3`), check the *unpacked*
   version word (`0x4041000c`) equals the table version, check unpacked length `< 0xF001`; then
   **DYB-unlock + erase + program `0x40000`** and spin on "COMPLETE / PLEASE RESTART ME".
   Any check that fails shows an error ("LENGTH ERROR" / "CRC CHECK" / "VERSION CHECK"), waits
   ~2 s, and **returns the non-zero code** -- which makes `d2 != 0` and **force-opens the recovery
   menu** (`0x80000c56`).

So with garbage, a truncated stream, or an all-`0xFF` region the self-upgrade is a no-op; with a
table whose version is bumped but whose section-2 content is unchanged it fails the version check
and *drops you into the recovery menu*; it only reflashes `0x40000` when fed a genuinely modified,
correctly resealed, higher-versioned bootstrap. That last case is the sole way stored-container
content reaches the bootstrap region, and it is exactly what the brick checker forbids (§4).

Reading the table [verified, 15 runs]:

- **Every FUNC-held case reaches the live STARTUP menu** -- the landmark order is
  `selfupg > menu > drawflush > menu_keypoll`, i.e. the self-upgrade ran and returned, the menu
  (`0x80002dc4`) was entered, it drew a full screen (flush `0x80001ab4`), and it is sitting in its
  key-input loop (`0x800013ac`). The menu is **byte-identical** across stock, corrupt-main,
  all-`0xFF` and truncated (1486 lit pixels each): proof it does not depend on the container. The
  rendered screen (`out/T1.5/art/stock_func.txt`) reads `STARTUP MENU` (inverted title) over
  `1 ... TEST MODE / 2 ... EMPTY RESET / 3 ... FACTORY RESET / 4 ... OS UPGRADE / 5 ... EXIT`.
- **No key** -> the init returns with bit 6 clear and the normal loader runs. **Silent panel** ->
  the key read times out, bits 5+6 are set (`boot_flags=0x40060`), and section 4 runs. Neither is a
  menu case, as expected; both are reached whatever the container holds.
- **hostile-sec2** (section-2 table version bumped to `0x0202`, content left stock): the
  self-upgrade fails its version check (unpacked version `0x0201` != table `0x0202`), returns
  non-zero, and the **menu is force-opened even with no key and even with the panel silent**
  (1129 lit pixels = the reduced recovery menu, `TEST MODE` + `OS UPGRADE` only, no EXIT). This is
  a recovery aid, not a brick.
- **No run reached a bootstrap-region flash write.** The `flash_erase`/`flash_program` landmarks
  (`0x80002896`/`0x8000282a`) never fired in any of the 15 runs.

### OS UPGRADE receive path, driven

A separate probe (`out/T1.5`, `osupgrade=True`) runs to the live menu, then follows the menu's
"4 OS UPGRADE" branch into `FUN_80003e5a` (the only synthetic step is the key-navigation; the
receive setup, the "READY TO RECEIVE" draw and the MIDI-driven wait all run unmodified). Result,
for both stock and all-`0xFF` flash [verified]:

- reaches `READY TO RECEIVE` (rendered in `out/T1.5/art/osupgrade_ready.txt`) and then the
  MIDI-wait spin `0x80003ede`;
- **flash reads after entering OS UPGRADE: none.** The receive path reads only UART9; it does not
  touch the stored container. (That the commit then accepts a stock file end-to-end is already
  shown by T1.2's `bootcheck`, which reaches UPGRADING on stock, `-r` and recompressed-l0.)

### What the harness stubs, and what runs for real

Runs unmodified: the whole reset path and `FUN_800009c6`, the self-upgrade `FUN_80001c48` (CRC,
version and length checks, depacker), the section lookup `FUN_80005462`/`FUN_800053ec`, the key
bitmap parser and testers (`FUN_80001302`/`FUN_8000136c`/`FUN_80001330`), the menu `FUN_80002dc4`
and its key loop, the OS-UPGRADE receive `FUN_80003e5a`, and all panel drawing.

Stubbed (each returns to its caller; the caller cleans its own args, as on hardware):
`0x800057a4` INTC/autovector setup, `0x8000240a` misc peripheral config, `0x800006ac` DDR bring-up
(and the DRAM-trouble flag `0x800083FC` is left 0 so the gate at `0x80000d7a` is not taken),
`0x800008cc`/`0x80000962` UART8/9 controller init, `0x80005336` panel power GPIO, `0x80002742` DYB
protect, `0x8000065a` busy-wait delay, `0x800010e6`/`0x800015bc`/`0x80000ff8` panel drain/detect,
`0x80005884` a GPIO strap. The panel version `FUN_80001518` and key read `FUN_80001276` are
answered per scenario; the FUNC bit is set at bitmap byte 2 bit 0 (keyid `0x11` -> bit `0x10` via
the table at `0x80006dc0`, byte `0x10>>3`, bit `0x10&7`), exactly as the real parser lays it out.
The SPI-NOR read (`0x8000F010`/`0x80007910`) is served from the flash image. `WDEBUG` at
`0x80000eb8` is overwritten with three NOPs in memory because QEMU's m68k core aborts translating
the basic block that contains it before any hook can fire.

Status MMIO forced so the hardware polls end: `0xFC0C0008`=`0x10` (PLL lock, bit 4, long read),
`0xEC070004`=`0x04000000` (UART8 USR TX-ready bit 2, byte read), `0xEC074004`=`0x0C000000`
(UART9 USR, MIDI path).

Nothing in the harness talks to hardware; the firmware and everything derived from it are read
only.

## 4. What a mod must never change to keep recovery intact

Recovery = hold FUNC at power-on -> STARTUP menu -> TRIG 4 OS UPGRADE -> send stock `.syx` over DIN
MIDI. Everything it needs lives in the **bootstrap (flash `0x40000`-`0x80000`)** and the **front
panel**, not in the stored container's main-OS/DSP sections. So:

1. **The bootstrap, section 2, must stay byte-identical to stock, and its section-2 table entry
   (`0x02010000`) must keep version `0x0201`.** [verified] The menu, the FUNC decision, the key
   parser, the UART8/UART9 drivers, the font, the OS-UPGRADE receive and the verify-and-commit all
   live here. A higher version in section 2's table entry *plus* a resealed higher section-2 image
   is the one and only way the self-upgrade `FUN_80001c48` rewrites `0x40000` -- a bricking risk and
   an unnecessary one. Keep section 2 and its table entry exactly stock.
2. **Never let an in-OS or console writer erase/program below `0x80000`, and keep the container
   `<= 0x200000` bytes** (T1.4): the normal writer `FUN_40139104` has no length clamp and wraps
   24-bit addresses, so an over-long container can reach `0x380000`/`0x3c0000` and, past `0xF80000`,
   wrap onto `0x0`/`0x40000`. The bootstrap region must never be a write target.
3. **Keep section 4 (the factory board-test program) and its in-place loader stock, and keep every
   build's depack margin non-negative at both `0x40400000` and the in-place `0x40200000` stage**
   (T1.2/T1.11). When the panel key read times out, the bootstrap boots through section 4's
   loader; a build that underflows the in-place stage hangs there with no menu (the panel is not
   answering on that path) -- a soft brick until the panel works. Stock has +31,182 B of margin;
   never flash a default-level recompressed build.
4. **Keep the panel-MCU firmware blob, its version word and its updater stock** (T1.4): main-OS
   `FUN_400dbbd8` reflashes the panel from the blob at `0x402F7D40` when the panel reports a version
   below `0x15`. The STARTUP menu is useless without a working panel (FUNC, the menu keys and the
   LED/label traffic all go over UART8/9 to it), so the panel updater and its blob must stay stock.
5. **Keep the `0x3c0000` serial record and the `0x380000` test/flag record intact** -- TEST MODE
   reads them, and the container must never be long enough to erase them.
6. **Do not introduce a software-reset into `0xB0B0DADA`@`0x48000000`, 5-key, or panel-timeout
   path on the mod side**; these set maintenance/section-4 flags. They are not recovery and must
   not be triggered inadvertently (no new `0xB0B0DADA` stores -- T1.4 R7).

If all of the above hold, the FUNC-held STARTUP menu and its OS-UPGRADE-over-MIDI receive are
reachable for any main-OS/DSP content the container might hold, including a half-written or erased
one. Verified here across corrupt, truncated and all-`0xFF` containers.

## 5. Harness usage (for the brick checker, T1.7)

`vendor/digikit/tools/recovery_harness.py` -- run from the digikit tree (`uv` env set up):

```
cd vendor/digikit
uv run python tools/recovery_harness.py \
    --stock /path/Digitone_II_OS1_12.syx \
    --boot  /path/ele3_out/01_type2.unpacked.bin \
    --json  out/T1.5/matrix.json --art out/T1.5/art
# options: --case {stock,corrupt-main,all-0xFF,truncated,hostile-sec2}  --panel {func,none,silent}
#          --limit N (instruction budget)
```

It prints, per case, where the run stopped, the landmark order, the boot-flags word, the flash
reads, and the number of lit pixels in the panel buffer; `--art` writes the rendered screen. For
the brick checker, the useful assertion is: **with the candidate's own bootstrap (section 2) and a
flash image built from the candidate's container, the FUNC run must stop at `menu_keypoll` with the
menu drawn, and no run (any panel, any case) may reach `flash_erase`/`flash_program`
(`0x80002896`/`0x8000282a`).** A candidate whose section 2 or section-2 table entry differs from
stock is the case to watch: if a FUNC run on it ever reaches a bootstrap write, refuse.

The harness returns the matrix as a dict from `main()`, and `run(container, Panel(mode), ...)` can
be called directly on an assembled container for a single case.

## 6. Caveats / open

- The hardware bring-up (clock tree, DDR, INTC) and the panel's wire protocol are stubbed, not
  emulated; the recovery decision depends on the panel's *answer* and on flash content, both of
  which run for real. [stated]
- The end-to-end OS-UPGRADE *commit* on received MIDI is not re-run here byte-for-byte (it is
  ~1.8 MB of SysEx); T1.2's `bootcheck` already shows the commit `FUN_80003c9c` accepts stock,
  `-r` and recompressed-l0 and reaches UPGRADING. [cross-ref]
- The self-upgrade reflash of `0x40000` was shown to be *not reached* on any tested container; a
  run that forces a matching unpacked+table version to observe the erase/program directly was not
  done (the writes are DSPI-driver spins under emulation). The decision logic is covered statically
  from the decompile. [open, low value]
