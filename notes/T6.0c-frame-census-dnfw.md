DSP: section 7 of OS 1.12 (byte-identical to 1.11), stock depacked boot stream `out/T3.8/stock/section_7_blob.bin`.

## 1. What dn2_firmware_explore reported, in our words

- They ran their own census on the 1.11 DSP image with their own runner (digikit's Runner plus their fixes): real
  ColdFire frames from the emulator (machine types 0-4), our two augmentations from T6.0 (random FX block and
  header flags; random slots, owners and tail), and fully random frames crossed with filter type. 3,285 blocks.
- They agree with T6.0: the 30-word tail is never read and never copied; six words are read straight from the
  receive buffer (`0x22`, `0xa54`, `0xa56`, `0xa7a`, `0xa7c`, `0xa7e`) by `0x1c2cd6`, `0x1c3084`, `0x1c3052`,
  `0x1c3069`, `0x1c309c`; the two 672-word copy loops are as we described.
- Their first pass found readers of `0x2a`, `0xa18` and slot `+0x50` (`0x9a8` on track 15) at `0x1c2545`,
  `0x1c1fda`, `0x1c1fe3`, and one case where flipping `0x2a` changed DSP memory. They traced these reads to a
  floating-point multiply-accumulate loop (`0x1c1fca..0x1c1fe3`, sibling `0x1c2535..0x1c254e`) whose pointer
  went wild in randomised frames: I0 = `0x258f68` with real frames, `0xffeb5968` with random slots, owners and
  tail, `0x804acf94` in a fully random frame. Their runner wraps such an address into the receive page, so the
  loop appeared to read frame words.
- Replaying those variants with both words flipped changed 0 DSP memory words (4 variants, 2 blocks each),
  against 131-647 words per block for a flipped track level. So `0x2a`, `0xa18` and `+0x50` stay unused.
- Their method: in a randomised block, a read outside the copy loops is first a question about the pointer
  register; a read only counts as a dependence if flipping the word changes DSP memory.
- Open on their side: (1) which frame field feeds I0; (2) three variants where their runner stopped on an
  unmodelled MMR at `0x1c1fca` and `0x1c2535` before the flip comparison.

## 2. Our check: the flip rule in sharcvm

**Set-up** [verified] (`out/T6.0c/flipcheck/`): a private copy of the sharcvm core with a per-access read log
(stock boot stream sha256 `336e34...`, the same bytes as `section_7_blob.bin`). Each run restores the whole DSP
state, runs 2 warm-up blocks, then 10 blocks with the word changed in every block, and compares L1, L2, the
32 MiB DDR, the MMR stores and the instruction count after each block against the unchanged run (the flipped
word's own rx bytes and image copy left out). Scenarios:
- 48 valid: 4 T3.3 captures as captured and again with note-ons (8); 40 synthetic, machine type 0-4 x filter
  type 0-5 with voice r on track r, plus 10 with all voices on one track. Note-on mask `0x22` in block 0,
  note-off `0x24` in block 5, `0x34 + 2r` = `0x7f00`. 31 of the 40 synthetic scenarios made sound.
- 12 random-voice: a fresh random voice frame every block, owners kept in 0..15.

**Independent re-run** [verified] (`out/T6.0c/verify-re-census/vflip.py`, `vflip_summary.txt`): an unmodified
core copy, 22 other scenarios (6 other captures, 12 with machine, filter and owner mixed per voice, 4 extreme
settings), 2 + 20 blocks each; plus a read log over 22 x 22 blocks and three runs of 400 consecutive blocks.

| frame word | reads outside the copy loops | flip changes DSP state? | verdict |
|---|---|---|---|
| tail `0xa80..0xabb` (30 words) | 0 | 0/2,880 valid (each word, ^`0xffff` and random), 0/720 random-voice; re-run 0/22 for all 30 at `0xffff`, `0x7f00`, `0x8000`, `0x0001`, `0x5555` and a per-block random stream | free |
| `0x2a` | 0 | 0/192 valid, 0/48 random-voice; re-run 0/22 | free |
| `0xa18` (k 40) | 0, also over 3 x 400 blocks | 0/192 valid (^`0xffff`, random, `0`, `0x7f00`), 0/48 random-voice; re-run 0/22 for `0`, `0xffff`, `0x7f00`, `0x8000`, `1`, `0xff`, stream | free |
| slot `+0x50` (k 65), `+0x6e` (k 80), all 16 rows | 0 | `+0x50` 0/864, `+0x6e` 0/48; re-run 0/22 | free (DSP side) |
| all 64 of the above together | n/a | 0/96 valid, 0/24 random-voice; re-run 0/22 | free together |
| `0xa28` (k 48, Reverb FX Routing) | 1 per block, `0x1c2e4a` (absolute `0x25ceb4`) | zero <-> non-zero: 48/48, always exactly one word, the byte `0x2579d4` = (value != 0); non-zero -> non-zero: 0/144; re-run 22/22 and 0/22 | read; not free |
| `0x9a8` (row 15 slot `+0x40`, k 57) | `0x1c2aac` (16-bit, through I4), only when row 15's machine word `0x94 + 30` is 0 | 8/48 valid, up to 3,521 words, instruction count changed, output changed in 4; re-run 2/22, exactly the two scenarios with machine type 0 on row 15 | read; real dependence |
| controls: track level `0x74`/`0x92`, REV_DEC, DEL_FDBK, `0xa7e` ^1 | read | 48/48 (up to 6,928 / 7,214 words), 48/48 (5,927), 48/48 (4 words), 47/48; re-run 22/22 for level, REV_DEC, DEL_FDBK, CHR_DPTH | the comparison catches changes down to one word |
| `0xa56` | only inside the 4-byte read of `0xa54..0xa57` at `0x1c3084` | 0/48 (^`0x2000`); re-run 0/22 (^`0x2000`, ^`1`, ^`0xffff`) | read but no dependence seen; **not** established as free |

Notes on the table:
- `0xa28`: `0x1c2e4a` is a short load from `0x25ceb4`, then a conditional move and a byte store at `0x1c2e63` to
  `0x2579d4` [verified]. No code we ran reads that byte: the only read nearby is a 4-byte read of `0x2579d0` at
  `0x1c1d8a`, which stops short of it [verified]. This matches T3.4 ("stored as a byte nobody reads").
- `0x9a8`: "FM Tone" for machine type 0 comes from dnfw's `docs/machine-list.md` [inferred mapping]. With FM Tone
  on other rows only, `0x9a8` was not a dependence, while slot `+0x40` on all 16 rows was (13/22) [verified].
  Flipping `0x9a8` and `0xa18` together, as in dnfw's replay, gave the same 8/48 as `0x9a8` alone [verified].
- `0xa56` shows dnfw's point: a read is not automatically a dependence.
- Limits [verified as stated]: "DSP state" here is memory, MMR stores and the instruction count; core registers
  were not compared. Every run calls only the block handler `0x1c9d6b`; no interrupt or other DSP task runs.
  A static scan of the T3.1 listings found absolute receive-buffer references only at `0x1ca029` (the handler's rx
  pointer) and `0x1ca505`/`0x1ca51f` (SPI DMA set-up), and image references only at the copy-loop set-ups
  `0x1c2877` and `0x1c301a` [verified]; computed pointers are not covered by such a scan [inferred]. Coverage:
  machine types 0-4, filter types 0-5, in-range slot values; no LFO destinations, no sequencer-played real frames.

## 3. Reads straight from the receive buffer

- The six words dnfw and T6.0 list are confirmed, with the same reader PCs [verified].
- The command word `0x00` is read from rx at `0x1c9da8` every block [verified]. T6.0's `words.tsv` has it; the
  T6.0 note text leaves it out.
- On a note-on block the DSP also reads, for each triggered voice, straight from the current rx frame: owner
  `0xa5a + 2r` (`0x1c31bb`), machine type `0x94 + 2r` (`0x1c31c2`), slot `+0x86` (k 92, `0x1c31c0`) and the
  sends `+0x7a`/`+0x7c`/`+0x7e` (`0x1c31ed`/`0x1c31fb`/`0x1c3207`) [verified]. T6.0 counted these reads (its rx read
  counts for those bytes are higher than for words only the copy loops read) but kept only the first and last
  reader PC per byte, so it did not name them [verified].
- Only command 3 runs the render. Commands 0-15, `0x100`, `0x103`, `0x8003` and `0xffff` run 190-291
  instructions, read only word 0, and touch neither the tail, `0x2a` nor `0xa18` [verified]. So a census that
  randomises word 0 never reaches the mix loops (20/20 frames) [verified].
- Voices make sound in sharcvm only with the note-on mask at `0x22` (dnfw's `drive-load-command.md`: byte 34),
  a non-zero `0x34 + 2r`, track levels, in-range slot values and a valid global FX block: the first two alone
  are needed but not enough (captures with both set stayed at peak ~1e-23) [verified]. T6.0's census script
  wrote the mask at `0x34` (`scripts/t60_dsp_reads.py` line 176) [verified].

## 4. The pointer in the voice-mix loops (dnfw's open question 1)

### 4.1 Where I0 comes from [verified: sharcvm stepping, write and read watches]

```
0x1c290d  M1 = 0x513
0x1c2937  lcntr = 16 (voice rows r = 0..15), I5 = image + 0x34 + 2r       image = 0x25c48c
0x1c293e  R4 = DM16(M1, I5)        pre-modify: image + 0xa5a + 2r = the owner word
0x1c2992  DM16 0x257898 + 2r = R4  the owner array, 16 halfwords, no clamp
loop A (outer DO 0x1c1fa8, 16 voices v):
0x1c1fab  R2 = DM16(I2 = 0x257898 + 2v)
0x1c1fad  R2 = R2 + R2
0x1c1fb0  R2 = FEXT R2 BY 0:16 (SE)      sign-extending
0x1c1fbd  R2 = LSHIFT R2 BY 7
0x1c1fc0  I0 = R2
0x1c1fc7  I0 = MODIFY(I0, 0x258f68)      raw byte offset, no scaling
=> I0 = 0x258f68 + (sext16(2 * owner) << 7) = 0x258f68 + 0x100 * owner for owner 0..15
loop B (outer DO 0x1c2515): the same into I1 (0x1c2518, 0x1c251d FEXT SE, 0x1c252a, 0x1c252d, MODIFY 0x259f68)
=> I1 = 0x259f68 + (sext16(2 * owner) << 7)
```

- Only `0x1c2992` writes the owner array; it is read by `0x1c1fab` (loop A), `0x1c2518` (loop B) and `0x1c2ade`
  (a sign-extended short load whose use was not traced). Only `0x1c293e` reads the image's owner words; only the
  copy loops `0x1c287d`/`0x1c3030` read them in rx.
- Changing one field at a time on row 5, only the owner word moved I0/I1 (owners 3, 9, 15, 0 gave I0 `0x259268`,
  `0x259868`, `0x259e68`, `0x258f68`). Fifteen other candidates moved neither register on any voice: machine
  type, filter type, note, `0x34 + 2r`, level, `0x54 + 2r`, slot `+0x50`, `+0x6e`, the whole slot, `0x2a`,
  `0x22..0x32`, `0xa18`, the global FX block, `0xa54`/`0xa56`/`0xa58`/`0xa7a`/`0xa7c`/`0xa7e`, and the tail.
  A stronger test agrees: frames random in every word except command 3, with owners forced to 0..15, matched the
  formula on 960/960 voice-blocks (`out/T6.0c/i0-source/p6_i0.txt`, `verify-i0-source/v1_i0.py`, `v4_range.py`).
- **One block late.** In steady state the voice loop runs about 1,125 instructions into the block, before the
  rx -> image copy at `0x1c3030` (about 8,123), so an owner change reaches I0/I1 in the next block (32 samples).
  Only the first block after FX init copies early (`0x1c287d`, about 1,026) and uses the current frame. Measured:
  owner of row 0 set to 7 gave block N I0 = `0x258f68`, block N+1 `0x259668`.
- **Sign extension.** `0x1c1fb0` and `0x1c251d` carry shifter-immediate opcode `0x12` (FEXT SE); plain FEXT at
  `0x1c28fc` is `0x10`. dnfw's `0xffeb5968` cannot come from a zero-filling FEXT (the most that gives is
  `0xa58e68`) [verified arithmetic], so their runner sign-extends as ours does. This is the PRM's table plus one
  decoder (digikit) that both runners share, with dnfw's own G11 fix for this opcode; not two independent decoders.

### 4.2 What the two loops compute [verified: injected signals, max relative error 2.2e-7 (A), 4.5e-7 (B)]

- **Bus A** at `0x258f68`: 16 tracks x 64 floats (`0x100` bytes): 32 samples of channel 0, then 32 of channel 1.
  Cleared every block by the loop at `0x1c1f48` (1,024 word writes). Per voice v:
  `bus[owner][n] += srcA_v[n] * g_n` and `bus[owner][32 + n] += srcA_v[32 + n] * g_n`, with
  `srcA_v` = DM `0x257ee8 + 0x100v`.
- **Bus B** at `0x259f68`: 16 x 64 floats, cleared at `0x1c24b5`. Each voice's mono DDR buffer
  (`*0x257ea8[v]`) is added into both halves.
- Gain: `g_n` = 14.1254 (`0x416201a3`, +23.0 dB) for A and 11.6266 (`0x413a068e`, +21.31 dB) for B; when the
  voice's flag byte at DM `0x2578b8 + v` is non-zero, it ramps linearly to 0 over the block (step G/31).
- **dnfw's "31-word blocks":** one sample is handled before the hardware loop and `lcntr 0x1f` does the other 31.
  Per block `0x1c1fca` runs 16 times and `0x1c1fda` 496 = 16 x 31 times.
- Who else touches bus A [verified]: loop A; `0x1c2055`/`0x1c205b` (a 16-track loop gated by masks at DM
  `0x257aa8` and `0x257984`); the in-place loop at `0x1c248f`; and two packers that together read all 1,024
  floats: `0x1c2680` (tracks 0-5) and `0x1c26c7`/`0x1c26c8` (tracks 6-15). Bus B has no reader but loop B.
- **The reply frame** [verified]: only the tracks 6-15 packer feeds it. Its stores at `0x1c26da`/`0x1c26e3`/
  `0x1c26e9` fill TX `0x2c49ec..0x2c546b`, exactly `0xa80` bytes = 32 records x 14 pairs of 24-bit samples, which
  fits dnfw's 32 x 28-channel records (`docs/for-digikit-coldfire-sharc-link.md`). The tracks 0-5 packer writes
  `0x2c10e8..0x2c18dc`, outside the TX buffer, with no core reader in 2 blocks (likely DMA [inferred]).
- [inferred]: bus A is the per-track sum (each voice into the track that owns it); bus B is a second per-track
  bus whose consumer did not run with our frames; the flag is a fade-out (voice cut or steal) against clicks.

| value | what it is | status |
|---|---|---|
| `0x258f68` | loop A, owner 0. All 247 T3.3 captures (LIGHTHOUSE) have owner 0 on every row; 640/640 voice-blocks gave it | [verified] |
| `0xffeb5968` | loop A, owner `0x45ca` or `0xc5ca`; a search of all 65,536 values finds only these two. sharcvm gives it exactly and then traps (unmapped read) | [verified] |
| `0x804acf94` | cannot occur at `0x1c1fca`: every loop-A address ends in `0x68`, and `0x804acf94 - 0x258f68` is not a multiple of `0x80`. It is loop B's **I0** for voice 0 at `0x1c2535`: the source pointer `0x804acf90` from the table at DM `0x257ea8` (`0x804acf90 + 0x80v`, written by FX init `0x1c1445` at `0x1c150b`) plus 4 after the first load. In loop B the owner-indexed register is I1 | value and arithmetic [verified]; that dnfw logged it at `0x1c2535` [inferred] |

The table value held in every block we sampled (647 stepped blocks, 960 random-frame voice-blocks, all
loop-B stops) [verified]. It is not frame-proof: an owner with `(w & 0x7fff) = 0x7fef` puts loop A's row
(`0x257e68..0x257f67`) over the table, after which loop B's I0 is `0x80000004` for every row, with no trap,

### 4.4 What an owner outside 0..15 does [verified: sharcvm, `i0-source/p8_range.txt`, `verify-i0-source/v13_windows.txt`]

There is no bounds check. Bit 15 is ignored (`0x8000..0x800f` act as 0..15); bit 14 acts as the sign.
- `0x10` points loop A at bus B (`0x259f68`), no trap. `0x1f` damages state; the block then traps at `0x1c30c1`.
- Many values make loop A read-modify-write 64 floats elsewhere in L1 without trapping: `0x10..0x1470` (L1 above
  bus A), `0x7e71..0x7fff` (below it), and the NW/SW/LW aliases of L1 (`0x5ef1..0x61b0`, `0x6371..0x68f0`,
  `0x6c71..0x7770`), each also +`0x8000`. What the row overwrites decides whether a trap follows later. How
  faithfully sharcvm models alias-space access widths is untested.
- `0x35..0x3f` (loop A) or `0x25..0x2f` (loop B) put a row on the frame image: `0x35` covers word `0x2a`, `0x3f`
  covers `0xa18` (computed; not flip-tested). `0x68a..0x6ba` reach the rx buffers (I1 for `0x68a..0x6aa`, I0 for
  `0x69a..0x6ba`): the loops then read `0x2a`, `0xa18`, `0xa28`, the tail, slot words, `0x9a8` and bytes past
  `0xabc`, and write into rx, with no wrapping at all. This is dnfw's artefact reproduced in a correct map.
- `0x1471..0x3fff` and `0x4000..0x5a70` go to unmapped addresses (above L1, or wrapped to `0xffe58f68..`); about
  67 % of all 16-bit owners trap. `0x7fff`/`0xffff` give `0x258e68`; that block completes and the next traps at
  `0x1c9af9`.
- Fully random frames (command word kept at 3) trapped at `0x1c1fca` in their first block in 10/10 and 8/8 runs,
  at the formula's address; the trapping voice is not always voice 0. With only the owners forced into 0..15,
  20 frames x 3 blocks ran without a trap.
- [inferred] dnfw's single "flipping `0x2a` changed memory" fits a wild row covering `0x2a`: the loop adds into
  the words it reads, so a flipped word feeds a write.

## 5. The MMR stops (dnfw's open question 2)

**sharcvm's map** [verified: `sharcvm.c` `space_of`/`to_byte`/`is_mmr`/`rd_bytes`/`wr_bytes`, `vm.py` REGIONS]:
core MMRs `0x30000-0x3ffff` and system MMRs `0x30000000-0x3fffffff` are plain stores (4-byte accesses only;
other widths there trap as unmapped); L1 `0x240000-0x39ffff` is one buffer, so the gaps between L1 blocks are
mapped; NW/SW/LW aliases (x4/x2/x8) and the system alias `0x28240000-0x2839ffff` map to L1; L2 `0x20000000`
(1 MiB), DDR `0x80000000` (32 MiB); anything else traps "unmapped". Strict mode also traps on every MMR access.
In normal mode a row in core MMR space does not trap (128 MMR reads and 128 writes per block, stored).

**Which owners reach an MMR** [verified: enumeration of all 65,536 owners, sharcvm's classification]:
- The loops can reach `0x258f68 + 0x100 * s` for s in -0x4000..0x3fff (loop B 0x1000 higher), always ending in
  `0x68`. That is at most 4 MiB either way, so L2, DDR and system MMRs are out of reach. The only MMR window is
  the core MMRs, `0x30068..0x3ff68`:
  - loop A (stop at `0x1c1fca`): owners `0x5d71..0x5e70` and `0xdd71..0xde70`;
  - loop B (I1): owners `0x5d61..0x5e60` and `0xdd61..0xde60`. Loop A always finishes before loop B starts
    (647/647 and 1,048/1,048 stepped blocks), so a first stop at `0x1c2535` needs loop A to pass: owner
    `& 0x7fff` in `0x5d61..0x5d70`, where loop A's row is just below the window (`0x2f068..0x2ff68`, unmapped:
    sharcvm traps, a wrapping runner passes) and loop B's row is inside it.
  - sharcvm does not scale modifiers outside byte space, so a row starting in the window stays in it and the stop
    is always the row's first load.
- In strict mode sharcvm stops with "read of MMR" at `0x1c1fca` for owners `0x5d71`, `0x5e00`, `0x5e70`, `0xde00`.

**A runner like theirs** [verified]: unmapped ranges backed by zero pages (so bad addresses pass) and strict MMR
on. 2,000 variants (1,000 with 16-bit owners, slots and tail; 1,000 fully random x filter type 0-5): 227 MMR stops,
210 at `0x1c1fca` and 17 at `0x1c2535`, none anywhere else. Every address was in `0x30068..0x3ff68`, ended in
`0x68` and equalled the formula; all 17 loop-B stops had owner `& 0x7fff` in `0x5d61..0x5d70`. An independent
re-run with another seed: 233 (220 + 13), same pattern (`out/T6.0c/mmr/lenient_strict.py`,
`verify-mmr-stops/f_lenient.py`). Side results of that runner: some runs ended at the undecodable PC `0x17ffe`
(9 strict, 10 non-strict) after a loop row hit the stack area `0x26e000..0x26f800`; 2-3 per 2,000 stopped at
`0x1c30c2` on a 4-byte read at `0xfffffffd` that no zero page can back. Neither is an MMR stop.

**Rates** [inferred, arithmetic]: with uniform 16-bit owners, `1 - (127/128)^16` = 11.8 % of blocks should stop
at `0x1c1fca` and 0.69 % at `0x1c2535`. Measured 10.5 % / 0.85 % and 11.0 % / 0.65 %. Three stops fits about two
dozen blocks with random owners, if their MMR range is `0x30000-0x3ffff`.

**How dnfw can check** [inferred until they do]: at a `0x1c1fca` stop read I0, at a `0x1c2535` stop read I1
(not I0); expect `addr = base + (sext16(2h) << 7)` mod 2^32 with base `0x258f68` / `0x259f68` and h the halfword at
`0x257898 + 2r` (= owner word `0xa5a + 2r` of the previous frame in steady state), an address in
`0x30000..0x3ffff` ending in `0x68`; with owners set back to 0..15 the stop goes away.

## 6. What it means for our plans

- **TAPE, AGE in `0xa18` (k 40).** DSP side confirmed free under the flip rule (section 2) [verified]. The
  glue (`tools/dspsplice/src/se_glue.c`, working tree) reads it once per block from the image word `0x25cea4`
  and maps knob values <= 1 to AGE 0, so stock kits (which carry k 40 = 1, T6.1 4.3) start with no ageing
  [verified: read in the source]. On the ColdFire side the stock builder writes smoothed k 40 into `0xa18` every
  frame; T6.1's path (c) uses exactly that (row `0x7a` on delay G), so no frame hook is needed [verified in T6.1].
- **Compressor values in the tail.** Confirmed free [verified]. The tail is never copied to the image, so our
  DSP code reads it from rx (the render's third argument, T6.0 1.3). If a tail value must change in the same
  block as an image word, read both from rx; se_glue.c states the copy runs before the FX bus, in which case
  image and rx hold the same frame [inferred here].
- **Spares.** `0x2a` and slot `+0x50`/`+0x6e` (32 words) remain DSP-side spares [verified]. The ColdFire fills
  `+0x50`/`+0x6e` from per-voice parameters, so using them needs the send hook at `0x40025e9e` [inferred].
- **`0xa28` (k 48) is not a free carrier.** Values 1..N leave the stock flag at 1 and changed nothing in our runs;
  0 flips the flag byte `0x2579d4`, which nothing we ran reads [verified]. T6.1's "k 48 on reverb G" idea is
  usable only with a range that never sends 0, or after finding out what the flag is for [inferred].
- **Do not touch slot `+0x40` (k 57) or `0x9a8`:** a live per-voice value for machine type 0 [verified].
- **Owner words `0xa5a..0xa78` must stay in 0..15** in any frame we build or a ColdFire mod changes. The DSP uses
  them as an unchecked index; a bad value writes floats into other L1 data (the pointer table, the stack, rx,
  code through the aliases) or core MMRs, or traps [verified in sharcvm]; on the unit that is a DSP crash while
  running, not a brick [inferred]. Matters for any 32-voice or voice-reallocation idea. Owner changes reach the
  mix one block (32 samples) late [verified].
