# T1.2: the unit's own code on a rebuilt 1.12

Date: 2026-10-05. Status: **done, with one safety finding**. Marks: **[verified]** = checked
against the bytes or run here; **[inferred]** = reasoned from structure.

Everything ran under Unicorn through digikit's harness (`emu/harness.py`), on the code of the
stock 1.12 file: the bootstrap a unit on 1.12 already has (section 2, sha256 `038aa5d1...`,
version word `0x0201`), the stock main OS (`a098f620...`) and the stock section 4. Each
candidate `.syx` was only data. No device was touched.

## Summary

- **On the normal boot path the unit unpacks the recompressed main OS exactly.** The bootstrap,
  run from `0x80000ee4` (just after its init and STARTUP-menu routine returns) with the
  recompressed container as flash, looks up section 3, reads it to `0x40400000`, depacks it to
  `0x40000400`, and jumps to `0x400004e8`. The image it wrote has sha256 `a098f620...`, the same
  as `ele3_out/02_type3.unpacked.bin`. Same for the `-r` control and stock. **[verified]**
- **Both validators accept all three files.** The bootstrap's verify-and-commit routine
  (`0x80003c9c`, used by the STARTUP-menu MIDI upgrade) reaches its "UPGRADING" branch
  (`0x80003ce8`), and the main OS's upgrade validator (`0x400dbdb0`, used by the USB and SysEx
  upgrades) returns 1. Two one-bit controls on the trailer are refused by both, each at the
  expected step; a resealed stream change is accepted by both and caught only by comparing the
  depacked image. **[verified]**
- **There is no build floor on Digitone II 1.12.** The validator is 52 bytes: content checksum,
  then the HMAC trailer. It returns only 1, 3 or 4. The Digitakt II 1.16 build-floor signature has
  no match anywhere in the main OS. "Unsupported downgrade" is in the error table but unreachable,
  as digikit found on 1.11. **[verified]**
- **Safety finding: the unit has a second main-OS loader, and the recompressed file breaks it.**
  Section 4 (digikit calls it UPDATER; it is a factory board-test program) has its own loader at
  `0x8000357c`, which stages section 3 at **`0x40200000`**, not `0x40400000`, and depacks it in
  place to `0x40000400`. The output (3,196,288 bytes) is longer than the 2,096,128 bytes between
  the two addresses, so the stream must stay ahead of the writer. The stock stream does, with
  31,182 bytes to spare. The tool's default (level 3) stream is 70,500 bytes smaller and falls
  39,318 bytes short. Run in that layout, the unit's code writes over input it has not read yet,
  1,623 bytes of the output come out wrong from `0x40303180` on, and the depacker then spins in
  its gamma loop (`0x8000576e`) and never returns. A rebuild at `-l 0` passes (margin 4,791 bytes).
  **[verified]**
- **When that loader runs:** the bootstrap hands over to section 4 only when boot flag bit 6 is
  set, and the only code that sets it (`0x80000b9a`) runs when the power-on key read from the
  front panel times out (`0x80001276`). So a healthy unit with its panel answering never takes
  this path. **[verified]** that this is the only setter; **[inferred]** that UART8 is the panel
  link and that a timeout means the panel did not answer. On such a boot a level-3 rebuild would
  hang where stock boots; the flash is unchanged, so power-cycling recovers it **[inferred]**.
- **The main OS also reads its DSP section correctly from the rebuilt container.** In digikit's
  emulator, a cold boot of the recompressed file reads section 7 from its new flash offset
  (`0x18efd0`, stock `0x1a0340`), and the boot is identical to stock: the same task creations at
  the same instruction counts, the same ladder snapshots, emucheck PASS, and a byte-identical
  main-screen PNG first latched at the same instruction (741,578,400). **[verified]**

## Which code unpacks the main OS

The bootstrap (section 2) runs at `0x80000400`; its file offset 0 is `0x800003FC`. The 16 bytes
there are a header: `0x00007656` (30,294 = the section's length minus 8), `0x80010000` (top of
SRAM), `0x80000de8` (entry), `0x0201` (version). Its last 4 bytes are a little-endian CRC-32 of
everything before them, so the whole section has the CRC residue `0xDEBB20E3`. **[verified]**
for the values and the CRC; the roles of the first two words are **[inferred]**.

Boot path, read in the disassembly (`m68k-elf-objdump -m m68k:cfv4e`) **[verified]**:

```
80000de8  entry; dispatch on d2 at 80000e9a (0 -> normal boot; 1..5 -> a jump table)
          reset copies 80007900..80007a56 to SRAM 8000f000 (80000e5a): the SPI NOR read
          (80007910 -> 8000f010) and "run section 4" (80007a00 -> 8000f100)
80000ee0  jsr 800009c6           init, panel key read, STARTUP-menu checks (T1.5)
80000ee4  moveq #64,d0 ; and.l 80008404,d0 ; beq 80000ef4
80000eee  jsr 8000f100           boot flag bit 6: run section 4 instead (see below)
80000ef4  jsr 80000596           the loader
80000efc  a0 = *(d0) ; push flags ; jsr (a0)     enter the main OS at *(0x40000400)
```

How d2 is set on a real power-on was not resolved. **[open]**

The loader `0x80000596` **[verified]**:

```
800005b8  pea -16(a6) ; pea 3 ; jsr 80005462       section lookup: ELE3 header at flash 0x80000,
                                                   then 16-byte entries from 0x80020
800005c6  pea 40400000 ; push len ; d0 = off + 0x80000 ; jsr 8000f010    flash read(off, len, dest)
800005e2  push dest (0x40000400 from the table) ; pea 40400000 ; jsr 80000432   depack(src, dst)
```

The depacker `0x80000432` (356 bytes) skips the stream's 8-byte header and returns the output
length. Byte-identical copies sit in the main OS at `0x40136820` and in section 4 at `0x80005728`.
**[verified]**

What each run checks [verified, from `tools/acceptoracle.py`]:

- **Boot path:** flash is `0xFF` with the candidate's container at `0x80000`; the SPI NOR read
  (`0x8000f010`) is served at its entry; DDR is filled with `0xA5` first. The run stops at the
  first instruction executed in `0x40000000-0x47FFFFFF`. Checked: that address (`0x400004e8` on all
  files, the main OS's own vector at `0x40000400`), the depacker's return value (3,196,288), the
  sha256 of the 3,196,288 bytes at `0x40000400`, that `0x40000000-0x400003ff` and everything
  between the output's end and the stage still hold `0xA5`, and that the last stage byte read is
  the stream's last byte (`0x40514353` stock, `0x40502fef` recomp). The flash reads it made: the
  32-byte ELE3 header at `0x80000`, the section entries at `0x80020/30/40`, then
  `0x83fd0` for exactly the table length (1,131,348 stock, 1,060,848 recomp) to `0x40400000`.
- **Verify-and-commit** runs from its entry with the decoded stream at `0x40000000`, as the
  bootstrap's receive path stores it ([length][checksum][container]). It never returns, so the
  run stops at `0x80003bfc` (UPGRADE ABORTED / PLEASE REBOOT, then a spin) or at `0x80003ce8`
  (the first instruction of the UPGRADING branch, before the flash erase at `0x80003dca`). No
  flash code runs.
- **Main OS validator** is called with a pointer to the same decoded stream, as its SysEx
  state machine passes `state + 32`.

Instruction budgets: the bootstrap's trailer check over a 1.8 MB container is about 49 million
basic blocks (41 s here), so those runs get 4,000,000,000 instructions. **[verified]** A first run
with a 400,000,000 budget stopped inside the trailer check on stock: a budget artefact, not a
result.

## The section 4 path in detail

- **What section 4 is.** Strings `#HELLO`, `HOWDY HO!`, `#STATUS`, `VERSION 1`, `PLATFORM`,
  `PCBA0109%c%d`, `FLASH`, `WRONG DEVICE TYPE %02x %04x`, `DRAM INITIALIZATION TIMEOUT`,
  `DATA CORRUPTION AT ADDRESS %08x`, `CLEARING %x`, and a full SPI NOR command set (read, erase,
  program, ID, lock registers). Its main routine fills `0x40000000-0x44000000` with a pattern and
  checks it (`0x800034ca`); if that passes it runs the loader at `0x8000357c` and boots the main OS;
  if it fails, or if flag bit 17 is set, it does not boot (`0x8000354e`). So it is a factory board
  test that boots the OS when the RAM is good, not an updater. **[verified]** code and strings,
  **[inferred]** purpose.
- **Its load address.** The bootstrap's "run section 4" routine (`0x80007a00`, at `0x8000f100`
  after the reset copy) reads the *stored* section, header included, to its table address
  `0x80000400` and jumps to its first long, `0x80000492`. The section's one absolute
  `jsr 0x80005728` (at `0x800035b6`) hits the depacker copy only in this layout. **[verified]**
  digikit loads section 4 without its 8-byte header (`emu/extract.py`), so its addresses for
  section 4 are 8 lower than the unit's (1.11's `0x80005720` there is `0x80005728` on the unit, if
  1.11 has the same layout **[inferred]**).
- **When it runs.** The boot flags word `0x80008404` is rebuilt on every boot: `move.l` at
  `0x80000b04`, then `or.l` at `0x80000b1a` (bit 18), `0x80000b3c` (bit 5), `0x80000b9a` (bits 5
  and 6), `0x80000c42` (bit 5), `0x80000da8` (bit 8), `0x80002fb0` and `0x80002fbe` (bits 0, 1).
  Only `0x80000b9a` sets bit 6, and only when `jsr 0x80001276` returns < 0. That routine sends
  `0x60, 0x01` on UART8 (`0xEC07000C`) and collects seven replies into the key bitmap at
  `0x80008414` that the STARTUP-menu checks read (`0x80001302`); it returns -1 when a reply does
  not arrive in time (`0x80000f50`: 10,001 polls with a delay). The main OS never references
  `0x80008404`. **[verified]** the writes and the branch; **[inferred]** that this is the panel's
  key read.
- **The margin.** Distance from the write pointer to the next unread stream byte, at its smallest,
  for each stream and stage (pure Python, the same codec as `dt2/elz.py`, the measure elekloader's
  `syx.inplace_depack` uses) **[verified]**:

  | stream | stored bytes | at `0x40400000` | at `0x40200000` |
  |---|---|---|---|
  | stock | 1,131,348 | 2,128,334 | 31,182 |
  | tool `-l 0` | 1,104,957 | 2,101,943 | 4,791 |
  | tool `-l 1` | 1,079,884 | 2,076,870 | -20,282 |
  | tool `-l 2` | 1,067,673 | 2,064,659 | -32,493 |
  | tool `-l 3` (default, `recomp.syx`) | 1,060,848 | 2,057,834 | -39,318 |

- **What goes wrong, two ways.** The unit's section 4 loader under Unicorn, with the recompressed
  container as flash: the depacked image differs from the stock main OS in 1,623 bytes, the first at
  `0x40303180`, and the run spent its 1,000,000,000-instruction budget at `0x8000576e`
  (`tst.b d1` in the depacker's offset-gamma loop) without returning, so the jump into the main OS
  never happens. A pure-Python model of the same in-place run (stream and output in one memory):
  the writer first reaches unread input at `0x40302fad`, 67 bytes before the stream's end
  (`0x40302ff0`), and the output first goes wrong at `0x40303180`, as in Unicorn. The model then
  stops at its own guard on gamma length (2^25), which the unit's code does not have; the unit's
  code carries on for a while (the image's last 38,912 bytes, from `0x40303180`, are all zeros, and
  most of them still come out right) before it spins. **[verified]**
- **Consequence.** On a boot where the panel key read times out, stock and `-l 0` boot; a level-3
  rebuild hangs before the main OS runs. Nothing is written to flash on this path, so a power-cycle
  with the panel answering boots normally. **[inferred]** If the panel never answers, the
  STARTUP menu cannot be entered either (it needs keys), and the main OS's USB upgrade cannot run,
  so a level-3 build would leave no way to reflash until the panel works. **[inferred]**

## Validators and the build floor

- **Bootstrap** (STARTUP menu, OS UPGRADE over DIN MIDI): `0x80003c9c`. Content checksum inline
  at `0x80003ca6-0x80003cce`: `sum((i+1) ^ word_i)` over `length/4` big-endian words from
  `0x40000008`, compared with `0x40000004`. On a mismatch, `jsr 0x80003bfc` (never returns). Then
  `jsr 0x80005e3a(0x40000008, length)`: key from `0x80005da0` (seed "Multiplier" at `0x8000707c`,
  constant after its NUL at `0x80007087`), HMAC-SHA256 over the container minus its last 32
  bytes, compared with them; `0` -> abort. Then UPGRADING, erase from flash `0x80000` in 256 KB
  units (`0x80002896`) and program 512-byte pages (`0x8000282a`). No version comparison on this
  path. **[verified]** The HANDOFF's Task 1 text says a failed checksum "falls into a loop that
  calls a 32-byte-tail check"; the code calls the abort routine directly, and checks the trailer
  only after the checksum passes. **[verified]**
- **Main OS** (Transfer over USB, and SysEx upgrades): validator `0x400dbdb0`, 52 bytes:

  ```
  400dbdb8  jsr 401226f8   content checksum (arg: [length][checksum][container]), 1 on a match -> 0: return 3
  400dbdca  jsr 400d2bc4   trailer (container, length)                           -> 0: return 4
  400dbdde  moveq #1,d0    pass
  ```

  Error table `0x40208c00`: No error, Checksum failed x3, Power adapter must be connected,
  Unsupported downgrade. Its only reference is `lea 0x40208c00,a0` at `0x4012a150`, indexed by
  the validator's return minus 1. Callers of the validator: `0x4012a0fc` (the SysEx receive state
  machine, "Waiting for confirm", "Incompatible OS", ...), `0x40109194` ("ERASING FLASH..."), and
  `0x40139114` inside the flash writer `0x40139104`, which validates again before erasing from
  `0x80000`. **[verified]**
- **Build floor: none.** No `move.l #imm,d1; cmp.l 16(a2),d1` (`22 3c ?? ?? ?? ?? b2 aa 00 10`)
  anywhere in the 1.12 main OS, and the validator's only return values are 1, 3, 4. Nothing reads
  the BUILD string on the upgrade path. **[verified]** Same as digikit's 1.11 result.

## Negative controls (in memory only, never written to disk)

On `recomp.syx`:

| control | bootstrap verify-and-commit (`0x80003c9c`) | bootstrap trailer alone (`0x80005e3a`) | main OS validator (`0x400dbdb0`) | unit's depacker / boot path |
|---|---|---|---|---|
| last trailer bit flipped | FAIL at `0x80003bfc`: checksum computed `0xc4bb0f06`, stored `0xc4bb0f07` | 0 | 3 (Checksum failed: content checksum) | not run |
| the same, preamble checksum redone | FAIL at `0x80003bfc`: checksum passes (`0xc4bb0f06`), trailer fails | 0 | 4 (Checksum failed: trailer) | not run |
| bit 4 flipped in byte 530,432 of the stored section 3 (header included), checksum and seal redone | PASS at `0x80003ce8` | 1 | 1 (pass) | output differs from stock (1 byte, at `0x4015d61f`); the boot path still enters `0x400004e8` |

All three **[verified]**. The first two show each check refuses on its own step. The third shows
what the validators cannot see: they check the container as sealed, not what it unpacks to, and
the bootstrap jumps into whatever the depacker wrote: its loader (`0x80000596-0x80000610`) and the
boot path (`0x80000ef4-0x80000f08`) have no check on the unpacked image **[verified]**. So the
depack comparison against the intended main OS is the only check that catches a wrong main OS
stream, and the brick checker needs it.

## What this does not show

- The bootstrap's code before `0x80000ee4` (`0x800009c6`: clocks, panel, the STARTUP menu) was not
  emulated; that is T1.5.
- The flash write itself (erase and program after `0x80003ce8`, the main OS's writer
  `0x40139104`) did not run; that is T1.4's area.
- The SysEx framing and per-packet checksums were not run through the unit's receive code here;
  the tool and digikit's checker cover them offline (HANDOFF).
- Section 8's consumer is another processor; only the codec was checked.

## Consequences for the next tasks

- **T1.6 (elekloader profile):** take `stage = 0x40200000` for Digitone II 1.12, the stricter of
  the two loaders, so `syx.inplace_depack` and `tests/test_releases.py` refuse a stream with a
  negative margin there. elekloader's own packer compresses better than Elektron's (on DT2 1.17,
  1,147,584 bytes against 1,385,586), so it will likely need a way to keep this margin. **[inferred]**
- **T1.7 (brick checker):** run both loaders (`acceptoracle.py --parts boot,updater`) on every
  candidate, or at least check the margin at both stages. Until then, build with `-l 0` or check
  the margin by hand. Any mod that changes the main OS changes the margin.
- **T1.8 (first flash of an unchanged rebuild):** use `recomp-l0.syx` (passes both loaders), or the
  byte-exact `-r` file, not the level-3 `recomp.syx`.
- **Digitakt II (elekloader's 1.17 profile, not checked here):** if its section 4 has the same
  loader at `0x40200000`, its repacked builds may have a negative margin there too (rough end-of-
  stream estimate: 2,096,128 + 1,147,584 - 3,275,616 = -31,904). Needs checking on a DT2 image
  before telling anyone. **[inferred]**
- **Corrections to HANDOFF and ROADMAP:** "`-c 3` with an unchanged main OS passes every check" and
  "a recompressed rebuild passes every offline check" hold for the normal boot path and both
  validators, but a level-3 rebuild fails section 4's loader. **[verified]**
- **digikit:** section 4 is not an updater, and it loads with its header (above). Its
  `emu/extract.py --oracle` constant and its docs say otherwise. Worth a correction upstream later
  (C1, with the user's approval).
