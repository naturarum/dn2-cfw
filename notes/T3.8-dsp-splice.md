## 1. The method [verified unless marked]

Tools (all new, in `tools/dspsplice/`; nothing in `vendor/` changed):

| file | what |
|---|---|
| `ldr.py` | section 7 as an editable list of blocks: parse (with `scripts/sharc_ldr_parse.py`), patch bytes inside one payload block, insert load or FILL blocks before FINAL, recompute the FIRST argument, serialise. Parsing stock and serialising gives stock back byte for byte (checked on every build) |
| `stub.py` | generates the hook stubs in selas syntax (section 2) |
| `build.py` | one recipe per candidate (`CG01`, `FLG1`): selcc, selas, seld with a generated LDF, splice, checks, `.syx`, `build.json` |
| `audit.py` | encoding audit of every instruction we add, against the stock image and against selcc's own hardware-validated output (section 2.3) |
| `vmrun.py` | loads a spliced section 7 into `tools/sharcvm`, runs the effect init and the whole block handler, reads the effect buffers exactly at the FX bus's call and return |
| `verify_cg01.py`, `verify_flg.py` | the proofs of milestones 1 and 2 |
| `src/` | `fxio.h` (the bus's I/O descriptor), `cg_post.c` (milestone 1), `flg_glue.c` (milestone 2) |

Steps of `python3 tools/dspsplice/build.py NAME`:
1. **Compile** our C with selcc `-proc ADSP-21569 -char-size-8 -O1` (the flags `tools/sharcvm/tests/fxcheck.py`
   already uses), generate the stubs, assemble everything with selas.
2. **Link at fixed addresses** with seld and a generated LDF: code (`seg_swco`) from byte `0x2dd600` = SW `0x16eb00`,
   data (`seg_dmda`, BSS) from `0x2e6000`; the stubs' register save area is at `0x2e7800`. The ELF is read with
   `tools/sharcvm/elf.py` (which already swaps selcc's big-endian parcels into the memory order the stream uses).
   The linker refuses nothing by itself, so `build.py` checks that every section lies in its planned range.
3. **Register census:** every register our C code writes (from its assembly) must be one the stubs save or a
   scratch/frame register; otherwise the build stops (section 2).
4. **Splice** into the stock stream (sha256 `336e340a...`, 95 blocks, checked first):
   - **hooks**: the FX bus reaches each effect through one 48-bit `CJUMP target (DB)` (Type 25a, raw
     `0x180400 << 24 | target`, T3.4). The 24-bit target is rewritten in place inside block 83's payload (the L1
     block 3 code); the patch helper refuses a byte that is not written by exactly one payload block (no FILL, no
     later overwrite) and checks the old bytes first. Chorus `0x1c1be1`: `0xb84d5c` -> our stub; for FLG1 also the
     chorus init call in the effect init `0x1c1445`, at `0x1c1695`: `0xb84f51` -> our init stub;
   - **new blocks** just before FINAL (dnfw's place for them): one load block per code/data section (payload =
     the memory bytes, padded to 4), a FILL for the save area and, for FLG1, a FILL that zeroes the flanger's
     state at boot;
   - **FIRST argument** of the main application (block 7) set to the byte count to the end of the stream:
     stock `0xc9bd8`, CG01 `0xc9e80`, FLG1 `0xcdf84`. This is the rule the stock stream itself follows for both of
     its applications and what selload writes; `sharc_ldr_parse` (so brickcheck check 11) checks it. dnfw left
     this argument stock and still booted, so the boot ROM evidently does not need it on this path [inferred];
     we keep the stream self-consistent instead.
5. **Checks at build time:** the stream passes all of `sharc_ldr_parse`'s structural checks; brickcheck's own
   static DSP scan (`bc_dsp.scan_sizes_and_blocks`: stream <= 1 MiB - 1, FINAL, no block into a cache range,
   every block inside known memory); the **final memory image differs from stock only** at the hook sites' three
   target bytes and inside our own ranges (computed region by region); no shift by an immediate in any of our
   assembly (0 in both builds).
6. **Wrap:** `elektron-firmware-tool -i Digitone_II_OS1_12.syx -c 7 section7.bin -V NAME -o NAME.syx` (the
   tool compresses section 7; every other section is copied as stored), then section 7 is depacked back out of
   the `.syx` and must equal the intended stream. Separately, **the unit's own depacker** (the main OS's copy at
   `0x40136820`, in the DSP loader's layout, under Unicorn: digikit's `tools/acceptoracle.py --parts depack`,
   run read-only) gives exactly our stream for both candidates (sha256 below; it compares against stock, so it
   prints `matches=False`, but the length and hash are ours), and sections 2, 3, 4, 5, 8 stay identical to stock.
7. **Audit** (section 2.3), **prove** in sharcvm (sections 4 and 6), then **brickcheck** with `--intended-dsp`
   (section 8).

## 2. Hooks: why a stub, and what it does

### 2.1 selcc and the stock code do not agree on the calling convention [verified]

selcc (`vendor/selache/selcc/src/target.rs`) treats R0, R1, R3-R7 as caller-saved and R8-R15 as callee-saved.
The stock code (ADI's compiler) keeps values in R3, R5-R7 across calls and treats R8 and R12 as scratch.
Measured in sharcvm with random values in R0-R15, I0-I5, I8-I15, M0-M4, M8-M12 (`verify_cg01.py`):

| called on its own | registers it changed |
|---|---|
| stock chorus `0xb84d5c` | R0 R1 R2 R4 R8 R12, I4 I12 I13, M4 |
| selcc's `cg_post` | R0 R1 R2 **R3 R5 R6 R7**, I4 I12 |
| our hook stub (stock chorus + `cg_post`) | R2 I12 I13 (R2 and I12 change in every C call by the convention; I13 is changed by the stock chorus itself) |

So selcc code must never be called straight from stock code (it would clobber R3, R5-R7 that the FX bus relies
on), nor stock code from selcc code (it would clobber R8 and R12). The stub sits between them.

### 2.2 The stub (`stub.py`, generated into `out/T3.8/<NAME>/build/stubs.s`)

- It is entered exactly as the routine it replaces: by the caller's `CJUMP` (which sets `R2 = I6`, `I6 = I7`, and
  pushes the caller's frame pointer and return address in its delay slots).
- It saves R0-R15, I0-I5, M1-M4 and MODE1 to a fixed save area (`0x2e7800`, 27 words, FILL-zeroed at boot) with
  absolute stores, the stock Type 14a form `DM(addr) = ureg`. That set is exactly the registers whose absolute
  load **and** store the stock image itself uses (it never stores I8-I15 or loads M0 that way). Registers outside
  it (I8-I15, M0, M5-M15, B, L) are not written by our C code (the census of section 1 step 3 refuses a build that
  writes them) and are preserved by the stock routines the stub calls; I4 and I12 are scratch in both conventions.
- Steps: `("stock", sw)` calls a stock routine with the caller's own R4/R8/R12 and MODE1; `("c", name, regs)` sets
  the C environment selcc assumes (`BIT CLR MODE1 0xE0A000` = no SIMD, no broadcast loads, round to nearest, no
  ALU saturation; `BIT SET MODE1 0x10000` = RND32; a NOP for the write latency) and calls our function;
  `("tail", sw)` restores everything and `JUMP`s to a stock routine, which then returns straight to our caller.
- It ends by restoring MODE1 and every saved register and returning with the stock C epilogue
  (`I12 = DM(M7,I6); JUMP (M14,I12) (DB); RFRAME; NOP`).
- It uses no stack of its own: the stock code's frames stay where they were, and our C code's frames sit below.
- The stub is not re-entrant (fixed save area); only the Audio Task runs the FX bus, once per block [inferred
  from T3.2 3.3: one task, one call site].

| candidate | hook at | was | now | stub steps |
|---|---|---|---|---|
| CG01 | `0x1c1be1` (FX bus) | `CJUMP 0xb84d5c` (chorus) | `fxh_chorus` `0x16eb00` | stock chorus, then `cg_post(io)` |
| FLG1 | `0x1c1be1` (FX bus) | `CJUMP 0xb84d5c` (chorus) | `fxh_chorus` `0x16eb00` | `flg_process(params, io)` (the stock chorus no longer runs) |
| FLG1 | `0x1c1695` (effect init `0x1c1445`) | `CJUMP 0xb84f51` (chorus init) | `fxh_chorus_init` `0x16ebc3` | `flg_init()`, then tail-jump to `0xb84f51` (the stock init still runs, with the caller's frame and its four stack words untouched) |
| FTD1 | both FLG1 hooks, and `0x1c1c58` (FX bus) | `CJUMP 0xb8482c` (delay) | `fxh_delay` `0x16ec7d` | `td_process(params, io)` |
| FTD1 | `0x1c166c` (effect init) | `CJUMP 0xb848cb` (delay init) | `fxh_delay_init` `0x16ed40` | `td_init()`, then return (the stock delay init is skipped, section 9) |

### 2.3 Encoding audit (`audit.py`) [verified]

The rule from dnfw's silicon finding (a fact, not their code): "decodes the same" is no proof of an encoding, so
compare our bytes with the encodings the firmware itself uses. Every instruction we add is decoded at its exact
address with digikit's table decoder and given one level:
- **exact**: identical to at least one of the 65,372 stock instructions once only the address, immediate and
  branch-offset fields are masked (digikit's own field layout, `sharc_visa_tables`);
- **exact-selcc**: not in stock, but identical (same masking) to an instruction of **selcc's own output for
  selache's 2,039 test cases** (`out/T3.6/cases/*.dxe`, built here with the same selcc commit `2b26d3b`; 2,036 pass
  in sharcvm, 6.17 M instructions). selache's author promotes a case only after it ran on an ADSP-21569 board
  with selcc (`vendor/selache/xtest/grow_drafts.py`), so these encodings have run on this chip [inferred: their
  claim];
- **shape**: same form and mnemonic as a stock (or selcc-corpus) instruction, only the data registers differ
  (e.g. `F7 = F5 * F6` vs stock `F2 = F1 * F4`);
- **UNSEEN**: anything else.
Any instruction carrying an immediate or an address (Types 6, 14a, 15a, 16a, 17a/b, 18a, 19a, 25a, 8a) must be
exact or exact-selcc; Type 6 shift immediates are also checked for the sign-extension rule.

| | instructions | exact (stock) | exact-selcc | shape | UNSEEN | findings |
|---|---:|---:|---:|---:|---:|---:|
| CG01 | 136 | 115 | 17 | 4 | 0 | 0 |
| FLG1 | 4,333 | 2,861 | 1,218 | 254 | 0 | 0 |
| FTD1 | 10,549 | 6,642 | 3,169 | 738 | 0 | 0 |

The stub itself is entirely `exact`. The 0 shift immediates of section 1 step 5 also hold for the whole
FLG1 code (selcc emits shift counts in registers only, T3.11 12.7).

## 3. Memory placement

| what | range (core bytes) | bytes | why there |
|---|---|---:|---|
| code (stubs + our C) | `0x2dd600-` (SW `0x16eb00-`): CG01 to `0x2dd888`, FLG1 to `0x2e1938` | 648 / 17,208 | L1 block 1 tail |
| data (selcc's `seg_dmda`: the flanger's sync table) | `0x2e6000-0x2e6034` | 52 | L1 block 1 tail |
| stub register save area (FILL) | `0x2e6800-0x2e686c` | 108 | L1 block 1 tail |
| flanger state `FlgSlot` (FILL, FLG1 and FTD1) | `0x300000-0x308400` | 33,792 (33,056 used) | L1 block 2 |
| tape delay code (FTD1 only) | `0x310000-0x315f90` (SW `0x188000-`) | 24,464 | L1 block 2, below the PM cache (section 9) |
| tape delay state `TdSlot` (FTD1 only) | `0x8005912c-0x80359680` | 3,147,092 | the stock delay's own DDR state (section 9) |

- **L1 block 1 tail** [verified static, T3.2 2.2]: the stream's last block-1 byte is `0x2dd52c`; nothing is loaded
  above it and no static reference names the range; the FreeRTOS heap is a fixed array ending at `0x2dd0b8`.
  All our block-1 bytes stay inside `0x2dd600-0x2e7000`, the range dnfw ran code in on a unit for weeks
  (prior-art 6.1) [inferred: their hardware reports], below a 32 KB DM cache (`0x2e8000`) and the 16 KB one the
  start-up configures (`0x2ec000`, T3.2 correction).
- **L1 block 2** for the 33 KB of flanger state [verified static, T3.2 2.3]: never written by the stream, no
  static reference in any address view; our range ends 79 KB below the PM cache (`0x31c000`; `0x318000` if it
  were 32 KB). Single-cycle, so the flanger's per-sample ring reads cost no DDR stalls (the stock chorus keeps its
  state in DDR). Two more pieces of evidence that this memory is usable at run time [inferred, other projects'
  hardware]: selache's own linker script runs its hardware tests with code in L1 block 2 and data in block 1
  (`vendor/selache/libsel/link.ldf`), and dnfw's Waverider M5 put its code and data in L1 block 2 from
  `0x300000` and passed their hardware test once the shift bug was fixed (their `waverider-m5-dsp.md`,
  `waverider-dsp-compare.md` section 11, which also withdraws the "no code in blocks 1/2" lead).
- **Not used, and why:** the stock chorus's own DDR state (4,928 B, too small for 33 KB); DDR `0x804ace8c-
  0x8052d790` (zero-filled, no static reference, but dnfw found the voice buffers at `0x804acf90 + 0x80t` in it);
  the L2 tail (dnfw: stock data words point into `0x200918c0-0x200c2000`, prior-art 6.1); the stock delay's 4 MB
  (kept for the tape delay, milestone 3).
- **Zero at boot:** FILL blocks clear the save area and the flanger slot, so the slot's magic word reads 0 until
  `flg_init` has run; `flg_process` runs `flg_init` itself if it ever finds no magic (belt and braces: the init
  hook normally does it at start-up, before the scheduler).
- **Run-time proof of "free"** is still open, as in T3.2: a write watch over the whole block in the emulator only
  covers what the emulator runs. In sharcvm, the stock effect init plus 12,000 blocks of the whole handler leave
  `0x2dd600-0x2e7000` and `0x300000-0x308400` all zero (section 6). [verified in sharcvm, not on the unit]

## 5. Milestone 2: FLG1, the flanger in the chorus slot

`out/T3.8/FLG1/`: `FLG1.syx`, `section7.bin`, `build.json`, `audit.json`, `verify.json`, `device_depack.json`,
WAVs (`vm_input.wav`, `vm_stock_chorus.wav`, `vm_FLG1_flanger.wav`: the whole handler's output, stock vs FLG1, on
`out/T3.11/dry/chords.wav`; `vm_FLG1_slot_wet.wav`: the slot's own wet output, low level).

- **Code:** `fx/flanger.c` unchanged (its SHARC-friendly structure and all four selcc workarounds of T3.11
  11.3/12.7 stay as they are; nothing needed fixing), plus `tools/dspsplice/src/flg_glue.c` (`flg_init`,
  `flg_process`), written to the same rules (no comparison initialisers, one declaration per variable, no table
  indexed by a fresh integer, no unions). selcc compiles them as they are; the register census and the audit
  pass; 0 shift immediates.
- **Lifecycle:** at start-up the effect init `0x1c1445` reaches our init stub instead of the chorus init: it runs
  `flg_init()` (clears and sets up the 33 KB slot, applies the fixed knobs, writes the magic) and then jumps on
  to the stock chorus init, which runs exactly as before with its caller's frame. Every block the FX bus calls
  our process stub instead of the stock chorus: `flg_process(params, io)` reads the four chorus parameter
  floats, calls `flanger_set` only for a knob that changed, snaps all smoothers on the first block, and renders
  32 samples of wet signal into the bus's chorus output buffers. The stock chorus no longer runs; its DDR state
  is initialised and left alone.

### 5.1 What each knob of the stock chorus page does now

The ColdFire side is unchanged: the page still says CHORUS, DPTH, SPD, HPF, WDTH, DEL, REV, VOL, and the frame
carries the same words (T3.3 k25-k31); E and F stay empty. Relabelling is ColdFire work for later (T5.0).

| knob (frame word) | stock chorus | in FLG1 |
|---|---|---|
| DPTH (k25 `0x9fa`) | modulation depth (delay table 5.4-7.7 ms) | **sweep depth**: 0 to +-3.32 octaves of delay around the centre (log sweep). 0 = a static comb; 96 = +-2.5 octaves = 0.16-5 ms around 0.9 ms |
| SPD (k26 `0x9fc`) | LFO 0.28-3.1 Hz, linear | **LFO rate** 0.02-10 Hz, log: 0 = 50 s per cycle, 30 = 0.087 Hz (11.5 s), 64 = 0.46 Hz, 96 = 2.2 Hz, 127 = 10 Hz |
| HPF (k27 `0x9fe`) | input high-pass | **input high-pass** of the wet path, 20 Hz-2 kHz, log: 0 = 20 Hz, 32 = 64 Hz, 64 = 200 Hz, 127 = 2 kHz (the lows stay dry and clean at high feedback) |
| WDTH (k28 `0xa00`) | stereo width | **stereo phase**: the right LFO 0-180 degrees ahead of the left (48 = 68 degrees, 64 = 90, 127 = 180): the sweep turns across the field |
| DEL (k29), REV (k30) | chorus -> delay / reverb sends | unchanged: the bus sends the flanger's output on |
| VOL (k31), per-track CHR send | return level / send | unchanged: the bus adds the dry track, so send + VOL set how deep the notches are (send and VOL near unity = full-depth notches) |

Fixed (no stock knob): **FDBK 107 = +68 % feedback** (resonant, damped, soft-limited), **MAN 50 = 0.9 ms
centre**, SHP sine, SLEW minimum (1 ms), **DAMP 12 = about 10 kHz** in the loop, SYNC off, OFS 0 (no stereo time
offset), POL normal. **The "slow, deep, resonant, swelly" default patch is DPTH 96, SPD 30, HPF 32, WDTH 48** on
the stock knobs; at SPD 30 one sweep takes 11.5 s.

What cannot be reached in FLG1: negative feedback, the Karplus-Strong comb range (MAN up to 77 ms), the LFO
shapes, tempo sync, OFS and POL. They exist in the code; they need the two empty slots (E, F) or a second page,
which is ColdFire work (T5.0/T6.0 found the frame room and the page mechanism). An alternative build could put
FDBK on HPF's knob (HPF fixed at 64 Hz) if the owner wants feedback under his hand sooner; that is a one-line
change in `flg_glue.c`.

## 7. Costs [verified in sharcvm: instruction counts, not cycles]

| | instructions per block, whole handler, no voices | vs stock |
|---|---:|---:|
| stock | 320,331 | |
| CG01 | 321,523 | +1,195 |
| FLG1, knobs still | 322,765 (max 322,841) | **+2,434** |
| FLG1, a knob moving every block (the ColdFire glides a turned knob) | 324,469 (max 324,543) | +4,138 |
| FLG1 fuzz (knob jumps, full-scale noise, all sends) | max 328,692 | +8,361 worst block |

- Per effect: the flanger itself is about 16.7k instructions per block against the stock chorus's 14.5k (T3.11
  12.7), plus about 150 for the stub. At the SHARC's 1 GHz (666,667 cycles per block, dnfw's measurement) the
  average increase is 0.37 % of a block, the worst block 1.3 %. The stock unit runs at 63-65 % DSP load (dnfw,
  measured on a unit), so about 35 % is free. [inferred: 1 instruction ~ 1 cycle; our state is in single-cycle
  L1 while the stock chorus's was in DDR, so if anything the cycle difference is smaller]
- **Stack:** the handler's deepest point goes from 940 to 1,344 bytes below its entry (stack painting in
  sharcvm), +404 bytes, all in our C frames under the chorus call. The Audio Task's stack is 4,000 bytes
  (`xTaskCreate(..., 1000, ...)` at `0x1ca009`, scaled by `lshift(R12, 2)` at `0xb88840` before `pvPortMalloc`)
  [verified]; with the task's own frame and an interrupt context on top that leaves well over 2 KB
  [inferred: the interrupt frame size on this port was not measured].
- **Memory:** section 7 grows from 836,956 to 854,280 bytes (+17,324; limit 1,048,575); stored (compressed)

## 9. Milestone 3: FTD1, the flanger and the tape delay [verified in sharcvm, not on the unit]

`out/T3.8/FTD1/`: FLG1 plus `fx/tapedelay.c` in the delay slot (`tools/dspsplice/src/td_glue.c`). Same method,
two more hooks: the FX bus's `CJUMP 0xb8482c` at `0x1c1c58` -> `fxh_delay` (`td_process`), and the effect init's
`CJUMP 0xb848cb` at `0x1c166c` -> `fxh_delay_init` (`td_init`).

- **State in the stock delay's own DDR** (`0x8005912c-0x80459388`, 4,194,908 B, T3.4): the `TdSlot` (3,147,092 B,
  checked at compile time to fit) starts at the address the bus passes as the delay's state. The stock stream
  already zero-fills it (block 88). The stock delay no longer runs.
- **The stock delay init is not run** (unlike the chorus init in FLG1): it would clear its rings over our state.
  What it writes, measured in sharcvm by diffing all memory around the call [verified]: its own DDR state
  (`0x8005912c-0x80059130` and `0x80459230-0x80459388`), its parameter struct `0x257934-0x25794c` and stack.
  The parameter struct is rewritten from the frame by the render's unpack before the FX bus runs, every block
  (T3.4 section 1), and only the delay routine reads it; so skipping the init changes nothing else.
- **Code in L1 block 2:** block 1's tail (39 KB) does not hold both effects (flanger 18 KB, tape delay 24 KB), so
  the tape delay's code goes to `0x310000-0x315f90` (SW `0x188000-`), below the PM cache. selcc's output is
  unchanged; only its section is renamed in the assembly so the LDF places it there. All calls between the two
  regions are absolute 24-bit CJUMPs.
- **Knob map (stock delay page -> tape delay):** TIME -> TIME (the same tempo-synced law, (TIME+1)/128 of a whole
  note; the tempo comes from the bus's descriptor, `0x257e80`); FDBK -> FDBK with the tape's own law, 0-110 %
  over the whole knob (stock: FDBK/64, so stock 64 = 100 % becomes 55 %; full knob = 110 %, held by the
  saturator); HPF -> HPF (resonant 2-pole in the loop, 20 Hz-4 kHz, 22 = 50 Hz); LPF -> LPF (resonant 2-pole,
  100 Hz-18 kHz, 102 = 6.5 kHz); WID -> WID (0 mono, 64 stereo as it comes, 127 ping-pong); **X on -> full
  ping-pong** (WID 127); REV and VOL stay the bus's. Fixed: RES 32 (mild resonance), WOW 20, FLUT 20, AGE 24
  (subtle wear), DRIV 32 (+3.9 dB). The noise seed is fx/render.c's, so the unit's noise equals the A/B renders'.

## 11. What is left, and what the owner should know

- **Nothing here has run on the unit.** Everything is proven in the emulators only: the boot stream structure,
  the unit's own depacker, the whole DSP block handler in sharcvm, and the brick checker. The encoding audit
  covers the known selas trap: every instruction we add occurs, apart from its addresses and immediates, in
  stock or in selcc's hardware-validated output, or is a stock operation with other data registers (738 of
  10,549 in FTD1); none is new. Only the unit can show that the DSP runs our code.
- **Run-time "free" memory** is proven statically and in sharcvm (stock never touches our ranges in 12,000
  blocks), not on the unit. dnfw's builds ran code and data in both L1 regions we use [their reports].
- **Brick checker coverage of the new code:** check 11's dynamic run feeds the inputs only to the reverb (and the
  delay's own TIME/FDBK), so the chorus slot (and in FTD1 the delay slot) run on silence there. Our
  `verify_*.py` runs drive both slots with signal and fuzz them. Suggestion for the main session (not done
  here, as it changes the gate): add `IN_CHR_L/R` and `IN_DEL_L/R` sends to `bc_dsp.dynamic_run`.
- **CPU on the unit:** the instruction counts above are not cycles. The real load needs the idle-time meter
  (G6/T4.1; dnfw's method: idle-task EMUCLK deltas) or the handler's EMUCLK word; with ~35 % free on stock,
  FLG1's +0.4 % and FTD1's +2.8 % (average) are small, but the tape ring's DDR traffic is not modelled.
- **Labels:** the chorus page still says CHORUS/DPTH/SPD/HPF/WDTH and the delay page its stock names; the new
  meanings are in sections 5.1 and 9. Relabelling, and putting FDBK and MAN on the empty E/F slots (with frame
  words from T6.0's free room), is ColdFire work for later (T5.0). The 2-page plan is separate.
- **Fixed parameters** can be changed by editing one line in `flg_glue.c` / `td_glue.c` and rebuilding; each
  rebuild must go through `build.py`, `audit.py`, `verify_*.py` and the brick checker again.
- **selcc vs ADI's calling convention:** selcc preserves R8-R15 across calls, ADI's compiler R3, R5-R7, R9-R11,
  R13-R15 (and treats R8, R12 as scratch). Measured here on the stock chorus and selcc code (section 2.1). Worth
  reporting to selache with the four miscompiles (T3.6 item 6), if the owner agrees: code that mixes the two
  needs a shim like ours.
- **Not done:** hand assembly of the hot loops (T3.11 11.4); a CPU meter; the tape delay with knobs on a second
  page; an elekloader DSP-section mod format (T3.10).
