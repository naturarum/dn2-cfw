# R1.1: the release patcher (Digiwerk Patcher and digiwerk-patch)

Date: 2026-10-23. Code: `tools/patcher/` (README.md for users). Nothing was flashed, signed or notarized.

## What it does

The user downloads Elektron's `Digitone_II_OS1.12_dist.zip` and drops it on the app; the .zip, the unzipped folder
and the .syx all work. The patcher carries one or more tested builds ("packs"). With several, the user picks one.
It refuses any input whose sha256 isn't `7e5b8a733d4ab1fdf7e5d22757f7d8eddaa3cbf71d0858874a791844c02ceb35`. It
rebuilds the chosen build and saves `<ID>.syx` next to the input, only if the result's sha256 is the tested build's.

## What a build changes, and what a pack holds

Checked on CMP4, OB01 and FL01 (mkpatch.py refuses any build that differs otherwise): the stored sections 3 (main OS,
elekloader's dense packer) and 7 (DSP, elektron-firmware-tool's packer); the 4-char version field; and what follows
from them: table offsets and lengths, 16-byte padding, the preamble's length and content checksum, the framing count,
every message's counter and checksum. Sections 2, 4, 5 and 8 are stored as stock.

**The trailer: the Digitone II is sealed.** The container ends with an HMAC-SHA256 of everything before it. The key
comes from the stock bootstrap (section 2: the seed `Multiplier`, a NUL, a 32-byte constant C; key = C ^
sha256(seed) ^ sha256(reversed seed), as elekloader's `seal_key` does it). The patcher derives it from the user's
file. It is never in a pack.

**A pack** (format 2, in mkpatch.py's docstring) holds:
- a header: id, version field, both hashes, lengths;
- the metadata: title, description, record line, brickcheck facts, and the DSP fields below;
- per replaced section: the decoded image as copy ops into the *pool* (the user's file decoded: every section
  depacked, then the decoded transport stream) plus our bytes (`ilit`);
- the packed stream's *skeleton*: the stream with every literal left out (tag and offset bytes, in decoder order),
  itself as copy ops plus a residue (`slit`). The tool walks the skeleton with the decoder and fills each literal
  from the image. Where both packers coded the same data alike (about 6.4 KB of section 7), the skeleton is copied
  from the user's file too.

| pack | bytes | ilit (our bytes), s3 + s7 | slit, s3 + s7 | ops | sha256 |
|---|---|---|---|---|---|
| CMP4 | 1,164,904 | 5,711 + 57,316 | 791,484 + 307,166 | 2,719 | `e071320a...` |
| OB01 | 1,165,066 | 5,771 + 57,316 | 791,542 + 307,166 | 2,749 | `bababc54...` |
| FL01 | 1,164,728 | 5,792 + 57,269 | 791,117 + 307,260 | 2,798 | `ef915801...` |

The skeleton is 94 % of a pack and doesn't compress (zlib or xz save about 5 %). Shrinking it would mean porting both
packers to C.

**Pack records.** Each pack has a hand-written JSON: `tools/patcher/packs/ID.json`, or `out/ID/pack.json` if present.
It holds the title, the description, `tested_on_unit` (a date, or "") and `effects`, by id: `cmp3` (3-band
compressor), `flng` (flanger), `tape` and `spng` (future). mkpatch.py checks the ids and that each has its icon in
`docs/identity/`. CMP4, OB01 and FL01 carry cmp3 + flng. mkpatch.py refuses a pack without a
brickcheck report under `out/brickcheck/ID-*/` that says ACCEPT, with every check PASS, for exactly this .syx: it
compares the report's candidate sha256. It fills in the hashes and writes the record line, e.g. "Brick check 12 of
12 · tested on a Digitone II, 22 Oct 2026" or "... · not yet tested on a unit" (`out/patcher/ID/pack.json`). Dates
entered: CMP4 and OB01 22 Oct 2026 (the owner's reports); FL01 none (not flashed yet).

## The Elektron-bytes check (stockcheck.py)

Every 16-byte run of a whole pack (header, metadata, ops, ilit, slit), and of its literal data end to end, is looked
up in: the stock .syx, its decoded stream (Elektron's packed sections as stored) and every stock section decoded.
**All three packs: about 1.147 M runs each, 0 hits.** mkpatch.py refuses on any hit, and the test proves it would.

An earlier wider run against all 28 ELE3 OS files in `out/firmware/` (`out/patcher/stockcheck-all-firmware.log`)
found two kinds of hit:
- skeleton runs inside other boxes' *packed* streams only: the same codec coding alike;
- two 16-byte runs of our ilit, rows of small integers in param-rows (12 of 16 bytes zero).

The check proves "no bytes of the 1.12 file"; that the rest is ours comes from the builds' sources.
`stockcheck.py --also` takes other firmware for builds that port code across boxes.

## Code

- **`dn2patch.c/.h`, the core.** libc only, its own SHA-256, no globals, no exit(). Every call takes a pack's bytes:
  - `dn2patch_info(pack)` gives the id, title, description, record, hashes and DSP fields;
  - `dn2patch_run(pack, in, check, ctx, &out, msg)` returns OK / NOT_STOCK / FAILED / NOMEM / CHECK_FAILED, with
    `msg` = a plain sentence, a newline, then the precise reason;
  - `dn2patch_is_build()` recognises an existing output.
- **`cli.c`, `digiwerk-patch`.** The packs are compiled in (`packs.h` from `mkpatch.py --embed`), so it stays one
  file. With several packs it lists them and asks for a number; `--pack ID` and `--list` work too. It accepts the
  .zip (`unzip -p`, no shell), handles Terminal's dragged-path forms, and asks before replacing a file.
- **`app/`, Digiwerk Patcher.** SwiftUI, macOS 13+, XcodeGen.
  - The packs are in `Contents/Resources/packs` (`index.txt` and `ID.dn2p`), one copy each, so the 766 KB binary
    carries no patch data (1.5 MB with the redesigned window).
  - **The window (redesigned 2026-10-23, after the owner's "looks quite plain").** It is 1040 x 640 pt, landscape,
    always dark: near-black page, slightly lighter panels, 1 px lines, square corners, white text, and one warm
    orange for refusals only. From the top:
    - a header bar: the pixel cog and wordmark; on the right, HELP and BACK TO ELEKTRON'S OS (a popover);
    - our three-block pixel marker and a heavy SF Pro headline, "Make your Digiwerk.";
    - the packs as cards in a row, scrolling sideways past three. The top shows the effects' icons at 3 pt per art
      pixel on a darker well. The caption has the id, BRICK CHECK 12/12, the title, the description and the
      tested line. The chosen card has a white outline and a filled square. A single pack's card comes chosen,
      with a panel beside it saying what the card means. With several packs none is chosen until the user clicks
      one; a file dropped before that is held, then made;
    - the steps as three panels, 01 to 03, with outlined capital buttons (SHOW IN FINDER filled white) and pixel
      ticks;
    - a status bar (a pixel tick, an orange "!" or an arrow; the small grey mono detail line), then a footer with
      "Not made or supported by Elektron."
  - **Fitting the window.** The title bar is hidden under the header bar. The view asks for 640 less the title
    bar, fills the full height, and the app pins the window to that size; an older saved frame was 672 pt.
  - **Checking it.** A debug build only (`#if DEBUG`, `DIGIWERK_SNAPSHOT=FILE`) writes the real window's geometry
    and an offscreen render. That confirmed 1040 x 640 and a layout identical to the harness's.
  - The pixel art is `docs/identity/*.svg` (make_icons.py), copied into `Resources/identity` at build time
    (`app/identity.sh`; docs/identity is only read). `Art.swift` draws it, and its own glyphs (marker, tick,
    arrows), as bitmaps at whole device pixels, without interpolation.
  - Not sandboxed, Hardened Runtime on; `DEVELOPMENT_TEAM` is left for the owner (steps in `app/build.sh`).

## For later: check stages and a DSP adder (designed, not built)

The owner wants the patcher to carry brick checks and a rough DSP memory/load "adder" when packs start combining.
The core has the hook for it. `dn2p_check(out, n, pack info, text, ctx)` runs on the output after the sha256 gate
and before anything is handed over; a non-zero return gives CHECK_FAILED, no output, and its text in the message
(tested both ways). Each pack carries `dsp_code_bytes`, `dsp_state_bytes` and `dsp_load_percent` in its metadata,
from `dsp` in its JSON (null, read as -1, for now). An adder stage would sum these over the chosen packs against the
DSP's budget, and refuse above the policy line (a few points over Elektron's load, never near 90 %).

## Tests (`make test`: 38 of 38 pass, 87 s; `out/patcher/test-results.txt`)

- **Every pack, byte for byte:** CMP4 `c1df74aa...`, OB01 `bfb88623...`, FL01 `a2179c0c...`.
  - Through the three-pack tool (`--pack`, and a number typed), plus the x86_64 slice under Rosetta.
  - Through the one-pack tool.
  - Through the app's own `Core.swift` (`app/test.sh`, 42 checks: every pack from the .zip, the folder and the
    .syx, and each pack's effects).
- **Refusals, no file left:** the 1.11 .syx, a truncated 1.12, a .zip without the stock file, a missing file, a
  build given as input (its own or another pack's), an existing different output, an unknown `--pack`, no choice.
  Also a pack corrupted in ilit (hash mismatch) or in slit (decode fails).
- **mkpatch refuses:** the 1.11 file, no brickcheck report, a report for another file, no pack JSON, an unknown
  effect id. stockcheck fails a pack with 16 stock bytes planted.
- **By hand, real launches with `open -a`:** the one-pack app with the .syx and with the .zip, and the three-pack
  app with the .zip. The three-pack launch ran before the no-pre-selection change; it took the first pack, CMP4.
  All wrote byte-identical files.
- **Screens** (`out/patcher/screens/`, rendered offscreen by `app/screens.sh` at 1040 x 640):
  - one pack: before, success, refusal (its pack is chosen, so a file is never held);
  - three packs: before, a file held, FL01 made, a refusal.
