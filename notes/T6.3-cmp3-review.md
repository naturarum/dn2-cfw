# T6.3 CMP3: storage review of comp-link-dn2 0.2

Date: 2026-10-21. Reviewer: storage only (kit storage, the part that could lose the owner's data). The subject is
`vendor/elekloader/examples/comp-link-dn2/` 0.2 (store.c, store.s, tail.s, mod.json) as linked in
`out/T6.3/CMP3.syx` (sha256 `28f10cba...`, main OS `out/T6.3/CMP3.main.bin` `13c562b3...`). Nothing was flashed,
committed, pushed or posted, and nothing was rebuilt. Marks: **[verified]** means run, or read in the bytes or the
stock disassembly. **[inferred]** means reasoned, not run.

## Verdict

**OK to flash with these unit checks** (section 3). No blocker and no major finding. Two minor items concern code
(3, 5) and one concerns the guide (1). None of them can corrupt stock data or crash the box.

## What I checked and ran

- **The built hooks.** I disassembled them from `CMP3.main.bin` (file offset `0x30c5c0` = `0x47e00000`).
  - The bytes are identical in C3EM's main OS at the same offset, so the emulator proofs ran this code.
  - The sites hold `jmp 0x47e0033e`+nop at `0x400dcf34`, `jmp 0x47e00372`+nop at `0x400dcef0`, and `0x47e00598` at
    `0x401da4f0`.
  - compl_ser and compl_load replay the stock 8 bytes exactly. They resume at `0x400dcf3c` (`movea.l 16(sp),a3`) and
    `0x400dcef8` (`movea.l 16(sp),a0`). They pass the two arguments in the right order, keep d0 and add code only
    when d0.b is 1.
  - No instruction in the image branches into either prologue. The only entries are the jsr at `0x4002fc50`, the
    jsr at `0x400de034`, the jsr at `0x400dde90` and the dead bra.w at `0x400dfb66`.
  - Registers: compl_decode saves d2-d7/a2-a6. compl_update saves d2/a2 and its locals do not overlap. compl_encode
    uses only d0/d1/a0/a1.
  - Writes: compl_encode and compl_update write only record +0x60..+0x97 (27 words, then 0xC3B1 at +0x96), plus the
    id-0 restore at +4. compl_decode writes only live k 70..96 (+0x8c..+0xc1). **No overflow** [verified].
- **The stock routine at slot 17** (`0x4002ffca`). It handles the vector type first, then the single type, else it
  posts the mirror job `FUN_4002fc34`. `only_ours` makes the same two dynamic casts with the same type infos in the
  same order, so it classifies a change exactly as stock does. `FUN_400dce5e(0x10,k)` returns 0 for any k > 69
  (unsigned compare), so a band knob writes only id 0 [verified].
- **Re-run** of the builder's `scripts/t63d_store.py built` on C3EM's warm snapshot: **PASS, 11/11**, 21.9 s, 279 MB RSS.
- **FxSetup object census** on the same snapshot (a small scratch script).
  - There is **one** FxSetup object (`0x446cfa90`). Its live pointer +0x10 is the current kit's FX setup (live kit 0
    of the 128-kit array at project +0xef371c). Its mirror +0x20 is kit 0's FX record in the working image.
  - So a kit change retargets this one object: `vslot09` sets +0x10 and then runs `vslot04(self,0)`, and
    `vslot12`/`vslot13` set +0x20 [verified, setter disassembly].
- **Callers.**
  - All 10 callers of the kit serializer `FUN_400ddfa8` reach the hooked `FUN_400dcf34`:
    - Save Kit `FUN_4003ff02` (`FUN_400441cc`, "Kit saved to", Temp/Proj);
    - the exports `FUN_400e4942`/`FUN_400e4a52`;
    - `MmcFs::vslot29`;
    - SysEx `FUN_400d5b38`;
    - project save `FUN_400e15f8`;
    - the four kit-mirror updates at `0x4003xxxx`.
  - All 6 callers of the kit loader `FUN_400dddb6` reach the hooked `FUN_400dcef0`. These include project load
    `FUN_400e18e6` (all 128 kits) and kit reload `FUN_40040948` [verified static].

## 2. Answers to the builder's pointers

1. **Slot 17**:
   - A stock single edit of k < 70 cannot lose or garble our words. It writes ids ≤ 45 (≤ +0x5f), and the encode
     rewrites our words from the current live values.
   - The id-0 slot and live FX k 0 never get a value stock could not put there, except band values on mixed
     vectors, which are harmless (finding 4).
   - The one real gap is the retarget window (finding 3), and it is minor.
2. **Decode**:
   - Clamping is enough for safety (finding 5).
   - The seed is right for every stock RAT index (finding 6).
3. **Boot and power cycle**: yes, every kit loads through the hooked loader at project load (finding 7). Unit check.
4. **Kit changes, copy/paste/clear/undo**: our words follow (finding 8), apart from the minor retarget window (3).
5. **Seeded over good**: no CMP3 path does this without a user save (finding 2). The zeroing premise is true only of
   stock/CMP2/CP2F, where it also covers the ordinary Save Kit (finding 1).
6. **Other checks**:
   - Concurrency is OK (9) and stock compatibility is OK (10).
   - There is no overflow.
   - Registers, stack, replays and resume addresses are OK.

## 3. Unit checks FLASH-CMP3.md should state more clearly

1. **Test 6 (power cycle)**:
   - After the power-on, open **two** kits, not only the one that was active, and check each kit's band pages.
     All 128 kits load through the same hook, but only the active kit's load was seen in the emulator.
   - Optionally, a second power cycle **without** saving: this records what the box keeps of unsaved band edits.
     They should behave like an unsaved stock knob.
2. **Test 5**:
   - Name the save: **Save Kit** (the "Kit saved to" message) and then **kit reload**.
   - Separately, **Save Project** and project reload. These are different code paths (`FUN_4003ff02` and
     `FUN_400e15f8`).
3. **Test 5, running**:
   - Switch between the two kits with the sequencer running, and turn a band knob around the switch a few times.
   - Then stop, reload neither, and step back to each kit: each must show its own band settings, not the other
     kit's. This is finding 3's case, which is unlikely to be hit, but it is cheap to look at.
4. **Test 9**:
   - +Drive kit library: save, load into another slot, **then power-cycle** and check the copy.
   - Optional: a SysEx/Transfer kit dump and reload. On CMP3 the dump carries the words.
5. **Test 7** should say which old projects seed: those last saved on stock 1.12, CP2F or CMP2 (or older). It should
   also say that a kit **kit-saved** on CP2F/CMP2 after a CMP3 session seeds as well.
6. A line for old-format projects (last saved by an OS before 1.12, or restored from such a backup): their band
   pages should show the old-kit setup (30Hz / 16.0k). Any other set of values means stale words (finding 5): note
   it and re-set the bands.
7. **"Going back to CP2F or CMP2"**: replace the in-place line. A **project** save there keeps the CMP3 band settings
   (stale). A **Save Kit**, a +Drive library save or an export there drops them, and on CMP3 that kit opens as an old
   kit. Also say that if a working state from CP2F is then saved as the project on CMP3, the project file gets the
   old-kit setup.
