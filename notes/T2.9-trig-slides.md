# T2.9: trig slides (p-lock slides) on the Digitone II, OS 1.12

2026-10-31. The owner: "trig slides for smooth p lock transitions ... per step trig slides would be the best
implementation, with per track / per pattern general p lock slew being second best", then on the behaviour: "it
should be like portamento. as soon as the previous step's gate goes off, params should start sliding in time to be at
100% of the target value when the next step's gate goes on ... i think i want it simple first: to implement and also
to perform on device ... maybe we can even start with per-track". Marks: **[verified]** = read in the code or run;
**[inferred]** = reasoned. Study only: nothing built or flashed.

## The plan (proposed to the owner 2026-10-31)

**v1, per track.** One SLIDE switch per track, saved with the kit. With it on, at each gate-off on the track the
engine takes the track's next trig and moves every continuous parameter that will change (the next trig's p-locks, and
the current trig's p-locks going back to the kit's value) in a straight line, to arrive exactly at the next trig's
gate-on. No gap (LEN reaching the next trig, INF, micro-timing making the gates overlap): no slide, the values change
at the gate-on as now. Trig conditions and fills: v1 slides toward the next trig as written; if it doesn't play, the
next trig that does sets its own values as now. Pitch keeps the stock PORTAMENTO; stepped parameters (machine, waves,
modes) change at the trig. Main OS only: no DSP code, no DSP room.

**v2, per step.** SLIDE becomes p-lockable: the track's value is the default, a lock on a step says whether the sound
slides into that step (hold the trig, turn the knob). The p-lock tables hold it; no new storage format.

## What the stock does [verified unless marked]

- **Gate-off.** The block handler `0x40025e36` (vector 191, 1,500 a second) counts each voice's gate down
  (`0x80005220 + 4v`, by `0x402a132c` per block) and calls `0x4002b06e(v)` when it ends. That routine knows the
  voice's track and note (`0x40288306 + 0x14v`: track, `+1` note), clears them, books the release time and clears
  the voice's bits in the track's and the note's masks.
- **A trig's parameters reach its voice in one copy.** In the handler's sequencer-event loop (`0x40025e36`, the calls
  of `0x4002549c` at decompile lines 579 and 590), `0x4002549c(set, row)` copies a whole parameter set (`set + 0x14`,
  101 words: the sound with the trig's locks) into the voice's row of the raw mirror (`0x80003b12 + 0xca * row`) and
  its machine record (`set + 0xde`, 0x99 bytes, to `0x8000487c + 0x99 * row`), and records `set` at
  `0x80003af0 + 4 * (row + 0x5ee)`.
- **A track parameter goes to all its voices.** `0x4002585a(value, track, k)` writes `k` into every row whose owner
  word (`0x80005308 + 4r`) is the track (notes/T3.3-fx-frame.md); a knob turn takes this path.
- **Every block, every row is smoothed** (`0x400db28e(0x80003af0)`: 1,734 words, one pole, 3 % of the way a block,
  into `0x800068e4`), then copied into the frame for the DSP (T3.3). So a p-lock already glides over about 20 ms; a
  slide is the same rows moved further, on a schedule.
- No parameter slide in 1.12: no SLIDE trig type; "Slew"/"SLEW" are an LFO page label (`SoundParameterSet::vslot22`
  shows "Slew" for parameters 0x51, 0x5b, 0x65 when the LFO's wave, 0x4f/0x59/0x63, is 6). Portamento (pitch) has
  its own setup menu (CONSTANT STEPS, EXPONENTIAL, GLIDE, GLISSANDO).

## To find next

1. Where the event loop's parameter sets come from (the `set` of `0x4002549c`): built at the trig, or ahead of it
   (micro-timing can fire a trig before its step, so the sequencer looks ahead somewhere). If the next trig's set
   exists at the gate-off, the target is free.
2. The time from a gate-off to the next gate-on on the track: the step clock, the track's length and scale, the
   trig's micro-timing, LEN.
3. Which of the 101 words are continuous (slide) and which are stepped (machine, waves, modes: jump at the trig).
4. Writing the slide: per block, the track's rows moved toward the target (as `0x4002585a` does), arriving at the
   gate-on despite the 3 % smoothing behind it (aim about 20 ms early, or move the smoothing state too).
5. A place for the per-track SLIDE (a spare kit byte, as Digiwerk's other settings) and where it shows on the unit.
6. v2: a lockable parameter row (param-rows / param-grow already add rows).

## The study, part 2 (2026-10-31): a design grounded in the code [verified unless marked]

**The next trig is known about a step ahead.** The sequencer task `0x400d99de` runs once per tick (its clock
`0x42c4f900` += 900,000 a tick) and, at the tick where a track's tick counter is 0, builds that step's event
(`0x400d87b8` for a sound track) and queues it with `0x40138e3c(event, time)`, time = now + (ticks per step - 1) ticks
+ swing (`local_30`) + micro-timing (`local_34`). The block handler takes events from that time-sorted list
(`*0x44645228`: buckets `+4` time, `+8` first event, `+0x10` next bucket; events chained at `+0x68`). So during
step N the event for step N+1 is already queued, from about one tick after step N's trig [inferred from the times].
A trig after empty steps is queued about one step before it plays.

**What a trig sets.** The event (`0x400d87b8`): `[4]` track, `[0xf]` the sound's parameter set (the kit's,
`kit + 0x34 + 0x48b t`, or a sound lock's from the pool `0x4240dbcb + 0x48b i`), `[0x15]` a lock set (filled by
`0x400d874c` from the pattern's lock table `pattern + 0x17e50` when the step has locks: `+8` count, then entries of 8
bytes, `[0]` k, `[1]` value). At the trig the handler copies the set's 101 words into the voice's row
(`0x4002549c`) and applies the lock set with `0x400db1f6`, which writes each locked value into the row **and** straight
into the smoothing state (`0x8000de60 + 4 (0x11 + 0x65 r + k)` = value << 16): p-locks jump, unsmoothed. A slide's
target is therefore the next event's set with its lock set applied, and a slide that has arrived leaves nothing for
the trig to change.

**The engine** (main OS only):
- a gate-off hook on the handler's call of `0x4002b06e(v)`: note the voice's track (`0x40288306 + 0x14 v`) and the
  time;
- per block, before the smoothing call (`0x4002717e`, `0x400db28e(0x80003af0)`): for a track with a slide pending,
  find its next type-1 event in the queue (track `[4]`), take its time and target; for every slidable k that differs,
  write start + (target - start) x progress into the raw word and the smoothing state of every row the track owns
  (owner `0x80005308 + 4 r`), so the slide is exactly linear and lands at the event's time;
- no gap (the event's time at or before the gate-off), a sound lock to another sound, or another machine: no slide.

**Which k slide** (the descriptor table `0x401f83a4`, `scripts/dn2_param_table.py`): range of 50 or more, except LFO
DEST (`k 4, 0xc, 0x14`, a list) and portamento (`0x5d`, `0x5e`). Fixed for every sound: LFO SPD, FADE, SPH, DEP;
filter envelope, BASE, WDTH, KEY.T; amp envelope, PAN, VOL; the three sends; BR, SRR, OVER. Per machine (`k
0x19-0x41`; FM TONE, WAVETONE, FM DRUM, SWARMER) and per filter (`k 0x42-0x44`; six filter machines): from their
rows, e.g. FM TONE's ALGO and ratio lists jump, HARM, the offsets and envelopes slide; the multimode filter's TYPE
(a morph, 0-127) slides, the legacy filter's (0-2) jumps. Masks precomputed from the table into the mod.

**Where the switch can live.**
- **The page:** the TRIG page's second page (RTRG: RTRG, VFAD, LEN, RATE, -, -, PTIM, PORT) has **E and F empty**,
  next to portamento (`scripts/t61_snap_tables.py ... pages`).
- **A new parameter needs a descriptor row:** rows end at 0x140; param-grow (the compressor's, proven on the unit)
  moves the table to DDR and makes room, so SLIDE in every build means param-grow in the base.
- **Saving it:** the live sound's word k 100 is free, but the sound serializer `0x400dd80a` copies only k 0-99 through
  the map `0x401fd330` (k 0 and k 65 share stored slot 0), so k 100 is never saved; the stored record has nine free
  slots (stored ids 4, 8, 12, 16, 20, 24, 28, 32, 107). Saving SLIDE = a patch in the serializer and the loader (live
  k 100 <-> stored id 107); a stock OS ignores that slot. Per step (v2) would need the pattern's lock save/load too
  (locks are stored by stored id).

## TS01, the first build (2026-10-31) [built and tested offline; not yet on a unit]

The owner's choices: SLIDE is a knob on the TRIG page's second page (RTRG, E); after empty steps the slide starts at
the previous gate-off (the look-ahead finds the next trig across them). Build: `scripts/ts01_build.py` (CFTE +
`vendor/elekloader/examples/trig-slide-dn2` 0.1: `ts.c`, `ts_stubs.s`, eleven sites), `out/TS01/TS01.syx`.

**How it works.**
- `0x400da184` (the scheduler's `jsr 0x40138e3c(event, time)`) -> `ts_queue_hook` -> `ts_queue`, and play start's
  two loads of `0x40138e3c` into d7 (`0x400d7f14` in `0x400d7e88`, `0x400d8380` in `0x400d806a`: the call for each
  track's first trig, built before play by `0x400d907a`, its step in `0x42c5ba73[t]`) -> `ts_start_hook` ->
  `ts_start`: for a sound track with
  SLIDE on, it reads the event (before queuing it: the handler may take and free it at once), publishes the trig (its
  time, step, set, all its locks), queues it, then asks the stock builder about the following steps with an event of
  its own (as `0x400d907a` does) until it finds a trig, and publishes that one too, with its time estimated as the
  scheduler will compute it (the step's place, plus that trig's swing and micro-timing). It puts back what the builder
  moves in that mode: the random generator (`0x402a12fc`, `0x402a1300`) and the preview PRE state (`0x4463fc79[t]`).
- The five loads of `0x4002b06e` in the block handler -> `ts_gateoff`: if the track plays, SLIDE is on and this was
  its last held voice (the voices whose record at `0x40288306 + 0x14 v` names the track, with a note), a slide starts from this voice's row toward the earliest trig still to play (the one queued,
  else the one looked ahead): every parameter that slides and differs, row word and target.
- `0x4002717e` (the handler's `jsr 0x400db28e`, the smoothing) -> `ts_block`: every slide one block on, written into
  the row word and the smoothing state of every row the track owns (so it is exactly linear), the target written in
  full the block before the trig is taken, then off. Off at once when a note is held on the track (the trig came, or
  another note), the sequencer stops, or SLIDE goes off. When a trig is queued for the track: the one it moves toward
  -> its exact time and values; one that plays before it -> it turns to that one. Unlocked targets follow the sound,
  so a knob turned during a slide moves where it lands. Returns the smoothing's d0.
- Which parameters slide: the track's machine and filter row (`0x400dc18e`) with a range of 50 or more, but LFO DEST
  and portamento; worked out once per machine and filter. Source and target must hold the same machine and filter
  (the row's machine record against the target set's), else the trig changes it.
- SLIDE: the sound's k 100 (row 0x155, uid 0x420, ON/OFF as Env. Reset's row 0x32, group "Portamento"), not
  p-lockable; saved in the stored sound's free id 107 (`ts_ser` at `0x400dd8b2`, `ts_load` at `0x400dd3e6`). A
  stock OS ignores it (SLIDE off). This keeps k 100 persistent by our own two stubs, which T6.1 3.2's rule ("never 65
  or 100") did not foresee.

**Stock facts found while building it [verified in the code].**
- The handler takes every event due before clock + 2 rate (`iStack_34`, computed at its start) in its event loop,
  then calls the smoothing; the clock moves on at its end. So a slide must land the block before its trig is taken,
  and never write once it is taken.
- The smoothing reads the mirror's words as signed 16-bit (`(short)` into the EMAC): slides interpolate signed.
- `0x400db28e` returns `0x800068e4` in d0; the handler pushes it for `0x400db390` (`0x40027192`).
- `0x40138e3c` writes only d0 and a0 (it masks interrupts inside): the scheduler may keep d1 and a1 across it.
- The scheduler (vector 121, `0x400d99de`) runs at level 2 (`0xfc048079` = 2, `0x400d972e`), the block handler
  (vector 191, `0x40025e36`) at level 5 (`0xfc04c07f` = 5, `0x40025584`): the handler preempts the scheduler.
- The step counter `0x42c5b964[t]` (a byte) is the step being built; it moves on when the tick counter
  `0x42c5b974[t]` reaches TICKS of the track's speed copy `0x42c5b9d9[t]`, wrapping at the pattern's length, or the
  track's when `pattern + 0x1dd59` is not 0. A step is built one step before it plays.
- An event's `+8` is its time less micro-timing; `+0xc` the micro-timing scale ((100 - QUANTIZE) x 0x147af >> 7);
  `+0x38` its trig flags, bit 0x10 swing; swing = `0x400d7e34()` x ticks per step x 18,000; micro-timing as queued =
  `(short)((scale x micro) >> 16) x 1,500`.
- The builder with a supplied event: no condition counters move, but it draws the probability generator
  (`0x40136984`: none at 100 %), writes the preview PRE state (`0x401369cc`; `0x40136c9e` copies it to the live one at
  play start), skips a note with negative micro-timing when QUANTIZE is not 100 (and may return 0), and returns 0 for
  a step without bit 0 (trigless locks are not targets).
- Gate-off sets the voice's track and note bytes to -1 and clears its bit in `0x4059db08` and in the track's mask
  `0x40288844 + 0x40c t`. `0x4002b1b6(t)` returns `0x4059db08 &` that mask, which is **not** the track's held voices:
  in the emulator it stays 0 through ordinary notes while the track's mask and the voices' track bytes show them
  (TS01's first build used it and its "a note is held" test never fired; fixed: the track bytes) [verified, emulator].
- Play start (`0x400d7e88`, `0x400d806a`) queues each track's first trig, pre-built by `0x400d907a` into
  `0x446494c4 + 0x6c t` (its step `0x42c5ba73[t]`, its micro-timing and swing `0x44649b84[t]`, `0x44649390[t]`), from
  its own loop, not through `0x400da184` (TS01's first build missed the first slide after PLAY; fixed) [verified,
  emulator].
- The warm snapshot's project has a 128-step pattern A01 (`pattern + 0x1dd54` = 128): the look-ahead from step 9 finds
  step 1 of the next loop 120 steps on [verified, emulator].
- `0x4002549c` also copies the set's machine record (`set + 0xde`, 0x99 bytes) to `0x8000487c + 0x99 row` (only if
  `0x400dc2fe(machine, row)` agrees): a row's machine and filter are bytes 0 and 1 there. When a trig's set is the
  one the row last took, the handler calls `0x400db0a8` instead of the full copy; `0x400db1f6` also marks each lock in
  a per-row mask (`0x4664c26c + 0x10 row`).
- PTIM is k 93 (row 0x22, group 0x0e, "Portamento"), PORT k 94 (row 0x23); Env. Reset is row 0x32 (k 75, 0..1,
  formatter `0x400e3568`).

**Limits of v1.**
- A trig nudged early is invisible to the look-ahead: the slide turns to it when it is queued, a step before it
  plays (a bend in the line).
- Trig conditions and probability: the slide aims for the next trig as written; if it does not play, the values stay
  at its target until the next trig that does.
- Trigless locks are not targets; one inside a gap loses to the slide for the parameters that slide.
- RTRG retrigs and arp notes: each held note stops the slide and the next gap starts it again from where the values
  are, so with them a slide moves only in the gaps. The handler plays a retrig by queuing the trig's own event
  again (it then takes `0x400db0a8` and the trig's locks again), so the locked words may step back at each retrig
  [inferred].
- A pattern change: the look-ahead stays in the current pattern; the next pattern's first trig is found when queued.
- SLIDE turned off during a slide: it stops where it is.

## TS02, per step (trig-slide 0.2, 2026-10-31) [built and host-tested; emulator next; not yet on a unit]

The owner: "start v2 per-step slides while I test". `scripts/ts02_build.py`, `out/TS02/TS02.syx`, fourteen sites.

**What changes.** SLIDE is p-lockable (row 0x155's flags_set 8 -> 0: its borrowed display entry, Env. Reset's,
has flags 4, lockable; TS01's had 0xc). A lock on a trig decides the slide into that trig; a trig without one
follows its sound's SLIDE (the target set's k 100). The scheduler's trigs are published when the sound's SLIDE is on
or the pattern has a SLIDE lane for the track (`pattern + 0x17e50 + 0x50a0 + 0x65 t + 100` not -1).

**The pattern's locks [verified in the code].** The live lock table (`pattern + 0x17e50`): 80 lanes of 0x102 bytes
(k, track, then 128 values, -1 unlocked), the lane index per track and k at `+0x50a0` (0x65 a track, -1 none), per
step counts at `+0x56f0`. The lock collector `0x400d874c` walks k 0..100, so a k 100 lock works in memory as it is.
Stored, a lane carries a stored id: the serializer `0x400de87c` takes `map[k]` (`0x401fd330`, a word each; FX track
`0x401fd160`), and the map ends at k 99: for k 100 it reads `0x401fd4c0`, the reverse map's first word, 0, so a SLIDE
lock saved without our fix would load as a lock on k 0. The loader `0x400de682` keeps lanes with stored id < 0x6b
(`moveq #0x6a,d4` at `0x400de6f8`) on tracks 0..15 and turns ids back into k with `0x400dce24`, called through a5
(`lea (-0x18cc,pc),a5` after `clr.l d2`, `0x400de6ec`). TS02: `ts_lmap` gives the serializer a copy of the map with
k 100 -> 107 (filled from the stock map on the unit, the first time), `ts_lpre` points a5 at `ts_lconv` (107 -> 100
on tracks 0..15, the rest through `0x400dce24`), and the id test becomes `< 0x6c`. A stock OS drops the 107 lane.

**DDR reads in hot paths (2026-10-31; corrected the same evening):** this note first said the data cache was off;
it is on for `0x40000000-0x47ffffff` (copyback; the main OS's CACR and ACR0 at `0x40000554`, notes/USB01), so our
.bss is cached. 0.2 also reads DDR less in its hot paths all the same: the look-ahead reads each step's trig flags (`pattern +
0x6a5 t + 2 step`, bit 0 set and bit 2 clear: the builder's own test) and builds only real trigs (every step when
the track remaps its steps, `+0x5a4`, or uses its other mode, `+0x498 == 1`); `ts_build` reads only the words that
slide (no target table in DDR); `ts_write` computes each value once for all the rows; `ts_block` reads one bitmask
when nothing slides. The stock itself reads the trig flags as halfwords at odd addresses for odd tracks
(`pattern + 0x6a5 t`): this CPU takes misaligned accesses.

**Layout.** The unit's compiler aligns ints on 2 bytes: `struct ts_rec` is 422 bytes there, `ts_pub` 852,
`ts_slide` 632; `scripts/ts01_live.py` takes the sizes from the map.

**Tests so far.** `scripts/ts01/test_ts.c`, 18 scenarios (ASan, UBSan): 0.1's 14, plus SLIDE off with a step locking
it on (the slide into that step only), SLIDE on with a step locking it off, a track remapping its steps (every step
built), and the lock storage helpers (the map copy filled once, 107 <-> 100). `scripts/ts02_build.py`: every check,
the stock part differs from CFTE's only in trig-slide's fourteen sites.
