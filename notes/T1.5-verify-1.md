# T1.5 verification 1: is the STARTUP menu always reachable? (independent refute pass)

Date: 2026-10-05 (run 2, verifier). Marks: **[verified]** = I checked it against the bytes
or a run I did here; **[inferred]** = reasoned from structure; **[open]** = not resolved.
All bootstrap addresses are section 2, running at `0x80000400` (file offset 0 = `0x800003FC`).

## Verdict

**Holds, with corrections.** The central claim is confirmed against the bytes and by my own
runs: **no main-OS/DSP content of the stored container at `0x80000` can stop the FUNC-held
STARTUP menu from coming up.** The menu, the FUNC decision, the key parser, the panel drivers,
the font, the OS-UPGRADE receive and the verify-and-commit all live in the bootstrap
(`0x40000`-`0x80000`); entering, drawing and idling the menu read nothing from the container
(only a 32-byte header probe and two 16-byte table entries are read on the whole pre-menu path).
I reproduced all 15 boots byte-for-byte and the OS-UPGRADE probe.

Two dependencies are real and the report states them: the front panel must work (a silent panel
means FUNC is never seen), and section 2 plus its table entry must stay stock (a genuinely
higher-versioned, resealed bootstrap is the one flash object that re-flashes `0x40000` and spins).

Corrections: (1) the menu font is **not** built by `FUN_80001a04` over rodata `0x800063a0` as the
report says - that routine builds a different 160-byte table and runs *after* the menu; the menu
draws glyphs from the static font at `0x80005ef8`. (2) "d2 (the reset selector) is 0 on a cold
boot" is **[inferred]**, not [verified] - the harness forces d2=0 and the code that sets it lives
below `0x40000`, outside our image. Neither correction changes the conclusion. One adversarial
case (a crafted section-2 content that makes the depacker run away before the menu) is untested
but is forbidden by the brick rules and writes only to DDR.

## Confirmed claims (checked here)

1. **Same bytes, same disassembly.** `01_type2.unpacked.bin` sha256
   `038aa5d188af120f...` (30302 B), extracted from the pinned stock `.syx`
   (`7e5b8a73...`). My independent objdump matches `out/T1.5/boot.dis` exactly. [verified]

2. **The decision tree matches the bytes.** Reset `0x80000de8` -> `jsr 0x800009c6` (init) at
   `0x80000ee0` -> on return, `moveq #64,d0; and.l 0x80008404,d0` at `0x80000ee4` tests boot-flag
   bit 6 -> bit 6 set `jsr 0x8000f100` (section 4), else `jsr 0x80000596` (normal loader). [verified]

3. **Menu gate (`0x80000c26`-`0x80000c66`).** `tstl d2` / FUNC test / enter:
   - `0x80000af8 sne d2; 0x80000b02 mvsb d2,d2` => inside init, **d2 = -1 iff the self-upgrade
     returned non-zero, else 0** (this is a different d2 from the reset selector).
   - `0x80000c4a pea 0x11; jsr 0x80001302` tests the FUNC bit; `0x80000c56 tst d0; bne` enters if
     FUNC held; `0x80000c5a tst d2; beq 0x80000c68` otherwise skips the menu unless d2 != 0.
   - `0x80000c5e movel d2,-(sp); 0x80000c60 jsr 0x80002dc4` enters the menu with arg d2
     (0 = full menu, non-zero = reduced recovery menu). [verified against the bytes]

4. **FUNC keyid 0x11 maps to bitmap[2] bit 0.** `FUN_80001302` indexes the table at `0x80006dc0`
   by keyid*4; I read `0x80006dc0 + 0x11*4` = bit index `0x10` => byte `0x10>>3 = 2`, bit `0`.
   The harness uses byte 2, bit 0 - correct. The 5-key `{0x12,0x13,0x14,0x15,0x23}` and 3-key
   `{0x0b,0x0e,0x26}` tables also resolve to the bits the report lists. [verified]

5. **Self-upgrade `FUN_80001c48` version gate.** At `0x80001c66`: `mvzw %fp@(-4),d3` (incoming
   version, 16-bit) and `0x80001c6a mvzw 0x80000408,d0` (running version, 16-bit) then
   `cmpl d3,d0; bcc 0x800021dc` -> returns 0 when running >= incoming. The running word at
   `0x80000408` reads `0x0201`. So stock (table version `0x0201`) no-ops; it proceeds only when
   the table version > `0x0201`. The lookup `FUN_80005462(2,...)` returns 0 when there is no ELE3
   header (`FUN_800053ec` checks `'ELE3'`+`'4'` at `0x80000`), so all-0xFF / truncated-before-header
   no-op immediately. When it proceeds and a check fails it returns 1/2/3, which drives d2 and
   force-opens the recovery menu. The erase/program (`0x80002896`/`0x8000282a`) are reached only
   after CRC (`FUN_80001bd0`, residue `-0x2144df1d` = `0xDEBB20E3`), the unpacked-version equality
   (`DAT_4041000c == local_8`) and the length check (`uVar2 < 0xf001`) all pass. [verified bytes]

6. **Boot-flag bit 6 has exactly one setter.** All seven writers of `0x80008404` in the
   bootstrap: `0x80000b04` (seed = DRAM flag << 17), `0x80000b1a` (strap, bit 18), `0x80000b3c`
   (bit 5, RSR+`0xB0B0DADA`), **`0x80000b9a` (`moveq #96,d0; or` = bits 5+6, the panel-timeout
   path)**, `0x80000c42` (bit 5, 5-key), `0x80000da8` (bit 8, 3-key), and `0x80002fb0`/`0x80002fbe`
   (bits 0/1, the menu's EMPTY RESET / FACTORY RESET selections). Only `0x80000b9a` sets bit 6.
   So the section-4 path is taken only on a panel key-read timeout, as claimed. [verified]

7. **The menu and the receive path read no container.** Call-graph reachability over
   `out/decomp/bootstrap/calls.tsv` from the menu `FUN_80002dc4` to the flash routines
   {`0x8000f010`,`0x80007910` reads; `0x80002896`,`0x8000282a` erase/program}: the only paths are
   `menu > 0x80003e5a(OS UPGRADE) > 0x80003c9c(commit) > erase/program` and
   `menu > 0x80002ae6(TEST MODE) > 0x80004942 > 0x8000470c(serial) > SPI read`. **Blocking TEST
   MODE and OS UPGRADE, no flash routine is reachable from the menu at all.** So entering, drawing
   and idling the menu touch no flash. [verified static]
   Confirmed dynamically: on every FUNC boot the only pre-menu container reads are the 32-byte
   ELE3 header probe at `0x80000` and (when a header exists) two 16-byte section-table reads at
   `0x80020`/`0x80030`. No section-3 bulk read on any menu path. [verified, my runs]

8. **OS UPGRADE receive reads nothing from the container.** I drove the receive path directly
   (`run(..., osupgrade=True)`), stock and all-0xFF: it reaches `READY TO RECEIVE` and the
   MIDI-wait spin `0x80003ede` with **zero flash reads after entering OS UPGRADE**. The commit
   `FUN_80003c9c` erases from `0x80000` only after the *received* file's checksum+HMAC pass; it
   never reads the stored container. [verified, my run]

9. **15-boot matrix reproduced byte-identical.** I re-ran `recovery_harness.py` from the stock
   bootstrap. My `out/T1.5-verify/matrix.json` diffs clean against the report's `out/T1.5/matrix.json`.
   Every FUNC case stops at `menu_keypoll` (`0x800013ac`) with a drawn screen (1486 lit pixels;
   1129 for the reduced hostile-sec2 menu); every no-key case stops at the loader `0x80000596`;
   every silent case stops at `run_sec4` `0x8000f100` with `boot_flags=0x40060`; hostile-sec2
   force-opens the menu even with no key and with the panel silent. **No run reached
   `flash_erase`/`flash_program`** - neither landmark appears in any of the 15 cases. The rendered
   `stock_func.txt` is byte-identical to the report's and shows the five-item STARTUP MENU. [verified]

10. **DRAM gate is hardware, not flash.** `0x80000d72 tstl 0x800083fc; beq +; 0x80000d7a halt`.
    `0x800083FC` is set by DDR training `FUN_800006ac`, not by any container read. It also sits
    *after* the menu returns (`0x80000d72` > menu call `0x80000c60`), so it cannot stop the menu
    from appearing - only halt after an EXIT on a board with bad DRAM. [verified bytes]

11. **`must_never_change` list is sound.** Each item traces to a real mechanism I checked:
    section 2 + its table version (claim 5), the unclamped 24-bit writer and `<= 0x200000`
    container (T1.4, not re-derived here), section 4 in-place margin (T1.2/T1.11), the panel blob
    + updater (dependency, see missed #2), the `0x3c0000`/`0x380000` records, and no new
    `0xB0B0DADA`/5-key/panel-timeout triggers. [verified for the bootstrap-side items]

## Refuted / corrected

R1. **The menu font is not built by `FUN_80001a04` over rodata `0x800063a0`.** The report's
    key finding says the menu "draws from bootstrap code + font tables (`FUN_80001a04` over rodata
    `0x800063a0`)". But `FUN_80001a04` (`0x80001a04`-`0x80001a6b`) copies a 160-byte (`0xa0`) table
    from `0x800063a0` into SRAM at `0x800086d4`/`0x800088d4`, and it is called from init at
    **`0x80000d66`, after the menu returns** (menu call is `0x80000c60`). The menu's glyphs are
    drawn by `FUN_800019ce`/`FUN_80001b94`, which take the font pointer as their first argument -
    `&DAT_80005ef8` in every menu and self-upgrade call. So the menu font is the static table at
    `0x80005ef8` (bootstrap rodata), not anything `FUN_80001a04` builds. **The conclusion is
    unaffected** - the font is still static bootstrap data, read with no container access, and the
    identical 1486-pixel render proves the text drew. Only the cited mechanism is wrong. [verified]

R2. **"d2 (the reset selector) is 0 on a cold boot" is [inferred], not [verified].** The report
    marks this [verified]. In the reset path, `0x80000df2 movel %sp@(12),d2` loads d2 from
    `[initial_SP + 4]`; whatever sets the initial SP and that word runs *before* `0x80000de8` and
    lives below `0x40000`, which is **not in our extracted image**. The harness simply writes d2=0
    before `emu_start`, so the run assumes the thing the finding claims to prove. The assumption is
    sound (d2 in 1..5 go to `halt`/`tpf` debug stubs that need JTAG, and d2 is set from RAM, not
    from the container), but it is not checked against silicon or against the pre-bootstrap code.
    This is **not a refutation of the menu claim**: the container at `0x80000` cannot set d2, so no
    flash content reaches this path. Mark it [inferred]. [verified that the harness forces it]

## Missed / gaps (as an independent refuter)

M1. **Adversarial self-upgrade depacker runaway - the one untested flash-content case that could
    stop the menu.** The self-upgrade runs *before* the menu and, when the section-2 table version
    is > `0x0201`, reads section-2 content to `0x40400000` and depacks it with `FUN_80000432` to
    `0x40410000` **before** any CRC/version check. The hostile-sec2 case only bumps the version and
    leaves section-2 content stock, so the depacker terminates (I confirmed the 16176-byte read to
    `0x40400000` and a clean VERSION-CHECK failure). A container that bumps the version **and**
    supplies crafted section-2 content with a plausible length (`< 0x10001`) but no `0x2ff`
    end-marker would make `FUN_80000432` consume input indefinitely into DDR and never return -
    hanging before the menu is ever entered. This is a genuine "flash content stops the FUNC menu"
    path the report does not test or mention. Mitigations: it requires deliberately crafting
    section 2 (forbidden by brick rule #1 - section 2 byte-identical to stock), it writes only to
    DDR `0x40410000` (never the bootstrap, never a reflash), and no accidental corruption of the
    main-OS/DSP sections can reach it (those are section 3/7/8, not section 2's content). Still,
    the headline "no flash content can stop the menu" should be read as "no main-OS/DSP container
    content, and no section-2 content that passes the brick rules". Worth a dynamic test
    (bump version + random section-2 body) or a depack-iteration bound. [open]

M2. **FUNC recovery depends on a working front panel, and the panel firmware lives in the
    container.** On a silent panel the key read `FUN_80001276` times out, no FUNC bit is set, and
    the boot takes the section-4 path, not the menu (my silent runs confirm this). So the menu is
    reachable *given the panel reports FUNC* - a condition outside the flash-content question but
    central to real recovery. The panel MCU firmware blob is at `0x402F7D40` inside the main OS
    (section 3) and the main-OS updater `FUN_400dbbd8` reflashes the panel on a normal boot. On the
    pure recovery path the main OS never runs, so a corrupt blob in a freshly-flashed container is
    never pushed and the panel keeps its working firmware - which is why recovery survives a broken
    main OS. But a main OS that boots far enough to run `FUN_400dbbd8` with a corrupt blob could
    brick the panel, after which FUNC recovery fails. The report scopes this correctly with
    must-never-change #4; I note it because it is the real-world limit on the "always reachable"
    claim. [verified the silent-panel behaviour; the panel-updater risk is cross-ref T1.4]

M3. **Acknowledged, not re-litigated:** the actual reflash erase/program of `0x40000` was never
    observed (DSPI spins under emulation); the end-to-end OS-UPGRADE commit on ~1.8 MB of received
    SysEx was not re-run (covered by T1.2 `bootcheck`); hardware bring-up (clock/DDR/INTC) and the
    panel wire protocol are stubbed. These are stated in the report's open problems and I agree
    they are low-value for this question. [agreed]
