# T2.1: the MIDI machine's "4 voices" on Digitone II OS 1.12

Task T2.1 (ROADMAP). Static analysis only, of `ele3_out/02_type3.unpacked.bin` (main OS, file offset 0 =
`0x40000400`), using the dump in `out/decomp/` (decompiled C, disassembly, xrefs) and `m68k-elf-objdump -m m68k:cfv4e`
for spot checks. No device, no emulator run.

Tags: **[verified]** = read in the disassembly or the raw bytes (or, where marked "(C)", read in the decompiled C of
that function, which was not cross-checked instruction by instruction). **[inferred]** = reasoned from structure.

## Answer in short

The hypothesis is right about where the 4 is, and wrong about how deep it goes.

* **The MIDI output engine has no voice limit.** There is no voice allocator for MIDI tracks. A trig's notes are a
  linked list (chain) in the pattern's note pool, and the MIDI task sends a note-on for **every** note in that chain,
  with no counter [verified]. Synth voices are a separate system that MIDI tracks never touch [verified].
* **The pattern format has no 4-note slot.** Notes are stored as a flat pool of 8192 six-byte entries per pattern.
  Each entry carries its own track and step, so a step can have any number of notes [verified]. Stock UI paths
  already put up to **16** notes on a step (NOTE EDIT, live and grid recording), on MIDI tracks too [verified].
* **The 4 is in the UI, in three places:**
  1. The MIDI TRIG page has exactly four note rows: NOTE, NOT2, NOT3, NOT4 (descriptor rows `0x1c`–`0x1f`). On a
     trig, these rows are the first four notes of the chain. Editing NOT2, NOT3 or NOT4 forces the chain to
     **exactly four notes**: it pads a shorter chain and **cuts a longer one** (`FUN_40055606`) [verified].
  2. The track-level default chord is four bytes (NOTE + NOT2..NOT4) in the track struct. It is used for track and
     trig-key previews, with a loop bound of 4 (`FUN_40054000`) [verified].
  3. Keyboard SHAPE chords (KEYBOARD SETUP) come from a table with four offsets per shape. With BASS on, a chord
     is still at most four notes (`FUN_40034460`, `FUN_40150204`). This applies to synth and MIDI tracks
     alike [verified].
* **Allowing N > 4 (for example 8) needs code only, not a new storage format.** Stock 1.12 loads chains of any
  length and plays all their notes [verified]. The only stock hazard: if someone edits NOT2–NOT4 on such a trig, or
  clears its locks, stock cuts it back to 4. Nothing extra needs to be stored anywhere else. The one exception is a
  track-level default chord longer than four notes: the track struct has no free bytes for one (section 4).

A cheap check needs no firmware change and is worth doing first on the unit: on a MIDI track, open NOTE EDIT on a
trig, add 6–8 notes, and watch MIDI out. Static reading says all of them go out (section 5).

## 1. Code that sends MIDI notes for a MIDI-machine track

### 1.1 Which tracks are MIDI tracks
* UI side: `FUN_40031274(kit, track)` returns bit `track` of the 16-bit mask at **kit + 0x5cda** [verified (C)].
  `FUN_400313f4` is its negation (is a synth track) [verified (C)]. `FUN_4003134e` returns machine id 4 for a MIDI
  track [verified (C)].
* Audio/sequencer side: `FUN_40025b76` copies kit + 0x5cda to **`0x8000537c`** (`0x40025b96`–`0x40025b9a`)
  [verified]. `FUN_40027c36` (is MIDI) and `FUN_40027c18` (is synth) test it (`0x40027c40`) [verified].

### 1.2 The path from the sequencer to the MIDI jacks
1. **Step scheduler** `FUN_400d99de` and `FUN_400d907a`. When bit `track` of kit + 0x5cda is set they call
   `FUN_400d8cbe`, otherwise the synth builder `FUN_400d87b8` [verified (C), lines around the `0x5cda` tests].
2. **MIDI event builder** `FUN_400d8cbe(track, pattern, ..., step, ...)`. It takes an event from a 64-entry pool
   (`FUN_4012a6e8`, 0x60 bytes each, built by `FUN_4012ba7a`) and fills it in. The note fields are
   [verified, `0x400d9020`–`0x400d9040`]:
   * `+0x14` = **pattern + 0x6a50** (the runtime note pool);
   * `+0x18` = the chain head for (track, step), read from pattern + 2·(0x9528 + track·0x80 + step) (`0x400d8eda`),
     or -1 if the step has no notes;
   * if the head is -1, a single inline note at `+0x24`: note = track +0x485, velocity = +0x480,
     length = +0x481, micro-timing 0.

   It also collects every p-lock of the 101 (0x65) MIDI parameters on that step into a list
   (`FUN_400d8c56`; 64 lists, `FUN_4012a674`) [verified (C)].
3. **Audio task** `FUN_40025e36` (the per-block real-time loop). Events of type 3 (MIDI) are linked into a list,
   and once per block that list goes to the MIDI task's queue `0x445ff870` as message type 1 [verified (C)]. Synth
   events take a different branch that calls the voice allocator (section 3).
4. **MIDI task** `FUN_4012ac88`. Its RTOS task is created by `FUN_4012ba7a`
   (`FUN_400012c8(&0x46679e7c, FUN_4012ac88, 8, stack 0x44618484, 0x4000)`). For each event in the list it does the
   following [verified, disasm `0x4012b414`–`0x4012b620`]:
   * The channel comes from `FUN_4012a3b2`: the MIDI preset mirror word at `0x4461747a + track·0xca`, gated by
     enable-mask bit 0 [verified (C)].
   * The status byte is `0x90 | ch` (`moveq -0x70` at `0x4012b42a`, `or` at `0x4012b42e`).
   * **The note loop**: for each chain entry (6 bytes, `A3`):
     * note = per-track transpose (`0x4461823c + 4·track`) + entry[2], plus the global transpose when the track's
       bit is set in `0x44618234` (`0x4012b44e`–`0x4012b466`);
     * velocity = entry[3], or track +0x480 when negative (`0x4012b47a`–`0x4012b48c`);
     * length = entry[4], or track +0x481 when negative (`0x4012b46c`–`0x4012b476`);
     * a note outside 0..127 is skipped (`0x4012b490`–`0x4012b498`).
   * If the same (channel, note) is still sounding, it first sends that note with velocity 0. Then it sends the
     note-on (`0x4012b4b2`–`0x4012b506`).
   * It books the note-off: it takes a record from a 2048-entry free list (`0x446034b4`, 24 bytes each) and links
     it into a time-sorted list (`0x446034b0`). Length 0x7f (infinite) goes to a separate list (`0x446034a8`/`ac`)
     instead (`0x4012b50a`–`0x4012b5d8`).
   * It follows the chain: next = s16 at pool + 0xd000 + 2·index (`addi.l #0x6800` then `mvs.w (0,A0,D0*2)`,
     `0x4012b5f2`–`0x4012b600`), and loops back to `0x4012b442` until -1 (`0x4012b61c`).
   * **There is no counter in this loop.** The only exit is the end of the chain, or an entry whose micro-timing
     byte (entry[5]) differs from the first one's (`0x4012b442`–`0x4012b44a`). In that case the event is
     rescheduled for the later time (`LAB_4012b70a`, timer `FUN_40138cb6`/`FUN_40138e3c`). So each chord note can
     have its own micro-timing [verified].
5. **Note-off**: message type 3 (timer expiry) walks the sorted list and sends `0x9n note 0`, that is note-on with
   velocity 0. Message type 4 flushes both lists (all notes off). Message type 5 sends CC 120 (`0xBn 0x78 0`) on
   every channel in use [verified (C)].
6. **Output**: the bytes are appended to a buffer at `0x44600ca1` by `FUN_4012aaa6`, and flushed once per message by
   `FUN_4012a36c`: DIN (`FUN_40002612`, a 4 KB eDMA ring that busy-waits when full) and/or USB (`FUN_40004734`),
   selected by bits of `0x446181f0` [verified (C)]. See 4.5 for the 8-bit length counter.

Live notes (keyboard, preview, NOTE EDIT preview) for a MIDI track take a separate path. Note-on
`FUN_40121db2` and note-off `FUN_40121b0a` test `FUN_40027c36` and call `FUN_4012bb90`. That builds an event with
head = -1 and one inline note (`+0x26` note, `+0x27` velocity, `+0x28` length 0x7f or computed) and posts it straight
to the MIDI task queue [verified (C)]. One key press is one note; there is no polyphony counter on this path either.
`FUN_40123510` is a second, direct note-on sender (`0x9n` with range checks). It is called only from
`FUN_400576a4`, in one keyboard mode, and I did not trace it further [verified (C)].

**Notes per trig at playback: as many as the step's chain holds** [verified]. The bookkeeping arrays are sized for
16 channels × 128 notes (`0x466775f8`, `0x446014a8`), plus 2048 pending note-offs and 64 events in flight
[verified (C), init in `FUN_4012ba7a`].

## 2. Where the limit lives

### 2.1 Pattern note storage (no per-trig slots)
* **Runtime** `Digisharc::patternNotePool_t`, at pattern_t + 0x6a50, 0x11400 bytes [verified (C): `FUN_400350b6`,
  `FUN_40034f9c`, `FUN_400357f0`, `FUN_400de4b0`]:

  | offset | contents |
  |---|---|
  | `+0x00000` | `entries[0x2000]`, 6 bytes each: track, step, note (absolute), velocity (-1 = track default), length (-1 = default), micro-timing (signed) |
  | `+0x0c000` | `head[16][128]`, s16, -1 = no notes |
  | `+0x0d000` | `next[0x2000]`, s16, -1 = end; the chain is kept sorted by micro-timing |
  | `+0x11000` | free bitmap, 0x400 bytes, set = free; allocation is `FUN_40034f26`, -1 when the pool is full |

* **Storage** `Digisharc::patternNotePoolStorage_v0_t`: only the 0xc000-byte entry array. Track byte 0xff = unused.
  The links are rebuilt on load by `FUN_400de4b0`. It walks all 0x2000 entries and inserts each valid one into its
  chain, with no per-step count check (only `-1` checks and the `cmpi.l #0x2000` loop bound at `0x400de5d6`)
  [verified]. On save the entry array is copied as it is (`FUN_400de5f0`, 0xc000 bytes; per-step copy
  `FUN_400de61a`) [verified (C)].
* **`patternStorage_v4_t`** (`FUN_400de77a`: the version word must be 4) [verified (C)]:

  | offset | contents |
  |---|---|
  | `+0x0` | u32 version = 4 |
  | `+0x4` | 16 × trackStorage, 0x4a3 bytes each → runtime track 0x6a5 bytes (`FUN_400de0ee`) |
  | `+0x4a34` | note pool, 0xc000 bytes |
  | `+0x10a34` | parameter locks, 0x50a0 bytes → runtime pattern + 0x17e50 |
  | `+0x15ad4` | pattern settings → runtime pattern + 0x1dd40 |

* Capacity: **8192 notes per pattern, shared by all 16 tracks** [verified]. That is an average of 4 notes per step
  per track at 128 steps on all 16 tracks. When the pool is full, `FUN_400350b6` stops adding and the chain is
  quietly cut [verified (C)].
* For comparison, the Digitone mk1 import (`FUN_4001464c`, `Digitone::patternStorage_v11_t` →
  `Digisharc` v3) reads 8 bytes per step: a base note plus seven signed offsets. It writes each into the pool as an
  absolute note [verified (C)]. So mk1 stored up to 8 notes per trig, and the DN2 pool stores absolute notes.

### 2.2 The four TRIG-page note rows (MIDI tracks only)
* Parameter descriptor table at **`0x401f83a4`**, 0x141 rows of 0x3c bytes. `scripts/dn2_param_table.py params`
  dumps it [verified, bytes]:

  | row | long / short | group | id | range | default | formatter |
  |---|---|---|---|---|---|---|
  | `0x14` | Trig Note / NOTE | 0x1d | 0 | 0..127 | 60 | |
  | `0x15` | Trig Velocity / VEL | 0x1d | 1 | | | |
  | `0x16` | Trig Length / LEN | 0x1d | 2 | | | |
  | `0x1c` | Note 1 / NOTE | 0x16 | 8 | 0..127 | 60 | `0x400e3030` (plain) |
  | `0x1d` | Note 2 / NOT2 | 0x16 | 9 | 0..127 | 64 | `0x400e3254` (value − 64) |
  | `0x1e` | Note 3 / NOT3 | 0x16 | 0xa | 0..127 | 64 | `0x400e3254` |
  | `0x1f` | Note 4 / NOT4 | 0x16 | 0xb | 0..127 | 64 | `0x400e3254` |

  The formatter `0x400e3254` is `addi #-0x4000` then plain print [verified, objdump]. No other group-0x16 rows
  exist [verified].
* `TrigParameterSet::vslot27` (`0x40038d14`) accepts group-0x16 rows only on non-synth tracks, via
  `FUN_400313f4` [verified (C)]. So rows `0x1c`–`0x1f` are the MIDI TRIG page's chord notes.
* **Track level (no trig held)**: `TrigParameterSet::vslot10`/`vslot31` read and write runtime track **+0x485**
  (NOTE), **+0x486**, **+0x487**, **+0x488** (NOT2..NOT4). The getters are `FUN_4004ebbc`, `FUN_4004ec8c`,
  `FUN_4004ed10`, `FUN_4004ed94`; the setters are `FUN_4004ec38`, `FUN_4004ecbc`, `FUN_4004ed40`, `FUN_4004edc4`
  [verified (C)].
  * In storage these are trackStorage **+0x480** (NOTE) and **+0x486..+0x488** (`FUN_400de0ee`) [verified (C)].
  * Defaults: 60, 64, 64, 64 (`FUN_400e752c`) [verified (C)].
  * `FUN_4004ebec`, "get note i, i < 4", indexes the same four bytes and has no callers or references
    [verified].
* **Trig level (trig held)** [verified (C)]:
  * `TrigParameterSet::vslot16` reads notes[0..3] of the step chain: `FUN_40051880` (+0), `FUN_400518f8`
    (+4, needs ≥ 2 entries), `FUN_40051978` (+8), `FUN_400519f8` (+0xc).
  * `vslot17` writes NOTE through `FUN_40051c34` (replaces notes[0] only). It writes NOT2/3/4 through
    `FUN_400556d2`, `FUN_4005574a` and `FUN_400557c2`, which call **`FUN_40055606(track, step, k=1..3, value)`**.
* **`FUN_40055606` is the hard 4** [verified, disasm]:
  * `0x40055612 moveq 3` / `0x40055664 cmp`: if the chain has ≤ 3 notes, pad it to 4 with
    `{note -1, vel -1, len -1, utm 0}` (`FUN_4019c390`, vector insert);
  * `0x40055680 moveq 4` / `0x40055684 beq` / `0x40055686 addi #0x10`: otherwise, if it has more than 4,
    **truncate to 4**;
  * then notes[k].note = value (`0x40055698`), and write the chain back (`FUN_400350b6`).
  * Clearing a trig's locks (`FUN_4005583a`) goes through the same three setters with -1, so it also leaves
    exactly four entries [verified (C)].
* **Preview chord**: `FUN_40054000` builds the track's default note list. That is the base note (+0x485) and, on
  MIDI tracks only, base + (track[0x485+i] − 64) for i = 1..3, skipping 64 (`0x400541fa addq` /
  `0x400541fc moveq 4` / `cmp`) [verified]. Callers: `FUN_4005803c` (TrackSelectionView, track preview) and
  `FUN_40058228` (KeyboardView, trig-key preview modes) [verified (C)].
* New trigs: `FUN_400544d8` (called from `FUN_40054690` when a trig bit is set) writes **one** chain entry,
  `{note = track +0x485, vel -1, len -1, utm 0}` [verified (C)]. I did not find code that copies the track-level
  NOT2..NOT4 onto a new trig (see Open questions).

## 3. Synth tracks, and live play on MIDI tracks

* **Synth voices are a separate allocator.** `FUN_4002a6a2(track, note, ...)` is called from the audio task
  `FUN_40025e36` once per chain note of a synth event. It returns a 64-bit pair: voices to start and voices to
  steal [verified (C)].
  * There are 16 voice records, 0x14 bytes each, with fields at `0x40288305`, `0x40288308`, `0x40288310` and
    `0x40288314` + 0x14·v. `FUN_4002a414` loops over them 0x40/4 = 16 times [verified (C)].
  * The per-track allowed-voice masks are at `0x4059d96c`, the per-track unison count at `0x4059da00[track]`, and
    the per-track voice config at `0x40288444 + track·0x40c`.
  * The VOICE menu (`VoiceMenuView`; strings VOICES, REUSE, STEAL, DYN, UNISON, V.AMNT) edits
    `VoiceConfig` (`voiceConfigStorage_v0_t`) [verified, strings].
  * MIDI events never reach `FUN_4002a6a2`. The scheduler sends MIDI tracks to `FUN_400d8cbe` → type 3 → MIDI
    task [verified]. **So MIDI tracks neither use nor count against the 16 synth voices** [verified].
* **`SMVoiceStates` is not a limit.** It is a UI Observable singleton (`FUN_4018cf86`, 0x28 bytes) holding a 32-bit
  word (+0x20) and a flag (+0x24). Both are set by UI message 0x24 (`FUN_40049eb8`, from `switchD_4002f196::caseD_c`)
  and read for the VOICE menu (`FUN_40027f24`) [verified (C)]. It reports synth voice activity to the screen.
* **`NotePool`** is the `ValueWithMirror<patternNotePool_t, patternNotePoolStorage_v0_t>` wrapper around the pool
  in 2.1. Its `vslot17` is updateMirror (`NotePoolStepChangedInfo` → one-step copy `FUN_400de61a`) [verified (C)].
* **Live keyboard on a MIDI track** [verified (C) unless marked]:
  * *Chromatic*: each key is one note on the live path in 1.2. There is no per-track polyphony counter. A shared
    1024-node held-note pool (`FUN_40126f36`) handles hold and sustain.
  * *Chord, SHAPE*: `FUN_40034460` → `FUN_40150204` reads four signed offsets from the table at **`0x4020e235`**
    (shape s uses bytes `0x4020e235 + 4s .. +3`, -1 = unused). The first twelve are maj, min, 7, m7, maj7, dim,
    dim7, sus2, sus4, 6, m6, add9 [verified, bytes]. BASS adds a bass note only when the shape has ≤ 3 notes;
    otherwise it replaces one (`0x40034624 moveq 3; cmp; bge`) [verified]. **Maximum 4 notes**, synth and MIDI
    tracks alike.
  * *Chord memory*: mode 5 of `FUN_40034460` plays the stored slot, up to 16 notes (15 when learned in the
    editor) [verified (C)].
  * The note list is then sent one note at a time (`KeyboardView::vslot02` → `FUN_40057ea0` → `FUN_400576a4` →
    `FUN_40121db2`) [verified (C)].

## 4. What N > 4 (for example 8) would take

### 4.1 Storage: no change
The pool already stores any number of notes per step. A modded OS that writes 8 notes on a MIDI trig produces a
project that **stock 1.12 opens and plays with all 8 notes** [verified: loader 2.1, engine 1.2]. No extra notes
need to go anywhere else. Requirements for stock-safe entries [verified (C), `FUN_400de4b0` head index = step +
track·0x80 with no range check]:
* track must be 0..15 and step 0..127; other values would index past `head[]` on stock;
* every entry should belong to a real (track, step).

Stock behaviour to accept [verified]:
* editing NOT2/NOT3/NOT4 on such a trig cuts it to 4 notes;
* clearing its locks cuts it to 4 notes;
* NOTE edits move only note 1 (absolute), and relative NOTE edits move all of them (`FUN_40051d04`).

### 4.2 Minimal code changes [inferred unless marked]
1. **Stop the truncation** in `FUN_40055606`: change `0x40055684 beq.b` (`67 0a`) to `bra.b` (`60 0a`). Chains
   longer than 4 then survive NOT2–NOT4 edits and lock clears; shorter ones are still padded to 4. This is a
   one-byte patch [instruction verified; effect inferred].
2. **A way to enter notes 5..8.** Options, cheapest first:
   * Use **NOTE EDIT**, which already allows 16 notes per step on any track, if the test in section 5 confirms it
     opens on MIDI tracks and those notes reach MIDI out. If so, the stock firmware already has a >4-note MIDI
     machine; only the TRIG page shows 4.
   * Use **chord memory** + KEYBOARD chord mode + recording: up to 15–16 notes per trig, recorded through
     `FUN_40045188`/`FUN_4002c902` (cap 16).
   * Add **NOT5–NOT8 rows**. That needs new descriptor rows: the table at `0x401f83a4` is a fixed 0x141 rows in
     flash, so it would have to move or reuse unused rows. It also needs new cases in `TrigParameterSet::vslot10/
     16/17/18/19/27/31` (switches on row ids `0x1c`–`0x1f`), page-layout entries (not located), and a generalised
     `FUN_40055606`. This is the largest option.
3. **Keyboard SHAPE chords beyond 4** (only if wanted): a new shape table, widen the four-int array in
   `FUN_40034460`/`FUN_40150204`, and lift the BASS cap at `0x40034624`.
4. **MIDI output burst size** (needed for big chords on many tracks): see 4.5.

### 4.3 Track-level default chord beyond 4
trackStorage has **no spare bytes**. `FUN_400de0ee` reads every byte from +0x480 to +0x4a2, and 0x000–0x47f is
128 step words plus seven 128-byte per-step arrays [verified (C)]. A default 8-note chord therefore cannot sit in the
track without a new format. Stock-compatible alternatives [inferred]:
* keep defaults at 4 and store longer chords only per trig (they already round-trip through stock);
* point a track at a **chord memory slot** (16 notes) for its default chord, with the pointer kept in a mod-owned
  side file on +Drive (stock ignores it);
* do not "park" notes on hidden steps of the pool: they would play if the pattern got longer, and a bad
  track/step byte corrupts stock's link tables.

### 4.4 Pool capacity
8192 notes per pattern. 16 tracks × 64 steps × 8 notes = 8192 fills it. Dense 8-note patterns at 128 steps on
many tracks will hit `FUN_40034f26` returning -1, and chains will be cut quietly [verified (C)]. The mod's UI
should report it.

### 4.5 MIDI output buffer length is 8-bit
`FUN_4012aaa6` keeps the note-output length in a **byte** at `0x44600ca0`: `mvz.b` at `0x4012aaa6`, `move.b` at
`0x4012aac2`. The buffer at `0x44600ca1` runs 1024 bytes up to the CC buffer at `0x446010a1` [verified]. The counter
is cleared once per MIDI-task message, and the buffer is flushed once at the end (`FUN_4012a36c`) [verified (C)].

More than 255 bytes of note messages in one message makes the counter wrap, so bytes are overwritten and lost
[inferred]. Example: about 11 MIDI tracks × 8-note chords firing in the same audio block (3 bytes per note-on, 6
with a retrigger note-off). Stock can already reach this with 16-note steps; 8-note chords make it likelier.

Fix options for the mod [inferred]: widen the counter to 16-bit (append and flush code, plus the clear at the
top of the `FUN_4012ac88` loop), or flush from `FUN_4012aaa6` when the counter would pass about 0xf0. DIN itself
does not drop: `FUN_40002612` busy-waits on its 4 KB ring [verified (C)]. DIN bandwidth stays the physical limit:
3125 bytes/s, so one 8-note chord is about 7.7 ms.

## 5. Tests that need no firmware change (for the unit or a later emulator)
All of these use stock 1.12 and a MIDI monitor on DIN or USB.
1. On a MIDI track, REC + NOTE EDIT on a trig, add 6–8 notes, play. Expect all notes on MIDI out (1.2). If NOTE EDIT
   refuses MIDI tracks, the gate is in `MainScreenView::vslot02` near the `FUN_4001ce42` call.
2. On the same trig, hold it and turn NOT2. Expect the chord to drop to 4 notes (`FUN_40055606`).
3. KEYBOARD SETUP with SHAPE = a 7th chord and BASS on, on a MIDI track. Expect 4 notes per key.
4. Chord memory slot with 8 notes, keyboard in chord-memory mode, on a MIDI track. Expect 8 notes per key.
5. Set the track-level NOT2 to +4 (no trig held), place a new trig, play. Expect: a single note (2.2, new trigs) or a
   chord. This settles the open question below.

## Open questions
* **Track-level NOT2–NOT4 on new trigs.** `FUN_400544d8` writes only NOTE. I found no other reader of +0x486..+0x488
  besides `TrigParameterSet::vslot10` and the preview `FUN_40054000`. Either stock does not apply the default chord
  to new trigs, or it applies it through a virtual call I did not trace. Test 5 decides.
* **Absolute or offset per-trig NOT2–NOT4.** The engine and every writer I read treat pool notes as absolute (mk1
  import, `FUN_40051d04`, NOTE EDIT). The NOT2–NOT4 formatter prints value − 64, and `TrigParameterSet::vslot16`
  returns the raw pool byte. The conversion between them (if any) is in page-view code I did not find.
* **Which page lists rows `0x1c`–`0x1f`.** The tables at `0x401d3a80`–`0x401d3f00` list rows in order but look like
  save or CC orders, not page layouts.
* `FUN_4012a814` (CC, PB, AT output for MIDI params ≥ 0x19) and `FUN_4012abc6` (bank and program change) were not
  read in detail; they do not carry notes.
