## Answer in short

- **The arp is part of the voice interrupt, and its only output is the internal voice allocator.**
  It is fed by internal-voice note events. It clocks itself with its own type-9 events, every 90,000
  time units (1/60 step). It plays a note by copying a template event back into the interrupt's own
  queue, and that note goes to `FUN_4002a6a2`, the voice allocator. No code on this path makes a MIDI
  event. [verified]
- **Two kinds of barrier keep it away from MIDI tracks:**
  - *UI:* three call sites of `FUN_40031274` (isMidiTrack). Two of them matter (ARP key, ARP menu
    auto-close); the third is the LED.
  - *Engine structure:* the sequencer sends MIDI-track trigs down a separate MIDI-event path, and skips
    the arp step-sync event for them. Live keys on a MIDI track bypass the interrupt entirely.
  No code inside the arp tests "MIDI track". [verified]
- **None of the seven named direct mask readers is an arp gate.** Six are kit storage, notification,
  sound-snapshot or MIDI-task mirror code. `FUN_400b8b00` is a false hit: its `0x5cda` is the code
  address `0x400b5cda`. [verified]
- **MIDI notes leave through the same interrupt:** a type-3 voice event wraps a MIDI event; the
  interrupt appends it to a list; once per interrupt pass the list goes to the MIDI task. The MIDI task
  sends the note-on and books the note-off itself. [verified]
- **Design (section 4).** All workable options keep the stock arp in the interrupt. They add one
  "sink" that turns a note on a MIDI track into a MIDI event, appended to the list the interrupt
  already forwards. Arp notes then reach MIDI out by exactly the path, and with exactly the timing, of
  stock MIDI-track trigs. Options, smallest first:
  1. live keys only;
  2. sequenced trigs too (v1's design, corrected);
  3. sequenced trigs that also keep their MIDI p-locks.

  Where the new code lives is open, pending the free-memory measurement.

Time units [verified constants; tempo reading inferred]:
- The clock `0x80005398` advances by 2 × `[0x402a132c]` per interrupt pass (`0x40027b04`).
- `[0x402a132c]` is set by `FUN_4013735c`, called from `FUN_4002578e`, which clamps it to 3,600..36,000.
  That fits BPM × 120 over the 30–300 BPM range [inferred]. At 120 BPM the value is 14,400.
- The sequencer time `0x42c4f900` advances 900,000 per handler call (`0x400d9a12`–`0x400d9a1e`).
- One step is 6 × 900,000 = 5,400,000 units. The trig length table `0x401d8ce8` is in half units:
  LEN 1.000 = entry 14 = 2,700,000 [verified].
- Passes per step = 5,400,000 / (240 × BPM) = 22,500 / BPM. If a step is a 16th note, one pass is
  ≈ 0.667 ms at any tempo [inferred].

Events [verified]:
- Each event is 0x6c bytes:
  - allocated by `FUN_40138cb6`;
  - scheduled by `FUN_40138e3c(ev, time)`;
  - copied by `FUN_40138d20(dst, src)`;
  - word `[n]` is at byte offset `4·n`.
- `FUN_40138b80` (called at `0x40026110`) returns the first time bucket. The interrupt processes every
  bucket whose time is before the pass end `fp−48` = clock + 2·`[0x402a132c]` (`0x40025ee8`–`0x40025f06`,
  `0x40026efa`–`0x40026f02`).
- Inside a bucket, events are chained through `+0x68`.

### 1.3 Note in (the note-on branch of the interrupt, from `0x400266b8`)

1. **Arp-generated event** (`flags & 0xc0000 == 0x80000`, flags = `ev+0x38`): note =
   `FUN_4002a0bc(t, ev[0x18])` (held note + per-step offset + 12 × octave), written to `ev+0x26`. A
   negative result means no note this tick (`0x400266c6`–`0x400266f6`). [verified]
2. **Retrigger copy** (`flags & 0x40000`): played as is (`0x400266fa`–`0x40026704`). [verified]
3. **Any other note:**
   - sound = `ev[0x10]`, or `ev[0xf]`, or `[0x800052a0]+0x34+t·0x48b` (`0x40026708`–`0x40026722`);
   - then `FUN_40029cd4(t, noteRec, pool, idx, defaultLen, bucketTime, ev[5], sound, &arpOn, &restart)` at
     `0x40026762` [verified]. `ev[5]` is the source: 1 = sequencer, 2 = live.
   - Mode 0: `arpOn = 0`, and the note plays normally. [verified (C)]
   - Otherwise:
     - each chain note is added to the held set. A sequenced note with a finite length also gets an
       expiry at `time + 2·0x401d8ce8[len]`.
     - If the set was empty, a new generation number is returned; otherwise 0, and the note itself is
       swallowed.
     - A higher-ranked source restarts the arp (live over sequencer); a lower-ranked one is ignored
       while the arp runs. [verified (C)]
   - `restart` releases the track's voices through `FUN_4002b1b6` (`0x4002677e`–`0x400267d4`).
     [verified]
4. **New generation** (`0x400267e4`–`0x400268d2`) [verified]:
   - The event becomes the template: `ev+0x29` = micro-timing, `ev[0x18]` = generation, flags
     `|= 0x80000`, `ev+0x27` = velocity, `ev[8] = −1` (inline note). It is copied to
     `0x4058f958+t·0x6c` (`0x4002681e`).
   - Counter = `0xb40` (`0x40026806`, `0x40026832`); the sound is stored at `0x4058f8d8[t]`.
   - **If the sequencer is playing and the source is live** (`FUN_4002a3f2() != 0` and `ev[5] > 1`,
     `0x40026840`–`0x40026864`): set resync pending, swallow the note, and wait for the sequencer's
     next step sync.
   - **Otherwise:** play the first arp note at once, and schedule the first self tick (type 9,
     `[5] = 0`, `[6]` = generation) at `now+90000` (`0x400268b4`–`0x400268c0`) or `bucket+90000`
     (`0x400268c4`–`0x400268ce`).

### 1.4 The arp's own clock: type-9 events

All three creators of type-9 events in the image, from a scan for `jsr 0x40138cb6` followed by
`moveq #9`: `0x400263b2` (self tick), `0x4002688a` (first tick), `0x400da048` (sequencer step sync).
[verified, `t22_v2_checks.py`]

The handler is at `0x40026352`:
- **Self tick** (`[5] = 0`) [verified]:
  - It needs a non-empty held set (`FUN_4002a3a6`, `0x40026380`) and the current generation
    (`0x40026392`–`0x400263ae`).
  - It schedules the next tick at bucket time + 90,000 (`0x400263f2`).
  - It decrements `0x4058f918[t]` and fires when bit *speed* (`sound+0x160`) of the word
    `0x401d5fe4[counter]` is set (`0x40026422`–`0x4002645a`). The counter wraps to `0xb40` at 0.
- **Sequencer step sync** (`[5] = 1`): it acts only when a resync is pending (`FUN_4002a3bc`,
  `0x4002636c`). It then starts the tick chain, sets the counter to `0xb40` (`0x40026418`), and fires
  one note at once. [verified]
- **Firing** (`0x4002645e`–`0x400264a0`): copy the template into a new event (`FUN_40138d20`,
  `0x40026484`), and link it after the current event in the same bucket, with SR = `0x2700`
  (`0x4002648a`–`0x4002649e`). It is processed in the same pass, as case 1 of 1.3. [verified]

Rates [verified, table scan in `t22_v2_checks.py`]:
- A tick is 90,000 units = 1/60 step. `0xb40` = 2,880 ticks = 48 steps, the common cycle of all speeds.
- The 23 speeds fire every 960, 720, 480, 360, 320, 240, 192, 180, 160, 120, 96, 90, 80, 60, 48, 45,
  40, 30, 24, 20, 15, 12 and 10 ticks: 16 steps down to 1/6 step.
- The default speed `0xd` = 60 ticks = 1 step. `FUN_400e7e38` writes it at `0x400e7e42`–`0x400e7e44`,
  to `base+0x82`; with base = `sound+0xde` that is `+0x160`. The default note length `0xe` goes to
  `+0x162`. [verified bytes; base inferred from the offsets]
- At 120 BPM a tick is ≈ 3.1 interrupt passes, so each tick is handled in the pass that contains its
  time [inferred].

**The sequencer step sync** (`FUN_400d99de`, `0x400da048`–`0x400da07a`):
- For a track not in the MIDI mask, at each step boundary it handles, it schedules a type-9 event with
  `[5] = 1` and `[4] = t` at `0x42c4f900 + (d4−1)·900000`. `d4` comes from the per-track scale table
  `0x401f6f18` (`0x400d9fec`).
- This happens before the trig builder runs, so it happens on empty steps too.
- The MIDI branch (`bne.s 0x400da09e` at `0x400da046`) jumps over it. [verified]
- So the sync matters only for an arp started by a live key while the sequencer plays: that arp waits
  for it. [verified flow]

### 1.5 Where the arp's notes go: the internal voice allocator

From `0x400268de` the note path is:
- retrigger setup `FUN_400db688`;
- transposition: `0x80005381[t]`, plus the global `0x80005380` when the track's bit of `0x8000537e`
  is set;
- a 0..127 range check (`0x40026980`–`0x400269aa`);
- for each chain note with the same micro-timing, **`FUN_4002a6a2(t, note, …)` at `0x400269e6`**, which
  returns voices to start (`d1`) and voices to steal (`d0`). [verified]

Its 9 stack arguments, as pushed at `0x400269b4`–`0x400269e4` [verified]:

| arg | value |
|---|---|
| `4(sp)` | track `d3` |
| `8(sp)` | the raw note from `noteRec+2` |
| `12(sp)` | `ev[1]` |
| `16(sp)` | `0xf` |
| `20(sp)` | `&fp−72` |
| `24(sp)` | `ev[5]` |
| `28(sp)` | `ev[0x17]` |
| `32(sp)` | `flags & 0x80000` |
| `36(sp)` | sound |

The transposed pitch stays in `d2` for the voice; `a2` is the note record.

For each started voice `v` [verified]:
- pitch goes to `0x8000dda0[v]`, velocity to `0x8000dd40[v]`;
- the gate length goes to `0x80003af0 + (0x5cc+v)·4`:
  - for arp notes (flag bit 19, `0x40026a5a`) it is `0x40288048[sound+0x162]`;
  - otherwise it is `0x401d8ce8[noteRec+4]` (`0x40026a7c`).
- **The gate length is the note-off:** this path schedules no off event for arp notes [verified: no
  event is created between `0x400268de` and `0x40026c46`].

Live key releases arrive as note-off events (`[1] = 0`, `0x40026cd6`…): `FUN_40029fa6` removes the note
from the held set (`0x40026d3c`), and a second allocator call at `0x40026d86` releases voices.
[verified]

**No MIDI output in this path:**
- The interrupt allocates MIDI events in only two places: the type-2 config path (`0x40026232`) and
  the type-5 path (`0x40026312`).
- Type 3 only forwards a MIDI event built elsewhere.
- A note that reaches the allocator never becomes MIDI. [verified, scan of `out/T2.2-v2/isr.s`]

### 2.4 The engine path: why a MIDI-track trig never reaches the arp

1. **Sequencer step handler** `FUN_400d99de`, `0x400da036`–`0x400da046`: `movea.l 0x42c5b9ac,a0;
   clr.l 96(sp); mvs.w (0x5cda,a0),d0; btst d2,d0; bne.s 0x400da09e`. A MIDI track jumps to
   `FUN_400d8cbe` (`0x400da0b4`). That skips the type-9 step sync (`0x400da048`) and the voice builder
   `FUN_400d87b8` (`0x400da098`). [verified]
   - Live registers here: `d2` track, `d4` step ticks, `d5` pattern (`0x42c5b9a0`/`0x42c5b9a8`),
     `d6` kit for this trig's sound (`0x42c5b9ac`, or `0x42c5b9b4` at `0x400da004`), `d7` pointer to
     the step byte.
   - `d0`, `d1`, `a0`, `a1` are dead at both targets. [verified, listing `0x400d9f80`–`0x400da1c0`]
2. **Pending-step builder** `FUN_400d907a`, `0x400d91bc`–`0x400d91c8`: the same test and branch, and no
   step sync at all. [verified]
   - Callers [verified]: the transport (`FUN_400d929c`, from `TransportView::vslot02`), pattern/kit
     set (`FUN_400d93b0`), p-lock change observers (`FUN_4003d7e4`, typeinfo
     `PatternParamLocksParamChangedInfo`), `MainScreenView::vslot02` and `PatternGridView::vslot02`.
   - It fills per-track static events (`0x446494c4+t·0x6c`, MIDI `0x4464b5a4+t·0x60`) for the current
     step [verified (C)]. Probably the step that is pending when playback starts or the pattern
     changes [inferred].
   - At this site `a0` (kit) and `d0` (step) are live after the branch: both are pushed at
     `0x400d91de`/`0x400d91e0` and `0x400d9226`/`0x400d9228`. [verified]
3. **Voice interrupt:** a type-3 event (wrapped MIDI event) is appended to the MIDI list, and control
   jumps to the end of the loop, `0x40026e50` (`0x40026294`–`0x400262ee`). It never reaches
   `FUN_40029cd4` (`0x40026762`). The interrupt reads no MIDI mask: its copy `0x8000537c` is read only
   by `FUN_40027c18`/`FUN_40027c36`. [verified]
4. **Live keys:**
   - Note-on `FUN_40121db2` (`0x40121f2a`, `0x40121f3c`) and note-off `FUN_40121b0a` (`0x40121bcc`,
     `0x40121be6`) send a track for which `FUN_40027c18` says "not MIDI" to `FUN_4013801c`. That posts
     a voice event to the interrupt, so the arp sees it.
   - A MIDI track (`FUN_40027c36`) goes to `FUN_4012bb90` instead, which posts a MIDI event straight
     to the MIDI task. [verified]
   - `FUN_40027c18` and `FUN_40027c36` are called only from those two functions, from the preview
     chord `FUN_40054000` (`0x40054134`) and from `FUN_4003ef36`. [verified]
5. **Output:** even a MIDI-track note that got into the arp would come out at `FUN_4002a6a2` (1.5).
   [verified]

**So the exclusion is structural.** Unlocking the UI makes the arp settings editable on a MIDI track,
but no MIDI-track note would reach the arp, and no arp note would reach MIDI out. Both directions need
code. [inferred from 1–5]

## 3. The MIDI-machine note-out path

### 3.1 Building the event: `FUN_400d8cbe`

`FUN_400d8cbe(t, pattern, kit, step, staticEv, &utmOut, &swingOut)` returns a **voice event of type 3**
that wraps a **MIDI event** [verified (C); MIDI event fields confirmed in the MIDI task's disassembly,
3.3]:

| voice event | value |
|---|---|
| `[0]` | 3 |
| `[4]` | track |
| `[5]` | 1 (sequencer) |
| `[3]` | micro-timing factor (from track `+0x48e` or pattern `+0x1dd5b`) |
| `[6]` | the MIDI event |

| MIDI event | value |
|---|---|
| `[0]` | 0 (note event; the allocator clears it) |
| `[1]` | p-lock list: `FUN_4012a674`, filled by `FUN_400d8c56` from the 101 lock slots at `pattern+0x17e50` |
| `[2]` | track |
| `[3]` | 1 = note on |
| `[4]` | trig flags: bit 7 = play the notes, `0x400` = LFO trig, from the step word, or the track defaults at `+0x482` |
| `[5]` | pool `pattern+0x6a50` |
| `[6]` | chain head, or −1 = inline note at `+0x24`: note `+0x26` = track `+0x485`, velocity `+0x27` = `+0x480`, length `+0x28` = `+0x481`, micro-timing `+0x29` = 0 |
| `[0xb]` | track data |
| `[0xd]` | 1 (sequencer) |
| `[0xf]`, `[0x10]` | track speed factor (table `0x401f6f1b`) and the same micro-timing factor; read only when a later micro-timing group is rescheduled (3.3, item 7) |

- The 64 MIDI events are 0x60 bytes each; the pool is built by `FUN_4012ba7a` [verified (C), T2.1].
- `FUN_400d99de` schedules the voice event at `0x42c4f900 + (d4−1)·900000`, plus the builder's two
  timing outputs, and stores the base time in `ev[2]` (`0x400da0c0`–`0x400da0dc`,
  `0x400da15e`–`0x400da184`) [verified]. The two outputs are the micro-timing scaled by `[3]`, and an
  offset from `FUN_400d7e34` when step flag `0x10` is set [verified (C)].
- The synth builder `FUN_400d87b8` reads the same 101 lock slots for synth parameters (`FUN_400d874c`,
  into voice event `[0x15]`). The lock table is shared; its meaning depends on the machine.
  [verified (C)]

### 3.2 Through the voice interrupt

Type 3, `0x40026294`–`0x400262ee` [verified]:
- MIDI `[0xc]` (`+0x30`) = the bucket time.
- MIDI `[0xe]` (`+0x38`) = the pass end (`fp−48`) when the bucket is flagged "now", else `ev[2]`.
- If `ev[5] = −1`, the MIDI event is freed (`0x400262e2`).
- Otherwise it is appended to the pass's list: head `fp−180`, tail register `a5`, link `+0x5c`
  (`0x400262ca`–`0x400262de`).

Inside the event loop (`0x40026110`–`0x40026f70`), `a5` has no other use: every write to it is a list
append or the reset at `0x4002611c`. [verified, scan of the listing]

At the end of the pass (`0x40026f26`–`0x40026f66`), if the list is not empty [verified]:
- a message is taken from the ring `0x4058f560` (32 × `0x14` bytes, `FUN_40025e0a`, no full check);
- it gets `[0]` = 1, `[4]` = list, `[1]` = clock, `[2]` = pass end, `[3]` = `[0x4058f554]`;
- it is posted to the MIDI task queue `0x445ff870` (`FUN_40001896`).

**Every pass also polls the pending note-offs** (`0x40026098`–`0x400260ea`): `FUN_4012a7c6` returns the
time at the head of the MIDI task's sorted off list `0x446034b0`. If that time is before the pass end, a
type-3 message (clock, pass end) is posted. [verified]

### 3.3 The MIDI task

`FUN_4012ac88` loops on `FUN_40001928(0x445ff870)`. Per message it clears the note and CC output counts
`0x44600ca0` and `0x446010a1` (`0x4012acac`, `0x4012acb2`). [verified]

**Message 1, the event list** (`0x4012acc0`…). For each MIDI event, by `[0]` [verified]:
- `[0] = 2` (`0x4012ace2`): kit/config. Copies per-track values to `0x4461823c+4t`, a global value to
  `0x44618238` and its track mask to `0x44618234`. These are added to every note, so they are read
  as transposes [inferred, as in T2.1].
- `[0] = 3` (`0x4012ad62`): per-track clock deltas and the MIDI tracks' LFO/CC refresh (`FUN_401376bc`
  for each track in `0x4461827c`) [verified flow; meaning inferred].
- Otherwise (`0x4012af14`), a note event:
  1. If `[0xd] = 1` (sequencer), the mute/solo masks `0x446181e8`/`0x446181ec` and `0x446173c0` are
     checked; a muted track's event is dropped (`0x4012af2c`–`0x4012af9a`).
  2. Note pointer: `[5] + 6·[6]`, or `+0x24` when `[6] < 0` (`0x4012af9e`–`0x4012afb4`).
  3. `[3] = 1` means note-on, otherwise the off loop at `0x4012b624` (`0x4012afc4`).
  4. The p-locks are sent first (`0x4012afcc`–`0x4012b2c0`). If the event has no lock for a parameter
     that the previous trig of this track locked, the base value is resent: the restore loop at
     `0x4012b140`–`0x4012b1ec`, entered at `0x4012b008` when the per-track word `0x446173c8+4t` is
     set. [verified flow; meaning inferred]
  5. The note gate: `[4] & 0x400` runs the LFO-trig block, then `[4] & 0x80` is required for notes
     (`0x4012b2cc`–`0x4012b2e6`). Without bit 7 the event is freed after its locks.
  6. The note loop, `0x4012b414`–`0x4012b61c`:
     - channel `d7` from `FUN_4012a3b2`; < 0 means none;
     - note = raw note + per-track transpose (+ global);
     - velocity and length fall back to `[0xb]+0x480/+0x481` when negative;
     - notes outside 0..127 are skipped;
     - if the same channel and note is sounding, `9n kk 00` goes first (`0x4012b4b2`–`0x4012b4ea`);
     - then the note-on (`0x4012b4ec`–`0x4012b506`);
     - **the note-off is booked** (`0x4012b50a`–`0x4012b5d8`): off time = `[0xc] + 2·0x401d8ce8[len]`,
       in a record from the 2,048-entry free list `0x446034b4`, linked sorted into `0x446034b0`.
       Length `0x7f` goes to the unsorted infinite list `0x446034a8`/`0x446034ac` instead.
  7. A later micro-timing group is rescheduled: a new type-3 voice event, scheduled back into the
     interrupt's queue (`0x4012b70a`–`0x4012b784`). Otherwise the event is freed (`0x4012ba6e`,
     `FUN_4012a6b2`, which also frees its lock list).

**Message 3** (`0x4012b7f6`–`0x4012b894`): sends `9n kk 00` for every booked off due before `msg[2]`.

**Message 4** (`0x4012b898`–`0x4012b9c8`): flushes both off lists (all notes off).

**Message 5** (`0x4012b9cc`–`0x4012ba20`): CC 120 on every channel in use. [verified]

**Output:**
- `FUN_4012aaa6` appends to `0x44600ca1`. The count is the **byte** at `0x44600ca0` (`mvz.b` at
  `0x4012aaa6`, `move.b` at `0x4012aac2`).
- It is flushed once per message (`0x4012ba32`–`0x4012ba48`, `FUN_4012a36c`) to DIN and/or USB.
- More than 255 bytes in one message wraps the count. T2.1 and its verifier covered this, including
  stuck notes after wrapped off bursts. [verified]

### 3.4 Live notes on a MIDI track

`FUN_4012bb90` builds a MIDI event and posts its own type-1 message (ring `0x445ff890`, 64 slots) [verified
(C)]. Its fields:
- `[0xd] = 2` (live; no mute check);
- `[0xb] = 0` (no track data);
- `[6] = −1`, with the note and velocity inline;
- length `0x7f` (infinite, ended by the key's note-off), or a given length with `[0xc]` = clock;
- `[1]` = the lock list from the caller.

### 3.5 What any arp-to-MIDI sink must produce

From 3.2–3.4, a note becomes MIDI with no change to the MIDI task if it is a MIDI event with the
following fields [verified field use; the combination itself is untested]:

| field | value |
|---|---|
| `[0]`, `[1]` | 0 (the allocator clears them) |
| `[2]` | track |
| `[3]` | 1 |
| `[4]` | `0x80` |
| `[6]` | −1 |
| `+0x26` | the **raw** note. The MIDI task adds the transposes; the interrupt's transposed pitch (`d2` at the allocator call) would transpose twice |
| `+0x27` | velocity ≥ 0 |
| `+0x28` | length index, 0..`0x7e` |
| `+0x29` | 0 |
| `[0xb]` | track data, or a velocity and length that are never negative. A live template has `[0xb] = 0` (`FUN_4013801c` clears it), so a negative value would make the MIDI task read near address 0 |
| `[0xc]` | the bucket time |
| `[0xd]` | the source: 1 = sequencer, so mutes apply; 2 = live |

In the interrupt, the event is appended with the `fp−180`/`a5` protocol. With an inline single note,
`[0xe]`–`[0x10]` are never read (`0x4012b604`–`0x4012b608` → `0x4012b706` → free). [verified]

Hazards the sink must respect:
- **`FUN_4012a6e8` has no empty check.** With an empty free list `0x4460f4b8` it returns 0, and its
  next head is read from address `0x5c` (`0x4012a6ee`–`0x4012a6f8`) [verified bytes]. The sink must
  test `[0x4460f4b8] != 0` first, and drop the note otherwise.
- Arp notes add no queue messages: they ride on the pass's list. The 32-entry message ring and the
  64-slot queue see no extra load. [by design]
- The 8-bit output count: an arp note costs 3 bytes, or 6 with a same-note retrigger. Sixteen
  arpeggiating tracks in one pass add ≤ 96 bytes to whatever stock chords the same pass carries. That
  is the T2.1 hazard; the arp adds nothing new to it. [inferred]
- DIN: 3 bytes at 31,250 baud ≈ 0.96 ms per note. USB is not limited this way. [arithmetic]

## 4. Design options for sending arp notes to MIDI out

All options keep Elektron's arp where it is, in the voice interrupt, and add a **sink**. Where the
interrupt would give a MIDI track's note to the voice allocator, the sink builds the MIDI event of 3.5
and appends it to the list that the interrupt already posts to the MIDI task. The options differ only
in which notes reach the arp on a MIDI track. Code is in `out/T2.2-v2/arp_midi_v2.s`; it assembles with
`m68k-elf-as -mcpu=54418`, but has never been run.

  2. Otherwise take a MIDI event and set: `[2]` track, `[3] = 1`, `[4] = 0x80`, `[6] = −1`, and
     `[0xd]` = 1 when `ev[5]` is 1, else 2.
  3. Inline note: the **raw** note from `a2+2`. Velocity from `a2+3`; if negative, the track default
     `[0xb]+0x480`; if that is missing or negative, 100.
  4. Length:
     - an arp note uses `arp_len_lut[sound+0x162]` (sound = `0x4058f8d8[t]`);
     - an INF arp note (index 127) uses `speed_len[sound+0x160]`, one arp period;
     - any other note keeps its own length, or `0x7f` when it is negative and there is no track data
       (a live note, which its key-off ends).
  5. `[0xb]` = `ev[0xb]`, `[0xc]` = the bucket time, `[0xe]` as the type-3 path.
  6. Append with `fp−180`/`a5`, and return `d0 = d1 = 0` (no voice).

  It saves and restores `d2`, `d3`, `a3`, `a4`; `a2`, `d4`–`d7`, `a6` are not touched.
- **`cave_off`**: in the note-off loop, a MIDI track skips the allocator (no voice can belong to it).
  The caller overwrites `d0` (`0x40026d90`) and tests `d1` (`0x40026d96`). [verified]
- **`cave_liveon`**: a MIDI track whose arp is on (mode byte at `[0x800052a0]+0x34+t·0x48b+0x15f`) is
  reported "not MIDI". `FUN_40121db2` then posts the key to the interrupt (`FUN_4013801c`) and builds
  the voice-style lock list, which is consistent with that route. All other tracks go to the stock
  `FUN_40027c18`.
- **`cave_liveoff`**: a MIDI-track key release goes to **both** engines, whatever the arp state is at
  release time.
  1. It calls `FUN_4013801c(d6)` (the caller's event struct, `a6−0x40`, filled at
     `0x40121ba2`–`0x40121bc8`) [verified]. This removes the key from the arp's held set and is
     harmless if the key is absent.
  2. It returns 0, so the stock code also posts the release to the MIDI task. That sends `9n kk 00`
     only if the note is sounding (`0x4012b680`–`0x4012b6d8`) [verified].
- **`cave_sync`**: for a MIDI track whose arp is on, schedule the same type-9 step sync that audio
  tracks get (`[0] = 9`, `[5] = 1`, `[4] = t`, time `0x42c4f900+(d4−1)·900000`), then take the stock
  MIDI branch. It uses `d0`, `d1`, `a0`, `a1` only, which are dead at both targets (2.4). The arp mode
  is read from the kit in `d6`, as `FUN_400d87b8` will use it.
- **`cave_seq`** (v1's `cave_seq`, re-checked): a MIDI track whose arp is on takes the stock *audio*
  path, which builds the step sync and the voice event from `FUN_400d87b8`.
- **`cave_pre`**: the same decision for `FUN_400d907a`. It keeps `d0` (the step) in `a1`, because
  MOVEA leaves the condition codes alone and `a1` is dead after the branch. It returns Z for the
  caller's `bne.s`; the caller then reloads `a0` with `movea.l 0x42c5b9ac,a0`, which also leaves the
  condition codes alone.

**Tables** (`scripts/t22_v2_checks.py --lut`) [verified]:
- `arp_len_lut`, 128 bytes: arp length index → the first MIDI trig length that is not shorter. Exact
  for 96 of the 127 timed values; at worst +84,375 half units = 1/32 step.
- `speed_len`, 23 bytes: speed → the first trig length ≥ one arp period (period × 45,000 half units).
  Exact for 12 of the 23 speeds. The largest excess is 450,000 half units (1/6 step), at speed 4,
  whose period is 5⅓ steps. Speed `0xd` (1 step) gives `0x0e` = LEN 1.000.

### 4.3 Timing and jitter (the same for options 1–3)

- **Onset.**
  - A type-9 tick is scheduled at an exact time (a multiple of 90,000 units after the arp start or
    the step sync), and is handled in the interrupt pass that contains that time. The arp note it
    fires is linked into the same bucket, so it is handled in the same pass (1.4) [verified].
  - The sink appends the MIDI event in that pass. The list is posted at the end of the pass
    (`0x40026f5a`), and the MIDI task sends it when it runs.
  - **That is the same path, in the same pass, as a stock MIDI-track trig**: type 3 at
    `0x40026294`, posted at `0x40026f5a` [verified]. Arp notes on MIDI out therefore get the latency
    and jitter that stock MIDI tracks already have.
  - Expected magnitude [inferred]:
    - ≤ 1 pass of quantisation (≈ 0.67 ms);
    - plus the MIDI task's wake-up latency (not measured; the task is created with priority 8);
    - plus DIN serialisation, ≈ 0.96 ms per 3-byte note-on, and another 0.96 ms when a same-note
      retrigger off goes first.
- **Relative to internal voices.** On a synth track the arp starts its voice in that same pass.
  MIDI-out arp notes lag by the post, the task latency and the serialisation, exactly as stock MIDI
  trigs lag synth trigs. [inferred]
- **Note-off.**
  - The MIDI task books the off at `[0xc] + 2·len` (3.3). The interrupt polls the earliest pending off
    at the start of every pass (`0x400260a2`) and posts message 3 when it is due before the pass end
    [verified].
  - So offs are also ≤ 1 pass late, plus task latency.
  - Lengths are rounded up by the LUT: at most 1/32 step, and exact for 96 of 127 values.
- **Order at the same instant.** An off due in a pass is posted at the start of the pass
  (`0x400260de`); the pass's note list is posted at its end (`0x40026f5a`) [verified]. So a note that
  ends exactly when the next arp note starts goes off before the next note-on. That keeps the
  "one arp period" INF gate clean.
- **Live arp while the sequencer plays.** It waits for the next step sync (1.3 step 4), as on synth
  tracks. In option 1 the sync comes from `cave_sync`; in options 2 and 3 from the stock audio path.
- **Cost in the interrupt.** About 70 instructions per MIDI-track arp note, and none for audio tracks
  beyond a mask test (the sink tail-jumps). [inferred from the sketch]
- **Bursts.** At most one arp note per track per tick. Sixteen tracks on the same tick add ≤ 96 bytes
  to one message's 8-bit output count (3.5). [inferred]

### 4.5 Option 0: UI only (smallest; not a solution)

- **Changes:** the two UI branches (5 bytes), plus the LED if wanted (2 bytes). No caves.
- **Effect:**
  - the ARP menu and FUNC+ARP work on MIDI tracks;
  - the settings are stored in the track's sound record (1.2).
  - Nothing is sent: MIDI-track notes never reach the arp (2.4).
- **Why list it:** it is the lowest-risk first flash. It checks the UI patches, and whether the arp
  settings of a MIDI track survive a save and reload, before any interrupt code changes.
- **Code location:** none.
- **Timing, note-offs:** unchanged from stock.
- **Tests:** E1 and U1 in 4.11.

### 4.6 Option 1: live arp to MIDI out (smallest working option)

- **Changes:** UI (2 or 3 sites) + sink + off guard + live note-on and note-off routing + `cave_sync`.
  That is 8 sites (7 without the LED) and 692 bytes of new code and tables.
- **Behaviour:**
  - Keys played on a MIDI track whose arp is on go to the interrupt, through the arp, and out on the
    track's MIDI channel. That covers the unit's keyboard, and an external MIDI keyboard on the track's
    channel, which `FUN_4012213a` sends through the same `FUN_40121db2` [inferred].
  - Sequenced trigs on that track stay stock: plain MIDI notes, with their p-locks.
  - While the sequencer plays, a live arp starts on the next step, as on synth tracks.
  - Arp off: everything is stock.
- **What stays stock:** the sequencer routing, the MIDI task, and every synth track (each hook
  tail-jumps or returns the stock answer for them).
- **Code location:** 4.2.
- **Timing:** 4.3. Same path as stock MIDI notes.
- **Note-offs:** 4.4. The live release to both engines is what makes it safe to toggle the arp while
  a key is held.
- **Risks:**
  - In one live mode the event's sound is the snapshot pointer `0x445e311c[t]`, whose record is
    stale for MIDI tracks (2.3, `FUN_400f8082`) [inferred].
  - A live key on a MIDI track now runs the interrupt's synth note-on code before the arp: the
    voice-mask bookkeeping at `0x400265d2`–`0x4002661e` reads the track's allowed-voice mask at
    `kit+0x5ce0+2t`, which `FUN_400e71a8` zeroes. If it is not 0 on a MIDI track, that code can
    release internal voices [inferred]. Unit and emulator tests watch for this.
- **Tests:** E1, E2a, E2b, E2c, U2.

### 4.7 Option 2: sequenced trigs through the voice path (v1's design, corrected)

- **Changes:** option 1 with `cave_seq` instead of `cave_sync`, plus `cave_pre`. That is 9 sites
  (8 without the LED) and 672 bytes.
- **Behaviour:** on a MIDI track whose arp is on, a trig takes the stock audio path:
  - the step sync and the voice event from `FUN_400d87b8` (which reads the same pattern pool and
    trig data);
  - its notes enter the arp's held set for the trig length, as on a synth track;
  - the arp's output goes through the sink;
  - live keys work as in option 1.
- **Costs** [inferred from 3.1 and 3.3]:
  - **The trig's MIDI p-locks (CC, pitch bend, aftertouch, program) are not sent**, because the MIDI
    event is never built.
  - The voice builder instead reads the same 101 lock slots as *synth* parameters, into voice event
    `[0x15]`. No voice is started for a MIDI track, so they are applied to no voice. But the per-track
    loop at `0x400265b8`–`0x4002665a`, taken when the flags have `0x20000` and `flags & 0x81 = 1`,
    applies `[0x15]` to every voice whose owner word `0x80005308[v]` equals the track. With the sink
    no voice is ever owned by a MIDI track, unless an old owner word survives from before the track
    became MIDI [verified loop; the rest inferred]. Test.
  - The trig's LFO-trig flag (`0x400`) and the MIDI task's per-trig handling are skipped.
  - Mutes still apply (in the interrupt), and the MIDI task checks them again for `[0xd] = 1`.
- **Timing and note-offs:** 4.3 and 4.4. Sequenced arps start in the pass that holds the trig's time
  (no sync wait), the same as synth tracks.
- **Tests:** E1, E2a–E2d, U3.

### 4.8 Option 3: option 2, keeping the trig's MIDI p-locks

- **Changes:** option 2, but for an arp-on MIDI track the sequencer cave builds **both** events:
  - **First**, the stock MIDI event via `FUN_400d8cbe`, with bit 7 of the MIDI event's `[4]` cleared.
    The MIDI task then sends its locks and LFO trig, and drops its notes at the gate at
    `0x4012b2d8`–`0x4012b2e6` [verified gate].
  - The cave schedules it at the step's base time, `0x42c4f900+(d4−1)·900000`, with `ev[2]` set as at
    `0x400da178`. The micro-timing could be added as at `0x400da0c0`–`0x400da0dc`.
  - **Then** it returns "audio", so the stock code builds the step sync and the voice event for the
    arp.
  - The hook stays at `0x400da036`; the voice-builder call at `0x400da098` is a 4-byte `jsr (d16,pc)`,
    too short for a long jump.
- **One more patch is needed in the MIDI task.**
  - The arp's note events carry no locks. At the first one after a locked trig, the restore loop
    (`0x4012b008` → `0x4012b140`–`0x4012b1ec`) would send the track's base values again, so a p-locked
    CC would last only until the first arp note [verified flow; meaning inferred].
  - Fix: a marker in the sink's events (for example `[8]`, which `FUN_400d8cbe` and `FUN_4012bb90`
    both set to 0 [verified (C)]).
  - Plus a hook on the restore test, `tst.l (0,a6,d5.l*4); beq.s 0x4012b06a` at
    `0x4012b016`–`0x4012b01b` (6 bytes) [verified bytes]: a `jsr` to a cave that returns to
    `0x4012b06a` (no restore) for marked events, and otherwise repeats the test. That `0x4012b06a` is
    the "nothing to restore" path is [inferred].
  - Alternative: give each arp event a copy of the step's lock list. That costs MIDI bandwidth, and a
    list cannot be shared, because `FUN_4012a6b2` frees it with the event.
- **`FUN_400d907a`:** its static events (2.4) would also need the double build. The smaller choice is
  to keep `cave_pre`'s option-2 behaviour there. Then a trig that this pending-step path fires (at
  transport start or a pattern change) loses its locks.
- **Size:** ≈ +150 bytes for the double build and ≈ +30 bytes for the restore gate. [estimate]
- **Timing and note-offs:** as option 2. The lock-only event is sent at the step time, before or with
  the first arp note.
- **Tests:** option 2's, plus U4.

### 4.9 Rejected: a second arpeggiator in the MIDI task

- It would copy the arp logic (`FUN_40029cd4`, `FUN_4002a0bc`, held sets, expiry, 1/60-step clock) into
  task context, more than a kilobyte.
- It would need a clock: the MIDI task only wakes on queue messages, so the interrupt would have to
  post tick messages anyway.
- Its timing would add task latency to every tick.
- The sink reuses Elektron's arp, settings, sync and timing, so this has no advantage.
- UI-only (option 0) and "patch `FUN_40031274`" are not solutions either: the second would change
  every hidden virtual caller (2.1).

### 4.10 Review of the v1 sketch (`out/T2.2/arp_midi_sketch.s`)

What it gets right [verified against the bytes]:
- the sequencer site and its registers;
- the allocator's stack layout;
- `a2` as the note record;
- `fp−36`/`fp−44`/`fp−48`/`fp−180` and `a5` as the ISR's frame and list tail;
- the raw-note copy;
- the MIDI event layout;
- the list append.

Six defects, all fixed in `out/T2.2-v2/arp_midi_v2.s`:

1. **`[0xd]` is always 1.** Live arps would then be dropped by the sequencer mute and solo masks
   (`0x4012af2c`). Stock live MIDI notes use 2 (`FUN_4012bb90`). The fix copies the source from
   `ev[5]`.
2. **No empty-pool check** before `FUN_4012a6e8`, which reads address `0x5c` when the pool is empty
   (3.5). The fix tests `0x4460f4b8` and drops the note.
3. **INF arp length becomes `0x7f`.** Every arp note then goes to the MIDI task's infinite list. With a
   cycling arp they pile up until the same note repeats or a flush. The fix plays one arp period
   (4.4).
4. **`cave_live` replaces all of `FUN_40027c18`.** Its two callers then route a key's release by the
   arp state at release time. If the arp is toggled while a key is held:
   - a press that went to the MIDI task can be released into the interrupt, and the MIDI note
     hangs;
   - or a key stays in the arp's held set, and its ticks run on.

   v1 named this risk. The fix hooks the two call sites separately and sends releases to both engines.
5. **Only `FUN_400d99de` is rerouted.** `FUN_400d907a`'s pending trig (transport start, pattern
   change, lock edits) still goes to the MIDI builder, so it plays as a plain MIDI note instead of
   feeding the arp [inferred]. Fixed by `cave_pre`.
6. **The LUT is searched at run time,** up to 126 compares inside the interrupt per arp note. It is
   correct but slow. Replaced by the 128-byte table.

Robustness, not a defect: a negative velocity with `[0xb] = 0` would make the MIDI task read near
address 0. Live velocities are explicit (`FUN_4013801c`), but the v2 sink still falls back to the
track default or 100.
