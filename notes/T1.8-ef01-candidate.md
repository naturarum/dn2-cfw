## 1. The build and what `-V` may hold

**Command** (no `-c`, so the tool's repack path; sections are copied as stored) [verified]:

```sh
vendor/elektron-firmware-tool/elektron-firmware-tool -i Digitone_II_OS1_12.syx -V EF01 \
    -o out/T1.8/EF01.syx --emit-container out/T1.8/EF01.container.bin
# version: set to "EF01"; trailer: HMAC-SHA256; container: 1886016 -> 1886016 bytes
```

**Independent byte check** (`scripts/t1.8_verify_version_only.py`, digikit's `decode_syx` for the
transport, everything else its own; result in `out/T1.8/version-only.json`) [verified]:

| what | stock | EF01 |
|---|---|---|
| `.syx` bytes / SysEx messages | 2,390,304 / 18,676 | same |
| container length (`0x1cc740`) and section table | | identical |
| sections 5, 2, 3, 4, 7, 8 (stored bytes) | | identical |
| container bytes that differ | | `0x14-0x18` (version), `0x1cc720-0x1cc740` (HMAC) |
| header `0x07..0x17` | `40062        1.12` | `40062        EF01` |
| content checksum (stream preamble) | `0x07a3d265` | `0xa6187778` |
| SysEx messages that differ | | index 1 (preamble + header) and 18674 (trailer) |

**The version field** [verified: `container.c` `container_version_field` / `container_set_version`,
and test builds into the scratch area]:
- It is the 4 bytes at container `0x14..0x17`. The tool finds it by the first `<digit>.<digit>`
  between `0x07` and `0x1c` and extends it over letters, digits, `.` and spaces; in stock that is
  `1.12` followed by `00` at `0x18`. So **at most 4 characters**.
- **Trap:** a longer name (`-V EF012`) prints "too long for field; unchanged" but **still writes
  the output file**, with `1.12`. Always check the "set to" line.
- A shorter name is padded with spaces at the end (`EF1` -> `EF1 `). An empty name gives 4 spaces.
- The tool writes any bytes (it accepted `ef01`, `E F1`, `EF-1`); it does not check characters.
- **Rebuild from stock each time:** EF01 has no `<digit>.<digit>` any more, so the tool can no
  longer find the field in `EF01.syx` (`-i EF01.syx` prints no version line; `-V EF02` on it says
  "field not found; unchanged").

**What the unit can display** [verified, bootstrap code and its font]:
- The bootstrap draws header bytes `0x0C..0x17` with its 6-pixel font at `0x80005ef8`, whose width
  table (`0x80005f0c`) has glyphs for all printable ASCII `0x20..0x7e` (115 non-zero entries). The
  splash draws all 12 bytes right-aligned (spaces included, 3 px each); TEST MODE skips leading
  spaces and stops at a NUL or at `0x18`.
- So: **4 characters, printable ASCII, no NUL**. Upper case and digits match Elektron's style.
  `EF01` fits exactly.
- Keep `0x07..0x13` (`40062` and the 8 spaces) stock. `0x08..0x0B` (`0062`) is the build id the OS
  compares and reports (below); brickcheck check 2 refuses any change outside `0x14..0x17`.

## 2. Where the unit shows the version

Both the main OS and the bootstrap cache the container's first `0x20` bytes from flash
`0x80000`, as elekloader found on the Digitakt II, and accept it only with `ELE3` at +0 and
`0x34` at +4 (unchanged in EF01). The version is header `0x14..0x17`; the build id `40062` is at
`0x07..0x0B`. [verified]

### Bootstrap: the power-on screen and TEST MODE (this is where to look)

- Header cache: `FUN_800053ec` reads `0x20` bytes at flash `0x80000` (SRAM flash read
  `0x8000f010`) into `0x80007e30`; `FUN_80005440` returns `0x80007e30`, or 0 if the magic is
  wrong. Only two callers: `0x80000c96` (the splash) and `0x80004a02` (TEST MODE). [verified,
  raw scan of the bootstrap for `0x80005440` and `0x80007e2c..0x80007e50`]
- **Power-on screen** (init `FUN_800009c6`, `0x80000c68..0x80000d6c`, after the STARTUP-menu
  decision, so on every normal boot): clear; draw `B` (`FUN_8000188e(font, 0x42)`) at the top
  left; measure header `0x0C..0x17` (12 bytes) with `FUN_80001b94`; set the cursor to
  x = 128 - width, y = 0 (`FUN_800016b0`); draw it (`FUN_800019ce`). It then looks up section 5
  (`FUN_80005462(5)`) and draws the build stamp at y = `0x3a` only if bit 0 of a table-entry field
  is set; it is not drawn for stock or EF01 in the emulator. The frame is flushed at `0x80000d6c`
  (`FUN_80001ab4`) and the loader runs next. So **the version is right-aligned at the top right
  of the first screen after power-on**, and stays until the main OS draws its own screen.
  [verified: disassembly, and the emulator below. How long it stays on the unit: inferred, at
  least while the loader reads and unpacks 3 MB]
- **TEST MODE** (STARTUP menu, TRIG 1; key id `0x19`, menu dispatch `0x80002f98` ->
  `FUN_80002ae6`): `FUN_80004942` composes the info lines, among them `"OS: %s"` from header
  `0x0C..0x17` with leading spaces skipped (`0x80004a02..0x80004a58`), so it shows **`OS: EF01`**.
  The page `FUN_80004aca` is drawn when a key event comes in: in the emulator, letting go of
  TRIG 1 or pressing UP draws it. [verified]
- **TEST MODE is safe but has no exit:** `FUN_80002ae6` has no `rts` (the fall-through into
  EMPTY RESET in Ghidra's C is an artifact), so the user leaves it by switching off. None of the 47
  functions reachable from it in the call graph is the bootstrap's flash erase `0x80002896` or
  program `0x8000282a`; those two are named only in the self-upgrade `FUN_80001c48` and the OS
  UPGRADE commit `FUN_80003c9c`. TEST MODE reads the header and the serial record `0x3c0000`,
  and tests keys, encoders, LEDs, the panel link and DRAM. [verified: static; register-indirect
  calls are covered only as far as the call graph resolves them, but no word in the bootstrap
  names either write routine outside those two functions]
- Key ids in the STARTUP menu, from the bootstrap's name table `0x80006ce4` [verified]: FUNC
  `0x11`, TRIG 1 `0x19` TEST MODE, TRIG 2 `0x1a` EMPTY RESET, TRIG 3 `0x1b` FACTORY RESET,
  TRIG 4 `0x1c` OS UPGRADE, TRIG 5 `0x1d` EXIT; in TEST MODE UP `0x0b` / DOWN `0x0e` scroll the
  info page.
- **Correction to T1.5:** TEST MODE's `FUN_80005440`/`FUN_800053ec` read the container header
  at `0x80000`, not section 5. Only the splash then looks up section 5. [verified]

### Main OS: reports the version, never draws it

- Header cache: `FUN_40134804` reads `0x20` bytes at flash `0x80000` (NOR read `FUN_401353ae`)
  into `0x4463fc2c` and sets the flag `0x4463fc28` to 1 only if +0 is `ELE3` and +4 is `0x34`;
  `FUN_40134850` returns `0x4463fc2c`, or 0. [verified]
- The image names `0x40134850` at exactly 7 sites (raw scan of the unpacked main OS); calls.tsv
  agrees. What each does with the header [verified, disassembly]:

| site | function | uses | what for |
|---|---|---|---|
| `0x400bb516` | `FUN_400bb4f8` | +8, 4 bytes (`0062`) | stores the build id in a settings record (`0x405ce86c`) |
| `0x400bb73a` | `FUN_400bb696` | +8, 4 bytes | compares it with the stored one; if different sets `0x42432d44` = 1 and stores the new id. EF01 keeps `0062`, so this does not fire |
| `0x400ce69e` | `FUN_400cd5f2` | +8, `%.16s` | factory console text, maintenance mode only |
| `0x400cf1ca` | `FUN_400cedfc` (init) | +8..+0x17, 16 bytes | `FUN_40005906` copies `0062        1.12` to `0x40287ad5`; the USB control handler `FUN_40005ff6` returns those 16 bytes for vendor request `0xC0`/`0x02` (`0x400062ec`) |
| `0x400e953c` | `FUN_400e9366` | +8, 4 bytes | build id in the backup-file header (`BackupFileExportAdapter`) |
| `0x4011ed5a` | `FUN_4011ed4a` | +8, `%.04s` | exception screen `EXCEPTION DS0062` |
| `0x40126272` | `FUN_40125f9e` | +8 (4 bytes) and +0x0C (12 bytes) | reply to `MidiRpcSoftwareVersionRequest` (Transfer's protocol) |

- Raw scans: the cache `0x4463fc28..0x4463fc4b` is named only inside `FUN_40134804`,
  `FUN_40134850` and `FUN_4013487a` (the section-table reader, +0x1C = count); the copy
  `0x40287ad0..0x40287ae7` only at `0x40005910` (the writer) and `0x400062ee` (the USB handler).
  The other main-OS uses of the immediate `0x80000` are the section-7 load (`0x400cf722`),
  allocation sizes, masks and the upgrade writer. No main-OS string names an OS version page
  (no `OS INFO`/`VERSION`/`ABOUT`; `VERSION 1` is the factory console). [verified, static]
- So on the main OS the version (`EF01`) reaches only **Transfer** (USB vendor request and the
  MIDI RPC reply). How Transfer displays or parses `EF01` was not checked. elekloader's notes say a
  Digitakt II unit reported `PD10` for a build so named. [inferred]
- The build id `0062` is what the OS itself compares and stores. EF01 leaves it stock, so going
  stock -> EF01 -> stock changes nothing the OS keys on. [verified that only +8 is compared;
  what `0x42432d44` triggers is inferred, and it is not triggered here]

## 3. What the unit does with the file (Transfer over USB)

From the 1.12 code; not run in an emulator (digikit cannot drive an in-OS upgrade yet). [inferred
unless marked]
- Transfer's route is the in-OS upgrade: `MidiRpcOsUpgradeStart/Write/End` in `FUN_40125f9e`, the
  per-message decoder `FUN_4012257c` into the 2 MiB buffer `0x4038bee0`, then the validator
  `FUN_400dbdb0` (content checksum and HMAC). [verified, T1.2/T1.4 and the code]
- "Incompatible OS" is decoder result 5: framing byte 8 is not `0x10`. EF01's framing is stock's
  (brickcheck check 1). Nothing on this path reads the version field. [verified]
- The OS-upgrade view (`FUN_401098d8`) shows `Receiving`, then a confirm window
  `UPGRADE OS NOW?`; on yes `PREPARING...` (`FUN_401094e8`), `ERASING FLASH...` and the validator
  again (`FUN_40109144`), then the writer `FUN_40139104` (from `0x80000` up), which ends with
  `Success! Rebooting` (`0x401391ca`, shown upper-cased via `FUN_40108ee6`/`FUN_401343b8`), a
  delay (`FUN_4013492c(3000000)`) and `jsr 0x400023f6` with interrupts masked (the restart).
  [verified: strings and calls; the screen order inferred]
- elekloader's README gives the user steps for the Digitakt II and Digitone II: Transfer, select
  the unit, **Connect**, drag the `.syx` onto **Drop files here**, press **YES** on the unit. Its
  Digitakt II build was flashed that way on a unit. That matches the confirm window above.
  [inferred for the Digitone II: Transfer's screens were not seen here]
- Going back from EF01: EF01's validator is stock's (section 3 identical), and T1.2 found no
  build floor on 1.12 ("Unsupported downgrade" unreachable), so the unit accepts stock 1.12 the same
  way. [verified for the code; on a unit: inferred]
- The in-OS upgrade never writes below `0x80000` (T1.4), so the bootstrap and its STARTUP menu
  survive even a failed or cut-off write. T1.5 reached the menu with a truncated container and with
  all-`0xFF` flash. [verified in T1.4/T1.5]

## 5. The checker's known gaps do not apply to EF01

The T1.7 red team found four gaps: a neutered validator `FUN_400dbdb0` passes, a changed section 7
is only depacked, check 7 misses computed flash references, and check 8 watches only the cold
boot. All four need changed code. EF01 has none: sections 3 and 7 are byte-identical to stock as
stored (this note's own comparison, independent of the checker), so the validator, the flash
driver, the writer and the DSP program are Elektron's. [verified]
