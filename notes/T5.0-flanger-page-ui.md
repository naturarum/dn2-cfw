# T5.0: how the Digitone II draws the chorus page and the chorus send, and a flanger page in the emulator

Date: 2026-10-06 (background agent). Firmware: Digitone II OS 1.12, main OS loaded at `0x40000400`.
Marks: **[verified]** = checked against the bytes or run in the emulator here; **[inferred]** = reasoned
from structure. Emulator only: nothing flashed, no hardware, nothing committed.

**Status: paused 2026-10-06** at the coordinator's request (overlap with dn2_firmware_explore; the owner
is contacting its author). What is below was found and proved up to that point; the open items are in
section 7.

## Summary

- **Drawing:** pages draw into a column-major 1 bpp Bitmap (y = 0 at the bottom) with a small set of
  primitives (section 2.2). Text goes through a 20-byte font record and `0x401153f8`; 17 fonts exist.
  Every per-parameter glyph is a frame of an icon "strip" (`std::vector<Bitmap>`), picked by value.
  The strips are built at boot by `0x40151b94` from pixel data in the image. [verified]
- **Which table drives what:** the page table in RAM (`0x42433c00`) gives the rows on each knob and the
  title. The descriptor table in the image (`0x401f83a4`) gives labels, long names and formatters. The
  display table in RAM (`0x4243425c`) gives each row's glyph-drawing function and, through it, its
  strip. [verified]
- **Chorus send:** row `0x43`, the cone strip `0x44646bdc` (13 frames, 19 x 17). The same strip is used
  by the external-input chorus sends. [verified]
- **Extracted:** 17 fonts, 142 strips (2,678 frames) and 513 single icons, in `out/T5.0/atlas/`. Contact
  sheet: `out/T5.0/index.html`. [verified]
- **Proved in the emulator (hot-patched build):** the new labels (FLG, FDBK, TIME, "Flanger Send"), the
  FLG page box and three redrawn glyphs (send, FDBK, TIME). Screens in `out/T5.0/before-after.png`.
  - The renamed page title ("Flanger") and the second page need a cold boot. That run was stopped
    when the work paused, so neither has run.
  - The brick checker passed 9 of 10 checks on the candidate. Check 8, the emulated cold boot, was
    stopped.

## 0. Two pages per send effect: yes, with the parameter rows as the real cost

The owner asked: "have you figured out how to make them multi-page? ... if you could confirm whether
this could be doubled (2 pages per effect)".

**Answer: yes, on the UI side.**
- The SEND FX view is already a multi-page view.
- Paging is driven by a list of page ids, and every UI behaviour follows that list's length.
- Adding a page is a few data and code sites; core-dn2's hooks are not needed for it.
- **The cost is the knobs, not the pages.** Each new knob needs a parameter "row", and there are no
  spare rows.
- **Status of the proof:**
  - Statically: verified.
  - Same mechanism on OS 1.11: run on the unit by dnfw (their LFO4 page).
  - Our 1.12 build: linked, its display-row copies ran in a hot-patch, and 9 of 10 brick checks
    passed.
  - Not yet seen on screen: that needs the cold boot that was stopped (section 7).

**How the send FX are navigated today** [verified: decompile, and stock runs in
`out/T5.0/emu/stock/page2/`]
- FUNC+FX opens one view, an `FxPageView`. The view class is `ParameterPageView`, a subclass of
  `View`.
- Its pages come from a `std::vector<int>` of page ids, `{17, 18, 19}` (DEL, REV, CHO).
  - The vector is built in MainScreenView's constructor `0x40060e72`. The array is at `0x401e0448`,
    and the count is a `moveq #3,%d1` at `0x40061616`.
  - The array is pushed at `0x40061624` before `make_shared<FxPageView>` (`0x4019fc1a`).
- In the view's key handler (`ParameterPageView::vslot02`, `0x4006787c`):
  - the page key again (FUNC+FX again) goes to the next page and wraps from the last to the first
    (`0x400680e8`-`0x4006811a`);
  - UP and DOWN step by one and stop at the ends (`0x4006837c`-`0x40068396`).
  - Both go through `setPage` (`ParameterPageView::vslot32`, `0x40063ade`), which clamps to the
    vector's length.
- Stock run: FUNC+FX gives Delay (1/3); FUNC+FX again gives Reverb (2/3); DOWN gives Chorus (3/3);
  more DOWN stays there; UP goes back.
- **What shows the page:**
  - the title "(i/n)" (`ParameterPageView::vslot19`, `0x40063f56`);
  - a marker at the right edge of the screen;
  - the FX key's LED, lit for all pages.

  The DN2 has no separate page LEDs on this view.

**How multi-page views work elsewhere** [verified]
- All parameter views are built the same way in the same constructor, each with its own list of
  page ids:

  | view | page ids |
  |---|---|
  | TRIG | `{1,2}` |
  | SYN | `{7..11}` |
  | FLTR | `{12,13}` |
  | AMP | `{14}` |
  | track FX | `{16}` |
  | LFO | `{4,5,6}` |
  | EUCL | `{3}` |
  | send FX | `{17,18,19}` |
  | MIXER | `{20..24}` |
  | MIDI-track views | `{27}`, `{29}`, `{30,31}`, `{32,33}`, `{34}`, `{35,36}` |

- A page id names a **page record** of 0x2c bytes, at `0x42433c00 + 0x2c * id` in RAM (ids 0-36).
  It is built at boot by `0x400c2c4e` and read only through `0x400c25d8`, which clamps the id to 36.
- The record holds:
  - the short name ("CHO");
  - the long name ("Chorus");
  - eight parameter rows, one per encoder A-H (0 = empty slot);
  - the LEVEL row.
- A ParameterPageView maps encoder n to row `record[2 + n]` of the current page.
- The FX view also tests the page id itself in three places (box label `0x4006f4a8`, the filter graphic
  over E-F `0x4006f70a`, the reverb graphic `0x4006f8dc`).
- dnfw found the same lists, record table and 36 bound on 1.11, and added a fourth LFO page to the MOD
  view (id 37, record from a cave on the accessor). It ran on the unit on 1.11
  (`vendor/dn2_firmware_explore/docs/lfo4-build-plan.md` sections 5, 5h, 5i).

**What a second page per effect takes** (all built in `vendor/elekloader/examples/fx-page2-dn2`, one
extra chorus page):
1. **A longer page list.**
   - The count goes from 3 to 4: `bytes` site at `0x40061616`, `7203` → `7204`.
   - The array is pointed at the mod's `{17, 18, 19, 37}`: `keep2` site at `0x40061624`.
   - For two pages per effect it would be `{17, 37, 18, 38, 19, 39}` with count 6.
2. **Page records for the new ids.**
   - `0x400c25d8` is replaced by a `jmp` to `fx2_pagerec` (`pagerec.s`). It returns the mod's record
     for id 37 and behaves as stock for every other id.
   - It changes d0 and d1 only, like the stock routine. That matters because it is a direct call from
     20 sites.
   - The record's names are static COW `std::string`s with refcount -1, so every copy clones them and
     nothing frees them. The record holds 8 rows and LEVEL = row `0x70` (VOL).
   - Ids 26 (OB8) and 28 (an empty TRIG) are not in any view's list either, but a new id is safer.
3. **The FX view's page-id tests.** Three `jsr` sites (`0x4006f710`, `0x4006f8e0`, `0x4006f4d0`)
   replace `movea.l (0x88,A0),A0; jsr (A0)` with `fx2_baseid`, which reports id 37 as 0x13 (chorus).
   This gives the FLG box, and no delay/reverb filter graphic over E and F.
4. **Eight parameter rows.** This is the hard part.
   - A knob is a descriptor row: names, range, formatter, and the mirror index k, which says where the
     value is stored and which frame word carries it.
   - It also needs a display row in RAM (flags and the glyph function). The glyph is chosen by row id,
     not by page.
   - **There are no spare rows.**
     - The descriptor table has a fixed 0x141 rows, and about 84 functions test that bound
       (`#0x140`/`#0x141`).
     - dnfw counted the rows on 1.11 and found no block of ten unused ones.
   - The proof borrows the eight "Error" rows 1-5 and 0xb-0xd:
     - `bytes`/`ptr` sites make them FX parameters: group `0x10`, k 70-77, names SHPE, PHAS, MULT,
       SYNC, WDTH, TONE, DRIV, NEG, and the plain-number formatter.
     - `fx2_tick` copies their display rows from row `0x69` (a knob), and from row `0x63` for SHPE
       (the LFO waveform glyph and names).
   - **Those rows carry MIDI CCs 1, 2, 6, 7, 10, 99, 120 and 121 in stock**, and the sites clear them.
     So a real build must not use them. A real build needs a grown descriptor table and display table.
     dnfw's lfo4 mod (1.11) moves the table and adds ten rows (see the correction at the end).
5. **Storage and frame (for the other agent; facts found on the way)** [verified]:
   - FX-setup words k 0-24 and 70-100 are all zero in the LIGHTHOUSE kit.
   - No descriptor row of the FX groups (`0x10`-`0x15`) uses them: their k are 25-69 only.
   - The ColdFire-to-DSP frame carries k 25-69 only (T3.3).
   - The setter path `FxParameterSet` → `0x4002585a(value, 0x10, k)` accepts any k < 0x65 (101).
   - So the 8 second-page values land in the kit's FX setup (k 70-77) and in mirror row 16
     (`0x800047b2 + 2k`), and never reach the DSP.
   - Whether the kit file saves all 101 words is the other agent's question.
   - The frame words k 40 (Delay FX Routing) and k 48 (Reverb FX Routing) are sent but used by no
     page.

## 2. How a page is drawn [verified unless marked]

Found by tracing the frame composition in the emulator (`scripts/t50_trace.py`: while DRAWALL
`0x4011d60a` runs, log every function entry and the arguments of the drawing primitives;
`out/T5.0/trace/chorus-calls.json`, `trackfx-calls.json`), then reading the routines in
`out/decomp/main_os`.

### 2.1 Screen and Bitmap

- The views draw into a local **Bitmap** (on the UI task's stack, `0x405c6904` in these runs),
  128 x 64, then `0x40115074` converts it to the panel's 1,024-byte page buffer.
- **Coordinates: x 0..127 from the left, y 0..63 from the BOTTOM row up** (the header is y 54-63, the
  bottom labels y 0-4). Same as elekloader's hello-marker note for the Digitakt II.
- **Bitmap object** (`0x1c` bytes, vtable `0x402069c4`): `+4` width, `+8` height, `+0xc` stride
  (32-bit words per column), `+0x10` pixel words, `+0x14` mask words, `+0x18` 0. Column-major:
  column x is `stride` big-endian words, pixel y is bit `0x80000000 >> (y & 31)` of word `y >> 5`
  (MSB = lowest y). This is digikit's layout (findings/07) and the community's (digisplash-ii,
  digistring), and it holds for every icon.
- **Constructor** `Bitmap(this, w, h, data, mask)` = `0x40113e2a` (3,065 call sites; almost all in
  the static initializer below).

| `0x40113fd4` | horizontal line | `(bmp, x0, y, x1, mode)`; mode < 0 XOR, bit 0 set/clear |
| `0x401141bc` | vertical line | `(bmp, x, y0, y1, mode)` |
| `0x40114906` | rectangle outline | `(bmp, x0, y0, x1, y1, mode)` |

| `0x401153f8` | **draw text** | `(bmp, font, x, y, mono, maxlen, str)` -> width; y is the glyph's bottom + ascent |
| `0x401156d4` | draw text, not mono | `(bmp, font, x, y, maxlen, str)` |

### 2.3 Fonts

There are **17 fonts**, registered by the static initializer `0x401ba106` as `{vtable 0x402069dc,
font*}` pairs at `0x44508e78 + 8k`. A font record is 20 bytes (the same shape octabam documents for
the Octatrack):

```
+0x00  max width (used for monospace drawing)
+0x04  (ascent << 16) | height
+0x08  -> widths, one signed byte per character code 0..255
+0x0c  -> offsets, one signed 16-bit word per code; -1 = no glyph
+0x10  -> glyph columns: one byte per column if height < 8, one u16 if height <= 16, else one u32;
          the MSB is the glyph's BOTTOM row; glyph c = width[c] columns from data + offset[c] units
```

Text advances width + 1 per character. Codes below 0x20 hold small symbols (play, arrows, boxes).
The ones these pages use (from the trace):

| font | size | used for |
|---|---|---|
| `0x40291ca0` (atlas `font-16`) | 4 x 5 | **knob labels and values** (DPTH, SPD, CHR, "127") |
| `0x40290dd0` (`font-14`) | 4 x 6 (proportional) | **page title and the value bubble** ("Chorus (3/3)", "Depth=127") |
| `0x402906b4` (`font-08`) | 3 x 6 | header pattern box "A01", tempo "81.0", the left page box ("CHO", "SYN 1") |
| `0x4028ffdc` (`font-07`) | 6 x 10 | the large pattern name on the main and track pages ("LIGHTHOUSE") |

All 17 are extracted (`out/T5.0/atlas/font-*.png`).

### 2.4 Icons and strips (the per-parameter glyphs)

- Every icon is a Bitmap object whose pixel and mask words are **in the image** (`0x402a....`-
  `0x402f....`). The objects themselves are built at boot by one static initializer,
  **`0x40151b94` (99,614 bytes)**: `pea mask; pea data; pea h; pea w; pea this; jsr Bitmap::Bitmap`,
  3,000-odd times. Single icons land at fixed RAM addresses (`0x44645xxx`-`0x44648xxx`); animated
  ones are built on its stack and copied into `std::vector<Bitmap>` **strips** (`{begin, end, cap}`).
- **A glyph's frame is picked by value.** `0x40115e3e(strip, value, range, mode)` returns
  `begin + 0x1c * i`, with n frames, last = n - 1, values in `v << 8` units:

  | mode | frame i |
  |---|---|
  | range 0 | i = value (the 96-frame knob strip is indexed directly) |
  | 0 | i = (range/2 + last * v) / range, rounded |
  | 1 | i = n * v / range |
  | 2 | i = 0 at 0, else 1 + last * (v - 0x100) / (range - 0x100) |
  | 4 | i = last * (v - 0x100) / (range - 0x100); at or above 0x7f00, the last frame |
  | 6 (the sends, faders) | i = 0 at 0, the last frame at or above 0x7f00, 1 + (v - 0x100)(n - 2)/(range - 0x200) between |
  | 8 | the last frame when v is the centre, else last * v / (range + 0x100) |
  | flag 0x10 | one frame fewer |

  The result is clamped to 0..last. The wrappers are `0x40115f88(strip, value, full)` (range
  `0x7f00` or 0) and `0x40115fac(strip, value, mode)` (range `0x8000`). [verified: decompile; the
  frames the trace picked match the screenshots; mode 8's purpose is inferred]
- The extractor `scripts/t50_glyphs.py` reads the strips and icons out of a snapshot's RAM and their
  pixels out of the image: **142 strips (2,678 frames) and 513 single icons**, PNGs in
  `out/T5.0/atlas/` (black = 0, white = 1, grey = masked out), `index.json` lists each one's
  addresses.

The ones on these two pages (vector address = where the strip's `{begin, end, cap}` lives):

| strip vector | frames, size | glyph | where |
|---|---|---|---|
| `0x4464680c` | 96, 19 x 17 | knob, pointer at value | chorus DPTH, SPD |
| `0x446466d8` | 12, 19 x 17 | high-pass curve | chorus HPF |
| `0x4464642c` | 12, 19 x 17 | stereo width (two ovals) | chorus WDTH |
| `0x44646a5c` | 13, 19 x 17 | delay send (rings) | track DEL, chorus DEL |
| `0x44645ca0` | 13, 17 x 17 | reverb send (room) | track REV, chorus REV |
| **`0x44646bdc`** | **13, 19 x 17** | **chorus send (cone)** | **track CHR**; data `0x402bfad0` (mask) + 13 frames from `0x402bfb1c`, `0x4c` bytes each |
| `0x44646980` | 14, 11 x 17 | fader | chorus VOL (LEVEL) |

### 2.5 Which table drives each knob's label, value and glyph [verified]

The FX page's draw is `FxPageView::vslot04` (`0x4006f5e4`). For each of the 8 slots it asks the view
for the slot's parameter row (vtable `+0xbc`); row 0 draws the dotted empty box (`0x446462a8`).
Otherwise it calls the knob routine **`ParameterPageView::vslot45` (`0x4006448a`)**
`(view, bmp, x, y, row, value, ...)`, with slot origins x = `0x18, 0x32, 0x4c, 0x66` (+1 in the
routine) and y = `0x22` (top row) / `0x07` (bottom row); LEVEL is drawn at x = -2.

| what | where it comes from |
|---|---|
| **which parameter is on which knob** | the **page table** in RAM, `0x42433c00 + 0x2c * page` (37 pages, built at boot by the static initializer `0x400c2c4e`): `+0` short name (`std::string`, "CHO"), `+4` long name ("Chorus", the title), `+8..+0x24` the rows of A-H (0 = empty), `+0x28` the LEVEL row. Chorus = page 19 at `0x42433f44`: `69 6a 6b 6c 0 0 6d 6e`, LEVEL `70` |
| **page title** "Chorus (3/3)" | `ParameterPageView::vslot19` (`0x40063f56`): `"%s (%d/%d)"` with the page table's long name, drawn in font `0x40290dd0` at (0x13, 0x38) |
| **page box** "CHO" | `0x4006f4a8`: by page id (`0x11` DEL, `0x12` REV, `0x13` "CHO" = the tail of the literal "NACHO" at `0x40221538`), font `0x402906b4` via wrapper `0x44508eb8`, centred at (7, 0x24) |
| **label under the knob** | descriptor table `0x401f83a4 + 0x3c * row`, `+0x30` short name (`0x400372da` reads it at draw time), centred at x + 9 in font `0x40291ca0` (`0x40115948`, align 1) |
| **header bubble** "Depth=127" | descriptor `+0x28` long name and the value text, font `0x40290dd0` (`HelpBubbleView::vslot04` `0x400f8716`) |
| **value text** (replaces the label while turning) | the parameter's formatter (descriptor `+0x34`; also a `std::function` in the display table below) |
| **glyph** | the **display table** in RAM, `0x4243425c + 0x44 * row` (`0x400c257c`), built at boot: `+0` flags, `+0x14` a `std::function` that draws the glyph (manager `+0x1c`, invoker `+0x20`), `+0x24` and `+0x34` two more (value text). `ParameterSet::vslot24` (`0x40036560`) tail-calls the invoker as `draw(functor, value, bmp, x, y + 7, flag)`. Each invoker is 18 instructions: pick a frame from **one fixed strip** (`pea strip; jsr 0x40115f88/0x40115fac`) and `jmp` the blit |

Invokers and strips per parameter (all 321 rows, `out/T5.0/display-table.txt` [verified, from the
snapshot]): the chorus send's invoker `0x400c0b22` draws strip `0x44646bdc` (mode 6) and is used by
rows `0x43` (track CHR), `0x8b`-`0x8d` (external-input CHR, LCHR, RCHR) only. The chorus HPF
(`0x400bc444`, strip `0x446466d8`) and WDTH (`0x400bc490`, strip `0x4464642c`) each serve one row.
DPTH and SPD use the generic knob invoker `0x400c0986` (strip `0x4464680c`). The LFO waveform
glyph already exists: invoker `0x400bc4dc`, strip `0x44648040`, rows `0x4f`, `0x59`, `0x63` (LFO1-3
WAVE), which matters for a flanger LFO-shape knob (section 6).

### 2.6 The chorus send

- **Track FX page** (FX key), encoder G = descriptor row `0x43` ("Chorus Send" / "CHR", group "FX",
  mirror index `k` 88, frame slot `+0x7e`, T3.3). Label, value text and bubble as above; the glyph is
  the cone strip `0x44646bdc` (13 frames, 19 x 17; frame 0 = an outline with a dotted base for 0,
  frames 1-12 fill from the bottom; mode 6 puts 0 on frame 0, 127 on frame 12 and spreads 1-126 over
  1-11).
- The **same strip and invoker** draw the external inputs' chorus sends (rows `0x8b`-`0x8d`, MIXER 5/6,
  "In Chorus Send", "CHR", "LCHR", "RCHR").
- The **FX MIXER page**'s chorus volume (row `0x6f`, "Chorus Mix Vol." / "CHR") is a fader (invoker
  `0x400c0a60`, strip `0x44646980`), like every volume.
- The chorus page's own DEL and REV sends use the delay- and reverb-send strips, so they look like
  the track page's DEL and REV.

## 3. Renaming and redrawing: the method that works

Two example mods on elekloader's local branch (`vendor/elekloader/examples/`, uncommitted), built with
`python -m elekloader.sdk.build` (`ELEKLOADER_CROSS=m68k-elf-`) into `out/T5.0/mods/`, linked with
core-dn2 0.1 (its 10 sites unchanged) by `python -m elekloader.patch`:

**`flanger-ui-dn2`** (`flanger_ui.c`, `flanger_art.h`, `mod.json`; 26 sites, `.run` 4,350 bytes, one
`ev_tick` handler). `mod.json` is written by `scripts/t50_make_mod.py`, which reads each site's stock
bytes from the image and checks they are what it expects.

1. **Names, no code: `ptr` sites on the descriptor table** (it is in the image and read at draw time,
   so a pointer to a string in the mod's `.run` works from the first frame). Rows `0x43` (track send),
   `0x6f` (FX MIXER), `0x8b`-`0x8d` (external-input sends): long name `+0x28` "Flanger Send" etc.,
   short `+0x30` "FLG", "LFLG", "RFLG"; rows `0x6b`, `0x6c` (knobs C, D): "Feedback"/"FDBK", "Delay
   Time"/"TIME"; group `+0x2c` of rows `0x69`-`0x70`: "Flanger". Never edit the shared strings in
   place ("CHR", "DEL", "Chorus" are each used by several rows; "Chorus\0" is followed by "DPTH", so
   "Flanger" would not fit) [verified: the pointer census in `t50_make_mod.py`; dnfw reached the same
   rule on 1.11, notes/prior-art-2026-10.md 6.3].
2. **Title and box: `keep2` sites on the `pea` that pushes the literal.** The page table's strings are
   `std::string`s built at boot from `pea 0x40210a96` ("Chorus", `0x400ca018`) and `pea 0x4022153a`
   ("CHO", `0x400c9fba`); the box pushes "CHO" again at `0x4006f4f8`. Pointing the `pea`s at "Flanger"
   and "FLG" changes what is built and drawn. The core's boot copy runs at `0x40000538`, before any
   static initializer, so the strings are in place [inferred: the cold boot that would show it was stopped; the hot-patch
   cannot, since the page table is built at boot].
3. **The LFO DEST browser's group name** for group `0x10` (`0x401f7b04 + 4*(0x10-5)` = `0x401f7b30`),
   "ERR" in stock: `ptr` to "FLG" (from dnfw's finding; only visible if chorus parameters become LFO
   destinations) [inferred: not exercised].
4. **Glyphs: repoint the strip vectors at run time.** On the first `ev_tick` (the UI loop, after every
   static initializer), `flui_tick` checks each stock vector (frame count, 19 x 17, stride 1, vtable)
   and sets `{begin, end, cap}` to the mod's own Bitmap objects (vtable `0x402069c4`, data and mask in
   `.run`): the chorus-send cone (`0x44646bdc`) becomes the flanger send glyph (13 frames), the HPF
   curve (`0x446466d8`) the FDBK glyph (12) and the WDTH ovals (`0x4464642c`) the TIME glyph (12).
   It leaves the old heap frames alone and sets `flui_state` = 1 when done (-1 if a vector does not
   look as expected, which then stays untouched). Any frame count and size work this way; the
   invoker picks the frame from the vector's length.

   The alternative, writing new pixels over the stock ones with `bytes` data sites, also fits the
   format (same frame count and size only), but the mod's `mod.json` would then carry ~2.8 KB of
   Elektron's pixel data as the sites' `stock` field. The run-time route ships only our own art
   [inferred: the data-site route was not built].
5. **Art.** `scripts/t50_flanger_art.py` draws the frames (`out/T5.0/art/*.png`, stock above, new below)
   and writes `flanger_art.h`: the send is a cup whose top edge is a wave with a shortening period
   (a sweep), filled from the bottom like the stock cone, with the stock dotted floor for 0; FDBK is
   a feedback comb `|1/(1 - g e^-jwT)|`, g 0 to 0.9, two resonant peaks growing; TIME is a
   through-zero comb `|cos(wT/2)|` with 0.6 to 3 notches as the delay grows. All 19 x 17 in the stock
   rounded box (FDBK, TIME) so they sit like the knobs around them.

**`fx-page2-dn2`** (section 0): a second chorus page.

Build `out/T5.0/build/flanger-FP01.syx` = core 0.1 + flanger-ui 0.1 + fx-page2 0.1, version FP01
(sha256 `b199823e...dfe0`): blob 5,660 bytes, RAM `0x47e00000-0x47e015fc`, margins 2,148,543 at
`0x40400000` and 51,391 at `0x40200000`, 185,222 bytes spare in the receive buffer (elekloader's

## 6. Plan for the full flanger page

The DSP side (T5.1) decides the parameters; this is the UI that fits them. Proposed page 1 (the stock
chorus page's slots and frame words k 25-31, plus E and F, which are empty on stock):

| knob | label | long name | storage | glyph | value text |
|---|---|---|---|---|---|
| A | DPTH | Depth | k 25 | stock knob | number |
| B | SPD | Speed | k 26 | stock knob | number (later Hz or a sync division: a formatter) |
| C | FDBK | Feedback | k 27 | new comb strip (done) | number; bipolar if the design wants negative feedback: the bipolar formatter `0x400e341a` (as PAN) and a glyph whose centre frame is zero (mode 8 may be meant for that [inferred]) |
| D | TIME | Delay Time | k 28 | new comb strip (done) | number or ms |
| E | SHPE | LFO Shape | new word | the stock LFO waveform strip `0x44648040` (TRI SINE SQR SAW EXP RAMP RND) | the LFO WAVE formatter `0x400e3610`, max 6 (both proven on the second page, section 0) |
| F | WDTH | Stereo Width (or LFO phase) | new word | the stock width ovals (keep the stock strip for it: give D its own new vector instead of replacing the HPF/WDTH ones) | number |
| G | DEL | Delay Send | k 29 | stock delay send | number |
| H | REV | Reverb Send | k 30 | stock reverb send | number |
| LEVEL | VOL | Mix Volume | k 31 | stock fader | number |

A second page (section 0) can carry what does not fit: LFO phase/sync/multiplier, feedback tone,
drive, polarity.

**Fitting.** Labels use the 4 x 5 font (`0x40291ca0`): at most 5 characters (about 24 px; the slots are
26 px apart), centred on the knob; values replace the label while the knob turns, in the same font, so
a formatter should keep to 5 characters. The header bubble ("Long name=value") uses the proportional
4 x 6 font across about 108 px, so long names of up to about 18 characters fit with a value.
Glyphs are 19 x 17 (17 x 17 for some), stride 1; the knob slot's box is x-1..x+17 around the label's
centre x+9.

**Glyphs for new parameters**, three ways, cheapest first:
1. **Reuse a stock strip and formatter**: copy the display row (0x44 bytes at `0x4243425c + 0x44 *
   row`) of a row that already draws it (LFO WAVE: row `0x63`) [verified: second page, knob A].
2. **A new strip for a stock invoker**: repoint a stock strip's vector when only the rows you take
   over use it (FDBK, TIME, the send) [verified].
3. **A new strip with its own invoker**: a C function `draw(functor, value, bmp, x, y, flag)` that picks
   a frame and calls the blit `0x40115adc(bmp, frame, x, y, 0)`, installed in the row's display entry
   (`+0x20` invoker, `+0x1c` manager non-zero) [inferred: the calling convention is read from
   `ParameterSet::vslot24` and the stock invokers, not run].

**Text for new value types** (Hz, ms, sync divisions, shape names): descriptor `+0x34` is a case
label inside `ParameterSet::vslot23` (`0x40036692`); a `bytes` site can pick any stock formatter. A new
one needs a case that jumps to mod code and back [inferred].

**What the page needs from elsewhere** (T5.1, T2.3, the frame agent): storage for E and F and for
page 2 (section 0: FX-setup words 0-24 and 70-100 are zero in the kit and unused by any row), the
words in the ColdFire-to-DSP frame, and real parameter rows (section 0).

## Correction (2026-10-13, main session)

The 2026-10-06 correction that stood here was wrong, and so was the "fix" made inline from it on 2026-10-12.
dn2_firmware_explore **did** grow the descriptor table on 1.11: their LFO4 first planned to reuse the dead ERR
rows, found there was no block of ten spare records, and moved the table into their mod area with ten added
rows, diverting the display table's reader for them (`docs/lfo4-build-plan.md`, 2026-09-21; code
`src/dnfw/patch/paramtable.py`). A build with the moved table ran on their unit on 2026-09-21, and their README
lists `lfo4` as confirmed on hardware. They leave one bound at 321 (`param_set_tables_build`, 1.11 `0x400dc7f0`)
because LFO4's slots pass 100. Our own prior-art survey had recorded their relocated table (notes/prior-art-2026-10.md,
"a relocated parameter table `0x46900000`"). For Waverider's pages they hook the label fetch instead
(`docs/waverider-m7-pages.md`). Our 1.12 work is T6.1/T6.5 and `docs/parameter-table-growth.md`.
