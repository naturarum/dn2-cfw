Date: 2026-10-06. Images: main OS 1.12 (`out/decomp/main_os`), DSP section 7 of 1.12 (= 1.11, `out/T3.2/mem`).
Marks: **[verified]** = checked against bytes, decompiled code read instruction by instruction, or measured in

## Answer (paused 2026-10-06; best current answer)

**Extra values per send effect: 8 each for chorus, delay and reverb, plus 4 for the compressor (28 in all),
carried to the DSP in the SPI frame's 30 unused tail words and stored in 28 reserved words of each kit's FX
record.** A full 3-band compressor (20 more values) does not fit in that record; it needs more storage (the kit
record's padding [inferred], or a mod-owned side store), not more frame room.

## 1. Frame room

### 1.1 The driver and the tag-only tail (ColdFire) [verified: disassembly of `FUN_400cf922`, emulator run]

`FUN_400cf922(payload_len, src, rx_len, rx_dst)` is called from the frame handler at `0x40025e9e` as
`(0xa80, 0x80005e60, 0xabc, 0x800053a4)` (6-byte `jsr` `4eb9 400cf922`). The test-mode handler `FUN_400d10f4`
also passes `0xa80`. What it does, instruction by instruction:

- It first copies the previous exchange's received frame, `rx_len` bytes from `0x80001a20`, to `rx_dst`.
- It continues only when DSPI2 SR (`0xEC03802C`) bit 28 (EOQF, the previous transfer finished) is set.
- If `payload_len > 0xaf0` it sends the excess over **DSPI1** (`FUN_400cf7f8`, staging `0x80001000`). Never
  taken on stock.
- The transfer length is `min(*(0x42441958), 0xaf0)`; `0x42441958` is set once at boot (`FUN_400cf7ec`) to
  `0xabc`. TX TCD 29: source `0x80002510`, 32-bit entries, destination PUSHR (`0xEC038034`), CITER = BITER =
  `0xabc/2` = 1,374 entries. RX TCD 28: POPR low half to `0x80001a20`, 1,374 x 16 bits.
- The staging buffer `0x80002510` holds one 32-bit PUSHR entry per 16-bit frame word: command half `0x8001`
  (CONT, PCS0), data half = the frame word. **The first loop writes both halves for the `payload_len/2` =
  672 payload words. The second loop writes only the command half (`move.w A0w,(0x0,A1,D0*0x4)` at
  `0x400cfa98`) for entries 672..1373: the data halves of the last 30 entries are never written.** The last
  entry gets EOQ and loses CONT (`0x0801`).
- The staging buffer has room for `0x578` entries (`0x80002510 + 0x15e0 = 0x80003af0`, where the raw mirror
  starts), i.e. for a payload of up to `0xaf0` bytes.

So the SPI frame is always `0xabc` bytes. Bytes `0xa80..0xabb` (30 words, "tag-only") carry whatever the data
halves of PUSHR entries `0x540..0x55d` (`0x80003a12 + 4j`, j = 0..29) hold. In the emulator (`scripts/t60_cf_frame.py`,
60 handler passes with the real driver, SR forced to "done") those halves were `0x0000` before and after, and
the only instructions that wrote anywhere in the staging buffer were the driver's four stores
(`0x400cfa80`, `0x400cfa88`, `0x400cfa98`, `0x400cfab0`) [verified]. Static references to the range: only the
driver [verified, `xrefs.sqlite`]. The DSP boot loader (`FUN_400cf4b0`) uses DSPI2 by PIO, not this buffer.

**Payload words the ColdFire never writes:** with the real handler and driver, 1,343 of the 1,344 payload
words were written every pass; only `0x2a` never was [verified, stopped sequencer; T3.3 found the same
statically].

**Can `payload_len` grow from `0xa80` to `0xabc`?** On the ColdFire, yes as far as the driver goes: it
handles any length up to `0xaf0` with this staging buffer. But the source buffer `0x80005e60` ends at
`0x800068e0` and the smoothed mirror starts at `0x800068e4`, so changing only the `pea (0xa80).w` at
`0x40025e9a` would send the smoothed header words (track levels) in the tail. Growing in place needs a moved
source buffer. It is not needed: the tail's data halves can be written directly (1.4). [verified for the
layout; inferred for "not needed"]

### 1.2 Which frame words the DSP reads (read census) [verified in the T3.6 interpreter]

`scripts/t60_dsp_reads.py` runs the whole stock block handler `0x1c9d6b` with a private build of the
interpreter core that adds a read watch (`out/T6.0/vm/sharcvm.c`: per-byte read counts with the first and
last reader PC; the shared `tools/sharcvm` is imported, not changed). Watched: the frame image `0x25c48c`
(`0xa80` bytes) and both SPI2 receive buffers `0x2c29d0`/`0x2c39d0`. 2,247 blocks: the 247 T3.3 captures; 400
with the global block and header words random; 400 with random per-voice slots, owners, note words and tail;
1,200 with all 16 voices on each machine type 0-4 x filter type 0-5, a note-on on the first block and random
slot values. Reads by the two 672-word copy loops (rx -> image, loads at `0x1c287d` and `0x1c3030`) are
counted apart. Results (`out/T6.0/dsp_reads/summary.txt`, `words.tsv`):

| frame words | read by the DSP? |
|---|---|
| tail `0xa80..0xabb` (30 words) | **never**, not even copied: the copy loops stop at `0xa80` |
| `0x2a` | never (and never written by the ColdFire: unused on both sides) |
| `0xa18` (k 40, Delay FX Routing) | never (T3.4 found no load either) |
| per-voice slot `+0x50` (k 65) and `+0x6e` (k 80), 16 voices each | never, with all 5 machines x 6 filters exercised [inferred beyond that: a parameter-dependent path could still read them] |
| everything else (1,310 payload words) | read |

Five words are read straight from the receive buffer, not from the image: `0x22` (`0x1c2cd6`), `0xa54`/`0xa56`
(`0x1c3084`) and `0xa7a`, `0xa7c`, `0xa7e` (`0x1c3052`, `0x1c3069`, `0x1c309c`, after the copy, through `I5` =
rx + `0xa7a`). So "the DSP reads only the image" is not quite true; it does not change the tail result.

### 1.3 The DSP side of the tail [verified: T3.2 SPI set-up, disassembly, interpreter]

- SPI2 receives `0xabc` bytes per frame (`0x1ca46a(0xabc)`, XCNT = 1,374 16-bit transfers) into 4 KiB
  ping-pong slots `0x2c29d0`/`0x2c39d0` (T3.2 3.4). The tail lands at rx + `0xa80`..`0xabb`, 16-bit words at the
  same byte offsets as the payload.
- The render copies only 672 32-bit words (`lcntr = 0x2a0` at `0x1c287a` and `0x1c302d`) into the image. The
  image cannot simply grow: right after it, `0x25cf10`..`0x25cff0` are live variables of the FX bus
  (`0x1c1943`-`0x1c1a45` read and write `0x25cf10`, `0x25cf14`, `0x25cf2c`.. in `out/T3.1/disasm/main.txt`). New
  DSP code reads the tail from the receive buffer instead: the render gets it as its third argument (`R12`,
  saved at `DM(I6-32)`), and the block handler computes it as `0x2c29d0 + 0x1000 * DM(0x2c0450)` (`0x1ca020`).
- Growing the SPI frame past `0xabc` needs both ends changed (ColdFire `0x42441958`, DSP XCNT in `0x1ca46a`)
  and also the return direction, whose ColdFire buffer `0x80001a20` has only `0xaf0` bytes before the TX staging
  [verified]. Time is the other limit: CTAR0 = `0xfa010000` is 16-bit frames at bus clock / 3; at a 125 MHz
  bus [inferred, not measured] that is ~41.7 MHz, so `0xabc` bytes take ~0.53 ms of the 0.667 ms frame.
  Not worth it: 30 free words are already there.

### 1.4 How a mod carries extra values to the DSP

The frame handler's call to the driver is a 6-byte `jsr` at `0x40025e9e`. A core hook there (an `ev_frame`
event, or one mod's stub) runs at 1,500 Hz in the vector-191 handler, before the driver rebuilds its entries.
It checks SR bit 28 (as the driver does), writes up to 30 words into the data halves at `0x80003a12 + 4j`, and
jumps to `FUN_400cf922` with the stack unchanged. Because the previous transfer has finished and the next one
starts only inside the driver, a set of words is never torn between two frames [inferred from the driver's
EOQF test; not measured on the unit]. Writing the halves from the UI task instead (`ev_tick`) also works but
can tear a multi-word update; then order the writes and add a check word.

The 32 words that both sides leave alone: the 30 tail words, `0x2a` and `0xa18` (k 40; the mod would overwrite
it in the TX buffer `0x80005e60 + 0xa18` from the same hook). The 32 per-voice words (k 65, k 80) are probably
free too but are not needed.

### 1.5 How many values, and the latency

- **Direct:** 30 tail words (32 with `0x2a` and `0xa18`) per frame, every frame: every value reaches the DSP
  one frame (0.67 ms) after the hook writes it, like the stock words (T3.3 6). That is already 8 extra values
  for each of chorus, delay and reverb plus 6-8 for the compressor.
- **Multiplexed:** one word as a slot index and 29 values per frame, slots sent round-robin: 29 x M values,
  each refreshed every M frames (M x 0.67 ms). M = 2: 58 values, 1.3 ms; M = 4: 116 values, 2.7 ms. The stock
  smoothing glides a change over tens of milliseconds (the 3 % per frame one-pole of T3.3, time constant about
  33 frames = 22 ms), so a few frames of extra delay are not audible [inferred]. The DSP side keeps the last
  value per slot; it must accept a slot only from a complete frame, which the frame-handler hook guarantees.
- So the frame is not the limit. **Storage is** (section 2).

## 2. Storage

### 2.1 Where the FX values live [verified: decompiled code read, emulator RAM]

| what | where (1.12) |
|---|---|
| live project | `0x41219970`; live kits at `+0xef371c`, stride `0x5d71` (23,921 B), 129 of them (128 patterns + 1); the frame handler's kit pointer `*(0x800052a0)` = `0x4210d08c` = kit 0 in the T3.3 snapshot |
| live FX setup (`Digisharc::fx_setup_struct`) | live kit `+0x48e4`: 101 words (index = k, the T3.3 mirror index) + the compressor routing long at `+0xca` |
| working project image (the state kept across power-off) | `0x405ce96c` (dnfw's 1.11 `0x405cd85c + 0x110`, shifted `+0x1000`); kit records at image `+0xae0200`, stride `0x2a00` (10,752 B = 21 sectors of 512) |
| +Drive project cache | two image buffers at `0x42c72a80` and `0x438bda90` (stride `0x312c04` longs); `FUN_400f685e(slot)` returns the cached image for a slot (or reuses a buffer without reading the slot), `FUN_400f6b2c` writes it to the +Drive |
| stored kit (`kitStorage` v4, `FUN_400ddfa8` writes, `FUN_400dddb6` reads) | `+0` `0xbeefbace`, `+4` version 4, `+8` name, `+0x1c` 16 words, `+0x3c` 16 sounds x `0x167`, **`+0x16ac` FX record (`0xa0` B)**, `+0x174c` 16 x `0x10c`, `+0x280c`.., `+0x2818` `0x51` B, `+0x2869`.., `+0x28ab` `0xbacef00c`: `0x28af` bytes used of the `0x2a00` slot |

**The FX record, `fxSetupStorage_v0_t` (`0xa0` bytes):** `+0` u32 version (must be 0, or the loader falls back
to the default FX setup `FUN_400e7140`), `+4 + 2*id` the values of ids 0..45, `+0x60..+0x97` **untouched**,
`+0x98` the routing long, `+0x9c` u32 zeroed by the serializer.
- Forward map k -> id: `FUN_400dce5e(0x10, k)`, table `0x401fd160` (70 longs, k 0..69): k 25..59 -> ids 1..35,
  k 68 (master overdrive) -> 36, k 60..67 -> 37..44, k 69 (pattern volume) -> 45, k 0..24 -> 0 (a fold sink;
  out of range also -> 0).
- Inverse map id -> k: `FUN_400dce24(0x10, id)`, table `0x401fd278` (46 longs).
- Serializer `FUN_400dcf34(stored, live)`: writes ids via the forward map for k 0..69, clears `+0x9c`, copies
  the routing long to `+0x98`, writes version 0. **No clear of the whole record.** Callers: the whole-setup
  mirror job `FUN_4002fc34` (from `FxSetup::updateMirror`, `0x4002ffca`) and the kit serializer `FUN_400ddfa8`.
- Loader `FUN_400dcef0(live, stored)`: needs version 0, reads ids 0..45 through the inverse map, the routing
  long from `+0x98`. **It does not clear the live struct** (live k 70..100 keep their values).
- Single edits: `FxSetup::updateMirror` (`FxSetupParamChangedInfo` / `MultipleFxParamsChangedInfo`) writes
  `stored + 4 + 2*map[k]` for the changed k only, into the working image (as dnfw found for sounds, this is
  what makes unsaved edits survive a power-off).
- Kit-record offsets agree with DNX's captures: id 1 (chorus DPTH) at kit `+5810`, id 36 (overdrive) at `+5880`,
  ids 37..45 at `+5882..+5898`, id 24 (k 48) at `+5856` ("constant 1"), the routing long at `+5956`
  ("`+5957` = 7"). DNX's "5900-5956 zero in all 2,176 kits, 28 slots" is exactly `+0x60..+0x97`.
- In the emulator's RAM (T3.3 snapshot) all 387 valid kit records (three images of 129) have the 28 words and
  the padding `+0x28af..+0x29ff` at zero; the live FX setup's k 0..24 and 70..100 are zero.

### 2.2 What survives where

| bytes | stock load | stock save | modded OS |
|---|---|---|---|
| FX record `+0x60..+0x97` (28 words) | ignored [verified, static] | kept by in-place serialization (`FUN_400e15f8` into the working image or a +Drive cache buffer holding the same project); lost or garbage when a kit is serialized into a fresh buffer (exports) [inferred, not run] | survives if the mod hooks the map and both (de)serializers [design] |
| kit padding `+0x28af..+0x29ff` | not read by `FUN_400dddb6` [inferred] | as above [inferred] | the same hooks, at kit level (`FUN_400ddfa8`/`FUN_400dddb6`) |
| stored sound ids 4, 8, .. 32 (dnfw's lfo4 lane) | folded onto slot 0 [dnfw, 1.11] | **zeroed** by a stock re-save [dnfw, 1.11] | per track, not per kit; already used by dnfw's lfo4 |

T2.3's answer for FX: use the 28 reserved FX-record words, with one of them as a check word (magic and
version) so stock-exported kits with garbage there load as defaults; values 0 must mean "default". If more is
needed, the padding (after a check of every reader of kit records) or a side store on the +Drive (dnfw's
Waverider uses sector `0x600000`).

## 3. Plumbing (design, from the 1.12 code)

Stock path for an FX knob [verified, decompiled code; T3.3 for the frame end]: `FxParameterSet::vslot31`
(`0x40037d86`) maps the descriptor row to k with `FUN_400dbe28` (accepts k < `0x65`), stores the value in the live
FX setup word k, then either calls `FUN_4002585a(v, 0x10, k)` directly or sends `FxSetupParamChangedInfo(k)` to
the FxSetup's listeners: `FxSetup::updateMirror` (storage) and `FUN_4003f8ce` (which calls `FUN_4002585a`).
`FUN_4002585a` writes the raw mirror row 16 (`0x800047b2 + 2k`, no bound); `FUN_40025444` copies the whole
setup there on kit change, `FUN_400daffc` jumps the smoother state; the frame handler's smoother
`FUN_400db28e` glides all 101 words of row 16; the frame copies only k 25..69.

For page-2 values the same path works with k 70..97:
- **UI:** descriptor rows (the table `0x401f83a4` is fixed in flash; dnfw relocates it) that map to k 70..97 in
  the FX group, on new pages (T5.0's subject). Or a parallel path: the mod's page writes the live word k,
  calls `FUN_4002585a(v, 0x10, k)` and posts `FxSetupParamChangedInfo(k)` itself.
- **Storage:** without a hook, `FxSetup::updateMirror` would write a k >= 70 into id 0 (the map returns 0), and
  nothing would be saved. Hook `FUN_400dce5e` (58 bytes) so k 70..97 -> ids 46..73, and extend
  `FUN_400dcf34`/`FUN_400dcef0` (or wrap them) to write and read ids 46..73 (`+0x60..+0x97`).
- **To the DSP:** a core event at `0x40025e9e` (section 1.4) copies smoothed row-16 words k 70..99
  (`0x800068e4 + 0xcc2 + 2k`) into the tail. Smoothing is the stock one, for free (proved, section 4).
- **DSP:** new code reads rx + `0xa80` (section 1.3) and scales like the stock unpacker (x 1/32512).

## 4. Proof of concept (frame path, end to end) [verified in the emulators; nothing flashed]

1. **ColdFire** (`scripts/t60_cf_frame.py --poc`, digikit's emulator, T3.3 main-screen snapshot): test values
   (`v << 8`, 30 distinct) go into FX k 70..99 through the stock setter, as a page turn would. A
   30-instruction 68k routine, hand-assembled into SRAM `0x8000F980` (emulator RAM only), replaces the `jsr` at
   `0x40025e9e`: if SR bit 28 is set it copies smoothed row-16 k 70..99 into the tail data halves, then jumps to
   the stock driver. 300 handler passes: the driver's TCD 29 is armed for 1,374 entries (EOQ on the last), the
   tail data halves were written only by the test routine (`0x8000f99a`), the 30 tail words equal the smoothed
   k 70..99, and smoothed k 70 equals stock k 27 (given the same value) on every pass (384, 570, 661, .. 746).
   The absolute values are the emulator's (its EMAC fractional mode is wrong, T3.3); on the unit they settle at
   the stored values [inferred, T3.3]. Wire frame saved: `out/T6.0/cf/main720M-poc.wire.bin`.
2. **DSP** (`scripts/t60_dsp_poc.py`, T3.6 interpreter): that wire frame goes into the SPI2 receive buffer as the
   DMA leaves it, and the stock block handler runs 300 blocks with noise input. **Output is bit-identical to the
   same frame with the tail zeroed.** New DSP code (`scripts/t60_probe.c`, built with selcc, linked by
   `scripts/t60_probe.ldf` into free L1 `0x2e2000`, verified zero in the DN2 image) is called after each block
   with the receive buffer the handler used: its 30 floats equal the tail words x 1/32512 exactly, every block
   (1,187 instructions per call at -O1).

Census without the PoC (`--passes 60`, stock code only): `out/T6.0/cf/main720M-census.json`.
