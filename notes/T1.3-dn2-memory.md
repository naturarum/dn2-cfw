## The reset code

`m68k-elf-objdump -D -b binary -m m68k:cfv4e --adjust-vma=0x40000400` on
`ele3_out/02_type3.unpacked.bin` (sha256 `a098f620...`). [verified]

```
400004e8  lea 4(sp),a0 ; move.l (a0),0x40287a60     save the boot flags the bootstrap passed
400004f2  movea.l #0x48000000,sp                      the stack top
4000052c  jsr 0x40001992 ; jsr 0x40001c14 ; jsr 0x400019b0
4000053e  jsr 0x4000045c                              SRAM copies
40000542  jsr 0x400004b2                              DDR clear
40000554  movec cacr (0xa50ce100) ; movec acr0 (0x4007e020)
40000568  jsr 0x40186fa2                              the OS's init (RTOS start)

4000045e  lea 0x402fd000,a2 ; lea 0x80000000,a1
4000046e  loop: move.l (a2)+,(a1) ... until a2 >= 0x40305000     copy 1 (32 KB)
4000047c  clr.l (a0)+ until a0 >= 0x80008000                      (runs once: 0x80008000)
40000486  lea 0x40305000,a2 ; lea 0x80008000,a1
40000492  loop: move.l (a2)+,(a1) ... until a2 >= 0x4030c980     copy 2 (0x7980 bytes)
400004a4  clr.l (a0)+ until a0 >= 0x80010000                      zero 0x8000f980-0x80010000

400004ba  movea.l #0x402fd000,a0 ; move.l #0x466b84d0,d1 ; d1 = (d1 - a0) >> 4
400004d2  loop: movem.l d4-d7,(a0) ; lea 16(a0),a0 ; subq.l #1,d1 ; bne     clear DDR
```

- The clear starts at `0x402fd000`, inside the image: the image's last 62,848 bytes are the
  (all-zero) SRAM init data, copied first and then cleared in DDR. So a format-1 blob appended
  at the image end (`0x4030c980`) is cleared at reset, as on the Digitakt II; whatever uses it
  has to copy it out before `0x40000542` (core-dt2 does this from the site `0x40000538`, which
  holds the same `jsr 0x400019b0` here). [verified] bytes; [inferred] that a DN2 core can use
  the same site.
- ACR0 `0x4007e020` maps `0x40000000-0x47ffffff` cacheable [inferred from the MCF5441x ACR
  layout], so `0x48000000-0x4fffffff` is the uncached view the OS uses for DMA buffers, as on
  the Digitakt II.
- The boot watch (below) saw the stack go down only to `0x47ffffcc` from reset to 400M. After
  the RTOS starts (task creation at 26.2M instructions), every task runs on its own stack in
  the cleared `.bss` (e.g. `0x42439900`, `0x4059ea34`, size `0x28000`). [verified] in the run.

## Static references (what names the candidate areas)

Three scans, by `scripts/t1.3_refs.py` (output `out/T1.3/refs-ddr-top.json`,
`out/T1.3/refs-sram.json`): every absolute operand in a linear objdump sweep of the whole image
(1,073,564 lines, 312,262 undecodable); Ghidra's `data_refs` (`out/decomp/main_os/xrefs.sqlite`,
which follows flow); and every big-endian 32-bit word of the image. Code ends at `0x401d07fb`
(the last Ghidra function below the panel blob); sweep hits above that are data decoded as code.
A computed address (base + index) is invisible to all three, hence the runs below. [verified]

DDR above the clear, `0x466b84d0-0x48000000`, and its alias `0x4e6b84d0-0x50000000`, hits
inside code only:

|---|---|---|---|

| `0x40172a7a`, `0x40173014` | `0x47efffff` | high word of the double `FLT_MAX` (as on the DT2) | [verified] value; [inferred] meaning |

the objdump sweep stands in for it.

SRAM, `0x80000000-0x80010000`: 547 objdump and 428 Ghidra hits in code. The highest address
named is `0x8000dea4`, the base of 17 rows of 404 bytes (`FUN_400daffc`: `move.l #202,d1` at
`0x400daffe`, `addi.l #0x8000dea4,d0` at `0x400db014`; `FUN_40025444` writes row `0x10`,
`FUN_4002549c` the row its caller gives, a track index [inferred]), which end at `0x8000f978`.
At 799M the highest non-zero SRAM byte is `0x8000f8f8`, inside row 16. Nothing names `0x8000f980-0x80010000`,
and no 32-bit word in the code holds an address in it. [verified]

## Runs in the emulator

digikit's emulator on branch `dn2-1.12` (notes/T1.1). digikit maps a 1 MB page on its first
access, read, write or fetch (`emu/harness.py`, `Machine._fault` and `ensure`), so a page that is
never mapped was never touched. [verified] in the code.

- **Cold boot, reset to 400M instructions** (`scripts/t1.3-watch.sh boot`, through
  `scripts/t1.3_bootwatch.py`; `out/T1.3/boot.log`, `boot.json`). Write watches on
  `0x466b84d0+0x7b30` (above the clear), `0x466c0000+0x50000` (the buffers' cached view),
  `0x46710000+0x18e0000` (to `0x47ff0000`), `0x47ff0000+0x10000` (stack top),
  `0x4e6b84d0+0x7b30` and `0x4e710000+0x18f0000` (the alias), `0x8000f980+0x680` (SRAM tail, as
  two watches), and the RTOS's current-task pointer `0x4664bcdc` as a positive control. Result:
  451 writes. None in the DDR or alias ranges; 26 on the stack top, lowest `0x47ffffcc`; 416 in the
  SRAM tail, all `clr.l` from `0x400004a4` at 97K-98K instructions; 9 on the task pointer.
  Pages mapped at the stop: none of `0x46700000-0x47efffff`, only `0x47f00000` (the stack's), and
  none of the alias above `0x4e700000`. [verified]
- **Session, 400M to 800M** (`scripts/t1.3-watch.sh session`; `out/T1.3/session.log`,
  screens `session-320M/425M/495M/600M/790M.png`, snapshot `session799M.snap`). From the
  ladder's `boot400M` rung, 32 key presses and releases and 7 encoder turns, through several
  pages (an LFO page at 495M). The same watches: 0 hits in every DDR, alias and SRAM-tail range,
  10,105 on the task pointer; guirun reports no newly mapped page. [verified] (run by the
  interrupted run; its log and screens checked here.)
- **Snapshots** (`scripts/t1.3_snapscan.py`; `out/T1.3/areas-scan.txt`). Over the ladder's rungs
  at 60M, 120M, 200M, 280M, 400M and the session's 799M: `0x46800000-0x47f00000` and its alias
  `0x4e800000-0x4ff00000` never mapped; `0x466b84d0-0x46800000` mapped (page `0x46600000`) and all
  zero; the stack page holds 37 non-zero bytes, all in `0x47ffffd0-0x47ffffff`; the SRAM tail all
  zero. [verified]
- **The watch method.** The interrupted run's boot watch crashed at the end, reading back a
  watched range with unmapped pages, so it had no summary; its hits were complete. Three
  27M-instruction probes
  (`out/T1.3/probe-*.log`) checked the method: a 25 MB range (`0x46710000+0x18f0000`) logs exactly
  the 26 stack writes a 256-byte range logs, with the same counts, and the nine-watch set logs
  them too. So big ranges do not lose writes. [verified]

## Why these areas

- DDR `0x46800000-0x47f00000`: 1 MB above the highest buffer the code names (`0x46709340`
  cached), and 1 MB below the stack top, whose page is the only one the runs touch there. All of
  it static-clean, never mapped in any run, never written. [verified] in emulation. Paths the
  emulator does not run could still reach it through a computed address; nothing found suggests
  one (the heap lives in `.bss`: task control blocks at `0x46679e7c`, `0x445e7764`, below the
  clear's end). [inferred]
- SRAM `0x8000f980-0x80010000`: the reset zeroes it after the copies; no code names it; only the
  reset writes it. It is free at run time only, not at the boot site, as on the Digitakt II.
  [verified] in emulation.
