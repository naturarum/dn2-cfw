Owner, 2026-10-31: "yes it plays all the way to 127, rebuild the spring builds. Let's get this whole thing ready for a
release", "I would like to remove the notice in the digiwerk patcher that some builds have not been tested ... But at

base firmware". Marks: **[verified]** = built, run in sharcvm, the emulator or the brick checker, file named;
**[inferred]** = reasoned; **[unit]** = played on the owner's Digitone II.

## 1. What changes from 0.2.1

- **Base 0.3** = base 0.2 (BA05's six mods) + **usb-multi 0.3** (UM03's: USB MULTI/MIDI, the fourth USB CONFIG
  choice; notes/USB01-class-compliant-multichannel.md, UM03 section). Main OS only, no DSP code; its run image and
  .bss add about 2.6 KB to the mods' 1 MB DDR region (UM03: 0x47e00000-0x47e075a4).
- **The six spring builds come back** (EEES, CEES, EFES, EETS, CFES, EFTS), their DSP sections rebuilt with the
  peephole pass left off spring.c (recipe key `peephole_skip`, as SX04, which played every stage on the unit:
  notes/SP02-spring-pack.md section 6). CFES no longer reuses SP02's section: it is built from its pack recipe like
  the other ten.
- Every build changes (the base), so no 0.2 unit-test date carries over: `tools/patcher/packs/*.json` have
  `tested_on_unit` "" until the owner plays each 0.3.0 file.

## 7. EFES locks the DSP; 0.3.0 ships eight builds (4 Nov)

- **CFTE on usb-multi 0.4 [owner, 4 Nov]:** 42 inputs, a few minutes recorded clean.
- **EFES locks [owner, 4 Nov], twice, USB MULTI/MIDI on:** once on a pattern change, once after 30-60 s of playing
  with a feedback building (the flanger or Elektron's delay). The screen keeps working; the sound freezes in silence
  or a buzz: the signature of 0.2.0's CFES and EFTS (30 Oct), whose cause is still open.
- **What the code rules out [read, 4 Nov]:** every ring index of the spring and the flanger is masked (no write outside
  their buffers); every feedback path is clipped inside its loop (the flanger's FL_FBMAX 0.99 with fx_sat, the
  spring's FX_CLAMP ±1.5 then y - 0.148y³, the stock delay's x(2-|x|) at 0xb84099), so nothing grows without bound.
  sharcvm models no interrupts, so a cause that needs one, or the chip's timing, can't show there.
- **A latent frame defect [found 4 Nov; harmless as the code stands]:** selcc's `fx_sin_q` (frame 8) stores R15 at
  DM(-0xA,I6) and `fx_cos_q` (frame 7) R14 at DM(-9,I6): one word below the frame, at I7 itself, where an
  interrupt's push can land. Callers: fl_sin2pi (flanger_lfo), fx_svf_g (fl_hpf_coef), sp_tpt (sp_coefs). R14 and
  R15 are live only in sp_input and flanger_process, which save both at entry and restore them at exit, and nothing
  reads the slot back after the call, so a clobber changes nothing today. To fix in the next DSP rebuild. Found by a
  frame-offset check over every build's `.s` (4 flags per effect file, all in these two functions).
- **Decision [owner, 4 Nov: "yes, go ahead with the eight"]:** 0.3.0 = 0.2.1's eight builds + multitrack USB. The six
  spring builds stay out, as in 0.2.1; the spring is shelved, no date. For each of the eight, the DSP section
  (`section7` sha256) is 0.2.0's, and the mods differ by exactly one, usb-multi 0.4 [verified: `out/ID/build-ID.json`
  against `out/release/0.2.0/builds/ID/build-ID.json`].
- **Changed for it [4 Nov]:** `scripts/release_tables.py` (PACKS: the eight), `app/test.sh` (REL the eight, the
  fourteen kept as a test set), `app/screens.sh`, `web/build.mjs`, `web/test.mjs` (its default note),
  `web/test-model.mjs` (8 built, the six spring combinations not built, the spring tile notBuilt); the release notes
  (no SPNG; "The six builds with the spring reverb stay withdrawn, as in 0.2.1"); the README back to 0.2.1's spring
  text, plus USB. [verified: web build, test-model, test.mjs on all fourteen, app/test.sh (incl. the fourteen),
  release_tables --check: all pass, `out/release-0.3.0-eight-tests.log`]
- **The owner's round:** `out/device-tests-0.3c/` (01-CFTE … 08-EEEE, copied from the second set, each checked against
  its build's sha256): CFTE an hour or two with USB MULTI/MIDI on, played the way EFES locked; a minute on each of

- **CFTE [owner, 4 Nov]: ok, about an hour of playing, no lock.** `packs/CFTE.json` tested_on_unit "4 Nov 2026", the
  pack remade (rebuilds ff646e5e, web core PASS), the tables rerun.
- **CETE, CFEE, EFTE, CEEE, EFEE, EETE, EEEE [owner, 4 Nov]: ok**, a minute of a pattern each (CFEE after the transfer
  freeze below). All eight `tested_on_unit` "4 Nov 2026"; packs remade (each rebuilds its build's sha256); the
  catalog's "NOT YET TESTED ON A UNIT" sentence dropped; tables rerun.
- **The CFEE transfer froze on "SUCCESS! REBOOTING" [owner, 4 Nov]:** the whole unit unresponsive; switched off and
  on, CFEE starts fine. Elektron's writer FUN_40139104 shows the message after the last write, waits
  (FUN_4013492c(3000000)), sets SR 0x2700, then FUN_400023f6 spins while UART8's output counters are above 0
  (0x4058e5d8, bytes queued for eDMA channel 35, handed on only by its done-ISR FUN_40001e7c; 0x4058e5e8, the
  interrupt-fed path FUN_40002340), then waits for UART8 TX empty, then writes 0x48000000 (the restart). With
  interrupts masked, anything still queued at that instant never drains: a hang in stock code after the write.
  [verified: out/decomp/main_os disasm] None of our mods writes UART8 or calls its two output functions [verified:
  grep]. Whether USB MULTI/MIDI makes it likelier is open (asked which USB CONFIG was on). Flash wear: SPI NOR,
  S25FL-S class per digikit (the DN2's part unconfirmed); that family is rated 100,000 erase cycles per sector,
  one per transfer.
