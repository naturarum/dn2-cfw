## Result

`scripts/dn2-live.sh` opens a window on the 1.12 main screen in about a
second and plays the unit from the Mac keyboard in real time: every button,
the 8 encoders, the LEVEL/DATA encoder and the encoder pushes have a key,
holding a key holds the button (FUNC and TRK chords work), and a key press
changes the screen in a median 52 ms. Headless runs of the same input path
prove an encoder step on SYN 1, FUNC menus, trig keys and arrows
(`out/T2.4a/proof/`). [verified]

Three things had to be fixed on the way, and they matter beyond this task:

1. **Idle skipping** makes the emulator run at 1.95x real time on the main
   screen instead of 0.22x. [verified]
2. **Encoders did not work** with one count per detent: the firmware's
   encoder filter swallows small, slow rotation. A detent model now gives one
   parameter step per key press. [verified]
3. **DTIM0, the firmware's time base, read 0 for ever** in the emulator,
   because no code in the firmware file programs it. It now counts.
   [verified that it was 0 and is never programmed; its real rate is
   inferred]

## Panel code map on 1.12 [verified]

Measured with digikit's own method, `tools/panelsweep.py`, from
`boot400M.snap`: it hooks the firmware's `queue_send` (`0x40001896`, bytes
checked by `emu/symbols.py`), injects every (channel, bit) through the UART8
receive path and reads the 16-byte event record the firmware emits.
Log and JSON: `out/T2.4a/panelsweep.log`, `out/T2.4a/panelsweep-dn2-1.12.json`
(125 s wall).

- Button records come from return address `0x4011fe18` (type 0, flag byte at
  +0x0B: `0x01` press, `0x10` release); encoder records from `0x4011fa60`
  (type 1, signed delta at +0x08). Sink queue `0x4664bce8`.
- Channels 0-5: code = channel * 8 + bit + 1 for all 48 positions.
- Channel 6: bit 0 -> 50, bit 1 -> 49, bit 4 -> 51, bit 5 -> 52, bit 6 -> 53,
  bit 7 -> 54. Bits 2 and 3 report code 0 (UNDEFINED): no control there.
- Encoder channels 0-8 report codes 1-9; the delta is signed (+1, +5, -1
  read back as sent).

This is exactly the `[panel]` table in `devices/digitone-ii.toml`, so the
existing map holds for 1.12 and nothing in it needed changing.

## Launch

```sh
scripts/dn2-live.sh                     # window, real time
scripts/dn2-live.sh --speed 0           # as fast as the Mac allows
DN2_SNAP=other.snap scripts/dn2-live.sh # start from another snapshot
```

The launcher runs `uv run python -m emu.live <snapshot> --syx
elektron-firmware/Digitone_II_OS1_12.syx` in `vendor/digikit` with
`DT2_SECTIONS=out/sections/dn2-1.12`. Default snapshot:
`out/T2.4a/warm/warm800M.snap`, taken 800M instructions after `boot400M.snap`
with timers saved (main screen up, +Drive set-up finished, idle):

```sh
cd vendor/digikit
DT2_SECTIONS=out/sections/dn2-1.12 uv run python tools/guirun.py \
  out/snapshots/dn2-1.12/boot400M.snap \
  --syx ../../elektron-firmware/Digitone_II_OS1_12.syx --limit 800000000 \
  --save-at 800M:../../out/T2.4a/warm/warm800M.snap      # about 3 min
```

`--save PATH` stores the state when the window closes; that file launches
again (checked: a snapshot saved in the kit SETUP menu reopens on it and the
arrows keep working). Other options and the headless mode: `vendor/digikit/docs/LIVE.md`.

## How the firmware takes panel input on 1.12 (what live control had to match)

Read from `out/decomp/main_os` and checked by running. Addresses are 1.12.

- **Panel driver timing** [verified: image bytes and runtime memory agree].
  `FUN_401200c4` registers `FUN_4011f8bc` on the RTOS timer wheel with mask 1
  (`jsr 0x40002aa4` with `(0x4011f8bc, 1)`), so it runs on every PIT2 tick
  (60 Hz) [inferred from the wheel masks in digikit's emu/pit.py]. It
  flushes accumulated encoder deltas every `[0x4029f0c0]` = 4 ticks (15 Hz,
  66.7 ms), clamped to +/-30, as type-1 records to queue `0x4664bce8`. Key
  auto-repeat starts after `[0x4029f0c8]` = 24 ticks and repeats every
  `[0x4029f0c4]` = 8 ticks; a second press within `[0x4029f0cc]` = 32 ticks
  is flagged as a double press (flag 5).
- **Encoder receive** `FUN_4011ff0c`: adds the delta to the accumulator
  `0x46676814 + 8*n` unless the direction reverses inside one flush (then the
  new delta is dropped), and ignores rotation for 40 ticks after an encoder
  push is released with little rotation (`0x445a1d9c`). [verified: decompile]
- **Main loop** case 1 (`0x4002f21e`-`0x4002f268`) builds an `EncoderEvent`
  (`FUN_4011332c`: +0x8 DTIM0 time stamp, +0xC encoder, +0x10 delta, +0x14
  push held, from `FUN_4011fac4(code + 0x28)`) and offers it to the views
  (`FUN_4002c55c` -> `FUN_4011dfe8`). [verified: decompile]
- **The encoder filter** `FUN_4011364e(handler, encoder, delta, cfg, pushed)`,
  shared by 28 views (`ParameterPageView::vslot17` `0x40067470` and every
  menu). State per encoder at `handler + 0x20 + 20*n`: +0 a countdown set to
  40, +8 velocity, +12 accumulated counts, +16 an idle meter. The tick
  `FUN_40113594` raises the idle meter by 1 up to 48 and decays the velocity
  by 2/3. While the meter is at 25 or more, rotation only lowers it by
  3 * |counts| and is swallowed; below 25, counts accumulate and
  `(counts / divisor) * stepmult * max(1, |velocity|)` steps are taken,
  `divisor` and `stepmult` from the parameter's config (+4 normal, +0x10 with
  the push held). LEV1's config: divisor 3, stepmult 1, pushed stepmult 4.
  [verified: decompile, and a probe hooked on the function's entry printed
  the config and the state for each call]
- **Consequence.** With one count per key press, nothing changed: 8 single
  counts on encoder A left TUN1 at 0.00, 8 on encoder D left LEV1 at 90, and
  a single +5 did nothing. Larger, faster deltas changed it by a few units.
  [verified: `out/T2.4a/try/`, before the fix] So the unit's encoders deliver
  many counts per turn, and keyboard control needs its own detent model.
- **The detent model** (`--encoder-mode step`, default): a code hook on
  `0x4011364e` (anchor bytes `4fefffd0 48d77cfc 142f0047 266f003c 206f0040`
  checked before it is installed) clears velocity, accumulator and idle
  meter and passes `n * divisor` counts for `n` keyboard detents. One key
  press = one step of that parameter, press-and-turn = its pushed step.
  Measured: LEV1 90 -> 94 after 4 presses, -> 92 after 2 Shift presses,
  -> 96 after one press with F4 held; track LEVEL 100 -> 103 after 3
  presses of 9; in SETTINGS each press of 9 moves the selection one row.
  [verified: `out/T2.4a/proof/1*.png`, `out/T2.4a/measure/level-sheet.png`]
  TUN1 moves 1/256 per step (8 presses showed 0.03) [verified], which is
  the finest step of that parameter's config.
  `--encoder-mode raw --raw-counts N` sends N raw counts per press instead.
- **DTIM0.** Every key and encoder record and tap tempo read DMA timer 0's
  counter (`0xFC07000C`; readers `0x400cece6`, `0x400dba98`, `0x4010d6e4`,
  `TapTempoView::vslot05`, `0x4011f8bc`, `0x4011fc8c`, `0x4011ff0c`,
  `0x40120644`). Neither the main OS nor the bootstrap writes any DTIM0
  register (`mmio.tsv`: the main OS only reads DTCN0, the bootstrap has no DTIM0 reference) [verified], so the code
  that starts it runs before them, from flash below `0x40000` [inferred],
  and in the emulator the counter read 0 [verified: snapshot memory]. emu.live
  makes it count at 132 MHz of emulated time. The rate is a guess: with
  132 MHz, tap tempo's constant `0xdd47440` gives 14,400 for 120 BPM, a
  plausible fixed-point tempo but not checked. It does not affect the
  detent model.
- **Redraw.** The UI task's render check `FUN_4002e322` runs on every DTIM3
  tick (30 Hz), but renders only when the screen object's dirty flag
  (`0x44671650` in this run) is set. On the idle main screen that happens
  once per emulated second; a page key sets it at once (write from
  `0x4011d5e4`). [verified: `--at`/`--watch` runs with tools/guirun.py]

## Speed and latency [verified: measured]

Apple M2 Pro, 1.12, `warm800M.snap`, main screen, 20 s per run. JSON
reports in `out/T2.4a/measure/*.json`.

| run | emulated s per wall s | instr/s | not skipped |
|---|---|---|---|
| as fast as possible, idle skipping on | 1.95 | 36.5M | 25% |
| as fast as possible, idle skipping off (digikit's GUI loop) | 0.22 | 4.2M | 100% |
| real-time pacing (the default) | 1.00-1.01 | 18.7M | 25% |
| after PLAY, as fast as possible | 1.96 | 36.8M | 25% |

- "Real time" is the timer clock: 18.72M instructions per emulated second
  after the intro (digikit's 4x rate; the real CPU is about ten times
  faster, docs/findings/03-ui-and-panel.md). The same unit emu/gui.py and
  tools/guirun.py report in; their warm run in this task logged 4.1M instr/s
  = 22% of real time (`out/T2.4a/warm/guirun-warm.log`).
- Where the time went: at idle, 75% of instructions were the priority-0
  task's `bra.s *` at `0x400cf246` (tools/guirun.py --trace-tasks), each
  pass costing two Python callbacks. Idle skipping ends the timer step there
  after one reschedule (vector 32) and credits the rest of the step; nothing
  but an interrupt leaves that loop and interrupts are only delivered between
  steps, so the guest sees the same order of events. The RTOS idle
  `0x40001c08` is skipped without the reschedule.
- Snapshot load 0.7-0.8 s; first frame on screen 0.7 s after start.
- **Key press to changed screen**, 28 presses spaced 1.2 s (arrows, page
  keys, encoder D both ways, trig keys): median 52 ms, range 22-146 ms wall;
  median 35 ms of emulated time. Input waited a median 0.1 ms (max 23 ms)
  in the inbox before reaching the firmware.
  (`out/T2.4a/measure/latency.json`)
- Every key of the sweep: median of the per-run medians 78 ms, max 357 ms
  (44 runs with a visible change).
- In the window itself (Tk, withdrawn, key handlers called directly):
  controls built, FUNC + FLTR opened SETUP, `?` opened and closed the map,
  reaction 56 ms (`out/T2.4a/measure/tk-smoke.png`). [verified]

## Limits

- **No sound.** The DSP is not emulated.
- **PLAY does not start the sequencer.** After PLAY the screen stayed
  byte-identical to the idle frame for 20 s, with the same CPU load
  [verified]. The likely reason is that the audio-rate SSI0/eDMA interrupt
  chain (eDMA50 -> vector 170 -> forced vector 191), which paces the
  ColdFire-DSP frame exchange, is not modelled in this configuration
  (digikit has an opt-in, DT2-derived model, emu/ssi.py, whose board clock
  is unknown) [inferred, not tested]. So sequencing, the arpeggiator and
  anything time-driven by the audio clock cannot be checked in the
  emulator yet. FUNC + PLAY still clears ("Cleared 1 sequence!").
- **Empty +Drive.** Reads return no data, so nothing can be loaded and saves
  are refused ("Prj must be re-saved!").
- **No LEDs, no MIDI.** Trig and key LEDs are not drawn; MIDI is not wired
  (T2.4 part two).
- **Encoder feel.** The detent model gives exact steps, not the real knob's
  dead zone and acceleration; `--encoder-mode raw` keeps the firmware's
  filter.
- **Speed.** 1.95x headroom on the main screen on an M2 Pro; heavier views
  were not measured one by one. If the Mac cannot keep up, the emulated
  clock lags (at most 0.25 s, then it lets go rather than fast-forwarding).
- **Layout.** US ANSI keysyms. Shift + digit is folded back with a US table;
  other layouts may need `--keymap`. F1-F8 need fn on Mac laptops unless
  "Use F1, F2, etc. keys as standard function keys" is on.
- The window was driven by calling its key handlers, never by a person on a
  real keyboard: Tk's key repeat and keysyms on macOS are not observed.

## Open problems

- Someone should play the window once on the Mac and say whether key
  repeat, Shift and the F-keys behave; the headless runs cannot show that.
- The sequencer: try digikit's opt-in SSI0 model (`emu/ssi.py`) with a
  request rate for 1.12 and see whether PLAY then runs. Needed before
  sequencer or arp mods can be tested in the emulator.
- DTIM0's real rate (affects tap tempo only). Tap tempo on the unit
  against the emulator would settle it.
- The 1 Hz redraw on the static main screen: what sets the dirty flag once
  a second was not traced (harmless: changes redraw at once).
- The detent hook and `RTOS_IDLE` are 1.12 addresses with an anchor check;
  a signature in `emu/symbols.py` would make them follow other builds.
- Upstream: emu.live, the idle skip and the DTIM0 counter are candidates for
  digikit (C1), after the user has tried it.
