# T6.1: can the parameter descriptor table grow? (study)

Date: 2026-10-12. Firmware: Digitone II OS 1.12, main OS at `0x40000400` (`out/decomp/main_os`).
Marks: **[verified]** = checked against the bytes, read instruction by instruction, or measured in an
emulator run named in the line; **[inferred]** = reasoned from structure, not run.
Emulator and static analysis only: nothing built for the unit, nothing flashed, nothing committed.

The owner's question: "Do you think we can confidently grow the table? I took it as off limits."

## Answer

**Yes, with conditions. Confidence: high that the table itself can be grown safely; medium that a
grown build behaves like stock everywhere, until a cold boot in the emulator and a short session on
the unit confirm it.**

Why it is less dangerous than it looked:

- **Row ids are never saved.** Kits, sounds, patterns, p-locks, LFO destinations and the mod-source
  destinations are all stored by the parameter's slot `k` (descriptor `+0x04`), through fixed
  `k` → stored-id tables. Rows exist only at run time. Growing the table therefore cannot, by
  itself, change how any project is stored or read. What a new row *can* do to a project depends
  only on the `k` it uses and on two flags, below. [verified: the kit, sound and p-lock serializers
  and loaders read, and the p-lock records the emulator wrote, section 3]
- **The table is reached in few, simple ways.** 56 instruction operands hold its address and 58
  compares hold its row count. All 114 are same-length operand edits, found by a raw scan of the
  image, not only by Ghidra's references. Nothing else in code or data points into it. [verified]
- **The relocation works in the emulator.** With the table moved to our DDR, all 114 operands
  patched and the boot-time map builder re-run, 25 screens over the main pages are byte-identical
  to stock and the rebuilt slot and CC/NRPN maps are identical to stock. With 8 real rows added and
  placed on the delay, reverb and chorus pages, the new knobs draw, turn, show their value text and
  write the kit's FX setup through the stock setter. [verified: hot-patch, section 5]

The conditions (each found and proved here):

1. **Three more structures depend on the row count**: the display table in RAM (glyphs, lock flags,
   randomiser), the `ParameterUpdateCache` used by MIDI CC/NRPN input (17 lanes x 0x141 rows), and
   the maps built at boot from the table. The first two cannot grow in place. [verified]
2. **The `ParameterUpdateCache` must be resized (or new rows kept out of it) before any new row gets
   a MIDI CC or NRPN.** In the emulator, a CC to a new row corrupted the cache's other bank, and the
   next flush sent bogus parameter changes for track 1 (rows `0x18`, `0x19`). [verified]
3. **A new send-FX row must be marked "not lockable" in its display flags.** Lockability comes from
   the display table (bits 0 and 3), not from the parameter's group. A new FX row copied from a
   lockable template took a p-lock in the emulator, and the lock was stored as a lock on the track's
   *sound* slot with the same `k` (filter envelope delay): user data damage that a stock OS would
   play back too. With the flag set, no lock is taken. [verified]
4. New rows must use a `k` that is free in their set and persistent in the stored format, and a
   value of 0 must mean "classic behaviour" (stock writes 0 into slots it has no row for). [verified
   for the maps; the rule is design]

**With the owner's preference** ("FX need no p-locks, but new synth or filter parameters must be
p-lockable"):

- **Send-FX knobs do not need growth yet.** The delay and reverb pages each get one more knob from
  the unused routing rows, by data alone (path c, proved in the emulator, saved per kit by stock
  code). The 11 dead ERR rows give 11 more. Growth is needed only past about 13 new FX knobs (second
  pages, the 3-band compressor).
- **Growth matters most for synth parameters**, and there it fits well: p-locks, LFO destinations,
  MIDI CC and save/load all key on `k`, and every machine has free, persistent `k` in its own window
  (FM Tone 2, WaveTone 15, FM Drum 10, Swarmer 32, the unused 5th machine 40). A new row there gets
  all of it from stock code. **The real limit for "new filter parameters" is storage, not rows:**
  the shared filter/amp/LFO block has no free persistent slot (section 3.2).

## 1. The two paths, rated against the owner's preference

| | send-FX knobs (no p-locks wanted) | synth / filter knobs (p-locks required) |
|---|---|---|
| **grow the table** | works; buys MIDI CC in/out once the cache and the CC-out channel check are fixed; storage still needs T6.0's reserved-word hooks for `k` 70+; no LFO either way (FX are not LFO destinations on stock) | the right tool for machine parameters: one row per parameter in a free machine slot gets p-locks, LFO destination, CC/NRPN, save/load and stock-compatible files from stock code; for shared filter parameters it is not enough (no persistent slot) |
| **values outside the table** (label hook, own page, kit reserved words) | acceptable: keeps per-kit save/load (with T6.0's hooks) and gives up only MIDI CC in/out, Overbridge, the help bubble/value text unless re-implemented, and the stock knob handling; more UI code than any other path | not acceptable: no row means no p-lock, no LFO destination and no MIDI CC |
| **ERR rows** (11, no growth) | cheapest real rows for chorus E/F etc.; everything stock-like; shared budget | possible for a few machine parameters (same rules as growth) |
| **routing rows on the empty slot** (delay G, reverb G) | cheapest of all: one knob per page, data only, stock storage | not applicable |

## 2. Inventory: everything tied to the row count or indexed by row id

### 2.1 The descriptor table [verified]

- `0x401f83a4`, 0x141 rows x 0x3c bytes = `0x4b3c` bytes, ending at `0x401fcee0`.
- **It cannot grow in place:** `0x401fcee0` is the start of another table (`0x48` bytes copied by the
  sound-format upgrade `0x400e0642`), followed by the `k` ↔ stored-id tables (`0x401fd160`,
  `0x401fd278`, `0x401fd330`, `0x401fd4c0`). dnfw found the same on 1.11.
- Row layout (as dnfw's modulation-mask doc gives it, re-checked on 1.12): `+0x00` group, `+0x04`
  `k` (slot), `+0x08` min, `+0x0c` max, `+0x10` default (all `<< 8`), `+0x14` bipolar, `+0x18`
  CC (s16) and `+0x1a` a second CC (s16; the LSB of a 14-bit pair), `+0x1c` NRPN, **`+0x20` a unique
  parameter id (0..387 with gaps, used for Overbridge, 2.9)**, `+0x24` modulation mask, `+0x28`
  long name, `+0x2c` group name, `+0x30` short name, `+0x34` formatter (a function), `+0x38` suffix.
- Row ids are also data in code: page records, page-view special cases, predicates (2.7).

### 2.4 Loops over all rows [verified]

| function | what | effect of growth |
|---|---|---|
| `0x400dc634` (bound `0x400dc954`) | the boot-time builder of the slot tables and CC/NRPN maps (dnfw's `param_set_tables_build`) | new rows are filed by their group and `k`; **last write wins** per slot and per CC, and appended rows come last, so a new row with a taken `k` or CC silently replaces the stock row |
| `0x4004b0b4` (bound `0x4004b17a`) | a sound randomiser (names the sound "RANDOM"): for every row whose display entry has a `+0x24` function, writes a random value into the sound's slot `k` | a new FX row with `k` 70+ and a copied randomiser would write sound slots 70+ (filter, amp): give new rows no randomiser, or one that fits [inferred: routine read, not run] |
| `0x400394be` (bound `0x4003950a`) | collects the rows of one machine (for a partial kit load, `0x400446c2`) | new machine rows are included |

### 2.5 Structures sized by the row count

| structure | where | size | growth |
|---|---|---|---|
| descriptor table | image `0x401f83a4` | `0x4b3c` | relocate (2.1) [verified] |
| **display table** | RAM `0x4243425c`, built by the static initializer `0x400c2c4e` (1,633 absolute writes), read only through `0x400c257c` | 0x141 x `0x44` = `0x5544`, followed by a static guard at `0x424397a0` | cannot grow in place; one reader, so relocate it or redirect rows ≥ 0x141 in the accessor [verified] |
| **`ParameterUpdateCache`** (class name from its vtable `0x401d9c60`) | heap, `0xfff4` bytes, pointer at `0x44648988`, made by `0x4018e93c` | `+0x18`: u16 values [2 banks][17 lanes][0x141 rows]; `+0x555c`: dirty bits [2][17][`0x504` bytes]; `+0xffe4` bank; `+0xffe8` a vector | must grow before new rows get CC/NRPN: the immediates `0x282`, `0x2aa2`, `0x504`, `0x5544`, `0x555c`, `0xffe4..0xfff0`, `0xfff4` in `0x4018e93c`, `0x400f5264` (set), `0x400f51a4` (get), `0x400f5352` (flush). Nothing else has a size that is a multiple of 0x141 (immediate scan for `0x141 * n`, n = 2..256:
only this cache and unrelated PC-relative offsets). An array sized by a rounded count would not
show this way [inferred: covered by the test plan, not excluded].

**The cache bug, measured** (`out/T6.1/emu/grown-cc-midicc/cache-trace.txt`): the set routine
writes lane 16 (FX), row 0x141 at `+0x18 + bank*0x2aa2 + 16*0x282 + 0x141*2`. In bank 0 that is
bank 1's lane 0, row 0; in bank 1 it is the first word of bank 0's dirty bits. MIDI CC 3 (given to
row 0x141) on the FX channel, values 3, 5, 1, 6: the value reached `k` 70 each time, but the flush
after values 5 and 6 also emitted (lane 0, row `0x18`) and (lane 0, row `0x19`): parameter-change
events for track 1's trig condition and amp trig that nobody sent. [verified]

### 2.6 Structures built from the table at boot [verified: `out/T6.1/stock-tables.txt`]

`0x400dc634` zeroes and refills, from the rows' group, `k`, CC and NRPN:

| table | address | entries (type) | notes |
|---|---|---|---|
| MIDI / trig / FX / sound slot → row | `0x42c657ac` / `0x42c65940` / `0x42c659a8` / `0x42c65b3c` | 101 / 26 / 101 / 101 (s32) | free FX slots 70..100; free sound slots 25..68 are the machine/filter windows, plus 100 |
| filter type x 3, machine x 40 slot → row | `0x42c65cd0`, `0x42c65d18` | 18, 200 (s32) | free per machine below |
| CC → row (MIDI, sound, FX) | `0x42c66674`, `0x42c66eb0`, `0x42c676ec` | 128 (s32) | CCs free in the FX map and not taken by the parser: 3 4 5 8 11 15 18 19 20 83-88 (93-95 left alone: the ERR-like rows name them Solo, Mute, Track Level) |
| NRPN → row (MIDI, sound, FX) | `0x42c66038`, `0x42c66874`, `0x42c670b0` | **399** (s32) | NRPN numbers above 398 do not fit (`0x400dca5a` rejects them) |
| per machine / per filter CC and NRPN maps | `0x42c67a84`, `0x42c67a0c`, `0x42c6797c`, `0x42c678ec` | `std::map<int,int>` | grow freely |

- Row ids are 32-bit everywhere they are stored (page records, these tables). Stock rows already
  go past 255, so no field can be a byte. [verified for the tables; inferred for the rest]
- **The ERR rows are in no map.** Their CC fields (1/33, 2/34, 6/38, 7, 10, 99/98, 120, 121, 123,
  64, 66) are not used by the table path: the CC parser `0x40122eec` handles 1, 2, 6, 33, 34, 38, 64,
  66, 94, 98, 99, 110, 120, 121 and 123 by number before the table is consulted, and 7 and 10 reach
  no map. So the ERR rows' CC fields are documentation of the parser, and inert in stock. **A
  repurposed ERR row that gets a real group must have them cleared or chosen**, or the builder
  files it under CC 1, 2, ... (where the parser takes most of them first anyway). [verified: maps
  from the snapshot, parser read]
- **Avoid CC 32..63 for new rows**, even where no map uses them: the parser takes 33, 34 and 38 as
  the LSBs of 1, 2 and 6 (seen in the emulator: CC 33 never reached the table), and MIDI reserves
  the range for the LSBs of 0..31. [verified for 33]

### 2.8 What makes a parameter p-lockable [verified]

`ParameterPageView::vslot35` (`0x40064ccc`, every page view's slot 35) asks the **display table**:
a row is lockable when its flags (`+0x00`) have bits 0 and 3 clear. Chorus rows have 1, delay and
reverb rows 8, the routing rows `0xc`; sound rows 0. The group is not consulted. If it says yes,
the lock is recorded by the parameter set's slot 17 as (active track, step, `k`), whatever the set
is (`FxParameterSet::vslot17` does exactly what `SoundParameterSet::vslot17` does).

Measured (`out/T6.1/emu/grown-plock-lockable/`): in grid recording, holding trig 1 and turning a new
chorus row (`k` 70) whose display entry was copied from LFO3 WAVE (flags 0) recorded a lock
(track 1, `k` 70) in the live pattern, and the working image stored it as sound lock id 77, which
any OS loads back as a lock on the sound's slot 70 (filter envelope delay). The stock delay TIME
knob, under the same keys, records nothing. With flag 8 on the new row
(`out/T6.1/emu/grown-plock/`), nothing is recorded either. dnfw's lane-16 work on FX locks
(`docs/fx-master-modulation.md` §26-28, 1.11) reads the gate as the `k` → id map; on 1.12 the UI's
gate is these flags.

### 2.9 Overbridge [verified as far as the device goes]

`0x400d5a54` sends a parameter change to the Overbridge stream (`ObAsyncDataOutputStream`, through
`0x40132eae` with `0x30` as the second argument, a message type [inferred]) carrying the row's
`+0x20` id as a 16-bit number. Stock ids run 0..387 with gaps, unique per row; they look like a
stable id for external tools [inferred]. New rows need an id the plugin does not already mean
something by (we used `0x400 + n`). What the plugin does with an unknown id could not be
established here (section 8). The `+0x20` getter `0x400dc27e` has no caller.

## 3. Persistence

### 3.1 What is stored, and by what [verified]

| data | key in RAM | key in storage | translation |
|---|---|---|---|
| kit FX values (`fxSetupStorage_v0_t`) | `k` 0..100 | stored id 0..45 | `0x401fd160` (70 entries, `k` 25..69 → 1..45, all else → 0); back `0x401fd278` |
| sound values | `k` 0..100 | stored id 0..106 | `0x401fd330` (100 entries, `k` 0..99); back `0x401fd4c0` (107) |
| p-locks (80 lanes of `0x102` bytes per pattern) | byte `k` + byte track (0..15) | byte stored id + byte track | the sound table; the loader `0x400de682` accepts only track < 16 and id < 107 |
| LFO DEST values (stored sound `+0x36`, `+0x38`, `+0x3a`) | value = `k` | stored id | the sound table, in the sound serializer/loader |
| mod-source destinations (4 x 4, `0x400dd2c4`) | `k` | stored id | `0x400dce5e(0, k)` |
| MIDI CC maps, slot tables, page records | row | not stored | rebuilt at boot |

So no persistent field holds a row id. Field widths: `k` and stored ids are bytes in locks and
destinations, u16 values everywhere.

Round-trips through the sound tables: every `k` 0..99 survives except **65** (→ id 0); **100 has
no entry** (the table ends, a lock on `k` 100 reads the next table's first word, 0). Stored ids 4,
8, .., 32 have no `k` (dnfw uses them for LFO4; a stock re-save zeroes them).

Measured in the emulator (`out/T6.1/emu/*/end.snap`, stored kit 0 in the working image):

- path c: turning delay G (row `0x7a`, `k` 40) to 4 made the stock `FxSetup::updateMirror` write
  `0x0400` into stored id 16. Per-kit storage, stock code, no hook. [verified]
- grown: values of `k` 70, 71, 72 all landed in stored id 0 (the fold sink): not saved, and
  harmless (id 0 loads into `k` 0, which no row uses). T6.0's map and serializer hooks are what make
  `k` 70+ persistent. [verified]

### 3.3 A project saved by a grown build, loaded by a stock OS

| what the grown build stored | stock OS on load | damage? |
|---|---|---|
| a new machine parameter (free `k` in its window) | loads the value into that slot; no row shows it; the frame carries it to the DSP, which the stock machine does not read [inferred] | none; the value survives a stock re-save |
| a p-lock on it | loads as a lock on (track, `k`); invisible; uses one of 80 lanes | none [inferred] |
| an LFO DEST pointing at it | modulates an unused slot; the DEST label shows no name [inferred] | none audible |
| new FX values in the kit's reserved words (T6.0) | ignored on load; kept by in-place saves; lost by exports | none [T6.0] |
| delay/reverb routing rows used as new knobs (path c) | stock loads `k` 40/48 (id 16/24) as "Delay/Reverb FX Routing"; no page shows them; the stock DSP ignores 40 and keeps `48 != 0` unread [T3.4] | none; values above 1 are out of the stock range but nothing reads them [inferred] |
| **a p-lock taken on a lockable new FX row** | loads as a lock on the sound's slot `k` (for `k` 70: filter envelope delay) | **yes, on both OSes** (2.8) |
| a p-lock on `k` 100 | stored with id 0: loads as a lock on slot 0 | lost [inferred] |

A stock project loaded by a grown build: new machine parameters read 0 (stock writes 0 into slots
it has no row for, `0x400e7eb0`), new FX words read 0 (T6.0).

### 3.4 Rules that keep projects safe

1. Every new send-FX row: display flags with bit 3 (or bit 0) set, so it is never p-lockable. Copy
   its display entry from an FX row, not from a sound row.
2. Every new synth row: a `k` that is free in its machine's window (3.2). Never 65 or 100.
3. One row per `k` within a set, and no CC already in that set's map (last write wins, 2.4).
4. 0 means "classic" for every new parameter: that is what a stock project carries.
5. No randomiser on a new row whose `k` means something else in the sound set.
6. No CC or NRPN on a new row until the `ParameterUpdateCache` is resized; NRPN numbers ≤ 398; no
   CC in 32..63 or among the parser's own (2.6).
7. An Overbridge id outside 0..387.
8. Persistence of `k` 70+ only through T6.0's hooks, with a check word.

## 4. The cheaper alternatives

### 4.1 (a) The dead ERR rows [verified]

- **11 usable:** rows 1-5, `0xb`-`0xe`, `0x11`, `0x12` (long name "Error", group -1, in no map, on no
  page). Row 0 is the clamp target and the "empty slot" id in page records: not usable as a knob.
  Rows 7-9 and `0xf` also show "ERR" as a short name but are Solo, Mute, Pattern Mute and Active
  Track. (dnfw: 10 dead + id 0 on 1.11; they reused 10 for LFO4.)
- **MIDI CCs:** inert in stock (2.6). T5.0's borrowed rows cleared them, which is right, but the
  reason is the builder, not stock behaviour.
- **Display entries:** generic knob, flags 0: **lockable**. For FX use, copy an FX row's display
  entry. T5.0's `fx-page2-dn2` copies row `0x69` (flags 1: correct) for seven rows, but row `0x63`
  (LFO3 WAVE, flags 0) for SHPE: as built, SHPE (`k` 70) would take p-locks, stored as locks on the
  track's sound slot 70 (filter envelope delay). The emulator run `grown-plock-lockable` is that
  exact case. Fix: set bit 3 of the copied flags. [verified]
- CC out: these ids are outside `0x69..0x83`, so their CC would go to the track channel, as for a
  grown row (2.7).
- They are below 0x141: no relocation, no bound sweep, no cache problem.
- Gives up: nothing compared with growth, for up to 11 knobs. The budget is shared with anything
  else that borrows them (dnfw's LFO4 uses 10 of the 11 on 1.11).

### 4.2 (b) A label hook with the values outside the table

dnfw's Waverider (1.11) relabels WaveTone's existing rows by hooking the short-name fetch
(`0x400372da` on 1.12) and redraws its own page; the values stay WaveTone's, so p-locks, LFO and
save/load are WaveTone's. For **new** values the knob would have to be handled by our own page code
writing T6.0's reserved kit words. That keeps per-kit save/load and gives up: MIDI CC in and out,
Overbridge, the help bubble and value text (unless re-implemented), the stock encoder handling
(fine steps, value popups, "FUNC+press"). For send FX this is acceptable in principle but costs
more UI code than ERR rows or growth; for synth parameters it gives no p-locks: not acceptable.

### 4.3 (c) The routing rows on the empty encoder slots [verified]

- Rows `0x7a` "Delay FX Routing" (`k` 40, group delay) and `0x83` "Reverb FX Routing" (`k` 48,
  group reverb): range 0..1, default 1, formatter `0x400e3592` ("Pre"/"Post"), no CC, no NRPN,
  Overbridge ids 128 and 138, display flags `0xc` (not lockable), glyph a two-state "PRE/POST FX".
- **Shown nowhere:** on no page record (`out/T6.1/stock-tables.txt`), in no menu found (no code
  names these row ids). The FX set files them at slots 40 and 48, so they are stored (ids 16, 24,
  kits carry 1) and sent in the frame (words `0xa18`, `0xa28`). The stock DSP never reads `0xa18`
  and stores `0xa28` as a byte nobody reads (T3.4).
- **The empty slots:** the stock delay page is A-F = TIME X WID FDBK HPF LPF, **G empty**, H = REV,
  LEVEL = VOL. The reverb page has **G and H empty**; the chorus page E and F.
- **Proved in the emulator** (`out/T6.1/emu/pathc/`, `grown/`): row `0x7a` on delay G and `0x83` on
  reverb G, by writing the page records in RAM; row `0x7a` changed by data alone to "Delay Mode" /
  "MODE", 0..6, plain-number formatter. The delay page shows eight knobs, "Delay Mode=4" in the
  header, the value stored in stored kit id 16 by stock code. Nothing else on screen changed.
- **What it takes on the unit:** the page record is built at boot by the static initializer (a
  `clr.l` of the slot at `0x400c9f68` for delay G, `0x400c9fde` for reverb G, `0x400c9ff8` for
  reverb H); a same-length edit there cannot load a row id, so one run-time write (first `ev_tick`)
  or T5.0's page-accessor hook places it. The labels, range and formatter are `ptr`/`bytes` sites on
  the descriptor. A glyph that is not "PRE/POST FX" needs a display-row copy at run time. A CC can be
  added by data and works through the stock maps (the row is inside the FX-channel range).
- New DSP code reads `k` 40 from frame word `0xa18` and `k` 48 from `0xa28` (or the image copies at
  `0x25cea4`, `0x25ceb4`): no ColdFire frame hook needed.
- **Limits:** one knob per page (two pages); value 1 must be the classic behaviour, because every
  existing kit carries 1; if a future Elektron OS gives these rows a meaning again, our values
  above 1 would be out of its range.

### 4.4 Range and value text by data alone [verified]

- Min/max/default (`+0x08/+0x0c/+0x10`, `<< 8`), bipolar (`+0x14`) and the formatter (`+0x34`) are
  data. In the emulator row `0x7a` went from 0..1 "Pre/Post" to 0..6 numbers, and the new chorus
  row showed LFO waveform names ("SQR") with the stock LFO waveform formatter.
- Stock formatters that print names: ON/OFF `0x400e3568`, Pre/Post `0x400e3592`, Post/Pre Filter
  `0x400e35bc`, ADSR/AHD `0x400e35e6`, LFO waveform names `0x400e3610` [verified on screen], LFO trig
  modes `0x400e367c` [inferred]; plain number `0x400e3030`, percent `0x400e317a`, bipolar
  `0x400e341a`.
- **Our own names need a formatter function:** it is called as `fmt(value << 8, char *out)` both
  by `ParameterSet::vslot23`'s tail jump and directly by `0x400c25a0`, and the stock ones end in
  `sprintf`. A C function in a mod can be pointed at by `+0x34`. [inferred: calling convention read
  from both call sites and the stock bodies, not run]

## 5. The emulator proof done here (hot-patch, RAM only) [verified]

`scripts/t61_grow_emu.py` loads stock's warm 800M snapshot in digikit, applies one variant inside
`build()` (before `emu.live` installs its hooks), and runs a key script headless.
`scripts/t61-emu.sh VARIANT [SCRIPT [NAME]]` runs it; `scripts/t61_compare.py` compares with stock
(`out/T6.1/emu/summary.txt`). Each run takes about 25 s.

| variant | what it does | result |
|---|---|---|
| `inert` | descriptor table copied to `0x47E40000` with room for 8 rows (copies of row 0); display table copied to `0x47E46000` the same way; 56 + 1 operands repointed, 58 bounds raised to `0x149`; builder `0x400dc634` re-run from the host (its outputs poisoned first) | all 25 screens of `scripts/t61-pages.script` (SEND FX 1-3 with turns and pushes on every empty slot, TRIG, SYN 1-2, FLTR, AMP, track FX, LFO with the DEST list stepped) identical to stock; rebuilt slot tables and CC/NRPN maps identical to stock |
| `grown` | inert + 8 rows: chorus SHPE (0..6, LFO waveform names) and PHAS on E/F, reverb TONE on H, two delay and two compressor rows off-page, one Swarmer row at `k` 33; path c's two rows on delay G and reverb G | only the three SEND FX pages differ; the builder files the FX rows at slots 70..76 and the Swarmer row in machine 3's slot 33; turns write `k` 70-72 and 40 through the stock setter and the raw mirror row 16 |
| `pathc` | no growth: rows `0x7a` and `0x83` on the empty G slots, `0x7a` as a 0..6 knob | only the delay and reverb pages differ; `k` 40 stored in kit id 16 by stock code |
| `grown-cc` + `scripts/t61-midi-cc.script` | row `0x141` gets CC 3 on the FX channel (channel 9 in this snapshot, found with `scripts/t61-midi-probe.script`) | CC reaches `k` 70, and corrupts the `ParameterUpdateCache` (2.5) |
| `grown` + `scripts/t61-plock.script` | grid recording, trig 1 held, knobs turned on FLTR, delay and chorus | stock behaviour (FLTR locks, FX does not) once new FX rows carry flag 8; with a lockable template (`T61_LOCKABLE_FX=1`) the new FX row locks onto the sound slot (2.8, `grown-plock-lockable`; `scripts/t61_locks.py` lists the records) |

What a hot-patch cannot show: the boot. The only boot-time reader of the descriptor table is the
builder `0x400dc634` (called from the app task's init `0x400bb3c0`), and the static initializer
`0x400c2c4e` does not read it, so re-running the builder covers the boot-time state for the table.
The display table and the page records are built by the static initializer and were copied/edited
after it. A cold boot with a real build is still the first item of section 7.

## 7. Test plan before any flash

**Emulator, in this order** (scripts named are the ones written here, to be extended):

1. **Inert build, cold boot.** Relocation + bounds + display redirect, no new rows, built with
   core-dn2 like any mod; cold boot in digikit (the `t50-emu.sh ladder` recipe) to the warm 800M
   snapshot; the brick checker with check 8. Pass: every screen of the full pass below identical to
   stock, slot tables and CC/NRPN maps identical to stock (`scripts/t61_snap_tables.py ... all`).
2. **Grow by 8, cold boot**, rows as in `grown` but following 3.4 (FX rows flag 8, no randomiser,
   machine rows in free slots of the machine on track 1 *and* of the other three).
3. **Scripted pass over every page, compared with stock:** TRIG, RTRG, EUCL, every SYN page of each
   of the 4 machines, FLTR for each filter type, AMP, FX, MOD 1-3, SEND FX 1-3, the mixer pages,
   the MIDI-track pages, MODULATION SETUP; on each page turn every encoder one step both ways,
   push it, hold FUNC and turn. Pass: identical `.txt` screens except where a new row was placed,
   and the new rows show their labels, values and glyphs.
4. **P-locks:** grid recording, a trig on each new row and on one stock row per page. Pass: FX rows
   record nothing; new machine rows record (track, `k`) with the right `k`; read back from the live
   pattern and the working image (`scripts/t61_locks.py`).
5. **LFO destinations:** for each LFO, step DEST through the whole list on each machine. Pass: the
   stock list plus the new machine rows, in slot order; LFO DEST values stored as the right id.
6. **MIDI CC and NRPN in:** every mapped CC and NRPN on every channel (track channels and the FX
   channel), stock vs grown; then the new rows' CCs. Pass: the same `k` changes as stock, the cache
   bank and dirty words clean after each flush (the `readout` in `t61_grow_emu.py`), no flush event
   for a row nobody sent (`T61_TRACE=0x400f5416`).
7. **MIDI out:** enable CC/NRPN out in SETTINGS in the script, turn every knob; compare the MIDI log
   with stock byte for byte; new rows on the channel and CC chosen.
8. **Save and load:** at minimum host-called round trips of the stock serializers and loaders on a
   kit, a sound and a pattern (`0x400ddfa8`/`0x400dddb6`, `0x400dd80a`/`0x400dd34e`,
   `0x400de90c`/pattern loader) with new values, new locks and an LFO DEST on a new row, then the
   same bytes loaded by the stock image in a second emulator run. Better: a formatted +Drive image
   for digikit's eSDHC model (T6.0's open item) and a real SAVE/RELOAD through the UI.
9. **Machine change, new sound, new kit, sound randomise, copy/paste of kit/sound/pattern, undo:**
   new values default as designed and nothing stock moves.
10. **Long run:** play a pattern with locks on new machine rows for minutes with MIDI in traffic;
    no fault, frame handler on time.

**Only the unit can show:**

- a real boot from flash with the relocated table (caches, timing), and power-cycle persistence;
- Overbridge: what the plugin does with an unknown parameter id (2.9), and its automation going
  the other way;
- a real +Drive save/load and Elektron Transfer of kits and sounds carrying new values;
- external MIDI gear (CC out on the FX channel, 14-bit pairs);
- the sound of the DSP side (new DSP code reading the new values);
- the user's real projects: load, play, save on the grown build, then load on stock 1.12 (on a
  copy of the project).

## 8. What could not be established

- **Overbridge**: the incoming automation path (no reverse lookup of `+0x20` was found; `0x400dc27e`
  is unreferenced) and the plugin's reaction to unknown ids.
- **Arrays sized by a rounded row count** (for example 0x150) would not show in the immediate scan.
  None was hit by the 25-screen pass, the MIDI and the p-lock runs, but they are not excluded.
- **What the bogus cache events do** to track 1 (the listener `+0x3c` was not followed); only that
  they are sent.
- **MIDI CC out** of new rows: static only (MIDI out is off in the snapshot's settings).
- **The randomiser** cross-talk is read, not run (the key for "randomise sound" was not found).
- **Save to the +Drive** and a stock OS loading a grown build's files: not run (no formatted +Drive
  image for digikit); the conclusions in 3.3 rest on the serializers and loaders read.
- A cold boot of a grown build: not run (it needs a real build; section 7 item 1).
- The per-machine SYN page table on 1.12 was not re-located (dnfw's 1.11 address is given).
