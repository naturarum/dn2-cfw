## Gap 1: the in-OS upgrade validator

The validator `FUN_400dbdb0` is 52 bytes, `0x400dbdb0-0x400dbde4` (functions.tsv; the next
function, a thunk, starts at `0x400dbde4`) [verified]. It returns 1 only if the content checksum
`FUN_401226f8` and the trailer check `FUN_400d2bc4` both pass. Pinning only its 52 bytes would leave
the same hole one call deeper, so check 6 now pins its whole static callee closure (calls.tsv) and
the data the trailer check reads [verified: closure computed from calls.tsv, bytes read from the
stock image]:

| range | what |
|---|---|
| `0x400dbdb0-0x400dbde4` | validator `FUN_400dbdb0` |
| `0x401226f8-0x40122732` | content checksum `FUN_401226f8` |
| `0x400d2bc4-0x400d2ca2` | trailer check `FUN_400d2bc4` |
| `0x4011e840-0x4011e982`, `0x4011e984-0x4011ecb8` | its HMAC and SHA-256 routines |
| `0x4013419c-0x401341cc`, `0x40134770-0x401347b6` | the two helpers they call (58 and 501 callers) |
| `0x40210a4a-0x40210a55` | the key seed string "Multiplier" |
| `0x4021b9ef-0x4021ba0f` | the 32-byte mask the trailer check XORs into the key |
| `0x40207da0-0x40207ea0` | the SHA-256 round constants (first word `0x428a2f98`) |

The writer `FUN_40139104` (already pinned) re-runs this validator before it erases (T1.4), so with
the closure pinned the writer's own gate is stock whatever its callers do. The writer's own callee
closure is not pinned: it reaches the std::string and UI code (about 120 functions) [verified, calls.tsv].

## Gap 2: section 7 (DSP) checks — new check 11

A changed section 7 used to pass if it merely depacked (check 2). Now the DSP is its own check 11
(`tools/brickcheck/bc_dsp.py`), and check 2 only notes that section 7 differs:

- **Section 7 must equal stock** unless the caller passes `--intended-dsp <depacked image>`
  (mirroring `--intended-main`). A changed DSP **with no intended image is "incomplete"**
  (check 11 SKIP), never accept [verified: run on a `-c 7` rebuild].
- With `--intended-dsp`, the depacked section 7 must equal that image **exactly**; otherwise FAIL.
- When a DSP change is intended, these run, each marked below as tested:

| check | rule | source | tested |
|---|---|---|---|
| size, stored | section 7 stored `<= 1 MiB` | ColdFire DSP loader `FUN_400cf4b0`, `cmpi.l #0x100000` at `0x400cf710`, `bhi 0x400cf716` [verified in the decompile] | yes |
| size, boot stream | depacked stream `<= 1 MiB - 1` | same loader, `addq.l #1,d2; cmpi.l #0x100000,d2; bgt` at `0x400cf746`-`0x400cf74e` [verified] | yes |
| parse | boot stream parses completely (header XOR/HDRSIGN, byte accounting, 4-byte counts) and ends with a FINAL block | `scripts/sharc_ldr_parse.py` (T3.1) | yes (stock) |
| CRC | the stream carries no payload CRC (no CALLBACK block); stated, not assumed | sharc_ldr_parse | yes |
| cache / regions | no load block writes into an L1/L2 cache range the start-up enables, or outside the known L1/L2/DDR regions | T3.2 + 2026-10-06 correction; prior-art 6.1 fact 2. Cache ranges: I-cache `0x39c000-0x3a0000`, DM `0x2ec000-0x2f0000`, PM `0x31c000-0x320000`, L2 reserved `0x200fa000-0x20100000` | yes (retargeted a block into the I-cache → refused) |
| bad shift | no mis-encoded negative-immediate shift (a pure LSHIFT/ASHIFT/ROT, +/- OR forms, whose 8-bit immediate is negative but whose sign-extension nibble is not `0xf`) in changed/new DSP code | prior-art 6.1 fact 1 (selas parks the SHARC with this form; every emulator gate passed it). Decoded with `tools/sharcvm/decode.py` -> digikit's decoder | yes (zeroed a stock shift's `dataex` nibble → refused; stock has 0) |
| dynamic | run the effect init `0x1c1445` then the whole block handler `0x1c9d6b` for a few hundred blocks with a stock-like frame and a test input; refuse on any trap, unimplemented-instruction stop, NaN/Inf output, or output above a loudness ceiling (default 4.0); report instructions/block vs the stock budget (320,281), warn above 1.5x | `tools/sharcvm` (T3.6) | yes (stock passes; a corrupted reachable instruction traps; NaN coefficients → refused) |

The dynamic run loads the candidate's section 7 into `tools/sharcvm` (parse the boot stream,
build the final image, write it over the stock baseline), runs the effect init fresh (the init
clears the effect state, so a corrupted zero-fill does not survive it — a real coefficient/code
change does), then the block handler. Stock: 200 blocks, peak 0.017, 320,281 instructions/block,
no NaN; ~13 s init + ~1 s. [verified]

**Limits (stated honestly):** the static bad-shift scan disassembles the candidate's executable
load blocks from their (instruction-aligned) starts and flags only bytes that differ from stock,
so unchanged stock code is never reported; a mis-encoded shift in a *new* block placed outside the
stock code regions, or inside a changed data block decoded as code, is a known residual (the
dynamic run is the backstop for reachable code). The dynamic run drives the global FX/mixer path
with a test input and no voices triggered (T3.6's `fullblock`): it exercises the effects and master
chain, not per-voice engines (those need the per-track frame, T3.3). sharcvm models no stalls or
DDR latency, so the instructions/block is an instruction count, not the unit's cycle count.

## Gap 3: check 7 is a tripwire, not the gate

- **Check 7 is now labelled a tripwire** in the report and its name: it is a byte scan of changed
  bytes, defeated by a computed or indirect reference (red-team `danger-computed` reaches the NOR
  driver via `base 0x40134000 + 0xa28` with no literal driver address). It still refuses every
  literal flash reference it sees, but the verdict no longer rests on it.
- **The real flash gate is check 6**, which keeps the whole NOR driver `0x40134A28-0x4013621C` and
  the in-OS writer `FUN_40139104` (`0x40139104-0x4013924C`) **byte-identical** to stock [verified:
  both ranges are in `bc_static.PROTECTED` and compared byte for byte; check 6 now says so
  explicitly]. A computed-address gadget cannot reach a flash write without going through these
  bytes, and they cannot change without check 6 failing.
- **Plus a dynamic in-OS upgrade flash watch (new check 12).** `scripts/t17b_flashwatch.py` drives
  the real writer `FUN_40139104` in digikit's emulator over the candidate's own container and
  watches every flash erase/program command and its wire address against T1.4-verify-2's window
  ([0x80000, 0x380000), no `0xE1/0xE3/0xE4/0x42/0x44`), two ways at once (a code hook on each NOR
  erase/program/protect driver entry, and a DSPI0 PUSHR `0xFC05C034` write hook that splits frames
  on the CONT bit). `bc_upgrade.py` runs it from the brick checker.
  - Stock / EF01 / the T1.9 cores: 8 block-erases `0x080000-0x240000` and ~3,684 page-programs
    `0x080000-0x24c600`, all in window -> ACCEPT, ~3 s from the warm 800M snapshot [verified:
    `out/T1.7b/emu/stock/report.md`].
  - A demonstration with a deliberately oversized declared length (`0xf90000`) marches 63 erases
    through the settings store and **wraps at the 24-bit SPI address back to `0x000000`** (the
    reset+bootstrap region); the watch flags every out-of-window address from both capture paths
    -> REFUSE [verified: `out/T1.7b/emu/overlen/report.md`]. This reproduces T1.4-verify-2 section 1's
    24-bit-wrap hazard and proves the watch catches it.
  - **Why the stock writer is faithful to a candidate:** the writer and the driver are byte-pinned
    by check 6, so the code issuing the frames is the bytes the candidate would run; only the
    container length (candidate's own) drives the extent. So check 12 is a runtime cross-check of
    check 3's in-window bound through the real DSPI0 driver, meaningful only when check 6 passes
    (the checker gates on that).
  - **Honest limits.** It drives the writer directly, not organically through a SysEx-over-DIN
    upgrade session: the feasibility study (T1.7b, `scripts/t17b_flashwatch.py` header and the
    `dn2_firmware_explore`-style call graph) found the organic path (SysEx reassembly `FUN_4012257c`
    -> `MidiRpcOsUpgrade` `FUN_40125f9e`/`FUN_40139280` -> the deferred job `FUN_401094e8`/
    `FUN_40109144` -> the "UPGRADE OS NOW?" confirm, all under the emulator's unblock-everything
    hack) a large, unproven effort that adds nothing over the direct harness, because the pinned
    writer+driver produce the same wire addresses either way [inferred from the call graph; the
    direct harness is verified]. The harness forces the validator `FUN_400dbdb0` to pass (a
    one-instruction shim at `0x4013911a`) so an oversized length can be tested; the seal is already
    proven by check 4, and a real sealed candidate passes the validator anyway. It seeds the NOR
    geometry cache (`0x402a12f4=0x40000`, `0x402a12f8=0x200`, the Spansion S25FL geometry T1.4
    measured) because the emulator HLEs the flash read so the real JEDEC probe never runs, and
    stubs three cosmetic console-print helpers that would otherwise block a no-scheduler run.
  - **It does NOT close the computed-address gadget** (`danger-computed`): that gadget sits off the
    upgrade path, so this watch never runs it, exactly like the cold-boot watch. Check 6 (driver +
    writer byte-identical) is what stops it.

## Gap 4: check 8's window

- Check 8 (the emulated cold boot) still watches the cold boot and the 600M instructions at the
  main screen. Check 12 adds the in-OS upgrade writer session with its own flash watch, which is
  the path that can reach a flash erase/program. The two together cover the boot path and the
  upgrade writer.
- **Not driven: scripted key sessions through SETTINGS/SYSTEM and the OS UPGRADE menu, and
  project save/load.** Driving them needs a candidate-specific warm snapshot (a ~10-min cold boot
  per candidate) and adds little for flash safety: the only main-OS code that writes the array is
  the upgrade writer (cluster A, check 12) and the console/settings writers (clusters B-D), and
  the console is behind the factory test-mode gate the checker already proves stays clear (T1.4
  section 5; check 9's boot-flag checks). This is stated as a limit rather than claimed. The time
  budget and coverage of each dynamic check are printed in the report (check 8: cold boot to 400M
  + emucheck 600M; check 12: the writer run, ~3 s, with the window it enforced).

## Remaining limits

- **The computed-address class is not fully closed.** Check 7 now catches the one `danger-computed`
  idiom, but a reference built another way (split further, via a register base, a RAM table) is still
  invisible to a byte scan. The gate is check 6 (driver + writer byte-identical) and check 12; a gadget
  that sits off the upgrade path is run by neither watch, so it would be accepted. This is the red-team's
  stated residual, not closed by any offline check short of exhaustive UI exploration.
- **Check 12 drives the writer directly, not an organic SysEx-over-DIN upgrade.** Faithful because the
  writer+driver are byte-pinned by check 6; the organic path was assessed as high-cost/low-value.
- **The DSP dynamic run** uses `tools/sharcvm` with a test input and no voices (the FX/mixer path), models
  no cycle timing, and its bad-shift scan covers in-place changes and new executable blocks, not a shift in
  a data block decoded as code. It is a strong offline check, not the unit.
- **Section 5 and the margin rule** are unchanged from T1.7.
